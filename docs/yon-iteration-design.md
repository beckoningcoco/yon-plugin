# 迭代表板：设计记录

> 这份文档记录**为什么这样设计**、**支撑它的实测数字**，以及**它现在还不成立的地方**，不是接口手册。
> 代码在 `src/host/iteration-{store,service,tools}.ts` 与 `src/client/iteration/`，用法在各自的 JSDoc 里，
> 测试在 `tests/iteration-{store,service,tools}.spec.ts`、`tests/http-iteration.spec.ts`、
> `tests/iteration-panel.client.spec.tsx`。
>
> 记录日期 2026-10-03。

## 一、要解决的问题

这个插件能做什么、在哪一步会卡住，只有它的作者知道，而作者不在现场。真正会撞上「这个工具在这个
场景下不够用」的，是**拿它干活的模型**：它为了拿到一个本该直接给出的答案绕了路，同一件事在一个
会话里问了使用者两次，或者只能靠猜。

这些时刻今天全部丢失，而且不是"没人记"，是**没有地方可记**：插件拿不到会话记录——唯一那个会话
句柄（`src/host/tools.ts:46-73`）只读 `sandbox/mode` 与 `approval/policy` 两个字段
（`:392-411`）——模型注意到了也没处说，会话一结束就没了。

所以这一格做的事只有一件：**给模型一个一次调用就写完的入口**，把这类遭遇写成一行，留给人看。

## 二、立身之本：模型只能追加

这是整个功能里唯一不能妥协的地方。

**模型不是站在插件开发者的立场评审插件，也没有任何改插件、排序、挑选的权限。** 它是使用者视角的
现场记录员。落到实现上就是三条，每一条都有一个具体的坏结果在挡：

| 约束 | 挡住的东西 | 实现位置 |
|---|---|---|
| 工具只有 `iteration_add` / `iteration_list` | 模型若能把自己那条标成 `fixed`，它就变成了**一个自治的产品负责人**——「这条我顺手修了」「这条不重要，划掉吧」。改不改、先改哪条是使用者的决定 | `ITERATION_TOOL_NAMES`，`tests/iteration-tools.spec.ts` 有一条用例专门盯着这个数组等于这两个名字 |
| 没有闸门（`dispositionOf` 对纯追加写返回 `run`） | 记一条不影响使用者拥有任何东西、不丢数据；加一道审批会把「顺手记一条」变成「要打断使用者一次」，模型于是学会不记——**这正是本功能唯一的失败方式** | `src/host/tools.ts:430-434` 现有规则，未改 |
| 提示词里四句话 | 工具 schema 能挡的那一半（改、删）挡不住另一半：模型可能因为记了一条就去改插件，或替使用者排序、把台账当待办 | `YON_PROMPT_TEXT` 末段，`tests/prompt.spec.ts` 一条用例逐句钉住 |

那四句逐字是：「记录不是改动，改不改由人决定」/「不要因此改插件」/「不要替使用者排序、挑选或把
记录当待办」/「每一条都要等他看过才算数」。措辞被改写成别的说法，用例就红——因为它防的不是
措辞，是四个不同的失败方式各有各的句子。

删和改状态都在面板里，由人做；删除还要点两次（`IterationManager.tsx` 的 `confirmId`），与
`project_create` 直写、`project_delete` 要确认是同一条线。

### 为什么没有第二个「人工录入」工具

行里没有作者字段，使用者说「记一条」时走的就是 `iteration_add`（描述里写了）。多一个 schema 几乎
相同的工具，只会多一次模型选错的机会。

## 三、存储：为什么是文档，不是追加流

台账落在 `~/.dsh/yon-panel/iteration.json`，形状抄 `src/host/home-store.ts`：一个 JSON 文档、
`read()`/`write()`、写串行化、原子写（tmp 兄弟文件 + `rename`）、BOM 按码点剥、坏条目跳过。

**没抄 `src/host/digest-log.ts` 的 JSONL 追加流**，而它的头注释（`:19-25`）里给自己写的三条理由，
在台账这里三条全反：

- 它是**只追加**的，适合一批跑完就再也不改的流水账。而台账一行**是要被改的**——状态从 `open`
  走到 `fixed` 正是留着它的全部意义——追加流答不了「这行现在是什么」。
- 它**吞掉自己的写入错误**（`digest-log.ts:211`）。它那么做的理由成立：丢一条审计行比让审计失败
  轻。这里反过来：模型记完一条、被告知"已记下"，它就不再看了；如果那次写其实失败了，这条记录
  就此消失而**没有任何人会知道要找它**。所以这一层的读错误一律上报，工具把失败原样交回模型
  （`tests/iteration-service.spec.ts` 的「读不出来时拒绝每一次改动，且不动使用者的字节」）。
- 也**没有抄项目领域**（`src/host/domain.ts` / `service.ts`）：那是使用者的记录 + 声明式 schema +
  级联删除，而台账是一份**给人手改的笔记**——正是 `home-store.ts:4-9` 给自己写下的理由。

两处刻意偏离 `home-store.ts`：坏行照样跳过，但**跳过几行要在读的结果里报出来**（`skipped`）——
丢掉一个 Home 登记是看得见的（少一行），丢掉一条笔记是看不见的（使用者从不知道它存在过）；
以及**不播种**：一个带着编造样本开局的台账会教会它的读者不要相信整个文件。

### 不做持久化的 summary

`digest-log.ts:216-251` 要折一份 summary，是因为那是追加流、可以到 2000 行、面板不会全取。台账是
几十行、面板手里就有全量，宿主再算一遍等于把同一个事实存两处。计数改成前端纯函数
`countRows(rows)`，面板因此**总是取整份台账**（不传 status 筛选），上面的计数才不会在读者点一下
筛选之后改口径。

## 四、去重：故意做笨

`create(..., { dedupe: true })`（只有模型那条路传它）在 `target` 与 `symptom` 都非空、且存在一条
`open` 行两字段 trim 后完全相同时，不追加，返回既有的那条 + `created: false`，工具据此回一句
「已经记过这一条了（id）」。

三条边界都是想过的：

- **精确匹配，不做模糊。** 模糊匹配需要一个人人说不清的门槛，而说清不了的门槛迟早会被调。
- **`target` 为空就不比。** 两条没有共同目标的笔记，共享的只有一句话——把它们当同一条会吞掉
  真的两条。
- **已经关闭的行不算重复。** 防的是"同一条抱怨记二十遍"，不是"这件事又发生了"；后者是新信息，
  照样追加。

面板手工录入那条路**不传 dedupe**：人有权记两条相似的，而且他知道为什么。

## 五、记录门槛：只在硬信号上记

工具描述里点名了五种，写死在那儿而不是留给模型自己判断：**为了拿到一个本该直接给出的答案而绕了
路** / **一个会话里反复问使用者同一件事** / **只能靠猜** / **某个工具给的答案看着笃定但事后发现
是错的** / **使用者明确抱怨这套工具**。同时写明「没有值得记的就是常态，宁缺勿滥」——一个塞满挑剔
的台账是没人看的台账，而"没人看"是本功能第二种失败方式。（第一种见第二节：模型学会了不记。）

第五条（2026-10-04 补）与前四条形状相反，值得单独说明：前四条说的都是**没拿到答案**，第五条说的
是**拿到了、而且是错的**。这一类最不容易留下痕迹——工具答得斩钉截铁，错了也看不出来，往往是几轮
之后实测才对上；不点名它就正好落在模型的盲区里。提示词（`prompt.ts:122`）与 `iteration_add` 的
描述（`iteration-tools.ts:117`）两处同一份名单，`prompt.spec.ts` 与 `iteration-tools.spec.ts`
各钉一半：模型是在**决定要不要调用**的那一刻读描述的，两处不一致就等于把它劝退。

## 八、明确不做

- 插件改自己（工具描述、提示词、技能正文、代码）——模型没有这个权限，插件也不自我升级
- 把台账写进知识库 / wiki——DSH 自己的记忆能力已覆盖
- 模型侧的状态变更与删除——只在面板里，由人做
- 分页——台账规模是几十行；`IterationListPayload` 留了加 `total` 的余地
- 条目互相引用 / 优先级排序 / 分组——先看真实数据再谈
- 「一键变成项目」联动——升级动作发生在仓库里，不在插件里
