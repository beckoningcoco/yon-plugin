# 消化一份素材

四步，一步都不能跳。**每一步的产出都从工具拿，不要凭印象做。**

```
0  素材准备    PDF 先抽成带页标记的文本          没有文本后面全做不了
1  重叠门禁    digest_audit（不给 product）      值不值得做
2  摸底        digest_plan                       分几章、每章从哪行到哪行
3  写页面      按下面的规范写                    按体量分页
4  验收        digest_audit（给 product）        七项全过才算完
```

## 第零步：把 PDF 变成文本

`digest_plan` 与 `digest_audit` 的 `source` 参数要的是**抽取出来的文本**，不是 PDF 本身。这一步不属于消化，但没有它后面四步一步都走不了。

优先用 xparse（表格与版式还原更好）：

```
npx --yes xparse-cli parse "<file>.pdf" --api auto --output "<输出目录>"
```

它会写 `<basename>.md` 进输出目录。`--api auto` 先跑免费额度，额度不足会返回 `PAID_QUOTA_REQUIRED` 与重置时间——**这时不要自作主张切 `--api paid`**，先告知用户。（实测踩过：CLI 不在 PATH 上、当天额度为 0 页，两个坑都是当场才发现的。）

额度不可用时的降级路径是 PyMuPDF，抽出的文本必须带**物理页标记**：头部三行（`# 标题`、`# 原始文件:`、`# 页数:`），每页正文前一行 `## 第N页`。

**这个页标记格式就是配置项 `pageMarkPattern` 认的东西**——换了抽取器就要同步改配置，否则溯源密度会直接掉到 0。

### 一条硬规则：PDF 不进库，抽取文本必须留

**源 PDF 不放进知识库。** 一份红皮书几十 MB，几百份就是几个 G——这是明令禁止的。PDF 用完即弃。

但**抽取出来的文本必须留下**，落到 `raw/articles/<日期>-<原名>.md`。它是这份消化**唯一的可复核依据**：`digest_audit` 的 `source`、`digest_sweep` 的自动配对，全靠它。丢了它，产物从此不可验。

实测一个库里 27 份 iuap 红皮书摘要，**只有 6 份的抽取文本还在**——其余 21 份永远无法复核，谁也不知道当初读的是原文还是照标题写的。而其中一份恰恰就是把**消息平台**讲成了 MQ 开发指南的那份。

**所以：抽之前先查，抽之后必须落盘。**

```
先看 raw/articles/ 里有没有这份文档的抽取文本（同名或同源）
  有 → 直接用它，不要重复抽
  没有 → 抽一份，落进 raw/articles/，并让产物的 sources 指向它
```

> ⚠️ 这条踩过两回：
> 一是**没查就抽**——库里于是出现内容实质相同的两份抽取文本（112 KB 与 106 KB，逐行比对只差一个空行与 CRLF）。
> 二是**抽完没落盘**——21 份产物留着 `source: "iuap-xxx红皮书 (129页)"` 这种指向库外 PDF 的写法，而那份 PDF 永远不会在库里，于是它们永久失去可复核性。

> 注：库的 `.wiki-schema.md` 里写的是「PDF / 本地 PDF → `raw/pdfs/` → 直接读取」，**这条与「PDF 不进库」冲突，应以后者为准**。`raw/pdfs/` 保持空目录即可。

## 第一步：值不值得做

先跑门禁，**不要先读文档**：

```
digest_audit(source="<源文档绝对路径>", vault="<vault id>")
```

不给 `product` 就是只跑门禁模式。看重叠率：

- **≤ 85%** → 有增量，继续
- **> 85%** → 大部分内容已在库里。**先问用户增量在哪**，别急着做

实测过一份红皮书与库里已有官方文档重叠 91.2%——不跑这一步就会花大力气生产 91% 重复的内容。

**验收时再看重叠，数会不一样，这是正常的**：门禁在消化**前**跑，那时库里还没有这批产物；验收时产物已经躺在库里、被算作「已有内容」了。所以判定用的是**排掉本次产物**之后的值，报告会把它和「连产物一起算」的值并列出来。实测一份 13 页的消化，两个数是 37.4% 与 77.5%——**差额是这次自己写进去的覆盖，不是与已有内容的重复**。产物做得越全，差额越大：不排掉产物的话，「做得好」会被显示成「像重复」。

## 第二步：摸底

```
digest_plan(source="<源文档绝对路径>")
```

它给你：页数、字符数、章节骨架、**每章的 offset 与 limit**。

**把 offset/limit 直接交给 read 工具分段读，不要按页号自己算范围。**

> ⚠️ 这条是踩出来的：按页号切章，把 2.3 部署架构的尾巴（p15–16）划给了下一章，
> 而负责下一章的人按"只写这一章"处理，**那半节从知识库里消失了**，直到最后
> 核对才发现。章常常跨页，`digest_plan` 给的范围是按标题边界算的。

它还会提示：源文档没有一级标题（章是从 `3.1`/`3.2` 的前缀推出来的，**标题是生成的，引用时用范围不要照抄标题名**）、图可能只剩图题、章节格式认不出来（这时要改配置）。

## 素材很大时：按行范围切片并行

`digest_plan` 给的 offset/limit 不只给你自己读——**它就是分派的依据**。实测一份 **1846 页 / 121 万字符**的红皮书，一个人从头读到尾不现实；按行范围切开派给多个 subagent，各自产出都合格。

**做法**：

1. 跑 `digest_plan`，拿到每章的行范围与字符数。
2. 按**体量**（不是按章数）均衡切，每份 15–45 千字符。某章太大就按二级小节切；几章都很小就合并给一个人。实测那本书的第三章 12 万字符，被切成「3.1+3.3 / 3.2 / 3.4+3.6 / 3.5」四份。
3. 每份派一个 subagent。prompt 里必须给全这几样：

| 要给的东西 | 为什么 |
|---|---|
| 源文件绝对路径 | 它看不到你的上下文 |
| **精确的 `offset` 与 `limit`** | 别给它章号让它自己找，也别写"第 X 到 Y 行"——把工具参数本身给它 |
| **一个已完成的成品页路径**，让它先读、照格式写 | **这条最关键**。不给样例时，frontmatter、页码约定、图的标注方式全都不一致 |
| frontmatter 八个字段的原文块 | 少一个就判 structure 不合格 |
| 页码格式，并写明「用 `## 第N页` 的 N」 | 否则它会误用原文页眉的页码（比物理页小 1） |
| 「只有图题的位置写『原图未随文本抽取』，**不要猜**」 | 不写这句，它会替图编内容 |
| 「**发现矛盾只报告，不要自行修正**」 | 自行修正会掩盖原文的问题，而记下矛盾正是这些页的价值之一 |

4. 收回来后**合并验收**（见第四步）——不要逐页对着整本比，那必然不合格。

**实测效果**：一份 73 页红皮书的两个接口页各自交出**术语 100%、保真 100%**（221 个标识符全部出自源文档）；处理 1846 页那本的四个 agent，各自都带回一份源文档的矛盾清单，**合计 23 条**——那些只有逐行读才看得见。

## 第三步：写页面

**一篇文档 = 1 个 `wiki/sources/` 索引页 + N 个 `wiki/topics/` 主题页**。

**按体量分页，不要按章号硬套。**「一章一页」只是个起点。实测一份 129 页文档，第六章「开放接口说明」占了 56499 字符（全文 76%），照「一章一页」会产出一个 80 KB 的怪物页——读不动也改不动；这时按二级小节拆（6.1 / 6.2 / 6.3 / 6.4 各一页）。反过来，前五章加起来才 9000 字符，就不必各占一页。

拆分不影响验收：`digest_audit` 看的是「源文档的章节有没有进产物」，不数产物有几个文件。

### frontmatter 五个必填

```yaml
---
tags: [标签]
created: YYYY-MM-DD
updated: YYYY-MM-DD
sources: [raw/articles/<源文件名>]     # 必须指向 vault 内的路径
platform_version: "BIP V5"            # 必填
project: ""
last_verified: YYYY-MM-DD             # 必填
status: unverified                    # 从文档抽取、未经环境实测的一律 unverified
source_type: doc
---
```

`status` 别随手写 `verified`——那个值表示"在真实环境验证过"。从文档读来的知识是 `unverified`。

### 正文必须做到

| 要求 | 为什么 |
|---|---|
| **每节标页码**，格式 `（p23）` | 用 **PDF 物理页号**。原文正文的页眉印的页码比物理页小 1，两者不要混 |
| **覆盖本章全部小节**，一个不落 | 验收会算覆盖率 |
| **照录清单、表格、步骤** | 不要概括成一句话——摘要式糊弄会让覆盖率掉到 20% 以下 |
| **照录约束**："必须/禁止/不支持/注意"一条都别丢 | 这些最容易被摘要吃掉，又最不能丢——使用者会因此踩坑 |
| **标识符原样保留** | `UCF-MDD`、`cdatarule`、`getQuerySchemmaByCond`（原文拼写）都不改写、不规范化大小写 |
| **图缺失就标注** | 写"原图未随文本抽取，此处无法还原"。**绝不凭图题想象图的内容** |
| **代码残缺就照残缺记录** | 注明"原文此处可能为代码片段，抽取后残缺"。**绝不补全代码或配置** |
| **原文笔误照录并加注** | 比如原文把 OMG 写成「OMGz」——照录，然后注明应为 OMG |
| **编者注用 `>` 引用块** | 见下，这是契约不是风格 |

### 编者注必须用引用块

```markdown
> 原文此处把 OMG 写作「OMGz」，应为 OMG 的笔误，上面按正字记录。
```

**这不是排版偏好，是契约**：`digest_audit` 的保真率检查会跳过引用块。批注里常常故意提到源文档没有的词（"原文拼写 `MddRefServcie`，疑为 `MddRefService`"）——后半截是要给的建议，不是事实声明。写在正文里就会被当成幻觉。

### 结尾两节

```markdown
## 原文没有讲清的
这里列真正缺的东西：图缺失、代码残缺、原文自己前后矛盾之处。

## 相关页面
- [[另一个主题页]]
```

## 第四步：验收

```
digest_audit(source="<源文档>", product="<页面文件或目录>", vault="<vault id>")
```

`product` 可以给**一个文件、一个目录，或一组路径的数组**。产物的页分居两处时（主题页在 `wiki/topics/`、索引页在 `wiki/sources/`）就给数组。

> ⚠️ **别把产物复制到别处再验收。** 副本不在库里，重叠那一项排掉的就是副本路径，而**库里的原件照旧被算作「已有内容」**：实测把 47.8% 虚报成 88.9%，一份合格的消化差点被判成「重叠过高、不值得做」。**给库内的真实路径**，排除才生效——报告在"排除一个都没命中"时会直接警告。
>
> ⚠️ 也不要直接把 `wiki/topics/` 整个目录传进去——产物和库里几千个既有页面同在那一层，那会把**全部**页面算成产物，保真率把别的文档的标识符统统报成幻觉。

七项全过才算完：

| 项 | 阈值 | 不合格怎么办 |
|---|---|---|
| 结构完整 | frontmatter 五个必填 | 补字段 |
| 中文术语覆盖 | ≥ 85% | 有整节没写进去 |
| 二级章节覆盖 | ≥ 60% | 漏了小节 |
| 约束句覆盖 | ≥ 85% | 把限制条件略掉了 |
| 保真率 | ≥ 98%（两个口径取低） | **看逐条出处**——真幻觉要删，合法引用/批注要改成引用块 |
| 溯源密度 | ≥ 50% | 加页码标注 |
| 可寻址 | ≥ 70% | 产物太概括，源文档的术语进不去 |

**保真率报的"找不到"不等于幻觉**。报告会给出每条的出处，逐个判断：引用别处来源的（保留）、批注原文拼写的（移到引用块）、原文用文字描述层级而产物写成点号路径的（可保留），**真正编造的要删掉**。

## 回头看：库里这一批做得怎么样

上面四步是消化**一份**素材。要问「库里已有的消化质量如何」，用：

```
digest_sweep(vault="<vault id 或绝对路径>", under="wiki/topics")
```

它按产物 frontmatter 里的 `sources` 自动配对源文件，**按源分组合并验收**，把最差的排在最前。

**分组这一步不是可选的。** 一份源文档常被拆成多个主题页，逐页对着整本源文档比覆盖率必然不合格——实测一份 129 页文档拆 10 页，单拿一页去比只有 12%–43%，十页合起来才是 98.7%。第一版 `digest_sweep` 就是逐页比的，于是报告说「30 份全部不合格」，连刚验收合格的那批也在里面。

除了覆盖率与保真，它专门分出三桶**根本没法验收**的产物：

| 桶 | 含义 |
|---|---|
| 来源缺失 | `sources` 指向的文件不在库里——页面在、来源没了，不可复核 |
| 无 vault 内来源 | `sources` 指向库外的 PDF 名（如 `"iuap-xxx红皮书 (129页)"`）——无从核对 |
| 读不到 | 文件损坏 |

**还有一格是「从未验收 N 组」**：能验收的组里，流水账中没有任何判定记录的。它是**单独一档**——既不是合格也不是不合格，是**没人验过**。实测一个真实库 13 个能验收的组里只有 2 组验过，**其余 11 组从未验收，而那 11 组这次全部不合格**。这是这整套东西里最该看的数：它量的是"绕过验收"的规模。

> ⚠️ **`status: superseded` 的旧页仍会被算进它声明的那一组。** 实测一份重做过的红皮书，组里带着两个已停用的存根页，而存根里保留着旧内容的外来标识符说明，于是整组的保真率被拉到 98% 以下。**看到某组只挂 `fidelity` 或 `structure`，先查这一组里有没有已停用的页。**

实测扫一个真实库（13100 份，`under` 用默认值）：

```
wiki 整树
  能验收        12 组   合格 1 / 不合格 11
  无 vault 内文件来源  12939 份
      6461  community-api-docs   ← OpenAPI 文档站抓取页
      5391  api_response         ← API 响应
       509  mdf-docs / 258 ynf-docs / 288 未标
  来源缺失        118 份
```

**「无 vault 内文件来源」这一桶必须再拆一层**，否则会得出错误结论：来源是**外部在线源**（`community-api-docs`、`api_response`）的产物本来就没有本地文件可对照，那不是缺陷；只有用 `source:` 指向一个**库外文件**（PDF 路径或 URL）的，才是「页面在、依据没了」。第一版把两件事混成一桶，报出「94% 无来源」，抽样看 frontmatter 才发现绝大多数是前者。

**`under` 要留默认值 `wiki`。** 同一份源的多页产物可能跨子目录——实测 MDD 的索引页在 `wiki/sources/`、5 个主题页在 `wiki/topics/`，按子树扫会把这一组拆成两半、两边都判不合格；而按整树扫，它是**全库唯一合格的一组**（6 页，术语 98.0%、保真 98.0%、可寻址 100%）。

同一源下若混了多代产物（实测一个组里既有 9/28 那代的一页、又有另一批 9 页，指向同一个源却是两次独立消化），合并验收会把两代的差异一起算——**不齐的那代拖累整组**。报告里有提示，看的时候要对照页名判断是不是同一代。实测消息那组内容本身是好的（术语 98.7%），却被同源的两份旧摘要拖进不合格（旧页缺 frontmatter 字段、正文无页码，把 structure 与 provenance 一起拉挂）。

**这个工具查出来的最险的一类，是覆盖率满分而保真率极低的产物**：实测 `raw/notes/2026-05-27-env-setup.md` 术语覆盖 100%、保真率只有 17%、可寻址 30%——术语都提到了，但绝大多数标识符在源文档里根本不存在。**只看覆盖率会把它当成好东西。**

## 接手旧产物：先判它是哪一种，再决定怎么处置

库里常有一批前几代留下的摘要，`sources` 可能指向同一个源。**别急着删，先分清四种**：

| 形态 | 长什么样 | 怎么办 |
|---|---|---|
| **覆盖不足** | 术语 10%–40%，但方向对、标识符都出自源文档 | 补写或重做 |
| **内容来自别处** | 保真率低（16%–60%），但那些"外来标识符"是**真实名字**（`pushBill.upstreamBillId`、`EventCenterClient.publish`），不像幻觉 | **是来源标注错了，不是编造**。改标注或重做 |
| **套模板编造** | 见下 | 改存根或删 |
| **根本没做** | 产物只有一个 `wiki/sources/` 索引页，源文档的章一节都没进去 | 重做 |

**「套模板编造」是同一套手法**：把一份领域红皮书套上通用领域概念。实测两例——

- 一份**消息平台**红皮书（讲模板、通道、待办、工作通知）被写成「消息队列开发指南」：消息队列、生产者消费者、点对点、发布订阅、死信队列
- 一份**单据流转**红皮书（推单/拉单/分单/回写）被写成「工作流开发指南」：流程定义、流程实例、审批节点、并行/串行、会签规则

两例都是**照书名想象"这个领域该讲什么"**。识别方法很简单：**翻开它的索引页，看「关键概念」那几行，逐个问"这些词源文档里有没有"**。这两例全是中文词，保真率一个都抓不到——只有术语覆盖率能反映。

### 处置方式

- **有反向引用就改存根，不要删。** 实测 `[[业务流开发]]` 有 6 处引用（含 `index.md` 与 `log.md`），删掉就是 6 个断链。改成 `status: superseded` + 一段说明写清"为什么被取代" + 指向新页。
- **顺手查 `[[链接]]` 是否有效。** 实测一个 `index.md` 的 446 个链接里有 6 个断链，其中两个指向的页面**从来不存在**。
- **`confidence: EXTRACTED` 不是这套 vault 的字段**——它是另一套工具留下的，规范里没有它。而 `last_verified` 才是必填（规范第 67 行），**语义是「消化日期」**：字段名说"验证"、语义说"消化"，规范自己就模糊，但删掉会触发「缺必填字段」的检查。
- **索引页会抄旧页的描述。** 实测一个 `index.md` 把两份编造页的说法原样抄了进去（"消息队列、异步处理"、"审批流、工作流、分支/并行/会签"），与被索引页自己的正文都矛盾。**改完旧页，回头看一眼索引。**

## 它验证不了什么

**只能验证"覆盖"与"保真"，验证不了"正确"。** 产物忠实照录了原文的错误取值，照样判合格。涉及配置值、接口路径、参数名时，用前请对照真实环境验证。

**还有一处已知漏网**：纯英文单词形态的臆造（`DAO`、`Service` 这类不成标识符形态的词）逃过保真检查。

**更要紧的一处**：**编造如果全是中文通用词，保真率会给满分。** 保真率只看标识符（英文/数字形态），所以「消息队列」「生产者消费者模式」「点对点、发布订阅」「死信队列」这类纯中文的臆造，一个都抓不到。

实测例：一份 129 页的**消息平台**红皮书（讲模板、通道、待办、工作通知），被人写成"消息队列开发指南"，列了上面那六条 MQ 概念——**没有一条在原文里**，而保真率报 **100%**，因为它整页只抽出 1 个标识符。只有**术语覆盖 1.9%** 这一项反映了问题。

**所以中文编造只能靠覆盖率间接发现：看不到覆盖率，就看不到这种错。** 一份产物哪怕保真率满分，也要看覆盖率那一行。

**中文术语这一项会带进抽取噪声。** 术语是 n-gram 抽出来的，PDF 抽取把行切碎之后会产生像 `检查迪调用环境是`、`迪调用环境是否正` 这样的片段——它们不是真术语，永远不可能出现在产物里，却占着分母。实测一份 129 页文档，375 个术语里 5 个是这种噪声（覆盖率仍 98.7%，因为分母够大）。**文档越小，噪声占比越高，越会压低覆盖率**；这时看报告里「未覆盖的术语」那一行，是碎片就放过。

## 关于阈值

在 `~/.dsh/yon-panel/digest_config.json`，九组参数可改（阈值、章节模式、术语词表、页码格式等）。按素材类型调整——网页素材没有页码，`pageMarkPattern` 要换；章节编号形态不同的文档要改 `chapterPattern`。

**这些数是实测校准出来的起点，不是"正确的"数。** 85% 和 98% 能分开实测样本，换成你的素材类型可能需要调。

## 一份做完的样子

实测一份 133 页红皮书（6 章）：

```
sources/xxx.md     4.4 KB    文档级索引：是什么、六章导航、读它的提醒
topics/xxx-第1章.md  6.5 KB
topics/xxx-第2章.md 28.9 KB
...                        一章一页
```

验收结果：中文术语 98.0%、标识符 99.1%、二级章节 100%、约束句 88.9%、保真率 98.0%、溯源 191 处（100%）、可寻址 20/20。判定合格。

第二份实测是一份 129 页的接口手册（6 章，其中一章占全文 76%），拆成 9 个主题页 + 1 个索引页、共 134 KB。验收：中文术语 98.7%、标识符 100%、一级章节 6/6、二级章节 68.8%、保真率 98.6%、溯源 78 处（50.0%）、重叠 37.4%（当时口径把本次产物自己也算进去了，含产物是 77.5%）、可寻址 20/20。判定合格。

**同一份产物在修复前被判过不合格**——不是产物有问题，是 `digest_audit` 的章节识别与 `digest_plan` 漂移成了两套实现，把参数表里的「0 表示操作成功，和result 等同」当成了一个一级章节。现已合并为单一实现，并由 `tests/digest.spec.ts` 钉住那次漂移。**记在这里是因为它说明一件事：验收报不合格时，先怀疑检查器，再怀疑产物。**

**对比**：同一个检查器对一份 1.1 KB 的"摘要式"产物判不合格——术语 2.8%、可寻址 5.0%。那份摘要列的六章内容与文档真实的六章**没有一条对得上**，是照标题想象出来的，而它标着 `confidence: EXTRACTED`。
