# 查用友知识库

> 这个技能由 `dsh-plugin-yon-panel` 插件预制：安装插件时它自动进入技能目录，卸载时自动消失。
> 知识库位于使用者自己的 Obsidian vault 里（通常是 `D:\yon-bip-obsidian\` 下的 BIP / NCC 两套），
> 路径由插件管理，**不需要你去翻目录或拼文件路径**。

## 什么时候必须用它

**写 SQL 之前、写涉及表名或字段名的代码之前。** 用友实体到数据库表的对应关系不适合靠记忆：

- 同一业务概念在不同产品线（BIP 旗舰版 / NCC）底层表完全不同；
- 引用型字段的 `name`（Java 驼峰名）和 `fieldName`（数据库列名）经常不一致；
- 字段编码、枚举取值这类细节，猜错不会报错，只会静默查出错数据。

## 两个工具，不要绕开

| 工具 | 用途 |
|---|---|
| `wiki_lookup` | 用一个名字找页面：实体 URI、物理表名、中文显示名、或它们的一段片段 |
| `wiki_read` | 读某个页面的全文，含字段清单（字段编码 ↔ 数据库列） |

**不要**去 grep vault 目录、也不要凭记忆拼 `wiki/entities/xxx.md` 路径：索引已经建好，
`wiki_lookup` 是毫秒级的，而全文检索几千个文件既慢又容易漏。

## 推荐顺序

1. 手上有什么就用什么去 `wiki_lookup`：代码里是 `voucher.order.Order` 就查 URI，报错里是
   `ucg_baseapi_api_info` 就查表名，需求里是"销售订单"就查中文名；
2. 看返回的**匹配方式**：`URI 精确` / `物理表精确` / `页面名精确` 是可靠命中，
   `包含` 只是片段相符，必须再核对一眼；
3. `wiki_read` 读中意的那页，拿 `物理表`、`domain/服务域` 和字段清单；
4. 再写 SQL。写之前**顺手核对一次**：关键的表名/列名用 `datasource_query` 发一条
   `SELECT ... WHERE 1=0` 验证存在性，比事后排查便宜得多。

## 可信度要自己判断

每个页面都带两个字段，**返回结果里一定会给**，请据此决定信几分：

| 字段 | 含义 |
|---|---|
| `version` | 知识适用的平台版本（BIP V5 / BIP R6 / NCC 2111 / NCC 2505…）。**版本不符就不要直接用。** |
| `status` / `verified` | `verified` 是已在真实环境验证过；`unverified` 是从文档提取、尚未验证；`outdated` 已过期 |

`unverified` 的页面**可以当线索，不能当结论**——用它定位，再用 `datasource_query` 确认。
两个页面说法矛盾时，先看 `version`：**不同版本的不同行为不算矛盾**；同版本矛盾才需要向使用者指出。

## 什么时候该写回去

知识库有 5000 多个实体页，但用友的实体远不止这些。查不到的时候，你往往**能把它查清楚**
——用 `datasource_query` 查数据库元数据，或反编译读实现。不写回去，这次学到的东西
会话一结束就没了，下次还得重查。这就是 `wiki_write` 的用途。

**顺序**：`wiki_lookup` → （查不到）→ `datasource_query` 实测 → `wiki_write`。

| 模式 | 什么时候用 |
|---|---|
| `create` | 这个实体在库里**没有**页面。需要 `page` / `uri` / `name` / `platformVersion` |
| `append` | 页面**已有**，你补一段新的（实测结果、查询示例、踩坑记录）。需要 `page` / `section` / `content` |
| `frontmatter` | 页面已有，你只是**更正验证状态**（`last_verified` / `status` / `project`） |

**没有"覆盖"这种模式**，工具层就不提供。已有的正文只能追加，不能改写——这是刻意的：
一页没人看的页面可以删掉，一页覆盖了 `verified` 内容的页面，毁掉的是别人对着真实环境
核过的东西，而且事后无从察觉。

### 写之前必须满足

1. **知识有依据。** `sourceType` 是必填的，它声明这条知识从哪来：
   `source_code`（反编译）/ `doc`（官方文档）/ `practice`（实测）/ `api_response` / `inference`（你的推断）。
   **`inference` 只能标 `unverified`** —— 工具会拒绝 `inference` + `verified` 的组合。
   这个库里 5419 个页面全是 `verified`；混进一条没有依据的，整体可信度就跟着打折。
2. **表名/字段名是查出来的，不是推出来的。** 写进页面的每个列名都该有 `datasource_query`
   的结果或反编译源码作依据。
3. **同 URI 同版本已有页面就别 create。** 工具会拒绝并列出那个页面，指你改用 `append`。
   如果这是**另一个平台版本**的知识，把 `platformVersion` 写成那个版本——不同版本的不同行为
   是事实，不是冲突。
4. **`content` 里不要写 frontmatter 和一级标题。** 这两部分由工具生成，标题行的格式是索引
   提取 URI 的依据；写错就等于写了一页永远查不到的页面。

写入会**停下来等使用者确认**，审批界面显示将要写入的内容。写完 `index.md` 与 `log.md`
会各追加一行——那是追加，不是重排，所以不会动到手工维护的目录结构。

## 边界

- **读**用 `wiki_lookup` / `wiki_read`；**写**用 `wiki_write`。没有覆盖正文的操作，
  需要重写某页时请使用者自己编辑；
- 知识库里没有的实体，如实告诉使用者"知识库未收录"，**不要用记忆里的表名充数**——
  但可以查清楚之后写回去；
- 知识库路径是使用者的本机配置。查不到任何东西时，先确认 Yon 面板「知识库」里登记了 vault，
  而不是反复换关键词猜。
