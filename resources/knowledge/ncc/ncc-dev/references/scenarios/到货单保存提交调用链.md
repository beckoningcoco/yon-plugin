## 1. 什么时候读我

- 客开要**在到货单保存提交前后插手**，或要知道到货单与采购/销售订单在同一动作上的差异。

## 2. 怎么拿到这条链

**入口 XML**：`<HOME>/hotwebs/nccloud/WEB-INF/extend/yyconfig/modules/pu/arrival/config/action/arrival_action.xml`
```xml
<action>
    <name>pu.arrival.saveandcommit</name>
    <label>到货单保存提交</label>
    <clazz>nccloud.web.pu.arrival.action.SaveAndCommitAction</clazz>
</action>
```
> ⚠️ **类名 `SaveAndCommitAction` 极其通用**，且不带业务前缀。`query-action.js --name pu.arrival.saveandcommit`
> 是唯一可靠的定位方式（`ncc_class_search` 会命中一堆同名类）。同族入口 63 个，其中相关的是：
> `pu.arrival.saveSend`（卡片态页签保存提交）/ `pu.arrival.commit` / `pu.arrival.uncommit` /
> `pu.arrival.approve` / `pu.arrival.unapprove` —— **注意到货单把"保存提交"和"保存 send"分成两个入口**。

**三步定位**：
1. XML / `query-action.js` → `nccloud.web.pu.arrival.action.SaveAndCommitAction`（`external/lib/uipu_nccloud.jar`）；
2. 父类 = **`nccloud.web.scmpub.pub.action.DataPermissionAction`**（`external/lib/uiscmpub_nccloud.jar`）；
3. 服务 = `ISCMPubSaveCommitService` → **与第 10 份同一个实现类** `SCMPubSaveCommitServiceImpl`（`modules/scmpub/META-INF/lib/scmpub_scmpub.jar`）。

| # | 层 | 位置 | 干什么 |
|---|---|---|---|
| 1 | HTTP | `POST /nccloud/pu/arrival/saveandcommit` | 到货单卡片保存提交 |
| 2 | 入口 | `SaveAndCommitAction#doAction:39`（`uipu_nccloud.jar`，111 行） | `extends DataPermissionAction`（**第三种入口基类**） |

**入口层额外做的两件事**（:68-69，保存成功后）：
```java
ArrivalScalaSetter.setArrivalScalaBillCard(card);          // 到货单标量（表头汇总量）回填

```
**这是到货单特有的**——保存提交后会重算并回填表头标量字段、做金额精度处理。

## 5. `AskWithCheckException`：第三类"不是报错"的异常

入口 catch 是**三分支**（:72-84）：

```java
catch (Exception e) {
    Throwable ex = ExceptionUtils.unmarsh(e);
    if (ex instanceof SaveAndCommitException) {              // ① 保存成功、提交失败
        return ((SaveAndCommitException)ex).getObject();     //    当"结果"返回（同第 10 份）
    }
    if (ex instanceof AskWithCheckException) {               // ② 需要用户确认
        Map resultMap = PfResumeExceptionNccUtils.handleResumeException(e);
        resultMap.put("exceptionType", "AskWithCheckException");   // ★ 打标签回前端
        return resultMap;
    }
    return PfResumeExceptionNccUtils.handleResumeException(e);      // ③ 其余走续跑
}
```

**`AskWithCheckException` 是"请你确认一下"语义**——不是失败，而是平台把决策抛回前端。
配合第 6 跳的 `skipCodes`：**前端确认后再次提交时，把 `"AskWithCheckException"` 放进 `skipCodes`**，
入口据它构造 `ArrivalUIToBSEnv`：

| 条件 | 设置 | 含义 |
| --- | --- | --- |
| `skipCodes` 含 `"AskWithCheckException"` | `env.setbBack(UFBoolean.TRUE)` | 已确认过，**放行** |
| `skipCodes` 有其它值（或两者都有） | `env.setbConfirm(UFBoolean.TRUE)` | 已确认 |
| `skipCodes` 为空 | 不设 env | 首次提交，可能被拦并返回确认请求 |

> 排查「到货单保存提交弹窗确认，点了再来一次就好了」——**这是平台的确认往返，不是 bug**。
> 客开要拦截/放行这类确认，认的是 `AskWithCheckException` 与 `ArrivalUIToBSEnv` 的两个布尔位。

## 6. 入口基类的三种形态（本批 5 份单据档案的规律）

| 基类 | 用的档案 | 提供什么 | 谁实现抽象方法 |
| --- | --- | --- | --- |
| `ICommonAction`（自己写 `doAction`） | 销售订单保存（第 7 份）、采购订单保存/保存提交（第 9、10 份） | 无 | — |
| **`AbstractGridAction<E>`** | 销售订单提交（第 8 份） | `doAction` 模板 + **权限检查**（`queryVos`→`checkPermission`→`action`） | `queryVos` / `action` / 三个权限元数据 |
| **`DataPermissionAction`**（抽象类，30 行） | **到货单保存提交（本份）** | **权限检查三种重载**（`IBill[]` / `IBill[]+actioncode` / `SuperVO[]`） | `getPermissioncode` / `getActioncode` / `getBillCodeField` + 自己的 `doAction` |

`DataPermissionAction` 全文（30 行）：
```java
public abstract class DataPermissionAction implements ICommonAction {
    public abstract String getPermissioncode();
    public abstract String getActioncode();
    public abstract String getBillCodeField();
    protected void checkPermission(IBill[] bills, String actioncode) {
        DataPermissionUtil.checkPermission(bills, getPermissioncode(), actioncode, getBillCodeField());
    }
    protected void checkPermission(IBill[] bills) { this.checkPermission(bills, getActioncode()); }
    protected void checkPermission(SuperVO[] bills) { ... }
}
```

> ⚠️ **`DataPermissionAction` 也有 7+ 个同名类**（`nccloud.web.action.*`、`nccloud.web.mmpub.pub.action.*`、
> `nccloud.web.lcm.pub.*`、`nccloud.web.scmpub.pub.action.*` …）。到货单用的是
> **`nccloud.web.scmpub.pub.action.DataPermissionAction`**（`uiscmpub_nccloud.jar`）。
> **第 10 份留下的"权限检查位置因入口而异"这句话，现在有了确定的解释：取决于入口继承哪个基类**——
> 继承 `DataPermissionAction` / `AbstractGridAction` 的白送权限检查；直接 `implements ICommonAction` 的没有。

### 未覆盖项的详情

- **两个"保存提交"入口的差别（⬜）**：`pu.arrival.saveSend` → `SaveSendAction`（label「到货单卡片态页签保存提交」）
  与 `pu.arrival.saveandcommit` → `SaveAndCommitAction`（label「到货单保存提交」）**都在**。
  一个单据有两个语义相近的入口在采购/销售里没见——**续做应对比这两个类**（可能一个是页签级、一个是整单级）。
- **`ResumeExceptionInfo`（⬜）**：入参不是卡片而是这个类，说明**到货单的保存提交支持"续跑"协议**。
  它与第 7 份的 `OffsetTempCache`、第 10 份的普通卡片都不同——**三个单据三套入参形态**。
- **事务边界（⬜）**：与第 10 份同源（`saveCommit` 的两趟），**未验**。
- **锁（⬜）**：五份单据档案在已读层都没有锁调用，**结论仍是"未验"而不是"没有"**。
- **`ArrivalScalaSetter` / `ArrivalPrecisionHandler`（⬜）**：表头标量回填与精度处理的规则未展开，
  客开若遇到"到货单表头汇总量与明细对不上"应从这两个类入手。
- **业务处理器清单（⬜）**：需连库。到货单的 `pk_billtype` 是 `"23"`、`actiontype` 是 `"SAVEBASE"`/`"SAVE"`：
  ```sql
  select c.actiontype, c.sysindex, c.isbefore, f.classname, f.methodname, c.conditionXpression
    from pub_actionconstrict c join pub_function f on c.functionid = f.pk_function
   where c.pk_billtype = '23' and c.actiontype in ('SAVEBASE','SAVE','APPROVE')
   order by c.actiontype, c.sysindex;
  ```
- **字段实测（⬜）**：需要能连 NCC2505 的库。
