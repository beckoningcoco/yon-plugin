## 2. 逐列最终实现（全部为库上实测，非推断）

| 表样列 | 实现 | 说明 |
|---|---|---|
| 第一列 单位（树） | 复用 05 手册的闭包 `e0..e7`（8 段） | 本体系最大深度 6，留一层余量 |
| 第二列 直联行账户数量 | 账户开户行 `bd_bank.defineCharacter → bd_bank_character_define_1.bcol49 = 1` | ⚠️ **数据待客户补**，见第 4 节 |
| 第三列 已直联账户数量 | `bcol49 = 1` **且** `nvl(a.ctm_direct_link_flag,0) = 1`（限定在直联行内） | 列名是 **snake_case**；元数据编码才是 `ctmDirectLinkFlag`；列注释「司库直联」。限定在直联行内是 2026-09-23 客户反馈后加的，见 5.2 |
| 第四列 已收到直连资料账户数量 | **不加**（需求方明确「用户未给出逻辑，不加这一列」） | |

| 第七列 非直联账户 | `bcol49 = 1` 且 `ctm_direct_link_flag = 0` | |
| 第八列 未直连成功账户 | `yonbip_fi_ctmpub.bam_direct_authorizemanage` 按 `bankAccount` 取 `audit_time` 最新一条，`handleresult = '0'` | `handleresult` 是 **VARCHAR 不是 INT**；`audit_time` 为空时退到 `create_time` 排序 |
| 第二语义模型 | 上述列的合计 | 按账户编码去重，不拿树模型行相加 |

**账户加入统计口径**（客户 2026-09-23 确认）：
`a.dr=0 and a.ytenant_id=… and nvl(a.acctstatus,0)<>1 and nvl(a.acctopentype,-1)<>2 and a.accountOpenDate is not null`
—— 排除**已销户**（`acctstatus=1`）、**财务公司开户**（`acctopentype=2`）、**开户日期为空**三类。

## 3. 两个必须记住的写法坑

1. **闭包里每一段的过滤条件必须带表别名**：`e0.dr=0 and e0.ytenant_id=… and e0.org_epm_systems_id=…`。
   写成不带别名的 `dr=0 and ytenant_id=…`，一旦该段 join 了 `e1`/`e2`… 达梦直接报
   **`[CODE:-2112] 有歧义的列名[ytenant_id]`**，而且报错位置指向语句结尾，不易定位。
   （05 手册里的成品是带别名的，本次用模板生成时踩过。）
2. **账户跨组织去重**用两层聚合：内层 `group by node_id, acct_code` 取各标志的 `max()`，外层 `group by node_id` 求和。
   与 05 手册的防 fan-out 同理。

## 4. 「直联行 / 不可直连」的数据现状（客户已确认「逻辑没问题，后续补数据」）

关联路径本身是通的（`bd_bank.defineCharacter` join `bd_bank_character_define_1.id` 命中 12/12，
`bcol49` 存在，SMALLINT）。问题是 `bd_bank`（135 家）里**只有 3 家被维护了特征项**：

| bcol49 | 银行 | 该开户行下的账户（未加任何过滤） |
|---|---|---|
| 1 | 中国工商银行 `00000004` | 75 |
| 1 | 中国人民银行 `00000003` | 44 |
| 0 | 财务公司 `system-002` | 142 |
| NULL | 证券公司 / 测试银行类别 等 7 家 | 4 |

其余 20 家银行（建行 32、中行 24、城市商业银行 14、交行 12、招行/华夏/农行各 8……）**完全没有特征项记录**，
另有 40 个账户 `bank` 字段为空 —— 这批账户在「直联行/不可直连」两列里都没有归属。
（本表加了「开户日期非空」这条后，这类账户大量被排除，落空比例从 179/440 降到 **10/77**。）

已排查的替代来源，都不比它好：

| 候选 | 实测 |
|---|---|
| `bd_bank_dot`（银行网点，23840 行） | 只有 **39** 行有特征项 |
| `tmsp_busineess_scope_directbanktype`（业务范围-直联银行类别） | 仅 **2** 行有效（财务公司、中国工商银行）；主表 3 条规则 `enable` 全 `='0'` 停用 |
| `tmsp_elebankaccountset`（电子银行账户设置，314 行） | `signStatus` **全部 `='0'`，无区分度**；只有 `bankInfo` 文本，无法精确关联账户档案 |
| `org_fin_bankacct_character_define_1`（账户自身特征项，397 行） | 有数据，但需求口径定在银行级；DM 的 `all_col_comments` 里特征项列（bcolXX）**无注释**，无法从库里确认哪列是「银企通道」 |

**两个来源互相矛盾**（需客户定以谁为准）：`bd_bank` 特征项把「财务公司」标为 bcol49=0，
而 `tmsp_busineess_scope_directbanktype` 却把「财务公司」登记为直联银行类别之一。

## 5. 口径已定的两件事 + 一件需提醒客户的事

### 5.1 开户日期为空的口径（已按客户口径落地）

客户 2026-09-23 定的口径是「**排除掉开户日期为空的数据**」，当前 SQL 用
`and a.accountOpenDate is not null`。实测影响很大：

| 口径 | 统计到的账户数 | 直联行 | 已直联 | 不可直连 | 直连率 | 非直联 | 未直连成功 |
|---|---|---|---|---|---|---|---|
| 不排除空开户日期 | 288 | 88 | 40 | 63 | 0.45 | 48 | 2 |
| **排除空开户日期（当前交付）** | **77** | **65** | **40** | **2** | **0.62** | **25** | **2** |

同口径下库里共 381 / 85 个账户（去重后仍为 381 / 85），落在组织体系内的去重账户数即上表的 288 / 77。
「已直联」两行都是 **40**：限定直联行后被排除的那 3 个账户（见 5.2）恰好都**不**受开户日期过滤影响。

原因：沿用排除口径后的 381 个账户里 **296 个开户日期为空**；非空的 85 个账户，开户日期
**最早 2023-01-01、最晚 2026-09-18**（全部落在 `[1997-01-01, 今天]` 内 —— 所以
「排除空值」与「按 1997-01-01~今天 区间过滤」在当前数据上**结果等价**，将来客户补了老数据就会分叉）。
**这 296 条要靠客户补**，否则报表只覆盖 77 个账户（全集团 440 个）。

### 5.2 「已直联」必须限定在直联行内（2026-09-23 已改）

最初按字段字面统计（只看 `ctm_direct_link_flag=1`，不看开户行），客户在前台发现
**有节点「直联行账户数量 = 0 但已直联账户数量 = 1」** —— 确实有问题，因为
实测有 **3 个账户**档案 `ctm_direct_link_flag=1`，但开户行（建行/中行/农行各 1）不是 `bcol49=1`。

**已改为** `bcol49=1 and ctm_direct_link_flag=1`，即第三列 ⊆ 第二列。改完既消除了该异常，也让
勾稽恒等式 **直联行 = 已直联 + 非直联** 在全部 629 个节点上成立（合计 65 = 40 + 25）。
影响：全体系已直联 43 → **40**，直连率 0.66 → **0.62**；`已直联` 非零节点数 11 → 5。

### 5.3 「已直联」的两个数据源不同步

55 个账户有直联授权单，其中 **17 个账户档案 `ctm_direct_link_flag` 仍为 0**。
本表按**档案字段**统计（需求文档明确），但要提醒客户：这张表与第二张报表的「直连情况」四列
若数字不一致，根源在此。

另：直连率按需求文档字面「相除后保留 2 位」输出为 **比率**（合计为 `0.62`）。达梦 `round` 为四舍五入
（实测 `30/48=0.625 → 0.63`）。若表样上要显示 `66%` 这种百分比，把公式改成
`round(分子*100.0/分母,2)` 即可。
