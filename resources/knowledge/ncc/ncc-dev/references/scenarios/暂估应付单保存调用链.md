## 4. 【核心】应付/应收里并存两套保存路径

| | **第 15 份：未确认应收单** | **第 16 份：暂估应付单** |
| --- | --- | --- |
| 入口类 | `EstiRecBillSaveAction`（113 行） | `BillSaveAction`（64 行） |
| 执行方式 | **`ArapBillUIUtil.executeBatchPM("SAVE", bill)`** | **`IArapEstiPayableBillService#saveEstiBills`** |
| 下一层 | 直接装配 `CloudPFlowContext` → `ICloudScriptPFlowService.exeScriptPFlow` | `EstiPayableBillServiceImpl`（64 行）→ BO（787 行） |
| 底层机制 | **PFlow 引擎**（与销售/库存同一个） | **BO + DAO + BSAction**（arap 自有分层） |
| 单据类型码 | 从 VO 属性 `pk_billtype` 读 | 服务实现里 `ArapBillTypeInfo.getInstance("23E1")` |
| 表 | `ar_estirecbill` / `ar_estirecitem` | `ap_estipayablebill` / `ap_estipayableitem` |

> **结论：同一个模块（`arap`）的应收与应付，保存走的是两条不同的路。**
> 排查财务单据保存问题时，**先确认是哪一条**：
> 入口里出现 `ArapBillUIUtil.executeBatchPM` → 走 PFlow（去 `pub_actionconstrict` 找业务类）；
> 入口里出现 `I*Service#save*` → 走 BO/BSAction（去 BO 与 BSAction 里找）。
>
> ⚠️ 本档案**不下"应收都走 PFlow、应付都走 BO"的结论**——
> 只验了这两张单据各一条路径；两边都还有别的入口（应收另有 `IEstirecbillService`，应付另有 `updateVOs` 等）。

## 5. arap 的三层分工（BO / DAO / BSAction）

`EstiPayableBO`（59 行）里看得很清楚：

```java
public class EstiPayableBO extends EstiBillBO {
    private EstiPayableDAO dao = new EstiPayableDAO();                    // ★ DAO：取数
    public AggEstiPayableBillVO[] findBillByPrimaryKey(String[] keys) {   //   经 ArapGeneralDAO 通用查询
        return (AggEstiPayableBillVO[])ArapGeneralDAO.getInstance().query(AggEstiPayableBillVO.class, keys);
    }
    public AggEstiPayableBillVO[] queryBillsBySourceBillID(String[] srcBillIDs) { return dao.queryBillsBySourceBillIDs(srcBillIDs); }
    public void deleteVOs(AggregatedValueObject[] vos) { new EstiPayableDeleteBatchBSAction().deleteVOs(vos); }         // ★ BSAction
    public AggregatedValueObject[] insertVOs(AggregatedValueObject[] vos) { return new EstiPayableSaveBatchBSAction().insertVOs(vos); }
    public AggregatedValueObject[] updateVOs(AggregatedValueObject[] vos) { return new EstiPayableEditBatchBSAction().updateVOs(vos); }
}
```

**三层**：

| 层 | 类 | 职责 | 证据 |
| --- | --- | --- | --- |
| **BO**（业务对象） | `EstiPayableBO` → `EstiBillBO`（787 行） | **业务逻辑**（校验、计算、组织循环） | `EstiBillBO#saveEstiBills` |
| **DAO**（数据访问） | `EstiPayableDAO` + `ArapGeneralDAO`（通用） | **取数**（按主键/来源单据/来源行查） | `dao.queryBillsBySourceBillIDs` 等 |
| **BSAction**（批处理动作） | `EstiPayableSaveBatchBSAction` / `...EditBatchBSAction` / `...DeleteBatchBSAction` / `...ApproveBatchBSAction` / `...UnApproveBatchBSAction` | **按动作分工**（增/改/删/审/弃审） | `EstiPayableBO` 与 `EstiPayableBillServiceImpl` 两处的委派 |

**服务实现 `EstiPayableBillServiceImpl`（64 行）的形态**——它几乎全是"模板方法 + 装配"：
```java
public class EstiPayableBillServiceImpl extends ArapBillBaseServiceImpl<AggEstiPayableBillVO>
        implements IArapEstiPayableBillService {
    protected ApproveBatchBSAction   getApproveBSAction()   { return new EstiPayableApproveBatchBSAction(); }
    protected UnApproveBatchBSAction getUnapproveBSAction() { return new EstiPayableUnApproveBatchBSAction(); }
    protected DeleteBatchBSAction    getDeleteBSAction()    { return new EstiPayableDeleteBatchBSAction(); }
    protected InsertBatchBSAction    getSaveBSAction()      { return new EstiPayableSaveBatchBSAction(); }
    protected UpdateBatchBSAction    getUpdateBSAction()    { return new EstiPayableEditBatchBSAction(); }
    protected IArapBilltypeInfo getArapBilltypeInfo()       { return ArapBillTypeInfo.getInstance("23E1"); }   // ★ 单据类型码
    public AggregatedValueObject[] updateVOs(...)     { return new EstiPayableBO().updateVOs(vos); }
    public AggregatedValueObject[] saveEstiBills(...) { return this.getEstiPayableBO().saveEstiBills(bills); }

```
—— **父类 `ArapBillBaseServiceImpl` 用 5 个 `getXxxBSAction()` 抽象方法把"增删改审弃审"抽成模板**，
子类只负责返回自己那套 BSAction + 自己的单据类型码。**这是 arap 的模板方法模式**。

> **单据类型码 `"23E1"`**（暂估应付单）——形态与前面所有链都不同：
> 销售 `"30"`、采购 `"21"`、到货 `"23"`、请购 `"20"`、库存 `"4C"/"45"`，
> 在这里是 **`"23E1"`（4 位带字母）**，且**由服务实现显式声明**（不是枚举类、也不是从 VO 读）。

## 6. `EstiBillBO#saveEstiBills` 在做什么（业务逻辑层）

`:61-106` 的骨架（787 行的方法，本档案只读到开头）：

```java
public AggregatedValueObject[] saveEstiBills(AggregatedValueObject[] bills) {
    if (bills == null || bills.length == 0) return bills;
    String billtype = bills[0].getParentVO().getAttributeValue("pk_billtype").toString();   // ★ 也是从 VO 读
    // ① 按组织收集"最早单据日期"（validateDate：pk_org → date）
    for (每个 vo) { pk_org = head["pk_org"]; date = head["billdate"]; ... }
    // ② 按单据逐条处理
    for (每个 vo) {
        String djlxbm  = head["pk_tradetype"];        // 单据类型编码（交易类型）
        String pk_org  = head["pk_org"];
        String pk_group= head["pk_group"];
        String prodid  = "AR";                        // ★★ 产品线由 syscode 决定
        if (head["syscode"].equals(ArapConstant.INT_ONE)) prodid = "AP";
        UFBoolean isinit = head["isinit"];            // 是否期初
        if (isinit) {
            boolean isInitClose = prodid.equals("AR")
                ? ((IInitBillCloseService)NCLocator.lookup(...)).isInitBillClosed(ArapConstant.ARAP_FUNCODE_ESTIRECBILL_I, pk_org)
                : ((IInitBillCloseService)NCLocator.lookup(...)).isInitBillClosed(ArapConstant.ARAP_FUNCODE_ESTIPAYBILL_I, pk_org);
            if (isInitClose) throw 02006pub-0077;      // 期初已关账
        }
        ...
    }
}
```

**三个要点**：

1. **应收与应付共用同一个 BO（`EstiBillBO`）**——靠 VO 属性 **`syscode`** 分流：
   `syscode == ArapConstant.INT_ONE` → `prodid = "AP"`，否则 `"AR"`。
   **"过账到应收还是应付"就出在这一行**（同为 `EstiBillBO`，输入不同则去向不同）。
2. **期初单据有单独的关账校验**：`IInitBillCloseService.isInitBillClosed(功能码, pk_org)`
   ——应收用 `ARAP_FUNCODE_ESTIRECBILL_I`、应付用 `ARAP_FUNCODE_ESTIPAYBILL_I`。
   报错资源 `2006pub_0 / 02006pub-0077`（**期初已关账不能保存**）。
3. **`validateDate` 按组织收集最早单据日期**——应是给"关账期间校验"用的（第 15 份的 PFlow 路径里没有这一步）。

> **本档案未读完 787 行**（只读到 :106）。后续应包含：期间/关账校验、来源单据校验、
> 金额与汇率计算、以及最终落库（经 DAO 或 BSAction）。**这是本档案最大的 ⬜**。
