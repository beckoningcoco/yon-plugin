# 部门保存调用链 — NCC2505

> 采集口径见 [_call-chain-collection-standard.md](./_call-chain-collection-standard.md)。
> 证据等级：**反编译**（本机无 NCC2505 数据库连接，字段未做实测；SPR 单列一轮）。
> 环境：Home = `E:/NCProject/NCC2505/HOME_BYZY_BIP`。

## 1. 什么时候读我

- 客开要在**部门卡片保存**前后插手：部门编码、负责人落组织主管、报表组织/预算组织这些"部门类型"数据的联动、部门版本。
- 排查「部门保存报 LockFailed」「改了部门编码，下级部门的内部编码没跟着变」「部门删了但组织主数据里还在」。
- 需要知道**部门的两套定义**：基础档案的 `org_dept`（riaorg，56 字段）与 **HR 的 `org_dept`（hrjf，38 字段）**——同表名、不同实体、不同 action（见第 2 节的入口辨析）。

> **部门是"组织型实体"，它保存时会同时写组织主数据**（`OrgVOAdapterFactoryBasic` → `IOrgUnitManageBasicService`）。
> 这一点与客户/供应商/物料/账簿都不同：那些写完自己的表就结束了，部门还要让"组织树"也认识它。

**与另两套模板的差别**：

| | `SingleBaseService`（客户/供应商/物料/科目） | `MultiManageTypeBaseService`（账簿） | **`TreeBaseService`（部门）** |
| --- | --- | --- | --- |
| 锁 | `BizlockDataUtil.lockDataByBizlock` + `BDPKLockUtil.lockSuperVO` | `PKLock` 组织维度动态锁 | **`RootLockUtil.lockBranchRoot`（根分支锁）+ `BizlockDataUtil`** |
| 落库 | `getPersistenceUtil().insertVO(...)` | `getMDService().saveBill(...)` | **`getPersistenceUtil().insertVOWithInnerCode(...)`**（树形，带 innercode） |
| 签名 | 单条 `T vo` | 数组 `T... vos` | 单条 + 数组两版（`insertVO` / `insertVOs`） |

**`insertLockOperate:172-178` 的树形锁值得单说**：
```java
List needToLockRoot = this.getParentNotExistsVOs(vos);   // 父节点不在本次待插入集合里的 = 根
for (SuperVO vo : needToLockRoot) this.getRootLockUtil().lockBranchRoot(vo);
BizlockDataUtil.lockDataByBizlock(vos);
```
`getParentNotExistsVOs:180-192` 用 `getPersistenceUtil().getParentPkFieldName()` 拿父字段名，
把"父不在本批里"的行当作**根**，逐个锁整条分支。**部门新增是锁"它所属的根分支"，不是锁自己**。

## 7. 部门版本机制（`DeptTreeBaseService` 在四个 db 方法里各补一刀）

`nc.impl.org.DeptTreeBaseService`（`modules/riaorg/META-INF/lib/riaorg_org_rt.jar`，187 行）
`extends TreeBaseService<DeptVO>`，构造函数 `super("b26fa3cb-4087-4027-a3b6-c83ab2a086a9", 2)`
—— mdId `b26fa3cb-4087-4027-a3b6-c83ab2a086a9`，第二参 `2` 是**树的持久化风格**。

它在增/改/删/启停四个点上都追加"版本行"处理：

| 方法 | 行 | 追加动作 |
| --- | --- | --- |
| `dbInsertVO` | :38-47 | `super.dbInsertVO` → `getEachTypeOrgVersionVO(vo, 2)` → 新版本行 `status==2` 走 `execEachOrgVersionInsertOperate`；`status==1` 走 `Update` |
| `dbUpdateVO` | :66-70 | `super` → `getEachTypeOrgVersionVO(vo, 1)` → `execEachOrgVersionUpdateOperate` |
| `dbDeleteVO` | :72-76 | `super` → `getEachTypeOrgVersionVO(vo, 3)` → `execEachOrgVersionDeleteOperate` |
| `dbEnableVO` / `dbDisable` | :49-64 | 同样 `(vo, 1)` → `Update` |

`getEachTypeOrgVersionVO(eachtypeorgvo, vostatus):78` 按 VO 的属性名把主表数据映射成一个版本 VO，
交给 `OrgTypeServiceAdapterBasic` 落库 → **版本表 `org_dept_v`**（`nc.vo.vorg.DeptVersionVO`）。

**部门自己还有一处版本相关的补充**（`DeptManageServiceBasicImpl#dbInsertVO:617-630`）：
```java
BDMultiLangUtil.setMultiLangValues(vo, "vname", "org", "0org0284");   // ① 多语言版本名

vo.setVno(time.getYear() + "01");                                      // ② 版本号 = 年份 + "01"
```

> `vno = 年份 + "01"` 是**很硬的一条约定**：部门版本号的形态就是 `202501`、`202601` 这种。
> 改部门版本要考虑它。`org_dept` 上的 `pk_vid` / `vname` / `vno` / `vstartdate` / `venddate` / `islastversion`
> 六个字段就是这套机制在主表上的投影（见第 8 节字段表）。

**`dbUpdateVO:642-648` 另有一处子部门联动**：`handleSubDeptVersionInnerCode(oldVO, newdeptvo):650`
用 `innercode like '<旧innercode>%'` 查出所有子部门的 `DeptVersionVO`，
把它们的 `innercode` 里的旧前缀替换成新前缀再 `updateVOList`。
—— **"改了部门的内部编码，下级部门的版本行跟着改"** 就出在这。
