## 1. 什么时候读我

- 要知道**客户档案保存/修改/删除，代码从哪进、在哪落库**，以便找地方挂插件或改逻辑
- 要判断**一个动作最终写哪几张表**（主表 + 子表 + 版本表 + 供应商表）
- 要理解 NCC 的**通用单据持久化路径**（`BDSingleBaseService` / `MDPersistenceUtil` / `VOPersister`
  是所有走元数据映射的单据的公共通道，换成别的单据只是最上面几跳不同）
- 要**加校验**（第 8 节有现成的 `getXxxValidator` 扩展点）、**理解版本机制**（第 10 节）、
  或者**排查"客户和供应商数据不同步"**（第 11 节）
- 手上有 SPR 报告，想把「远程调用」表里那条调用落到具体代码上
- 要问**客户保存有没有调用 `IRule` / 业务规则** → 直接看第 5 节

## 2. 怎么拿到这条链（三条路，优先级从高到低）

**第 0 条：先读档案。** 本案档案已建好，直接看第 3~11 节；只有档案没覆盖的维度才往下走。

**第 1 条：查 action XML 定位入口——不用开环境、不用录 SPR。**
nccloud 的「按钮 → 实现类」是**静态配置**，不在代码里（Action 类反编译出来没有 `@RequestMapping`、
没有 URL 常量）。映射在：

```
<HOME>/hotwebs/nccloud/WEB-INF/extend/yyconfig/modules/{模块}/{业务}/{子业务}/config/action/{X}.xml
```

```xml
<action>
  <name>uapbd.customer.saveCustomer</name>     <!-- 动作名：点换斜杠 → /nccloud/uapbd/customer/saveCustomer -->
  <label>客户信息卡片保存</label>               <!-- 中文按钮名：人话 ↔ 机器名的桥梁 -->
  <clazz>nccloud.web.uapbd.customer.baseinfo.action.CustomerSaveAction</clazz>
</action>
```

按 `label` 或 `name` grep 即可拿到类名。**注意 `label` 会重名**（「保存」在几百张单据里都有），
必须带上模块/业务一起找；全量 **31699 条**（NCC2505 实测：2817 个 XML / 6.41 MB），
**覆盖率未验**——老 UAP 界面（`/app/...`、直接 servlet）不走这套注册，找不到时别急着下结论。

**第 2 条：SPR 报告定位入口**——查不到、或要拿真实调用参数时用。

1. 录制一次「只保存」的 SPR（见 `ncc-spr-recording` 技能），报告里「远程调用」表会给出
   **真正的后端 HTTP 路径**，本例是：

   ```

   ```

   它是 nccloud 层的 REST 路由，不是 servlet，所以可以直接推类名：
   `nccloud.web.{模块}.{业务}.action.XxxSaveAction`。

2. **逐层反编译**：用 `ncc_class_search` 按类名找 jar，再用 cfr 反编译。命令模板：

## 5. 事件与规则链——客户保存时还会跑什么

第 3 节 `insertVO` 十步里的 `fireBeforeInsertEvent` / `fireAfterInsertEvent` **不是空动作**，
它们派发 `BDCommonEvent`，把订阅了这个单据的监听器叫起来：

```java
// nc.bs.bcsi.rule.bd.listener.CustomerListener
public class CustomerListener extends AbsBdDocListener {
    protected AbsBdInformRule getInformRule() { return new CustomerInformRule(); }
}

// nc.bs.bcsi.rule.bd.listener.AbsBdDocListener implements IBusinessListener
public void doAction(IBusinessEvent event) {
    if (event instanceof BDCommonEvent) execInformRule();
}
```

事件类型常量：`ADD="1002"` / `UPDATE="1004"` / `DELETE="1006"` / `BATCH_UPDATE="1061"`。
执行时 `rule.setOperType(operType)`，从 `((BDCommonEvent.BDCommonUserObj) event.getUserObject()).getNewObjects()`
取 VO，再调 `rule.process(vos)`。同族还有 `MaterialListener`（物料）、`SupplierListener`（供应商）。

> ⚠️ **客户档案走的是这条「事件订阅」，不是 `IRule` 插件链。**
> 反编译客户保存链上的 14 个类，`Rule` **零命中**——如果有人在找「客户保存调用的 `IRule` 代码」，
> 答案是**这条链上没有**。`IRule`（`nc.impl.pubapp.pattern.rule.IRule` + `RuleCollection` +
> `pub_pluginitem` 表）是**服务类单据**那条线。两套机制的区别与取证方法见
> [ncc-event-and-rule-mechanism.md](./ncc-event-and-rule-mechanism.md)。

**状态**：上面这条「代码链条」是反编译读出来的，**运行证据未验**——
本环境 `pub_pluginitem` 里有没有配置、录制时到底调没调，都还没查
（当时 `datasource_list` 的 16 条连接里没有能连 NCC2505 的库）。

## 6. 修改路径（`updateCustomerVO`，:376）

```java
public CustomerVO updateCustomerVO(CustomerVO customervo, boolean forceSave) {
    if (customervo == null) return customervo;
    getUniqueFieldTrimUtil().trimUniqueFields(customervo);
    this.updatelockOperate(customervo);                      // ★ PK 锁 + 业务锁（比新增多一把，见第 9 节）
    BDVersionValidationUtil.validateSuperVO(customervo);     // ★ 版本号校验（防并发覆盖）
    CustomerVO oldVO = this.retrieveVO(customervo.getPrimaryKey());
    this.resetVersion(customervo, oldVO);                    // ★ 从 oldVO 拷回 version/begindate/enddate
    customervo.setPk_customerpf(oldVO.getPk_customerpf());
    this.updateValidateVO(oldVO, customervo);                // ★ 带 oldVO 的校验（第 8 节）
    this.relationSupCheck(customervo, forceSave);
    this.setUpdateAuditInfo(customervo);                     // 修改人/修改时间
    this.fireBeforeUpdateEvent(oldVO, customervo);           // ★★★ 钩子：带 old + new 两个参数
    this.synchronizeCustInfoForUpdate(customervo, oldVO);    // ★ 客户↔供应商同步（第 11 节）
    this.synAllVersionCustomer(customervo);                  // ★ 同步所有历史版本（见下）
    this.dbUpdateVO(customervo);                             // ★★★ 真正落库
    this.custStructureService.synchronizeCustStructureForUpdate(customervo, oldVO);
    this.notifyVersionChangeWhenDataUpdated(customervo);
    customervo = this.retrieveVO(customervo.getPrimaryKey());
    this.fireAfterUpdateEvent(oldVO, customervo);            // ★★★ 钩子：带 old + new
    this.writeUpdatedBusiLog(oldVO, customervo);
    return customervo;
}
```

**`resetVersion`（:401）只做三件事**：把 `version` / `begindate` / `enddate` 从 oldVO 拷回新 VO
——**即这三个字段不接收前端传值**，防止改坏。

**与新增的关键差异**（写插件时最该注意的）：

| | 新增 | 修改 |
|---|---|---|
| 锁 | 只有业务锁 | **PK 锁 + 业务锁** |
| 版本校验 | 无 | **`BDVersionValidationUtil.validateSuperVO`**（版本号对不上就报错） |
| 事件参数 | `(vo)` | **`(oldVO, newVO)` 两个** |
| 事件名 | `fireBefore/AfterInsertEvent` | `fireBefore/AfterUpdateEvent` |
| 落库方法 | `dbInsertVO` | **`dbUpdateVO`** |
| 版本表 | `insertCustomerVersion` | **`synAllVersionCustomer`**（见下） |

**`synAllVersionCustomer`（:1053）**：修改主表时把改动同步到该客户的所有历史版本记录，
不只动最新那条——**这是"改了一个客户，几条版本一起变"的原因**。

## 10. 版本机制（客户档案与别的单据最不一样的地方）

**新增时**（`setVersionInformation` :889）：

```java
vo.setVersion(1);
vo.setBegindate(new UFDate("1970-01-01 00:00:00"));    // ★ 不是当前时间
vo.setEnddate(new UFDate("9999-12-31 00:00:00"));      // ★ 不是"永久"这个词，是个具体日期
```

**写版本表**（`insertCustomerVersion` :895）：

```java
CustomerVersionVO customerVersionVO = new CustomerVersionVO();
for (String attr : customerVersionVO.getAttributeNames()) {      // ★ 按"版本 VO 自己的属性名"逐个拷
    if (vo.getAttributeValue(attr) == null) continue;
    customerVersionVO.setAttributeValue(attr, vo.getAttributeValue(attr));
}
customerVersionVO.setLatest(UFBoolean.TRUE);
getCustomerVersionDAO().insertCustomerVersionVOWithPk(customerVersionVO);
```

**回填主表指针**（`updateCustomerVersioSourcePK` :905）：

```sql
update bd_customer set pk_customer_v = ? where pk_customer = ?
-- 参数：vo.pk_customer_v 为空时传 pk_customer，否则传 pk_customer_v；第二个参数恒为 pk_customer
```

**要点**：

- **主表 `bd_customer` 与版本表是两份数据**，靠 `pk_customer_v` 互指
- 新增时 `vo.setPk_customer_v(pk)`（**先把自己指给自己**）再写版本表
- 修改时 `resetVersion` 保证 version/begindate/enddate **不被前端改坏**，
  `synAllVersionCustomer` 把改动同步到**所有历史版本**
- `CustomerVersionVO.latest` 标记哪条是最新；`updateCustomerLatesetFlag`（:1821）负责切换
- **删除时版本表是显式删的**（`deleteCustVersion` :1570，两条原生 SQL），不走 MD 逻辑删

**客开注意**：**改客户数据时想清楚要改主表还是版本表**——只改主表会让版本对不上；
平台自己的做法是 `synAllVersionCustomer` 两边一起改。

## 11. 客户 ↔ 供应商同步（`issupplier` 的双向语义）

NCC 里客户和供应商**共用一套基础档案**，`issupplier` 决定它是不是同时也是供应商。

**新增后**（`synchronizeCustInfoForInsert` :1015）：

```java
CustSupplierVO newCustSupVO = new CustSupplierVO(vo);      // ★ 用 CustomerVO 构造出供应商 VO
if (!vo.getIssupplier().booleanValue()) {                  // ★ 不是供应商时，才补一条供应商记录
    getCustSupService().insertCustSupVO(newCustSupVO);
}
```

版本表同理（`synchronizeCustInfoVersionForInsert` :1022，`latest=TRUE`、`supversion=0`）。
**结论**：**`issupplier=false` 的客户，系统里也有一条对应的供应商记录** ——
这是"新建的客户为什么在供应商列表里能看到"的原因。

**修改后**（`synchronizeCustInfoForUpdate` :1042）：

```java
boolean isSupplier = vo.getIssupplier() != null && vo.getIssupplier().booleanValue();
CustSupplierVO custSupVO = getCustSupQrySer().queryCustSupVOByPk(vo.getPrimaryKey());
CustSupplierVersionVO custSupVersionVO = getBaseDAO().retrieveByPK(CustSupplierVersionVO.class, vo.getPk_customer_v());
if (isSupplier) this.synchronizeBaseInfo(vo, oldVO, custSupVO, custSupVersionVO);   // 4 参版（:1276）
else            this.synchronizeBaseInfo(vo, oldVO);                                 // 2 参版（:1091）
```

**`isSupplier` 决定走哪条路，而这两条路差别极大**：

| | `isSupplier = false`（不是供应商的客户） | `isSupplier = true`（同时是供应商） |
|---|---|---|
| 方法 | `synchronizeBaseInfo(vo, oldVO)` :1091 | `synchronizeBaseInfo(vo, oldVO, custSupVO, custSupVersionVO)` :1276 |
| 同步到几个对象 | **3 个** | **5 个** |
| 对象 | `CustomerVersionVO`、`CustSupplierVO`、`CustSupplierVersionVO` | 上面 3 个 **+ `SupplierVO`（真正的供应商档案）+ `SupplierVersionVO`** |
| 同步字段怎么定 | **硬编码** | **从配置读**（见下） |
| `def1~def50` 自定义项 | **只进客户版本表**，不进供应商 | 客户版本表（全量属性拷贝会带上） |

> **注意**：`isSupplier=true` 时**同时存在两套供应商记录**——客户侧的 `CustSupplierVO`（`bd_cust_sup`）
> 和真正的 `SupplierVO`（`bd_supplier`），**两个都要维护**。只改一边就会出现"客户视图改了、供应商档案没改"。

**路一（`isSupplier=false`，:1091）的分两段**：

*第一段：11 组关键字段「变了才同步」，且同步到上面那 3 个对象*
`pk_financeorg`（连带 `custprop`→`custsupprop`）、`pk_profitcenter`（连带 `innerprofitcenter`）、
`taxpayerid`、`ratetype`、`pk_areacl`、`name`、`mnecode`、`shortname`、`code`、`pk_custclass`、`pk_org`。

*第二段：无条件覆盖*
`CustomerVersionVO` 上连着拷 **80 多个字段**（`enablestate` / `email` / `tel1~3` / `memo` / `ename` /
`exTable` / `isretailstore` / `legalbody` / `pk_currtype` / `pk_customer_main` / `pk_customerpf` /
`pk_custtaxes` / `pk_country` / `pk_timezone` / `pk_format` / `url` / **`def1`~`def50`** /
`name2`~`name6` / `trade` / `registerfund` / `corpaddress` / `fax1~2` …）；
而 `CustSupplierVO` 与 `CustSupplierVersionVO` **只另外拿到 `name2`~`name6`**（:1261–1270）。
最后三个 `getBaseDAO().updateVO(...)` 一起落库。

**路二（`isSupplier=true`，:1276）——字段清单是配置驱动的**：

```java
// ① 客户版本表先做一次"全量属性拷贝"（除 ts）
HashSet<String> custAttrSet = new HashSet<>(Arrays.asList(customerVO.getAttributeNames()));
for (String attr : customerVersionVO.getAttributeNames()) {
    if ("ts".equals(attr) || !custAttrSet.contains(attr)) continue;
    customerVersionVO.setAttributeValue(attr, customerVO.getAttributeValue(attr));
}
// ② ★ 同步到供应商的字段清单从配置取，不是硬编码

List<String[]> attrs = synService.getCreateOrUpdateSynAttrs(CustSupSynConfVO.UPDATECHECK);
```

`ICustSupSynConfService` / `CustSupSynConfVO` 就是**「客商同步配置」**（界面上配"客户哪些字段同步给供应商"）。
逐字段处理的三种特例：

- **`registerfund`**：用 `compareUFDouble`（:1372）比，**不能用 `equals`**
- **`establishdate`**：用 `compareUFDate`（:1382）比，同理
- **`corpaddress`**：**不是字符串而是独立档案**——旧的先 `pService.delete`，新的 `clone()` 后
  换新 `pk_address`、`status=2`、`pService.insert`，再把供应商指向新 pk

处理完再把 `supplierVO` 的属性全量拷进 `supplierVersionVO`（同样跳过 `ts`），
然后还有**一小撮 14 个字段的硬编码白名单**只同步到 `CustSupplierVO` / `CustSupplierVersionVO`（**不含 `SupplierVO`**）：

```java

                         "name5","name6","mnecode","shortname","code","pk_custclass","pk_org"};
```

`pk_financeorg` / `pk_profitcenter` 是两个特例：改了会**同时 set 四个对象**
（`custSupVO` + `custSupVersionVO` + `supplierVO` + `supplierVersionVO`），
且 `custprop` 在客户侧叫 `custsupprop`、在供应商侧叫 `supprop`——**同一个值两边字段名不同**。

**落库方式也不同**（前两个走服务，后三个直接 DAO）：

```java
getCustSupService().synSupplierInfo(supplierVO);      // 走服务
getCustSupService().updateCustSupVO(custSupVO);       // 走服务
getBaseDAO().updateVO(supplierVersionVO);
getBaseDAO().updateVO(custSupVersionVO);
getBaseDAO().updateVO(customerVersionVO);
```

**另有两个硬编码搬运小方法**：`updateCustsupVOByCustVO`（:1392）与
`updateCustsupVersionVOByCustVO`（:1412），各搬 16 个字段
（`code`/`name`/`name2~6`/`pk_areacl`/`taxpayerid`/`custsupprop`/`pk_financeorg`/`pk_org`/
`pk_custclass`/`mnecode`/`shortname`/`pk_profitcenter`）。**调用点未追**。

**删除后**：`dbDeleteVO` 里 `getCustSupService().deleteCustSupVOByPK(...)` 连带删掉供应商记录（第 7 节）。

**客开注意**：**挂钩子改客户字段时，供应商侧不会自动跟着变**——同步只在这条链里发生。
若在 `fireAfterInsertEvent` 里改了客户字段，供应商侧已经同步完了，**两边会不一致**。
