# 数据模型与接口地图

> **读接口比抠 DOM 可靠得多**。画布是虚拟渲染、转换规则表是虚拟列表，DOM 只能看到视口内那几行；
> 而接口一次给全。业务流的接口都**同源**，在页面里 `fetch(url, {credentials:'include'})` 就能拿到
> （同源带 cookie，不用额外带 token）。

## 一、业务流主体 + 画布内容

`GET /iuap-apcom-supportcenter/businessFlow/getById?id=<业务流id>`

返回一个对象，**主体字段** + 一个叫 **`content` 的 JSON 字符串**（画布内容）。

### 主体字段（实测「普通销售（有发货）」）

| 字段 | 值 | 含义 |
|---|---|---|
| `id` / `code` | `7c59f9e0-7db8-45a6-b432-fe189dcf9bbb` | 预置流的 id 就是它的 GUID 编码 |
| `name` / `name2` / `name3` / `multiName` | 普通销售（有发货）/ 英文 / 繁体 | 多语言名 |
| `tenantId` | `jd4ofb7k` | 租户 |
| `subId` | `GYLFW` | 供应链服务 |
| `billCode` | `voucher_order` | **核心单据** |
| `transactionTypeId` / `transactionTypeName` | — / 普通销售（有发货） | 核心单据的交易类型 |
| `describe` | 销售订单、销售发货、销售出库单、销售发票 | 描述（自动汇总） |
| `version` / `isVerSupport` / `isCurrentVersion` | `V1.0` / true / true | 版本 |
| `isPreset` | **true** | 预置流（「预置」分类）；自定义流为 false |
| `isSystem` | false | |
| `isLane` | **false** | 是否启用业务泳道（影响触发设置可选时机） |
| `sysFlowId` | `9c94c7ac-…` | 系统流 id |
| `status` | true | 已启用 |
| `orgId` / `orgName` | `666666` / global企业账号级 | 组织 |
| `createTime` / `modifierName` / `updateTime` | — / 张佳鑫 / 2026-05-28 23:43:32 | 审计 |

### `content` 的结构

顶层 4 个键：**`nodes` / `edges` / `panZoom` / `versionId`**（`versionId="1.0"`）。

**`nodes`** —— 每个节点 `type` 都是 `ruleItemNode`：

| 字段 | 含义 |
|---|---|
| `id` / `nodeId` | 节点 id（两者相同） |
| `code` | 单据编码，如 `voucher_order` / `voucher_delivery` / `st_salesout` / `voucher_saleinvoice` |
| `name` | 单据名 |
| `subId` | 所属服务，如 `SCMSA`（供应链销售）/ `ST`（库存） |
| `isCore` / `isCoreDes` | **`"1"` = 核心单据**，`"0"` = 普通；`isCoreDes` 为「核心」 |
| `icon` | 如 `icon-rule-relation-fixedflow` |
| `left` / `top` | 画布坐标 |
| `columns` | 锚点定义数组，固定 5 项 `[Top, Bottom, Right, Left, MidCenter]`，每项含 `anchors` 与 `operation.arr`（可选后继单据提示）—— **属 UI 提示，不是核心配置** |

**`edges`** —— 每条边 `data.type` 都是 `billPush`（推单）：

| 字段 | 含义 |
|---|---|
| `id` | 边 id（GUID） |
| `data.type` | `billPush` |
| `data.bounds.source` / `.target` | 锚点，实测 `Bottom` → `Top` |
| `name` | **数组**，如 `["订单发货"]` —— 这就是画布上显示的连线名 |
| `dockers` | `[]` |

> ⚠️ **`content` 里没有规则**。`edges` 只有拓扑和名字，**边的规则要另外调接口**（见下）。
> 实测 `getById` 的返回里**搜不到任何规则编码**（如 `order_delivery`）。

## 二、边的规则：`flowRule/list`

`GET /iuap-apcom-supportcenter/flowRule/list?businessFlowId=<流id>&nodeId=<边uuid>`

**这是规则完整数据的来源。** 返回的规则对象有 **79 个字段**，常用的：

| 字段 | 含义 |
|---|---|
| `name` | 规则名称（= 连线名） |
| `id` / `ruleId` | 规则 id |
| **`ruleCode`** | 规则编码。**自定义规则的格式是 `userDefine_<业务流id>_<序号>`** |
| **`refRuleCode`** / `sysRuleCode` | 引用的系统规则编码，如 `order_delivery` |
| `nodeId` / `businessFlowId` / `businessFlowName` | 归属 |
| **`pushOpportunity`** | **触发设置**的取值（2=手工触发，见 `02` 第四节） |
| `pushRuleType` / `pushMode` | 推单类型 / 推送方式 |
| `showConvertedBill` | 推单过程（是否走转单画面） |
| `createUserType` / `createUserId` / `createUserName` | 新建单据制单人 |
| `originType` / `originDes` / `originSubId` / `originDomain` / `originBillType` | 来源单据 |
| `targetType` / `targetDes` / `targetSubId` / `targetDomain` / `targetBillType` | 目标单据 |
| `srcBizTypeId` / `srcBizTypeName` | **来源交易类型** |
| `tarBizTypeId` / `tarBizTypeName` | **目标交易类型** |
| `dataItems` / `groupItems` / `collectItems` / `filterItems` | 转换 / 分单 / 汇总 / 过滤的**自定义**内容 |
| `expression` / `expressionDisplay` | 公式 |
| `timeSetting` / `toDoSetting` / `failureToDoSetting` | 定时推送 / 待办消息 / 失败消息 |
| `pullMetaPk` / `pullType` / `pullDomain` / `pullMultiSelect` / `pullShowAll` | 拉单侧配置 |
| `description` / `order` / `extInfo` | 描述 / 排序 / 扩展 |

**实测一条自定义规则**（`JYTD_XS_01` 边①「订单生成发货单」）：
`pushOpportunity=2`、`pushMode=0`、`showConvertedBill=true`、`createUserType=0`、
`ruleCode=userDefine_2591409053897850882_525977`、`refRuleCode=order_delivery`、
`originDomain=udinghuo`、`originBillType=2`、`order=1`、
**`dataItems` / `groupItems` / `collectItems` / `filterItems` / `expression` / `timeSetting` 全是空字符串**
—— 说明这条规则**没有做任何自定义，全部沿用引用的系统规则**。

> **`originType` 的域名前缀不统一**：有的带（`udinghuo.voucher_delivery`）、有的不带（`voucher_order`），
> **精确等值匹配会漏**，要用 `includes` / `endsWith`，或者干脆按 `originDes` / `targetDes` 中文名匹配。

## 三、系统规则（单据转换规则）

`GET /iuap-apcom-supportcenter/domainMakeBillRule/getRuleByCode?tenantId=&isBusiObj=true&ruleCode=<规则编码>&bizFlowId=2`

**这是 7 个页签各页的数据源** —— 规则的界面内容基本都是从这里读出来渲染的。

顶层键：`code` / `name` / `subId` / `targetSubId` / `category` / `microServiceCode` /
`filterScheme` / `makebill_type` / `origin_type` / `target_type` / `originDomain` / `targetDomain` /
`originBillType` / `targetBillType` / `isSys` / `isHidden` / `isBusinessObject` / `pushOpportunity` /
`convertFlag` / `userDefine` / `createUserType` / …

实测 `order_delivery`：`subId=SCMSA`、`microServiceCode=yonbip-scm-scmsa`、
**`filterScheme=voucher_orderlist`**（来源数据过滤用的方案名）、`makebill_type=0`、`isSys=true`、
`originDomain=targetDomain=udinghuo`、`originBillType=targetBillType=2`。

### 三张子表，对应三个页签

**`makeBillRuleDetailList`** —— **转换规则**页。实测 327 条。

每条的键：`origin_field` / `target_field` / **`mapped_type`** / **`mapped_relation`** /
`is_write_back` / `is_edit` / **`childKey`**（目标子表）/ **`sourceChildKey`**（来源子表）/
`isHidden` / `isBusinessObject` / `category` / `subId` / `rule_id`。

- **`origin_field` 用 `!` 表示子表路径**，如 `orderDetailPrices!inventoryowner_name`。
- `mapped_type` 取值分布 `{0: 320, 1: 1, 3: 6}`；`mapped_relation` 取值分布 `{0: 87, 1: 14, 2: 17, 3: 209}`。
- `mapped_type=3` 的样本：`origin_field="0"`（常量字符串）→ `target_field=stopQty` / `stopMoney` / `stopPriceQty`
  → **`mapped_type=3` 是常量映射**。
- `mapped_type=1` 的样本：`firstlineno` → `firstlineno`。

**`makeBillRuleGroupList`** —— **分单规则**页。实测 1 条（`groupCode=voucher_order2voucher_delivery`）。

其 **`makeBillRuleGroupItemList`** 每项：
`sOriField`（→ 分组字段）/ `sTarField` / **`sOriFieldName`**（→ 分组字段显示名）/
`childKey`（→ 来源单据）/ `iOrder` / `bEnum` / `isItemMain` / `isItemSub`。
样本：`sOriField=stockOrgId, sTarField=stockOrgId, sOriFieldName=stockOrgId_name, childKey=orderDetails, iOrder=1, bEnum=false`。

**`makeBillRuleBackMainList`** —— **回写规则**页。实测 1 条。

其 **`makeBillRuleBackList`** 每项：
`sOrgRelateField`（→ 来源关联字段）/ `sOrgKey`（→ 来源回写字段）/ **`sBackType`**（→ 回写方式）/
`sTarRelateField`（→ 目标关联字段）/ `sTarKey`（→ 目标回写字段，**可含公式**）/
`sOrgChildKey` / `sTarChildKey` / `isFormulas` / `pubtsField`。
样本：`sOrgKey=sendQty, sTarKey="qty-stopQty", sBackType=sum, sOrgRelateField=id, sTarRelateField=sourceautoid, isFormulas=true`。

## 四、接口地图（全部同源 GET，`credentials:'include'`）

| 接口 | 用途 |
|---|---|
| `/businessFlow/getById?id=<流id>` | **业务流主体 + content** |
| `/flowRule/list?businessFlowId=&nodeId=<边uuid>` | **边的规则列表（规则完整对象）** |
| `/domainMakeBillRule/getRuleByCode?tenantId=&isBusiObj=true&ruleCode=<编码>&bizFlowId=2` | **单条转换规则的完整定义**（三张子表） |
| `/domainMakeBillRule/getAllRuleList` | 全部系统转换规则（实测 **1405 条**，返回约 160 万字符 —— 慎拉） |
| `/business/getAllTreeListByMddExt?serviceCode=XTLCZX0032` | 左侧可选单据树 |
| `/flowBill/getByBusinessFlowIdAndNodeId?businessFlowId=&nodeId=billItemNode_<uuid>` | 节点在该流中的配置 |
| `/business/getTransTypeTypeByFormId?formId=<域>.<单据>&tenantId=&isBus=true` | 交易类型列表（**formId 要带域名前缀**，如 `udinghuo.voucher_order`） |
| `/businessFlow/getUsedTransactionType?tenantId=&businessFlowId=&billCode=<单据>` | 该流已用过的交易类型 |
| `/form/processOperationList?tenantId=` | 「流程操作」的 5 个选项 |
| `/opportunity/list` | 「单据动作」——「单据对 → 可用动作」映射 |
| `/form/queryCategoryProcDefActivities?tenantId=&category=<subId>.<单据>&billType=2` | 单据流程活动 |
| `/config/systemMeta` / `/business/getU8cMetadataByMddExt?orgId=<orgId>` | 系统元数据 |

> ⚠️ **`getRuleByCode` 缺上下文时会 NPE**（报 `DomainMakeBillRuleModel.getMakeBillR…`）。
> 对**系统规则**（如 `order_delivery`）可以直接调通；对**自定义规则**需要业务流上下文，
> 这种情况改用 `flowRule/list`。

> ⚠️ **`getAllRuleList` 返回 1405 条、约 160 万字符**，不要随手全量拉进对话。
> 要筛"某两个单据之间有没有转换规则"，用 `originDes` / `targetDes` 中文名过滤。

## 五、一个可复制的取数写法

在**已登录的设计器页签**里用 `browser_eval`（同源，自动带 cookie）：

```js
// 取某条边的规则
const r = await fetch('/iuap-apcom-supportcenter/flowRule/list' +
  '?businessFlowId=2591409053897850882&nodeId=<边uuid>', { credentials: 'include' })
const rules = (await r.json()).data
rules.map(x => ({ name: x.name, ruleCode: x.ruleCode, refRuleCode: x.refRuleCode,
                  pushOpportunity: x.pushOpportunity, src: x.srcBizTypeName, tar: x.tarBizTypeName }))
```

**先在小结果上验证字段名，再决定要不要拉大表。**
