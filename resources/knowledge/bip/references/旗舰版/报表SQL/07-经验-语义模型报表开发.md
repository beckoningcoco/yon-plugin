## 一、平台硬规则

### 1.1 参数语法 【硬规则】

| 项 | 写法 |
|---|---|
| 自定义参数 | `${param('编码')}`，**不加单引号** —— 平台替换时自带引号，套一层会变成 `''值''` |
| 日期参数 | 不要用 `TO_DATE` / `STR_TO_DATE` / `CAST` 去包参数 |
| 空值兜底 | 自定义参数用 `<#if param('x')?? && param('x') != ''>` 包裹，判断要**双重**；只写 `??` 时用户传空串仍会过滤 |
| 租户 | 取法**以实际环境为准**：见过系统变量 `${var('tenantId')}`，也见过自定义参数 `${param('ytenantid')}`。以该语义模型参数列表里实际存在的编码为准，不要照抄别的环境 |

### 1.2 FreeMarker 位置 【硬规则】

- **标签内部**（`<#if …>` / `<#else>`）已在表达式模式 → 写 `param('x')`，**不能**写 `${param('x')}`
- **SQL 正文**（静态文本）→ 必须写 `${param('x')}`

写错会报：`You can't use ${...} (an interpolation) here as you are already in FreeMarker-expression-mode.`

### 1.3 平台校验的已知行为 【硬规则】

平台校验脚本剥 `<#if>` 时**保留 if 分支、丢弃 else 分支**，
所以 `<#else>` 里的默认值那一支平台校验覆盖不到，必须自己在库上单独跑一次确认。

## 二、通用工程方法

### 2.1 「跑通」不等于「正确」：三类静默错误 【方法】

报表 SQL 翻车很少是语法写错，多数是下面三类 —— **都不报错**，数字却是 0 或全部落在同一档，
看起来像「业务本来就没数据」。

| # | 类型 | 现象 | 为什么会发生 |
|---|---|---|---|
| 1 | **条件恒不成立** | 过滤后结果恒空 / 某列恒为 0 | 过滤值在该列里根本不存在（如该列实际全为 NULL、或该列用的是另一套编码体系） |
| 2 | **关联键不匹配** | 聚合恒 0 或全落「否」那一档 | 拿 A 表的标识去比 B 表另一个 ID 空间（两边看着同名同形，其实不同源） |
| 3 | **口径覆盖不全** | 部分行/列对、部分不对 | 只改了一处，另一处（另一段 SQL、另一个派生表、oracle 一样的兄弟条件）没同步 |

**判定方法**：不要因为"跑通了"就收工 —— 每个非零指标都要能**由明细推导出来**；
每个恒 0 的指标都要能说明"为什么它必然为 0"，而不是默认"业务没数据"。

### 2.2 一对多派生表的扇出 【方法】

**两张各自一对多的派生表，都直接 join 到同一张基表上** → 乘出笛卡尔积，数字虚高，**不报错**。

做法：每张派生表**先聚到 join 键唯一一行**再 join 回基表；互相独立的指标各自成一段派生表。

> 这条是 SQL 通用问题，与平台无关。闭包/树展开这类"一个明细对应多个上级"的场景同样适用（见 3.2）。

### 2.3 自检思路 【方法】

先想清楚「这个报表的数字之间，本来应该有什么恒等关系」，再用它反向验证。

| 检查 | 说明 | 适用 |
|---|---|---|
| **交叉恒等式** | 能互相推出的两列必须对得上（如 `合计 = 各项之和`、`期末 = 期初 + 增 − 减`） | 有内在勾稽关系的报表 |
| **两种算法对拍** | 换一种写法（或脚本）再算一遍同一个数 | 通用 |
| **明细清单核对** | 用明细行凑出那个数，而不是只看 `COUNT(*)` | 通用 |
| **边界值** | 区间端点、空值、极值单独试一遍 | 有区间/条件的报表 |
| **行数** | 输出行数是否符合预期（行的骨架不该被过滤/聚合改变） | 通用 |
| **单调性** | 层级汇总时：子级 ≤ 父级（**反常的定义是 子 > 父**） | 有层级汇总的报表 |
| **前后端一致** | 明细行与合计行在共享口径的列上必须一致 | 同时出明细与合计的报表 |

**原则**：一个只用一个子查询算出来的数字，没有任何交叉校验，最容易错（本文来源的开发过程里就因此报错过一个数）。

### 2.4 排错定位 【方法】

1. **逐段单独跑**：大 SQL 拆开，先确认每一段的行数/取值符合预期，再拼。
2. **改前 vs 改后同参数对拍**：确认改动生效，**不要靠"SQL 里有没有那行字"判断**——
   注释里留着旧写法，很容易让人误判"条件还在"。
3. **先验中间量**：换表/换关联后，先单独跑一次"该表在该条件下的行数"，与预期对照再改正文。
4. **枚举与取值一律实测**：**字段名不代表它用的是哪套枚举**。做法是把
   **字典表 + 实际取值分布 + 样例行**三者对上，再下结论。
5. **报错位置可能是假的**：多表 join 的场景里，某些错误（如"有歧义的列名"）报在语句结尾，
   真正的原因在中间某一段。按段排查比盯报错行号有效。

### 2.5 交付与协作 【方法】

- 每个数字都能给出**明细清单**（哪几行凑出来的）。
- **待确认项单独列出**，不要埋在正文。
- **版本化**：每次改动留版本号 + 证据 + 变更点。
- SQL 里保留"为什么这么改"的注释；但注释里的旧字样要与实际条件**区分清楚**，
  否则下次有人 grep 会误以为条件还在。

## 三、EPM 组织树相关（仅当需求涉及组织树时才适用）【条件适用】

> 完整的「组织树上卷」方案见 [[05-经验-组织树与子级数量统计]]，这里只记与之互补的几条。
> 不涉及组织树的需求，本节整节可跳过。

### 3.1 三个 ID 空间，必须分清

| 列 | 含义 | 用途 |
|---|---|---|
| `org_epm_orginization_ext.id` | **成员 ID** | 树遍历（`parent_org_id` 指向它） |
| `org_epm_orginization_ext.org_id` | → `org_epm_organizations.id` | 体系内组织 |
| `org_epm_organizations.org_source_id` | **真实组织档案 ID** | **挂业务数据只能用这个** |

**铁律**：树遍历走成员 ID；**业务表 join 必须经过 `org_source_id` 这座桥**。
直接拿 `ext.org_id` 去比业务表的组织字段，会因为 ID 空间不同而匹配不上，
算出一个**比本级还小**的数，而且不报错。（本文来源的开发过程里实际踩过：一度算出"上卷后 = 0"。）

### 3.2 上卷时注意

- **每一段的过滤都必须带表别名**（`e0.dr=0 and e0.ytenant_id=…`）。用模板生成时最易漏：
  第 1 段不带别名也能跑，第 2 段起 join 了 e1/e2 就报 **`[CODE:-2112] 有歧义的列名[ytenant_id]`**，
  而且报错位置指向语句结尾。
- 闭包输出给上层 join 的是**成员 ID**（`eX.id`），不是 `eX.org_id`；写反了行数会少且不报错。
- 展开层数用**实测的最大深度**，别拍脑袋（换组织体系要先跑一次深度统计）。
- 上卷后，**汇总不能拿明细各行相加** —— 同一个业务对象会被它的每一个上级各计一次（见 2.2）。

### 3.3 `innercode` 不可信

该列常与 UI 树的层级对不上 → **只信 `parent_org_id`**，不要用 `innercode LIKE 'x%'` 做上卷。

## 四、达梦（DM）方言与错误码速查 【硬规则】

| 现象 | 原因 / 改法 |
|---|---|
| `[CODE:-2267] 递归 WITH 子句必须具有列别名列表` | 递归 CTE 要写成 `WITH RECURSIVE x(a, b) AS (...)` |
| `[CODE:-2112] 有歧义的列名[xxx]`，位置在语句结尾 | 多表 join 时某段过滤没带表别名 |
| `[CODE:-2111] 无效的列名[x]` | 列名拼错，或该列不在这张表上 |
| `[CODE:-2207] 无法解析的成员访问表达式[x]` | 表/列别名写错（例如 CTE 里 `e.parent_org_id` 忘了 `AS parent_id`，外层却用 `parent_id`） |
| `[CODE:-2007] 语法分析出错` | 常见于把**保留字**当别名（实测 `both` 做列别名即报此错），或 `EXISTS(...) = 0` 这种写法 |
| `cast(current_date as char)` → `[CODE:-6149] 数据类型转换失败` | 改用 `to_char(current_date,'YYYY-MM-DD')` |
| 可用 | `TRUNC(date,'YYYY')`、`to_char(current_date,…)`、`nvl`、`nullif`、DATETIME 列与 `'yyyy-mm-dd'` 直接比较（隐式转换） |

## 五、本例的做法 —— 仅供参考，不构成规范 【本例】

> 以下是「金隅账户数量表」当时的选择。**换一张报表完全可以不这么做。**
> 列在这里只为说明"遇到这类要求时可以怎么选"，不是"应该这么写"。

**为什么拆成两段 SQL**：这张报表要求同时输出「一行一个组织」和「一行合计」，
而合计必须**按业务主键去重**、与明细的去重口径不同，所以拆成两段独立 SQL。
—— **如果报表只有一种粒度，一段 SQL 就够，不必拆。**

**CTE 结构**：当时用了 `cfg`（口径参数集中一处）+ `org_tree` + 业务明细 + 聚合 + `closure`。
好处是口径参数只有一个改动点、便于单独验证；但这只是**一种**组织方式，
数据量、可读性、维护成本上若有更合适的写法（子查询、临时表、视图、物化等），就用更合适的。

**日期参数**：这张报表带起止日期，所以需要处理「年初」「区间端点」「明细与合计的结束日折算是否一致」这些问题。
—— **不带日期参数的报表没有这些问题，本节不适用。**
（若确实带日期参数，值得记住一条：多段 SQL 共享同一时间口径时，**折算规则必须统一**，
否则同一参数下两段会差一天；这一点在"结束日当天恰好没数据"时不会暴露。）

**组织上卷**：明细要"含下级"，所以用了闭包展开 + 两层聚合。
—— **不需要含下级的报表，不必上卷。**
