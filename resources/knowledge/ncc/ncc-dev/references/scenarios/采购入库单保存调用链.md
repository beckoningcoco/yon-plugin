# 采购入库单保存调用链 — NCC2505

> 采集口径见 [_call-chain-collection-standard.md](./_call-chain-collection-standard.md)。
> 证据等级：**反编译**（本机无 NCC2505 数据库连接，字段未做实测；SPR 单列一轮）。
> 环境：Home = `E:/NCProject/NCC2505/HOME_BYZY_BIP`。
>
> 与 [销售出库单保存调用链.md](./销售出库单保存调用链.md) 同属库存（`ic`）链，**用的件套完全相同**
> （`ICBillVO` / `IICFilterData` / `ICPFResumeExceptionUtil` / `ICBillType`，`actionName="WRITE"`），
> 但**入口的写法不同**：销售出库是"35 行薄壳 + 继承模板基类"，采购入库是**自己写 416 行**（第 3 节）。

## 1. 什么时候读我

- 客开要**在采购入库单保存前后插手**，或要知道它与销售出库的差异在哪。
- 要处理**入库费用项**（`ic_purchasein_f` / `_bf`）——**采购入库比销售出库多两张费用子表**。
- 要理解**同一个库存体系里，两种入口写法并存**（继承模板 vs 自包含）。

## 2. 怎么拿到这条链

**入口 XML**：`<HOME>/hotwebs/nccloud/WEB-INF/extend/yyconfig/modules/ic/inbound/config/action/purchasein.xml`
```xml
<action>
    <name>ic.purchasein.save</name>
    <label>采购入库保存</label>
    <clazz>nccloud.web.ic.inbound.purchasein.action.PurchaseInSaveAction</clazz>
</action>
```
**定位**：`query-action.js --name ic.purchasein.save` → `PurchaseInSaveAction`（`external/lib/uiic_nccloud.jar`）。

> **与销售出库的入口对照**：销售出库的 `SaleOutSaveAction` 只有 **35 行**且 `extends SaveAction`（模板基类）；
> 采购入库的 `PurchaseInSaveAction` 是 **416 行**且直接 **`implements ICommonAction`**。
> 但两者**在 `doAction` 里做的事情几乎一样**（第 3 节的逐步对照）——
> **采购入库把模板基类的逻辑抄了一份**（在同一个 jar 里，但没能复用）。
> 这不是笔误：`PurchaseInSaveAction` 多了费用项与伪列处理，可能因此没走通用基类。

## 3. 链路（10 跳）与逐步对照

`PurchaseInSaveAction#doAction:64-103`：

```java
CloudPFlowContext context = ICPFResumeExceptionUtil.processBefore(request);   // ① 续跑前置（同销售出库）
String str = request.read();
ExtBillCard card = json.fromJson(str, ExtBillCard.class);                      // ② ExtBillCard（销售出库是 BillCard）
ICExtBillCardOperator operator = this.getOperator(card);                       //    ICExtBillCardOperator
ICBillVO[] vos = new ICBillVO[]{ (ICBillVO)operator.toBill(request) };
vos = this.fillBill(vos);
operator.setOriginBillcard(card);
if (vos != null && vos.length > 0) {
    this.checkReferencedBill(vos);                                            // ③ 只做被引用校验（无 checkncorrespond）
    vos = ((IICFilterData)ServiceLocator.find(IICFilterData.class))
              .filterFromFront(ICBillType.PurchaseIn.getCode(), vos);          // ④ 库存前置过滤
    context.setBillType(ICBillType.PurchaseIn.getCode());                      //    "45"
    context.setBillVos(vos);
    ICloudScriptPFlowService service = ServiceLocator.find(ICloudScriptPFlowService.class);
    context.setActionName("WRITE");                                           // ⑤ 与销售订单保存/销售出库同一个动作名
    try {
        AppInfoContext.setBtnCode("Save");
        Object[] ret = service.exeScriptPFlow(context);                        // ⑥ 引擎
        obj = ret instanceof ICBillVO[] ? (ICBillVO[])ret : (ICBillVO[])ret[0];
        this.handlerComputedPropertyField(obj);                               //    ★ 在 try 内、fillLocation 之前
    } catch (Exception e) {
        return ICPFResumeExceptionUtil.handleICResumeException(e);             // ⑦ 库存续跑异常出口
    }
    obj = ((IICFilterData)ServiceLocator.find(IICFilterData.class))
              .fillLocationVOs(ICBillType.PurchaseIn.getCode(), obj);          // ⑧ 货位回填（引擎后）
    this.processDelBody(vos);                                                  // ⑨ 剔删除行（含费用项！）
    try { new BillCombine().combine((AbstractBill[])vos, (AbstractBill[])obj); }  //    BillCombine（销售出库是 ClientBillCombinServer）
    catch (Exception e) { ExceptionUtils.wrapException(e); }
    this.processLocationVOs(vos, obj);                                         // ⑩ 货位客户端回填
    ExtBillCard retcard = this.afterProcess(operator, vos[0]);
    return retcard;
}
```

**与销售出库的逐步对照**：

| 步骤 | 销售出库（基类 `SaveAction`） | **采购入库（本类）** |
| --- | --- | --- |
| context 来源 | `ICPFResumeExceptionUtil.processBefore` | **同** |
| 入参类型 | `BillCard` + `SrcFlagDTO`（解析**两个**对象） | `ExtBillCard`（**只一个**） |
| 卡片操作器 | `ICBillCardOperator` | **`ICExtBillCardOperator`** |
| 通用出入库 srcflag | **有**（`assembly`→1 / `teardown`→2） | **无** |
| 校验 | `checkReferencedBill` + **`checkncorrespond`** | **只有 `checkReferencedBill`**（自己实现，105-148 行） |
| `filterFromFront` | 有 | **同** |
| billType | `getBilltype().getCode()`（子类给） | **硬编码 `ICBillType.PurchaseIn.getCode()`** |
| `actionName` | `"WRITE"` | **`"WRITE"`（同）** |
| `handlerComputedPropertyField` | 在**合并之后**（:90） | 在 **try 内、`fillLocationVOs` 之前**（:85） |
| `fillLocationVOs` | 引擎后一次 | **同** |
| 合并器 | `ClientBillCombinServer` | **`BillCombine`** |
| 删除行 | `processDelBody`（只剔表体） | **`processDelBody` 同时剔表体与费用项**（:164-182） |
| 结果比对 | `GridCompareUtils.compareBillCardGrid` + `dealCarrier` | **`afterProcess` 内做状态转换与精度处理** |
| 单据状态 | —— | **`operator.processICBillstatusForWeb(retcard)`**（:204） |
| 精度 | `getPrecisionHandler`（子类可覆写） | **`new PurchaseInExtBillCardPrecisionHandler(retcard, "body").process()`**（:205） |
| 长度 | 259 行（基类） | **416 行** |

> **结论**：库存链里**"继承模板"和"自包含"两种写法并存**。
> 客开若给一类库存单据挂逻辑，**不能假设它们共用同一个基类**——要逐个入口看它继承谁。

## 4. 采购入库特有的三件事

### 4.1 费用项（比销售出库多两张子表）

`processDelBody:164-182` 同时处理**表体与费用项**：
```java
ICBillBodyVO[] bodys = vos[0].getBodys();
// ... 剔除 status==3 的表体行 ...
Object[] fees = ((PurchaseInVO)vos[0]).getFee();          // ★ 费用项
if (!ArrayUtil.isEmpty(fees)) {
    ArrayList<Object> realfee = new ArrayList<>();
    for (Object body : fees) { if (body.getStatus() == 3) continue; realfee.add(body); }
    vos[0].setChildren(PurchaseInFeeVO.class, realfee.toArray(new PurchaseInFeeVO[0]));
}
```
—— `PurchaseInVO#getFee()` 是采购入库的**费用项集合**，落 `ic_purchasein_f`（费用项）与 `ic_purchasein_bf`（物料费用明细）。

### 4.2 伪列（`pseudocolumn`）清理——**但负责清理的方法没被调用（疑似产品缺陷）**

类里有一个 `processPK:184-200`，把服务端返回的表体与费用项的 `pseudocolumn` 置 null：
```java
private void processPK(ICBillVO[] vos, ICBillVO[] obj) {
    ...
    for (Object body : objbodys) body.setAttributeValue("pseudocolumn", null);
    for (Object body : objfees)  body.setAttributeValue("pseudocolumn", null);
}
```
**`pseudocolumn` 是卡片前后端通信用的伪列**（不是数据库列）。同类处理也出现在
第 10 份的 `dealPseudoColumn`（采购订单保存提交，`isfromCT` / `REVISE` 分支）。**清了它才能回卡片。**

> ⚠️ **但 `processPK` 在本类里从未被调用**——已验证：
> ① 全文 grep 只有 :184 的定义行，`doAction`（:64-103）与 `afterProcess`（:202-211）都没有调用它；
> ② 全 jar 扫描 56 个 `purchasein*` 类，只有定义类自身含该字符串；
> ③ 对该 class 文件做字节级统计，常量池里 `"processPK"` 只出现 **1 次**（仅方法名本身，
> **没有任何 `invokevirtual`/`invokespecial` 指令引用它**）。
>
> **即：这是一段死代码。** 按代码意图，采购入库保存后应清伪列；实际没有清。
> 好在这不影响正常保存（伪列清理可能由引擎层或卡片侧兜住），但**如果客开或排障时依赖
> "保存后伪列已被清空"这个假设，就会出错**。本档案把它如实标出，**不臆断后果**。
> —— 这正是采集标准说的"疑似产品缺陷要记录但不复现"的那一类。

### 4.3 单据状态转换与精度

`afterProcess:202-207`：
```java
ExtBillCard retcard = operator.toCard(vo);
operator.processICBillstatusForWeb(retcard);                       // ★ 单据状态（给 Web 用）
new PurchaseInExtBillCardPrecisionHandler(retcard, "body").process();   // ★ 表体精度
String[] headFields = new String[]{"cgeneralhid", "pk_org", "vbillcode", "icbillstatus"};  // ★ 字段名是 icbillstatus
```
—— 注意字段名 **`icbillstatus`**（卡片/Web 侧），而**数据库列是 `fbillflag`**（见第 5 节）——
**两者不是同一个名字**，写客开取状态时要分清是哪一侧。

### 未覆盖项的详情

- **现存量与成本（⬜，与第 13 份同一个缺口）**：入库要**加现存量、算入库成本**，
  这两件事不在入口里。连库查动作表：
  ```sql
  select c.actiontype, c.sysindex, c.isbefore, f.classname, f.methodname
    from pub_actionconstrict c join pub_function f on c.functionid = f.pk_function
   where c.pk_billtype = '45' and c.actiontype = 'WRITE' order by c.sysindex;
  ```
- **两张费用子表的写入时机（⬜）**：`_f` / `_bf` 由引擎写还是由业务类写、进价与费用怎么摊到入库成本，**未验**。
- **`PurchaseInExtBillCardPrecisionHandler(retcard, "body")`（⬜）**：第二个参数 `"body"` 说明**可以按部位做精度**，
  其他部位（表头/货位）的处理器未查。
- **`processPK` 为何放在 `processLocationVOs` **之前**调？**（⬜）**：从 :98-100 看，`doAction` 里
  `processLocationVOs` 之后直接 `afterProcess`，**`processPK` 反而没在这段里被调用**——
  它应在 `afterProcess` 内部（:202 之后）或别处。**这条调用关系未理清**，续做需读完 `afterProcess`（:202-416）。
  > ⚠️ 本档案第 4.2 节把 `processPK` 列为"采购入库特有"，是从方法体判断的；
  > **它的调用点没在已读范围内确认**，属于本档案的一处**弱证据**。
- **`icbillstatus` 与 `fbillflag` 的映射（⬜）**：卡片字段名与 DB 列名不同，
  `processICBillstatusForWeb` 做的转换规则未展开。
- **`BillCombine` vs `ClientBillCombinServer`（⬜）**：两者都是"服务端结果合并回界面 VO"，
  为何采购入库用前者、销售出库用后者，**未查**。
- **主表字段（⬜）**：见完成表第 8 项。
- **事务与锁（⬜）**、**字段实测（⬜）**：同上。
