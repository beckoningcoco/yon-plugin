# 业务流配置：端到端测试用例（可重复执行）

> **目的**：把「确认单 → 施工 → 保存 → 启用 → 回读 → 交付单」跑成一条**可重复的回归用例**。
> **适用**：旗舰版 BIP 业务流设计器；**不覆盖运行期推单**（由业务员按交付单第 5 节验收）。
> **关联**：`06-接单流程-从任务到确认单.md`、`07-配置交付完成-DoD与交付单.md`、
> `08-启用与发布-实测.md`、`00`–`05` 操作参考。
>
> **用法**：复制「七、测试记录表」到需求条目 `generated/`，逐条打勾；
> 失败时保留证据（接口 JSON / 截图），**不要直接重试覆盖**——先判定是配置错、环境错还是用例假设错。

## 四、测试用例

### T0 环境、权限与基线

**目的**：确认环境可用、参照流只读、基线可读。
**步骤**
1. `browser_targets` 找旗舰版页签，`browser_attach`。
2. `getById? id=REF_FLOW_ID`，读 `name / billCode / isPreset / transactionTypeName / version`。
3. 逐边 `flowRule/list`，读 `refRuleCode / pushOpportunity / pushMode / createUserType`。
4. 列表「预置」分类下确认「新增」按钮 `disabled`。

**断言**
- `code=200`、`isPreset=true`、`billCode=voucher_order`。
- 节点数 / 边数 = 参照流实际值（不写死）。
- 每条边至少 1 条规则。

**失败模式**
- 401/403 → 未登录/无权限，停。
- `data` 为空 → id 错或流被删，停。

### T1 复制参照流（路线 A）

**目的**：验证「照抄型」起点是否可用。
**步骤**
1. 鼠标**悬停** `REF_FLOW_NAME` 行，等右侧出现操作按钮（设计 / 停用 / 复制 / 编辑 / 日志）。
2. 点「复制」（`fieldid` 前缀 `businessFlowFe_businessFlowList_list_btn_copy`，后缀随实例变）。
3. 复制弹窗按实际字段填：名称 `TEST_NAME`、编码 `TEST_CODE`（弹窗字段以现场为准）。
4. 确定后读列表，找 `TEST_CODE`。

**断言**
- 列表出现 `TEST_CODE`，`isPreset=false`。
- `getById(TEST_FLOW_ID)` 200，节点/边与参照流一致（T2 细核）。

**失败模式**
- 复制后列表没有 → 读接口确认是否落库；刷新/重进列表。
- 复制不可用 → **记录，转 T11 新建路线**，不要硬试。

**清理**：失败时保留 `TEST_CODE` 记录，T9 统一清理。

### T2 复制结果基线核对

**目的**：确认复制带过来的内容，避免「看起来一样、实际少东西」。
**步骤**
1. `getById(TEST_FLOW_ID)` → `content.nodes` / `content.edges`。
2. 逐边 `flowRule/list`。
3. 与 T0 基线逐项比对。

**断言**
- 节点数、边数、核心单据 `isCore=1` 与参照流一致。
- 每条边 `refRuleCode` 一致；`pushOpportunity / pushMode / createUserType` 一致。
- 字段映射：`getRuleByCode` 的 `detailCount` 与参照流一致（全沿用）。

**失败模式**
- 节点/边/规则缺失 → 复制行为差异，记录实际差异，转 T11。
- 映射条数不一致 → 复制未带全，记录。

### T3 冲突场景：默认交易类型启用被拦

**目的**：验证「同交易类型唯一性」在启用时拦截。
**步骤**
1. 复制后**不改交易类型**（默认 `REF_TT`，通常已被参照流占用）。
2. 点「启用」→ 确认框「是否启用」→ 确定。
3. 读页面错误提示 / `browser_messages`。

**断言（二选一，按实际）**
- `REF_TT` 已被占用 → 报 `000-533-020003 交易类型不滿足唯一性校验`，`status` 仍 `false`。
- `REF_TT` 未被占用 → 启用成功；**记录「用例假设不成立」**，T4 改为直接测启用。

**失败模式**
- 启用成功但预期冲突 → 说明该交易类型未被占用，不是代码错，调整用例。
- 报其他错 → 记录错误码/文案，单独排查。

### T4 改交易类型（发出商品 / 普通发货）

**目的**：让测试流通过启用校验，并按业务口径设置两端交易类型。
**步骤**
1. 设计器选中 **E1（销售订单 → 销售发货）** → 规则「编辑」。
2. 基本信息 → **来源交易类型** = `发出商品`（`SO021`）；**目标交易类型** = `普通发货`（`SHIP001`）。
   **点下拉箭头 `.el-select__caret` 展开**，不要点 input（`readOnly`，不一定展开）；展开后再点选项。
3. E2（销售发货 → 销售出库单）→ 来源交易类型 = `普通发货`；目标随意（可留空）。
4. E3（销售出库单 → 销售发票）随意。
5. **判断选没选上**：看容器 `innerText`，不要看 `input.value`（恒为空串）。
6. 规则「确定」→ 返回设计器。
7. 回读：`flowRule/list` 的 `srcBizTypeId` / `tarBizTypeId` 或中文名 = 发出商品 / 普通发货。

**断言**
- E1 来源 = 发出商品、目标 = 普通发货；E2 来源 = 普通发货。
- 没有「核心单据的交易类型不能为空」提示。

**失败模式**
- 选不上 → 看 `innerText`；仍不行则检查下拉是否 disabled / 选项是否渲染。
- 找不到「发出商品」/「普通发货」 → 前置 P4 未满足，停。

### T5 保存 + 版本递增

**目的**：验证「保存自动生成新版本」，补 D3 的硬证据。
**步骤**
1. 保存前读 `getById(TEST_FLOW_ID).version` → `version_before`。
2. 点设计器右上「保存」（`fieldid` `businessFlowFe_designHeader_btn-save`）。
3. 读 `browser_messages`；若弹「是否应用改动」按 `09` 的坑处理（点「否」再保存）。
4. 保存后读 `getById(TEST_FLOW_ID).version` → `version_after`。

**断言**
- 保存提示成功。
- 记录 `version_before` / `version_after`；**若版本机制不体现在 `version` 字段，以实际为准，不硬判递增**。
- `isCurrentVersion=true`。
- 刷新后内容还在。

**实测（2026-10-18）**：`_01` / `_03` / `_06` / `_07` 保存前后 `version` 都是 `V1.0`，**未观察到保存时递增**。
**平台口径（使用者确认）**：开启版本控制（`isVerSupport=true`）的流，保存后变未启用，**重新启用时会更新版本号**；
未开版本控制的流保存后保持启用、`version` 不变。
所以不要拿「保存前后 version 是否变」当唯一判据；开版本控制的流要在**重新启用后**再看版本号。

**失败模式**
- version 没变 → 记录前后值；先确认保存是否真的成功（提示 + `updateTime`），再判断版本机制。
- 保存报错 → 按 `03` 的保存校验分支查。

### T6 启用

**目的**：验证启用动作与状态变化。
**步骤**
1. 回列表，选中 `TEST_CODE` 行。
2. 点「启用」→ 确认「是否启用」→ 确定。
3. 读 `getById` / 列表状态。

**断言**
- `status` false→true。
- `version` 不变（启用不产生新版本）。
- 列表「启用状态」= 已启用。

**实测（2026-10-18）**：
- 复制流 `_03` 启用两次都报 `000-533-020003`（来源从「发出商品」换成「借出转销售」仍报）；
- **保存阶段不校验唯一性**：目标=普通发货可以保存成功，唯一性校验只在启用时；
  所以「普通发货」是否冲突尚未坐实，需用「目标=普通发货的流点启用」复现确认；
- **`dr=true` 不占用交易类型**：新建 `_04` 用「发出商品」保存/启用成功，而被删的 `_01` 也是发出商品，
  证明逻辑删除不参与唯一性校验。之前把 `_03` 的冲突归因于 `_01` 逻辑删除，是错的。
- **版本控制**：`isVerSupport=true` 的流保存后 `status=false`；「重新启用更新版本号」按使用者口径记录。
  **复制流例外**：`SYS_FLOW_ID` 为空时，重新启用后 `version` 仍不变（`_07` 实测），版本号不作为阻塞项。

**失败模式**
- 报 `000-533-020003` → 先按 `10-交易类型占用-排查方法.md` 查占用者（SQL 直查），再决定停用 / 换类型。
- 按钮 disabled → 权限/状态，停。

### T9 停用 / 删除清理

**目的**：恢复环境，保证用例可重复。
**步骤**
1. **先停用**：选中 `TEST_CODE` 行 →「停用」→ 确定，确认 `status=false`。
   **不先停用直接删，会留下 `DR=1 / STATUS=1` 脏数据，仍占用交易类型**（校验 SQL 只看 `STATUS=1`，不看 `DR`）。
2. （可选）「删除」→ 确认（删除不可恢复，仅测试流）。
3. 回列表确认 `TEST_CODE` 不存在或已停用。

**断言**
- `status=false` 或列表无 `TEST_CODE`。
- 参照流、使用者正式流未被改动。

**实测（2026-10-18）**：删除后列表消失，但 `getById` 仍返回数据、`dr=true`——**逻辑删除，不是物理删除**。
**逻辑删除不占用交易类型**（`dr=true` 不参与唯一性校验；2026-10-18 用 `_04` 复现验证）。

**失败模式**
- 删除失败 → 保留停用状态，记录原因（权限/被引用）。

## 五、断言清单（可执行）

在已登录的设计器/列表页签里用 `browser_eval`（同源，自动带 cookie）：

```js
// 1) 读主体
const d = (await (await fetch('/iuap-apcom-supportcenter/businessFlow/getById?id=' + FLOW_ID, { credentials: 'include' })).json()).data;
const c = typeof d.content === 'string' ? JSON.parse(d.content) : d.content;

// 2) 节点/边
const nodes = c.nodes || [], edges = c.edges || [];
const core = nodes.filter(n => n.isCore === '1');

// 3) 逐边规则
const rules = {};
for (const e of edges) {
  const r = await (await fetch('/iuap-apcom-supportcenter/flowRule/list?businessFlowId=' + FLOW_ID + '&nodeId=' + e.data.id, { credentials: 'include' })).json();
  rules[e.data.name[0]] = (r.data || []).map(x => ({ ref: x.refRuleCode, opp: x.pushOpportunity, mode: x.pushMode, creator: x.createUserType, src: x.srcBizTypeId, tar: x.tarBizTypeId }));
}

// 4) 系统规则规模
const g = (await (await fetch('/iuap-apcom-supportcenter/domainMakeBillRule/getRuleByCode?tenantId=' + TENANT + '&isBusiObj=true&ruleCode=' + REF_CODE + '&bizFlowId=2', { credentials: 'include' })).json()).data;
```

**断言表达式**（按用例替换）：
- `core.length === 1 && core[0].code === '<核心单据编码>'`
- `nodes.length === <N> && edges.length === <M>`
- `Object.values(rules).every(arr => arr.length >= 1)`
- `rules['<边名>'][0].ref === '<refRuleCode>'`
- `d.status === true && d.version !== versionBefore`

## 六、失败模式判定

| 现象 | 先查 | 处理 |
|---|---|---|
| 复制后列表没有 | 接口是否落库；分类/筛选 | 重进列表；仍无 → 转 T11 |
| 节点/边数与参照流不符 | 复制行为 | 记录实际差异，不硬判失败 |
| 保存报「核心单据的交易类型不能为空」 | 规则基本信息是否设了核心单据那端 | 回 T4 |
| 启用报 `000-533-020003` | 同交易类型是否已被占用 | 换 `TEST_TT` 或停用冲突流（业务方决定） |
| 保存后 version 没变 | 保存是否成功；版本机制 | 记录前后值，写进 08 |
| 回读规则数 < 边数 | 保存是否部分失败 | 查 `flowRule/list`，回 T5 |
| 删除失败 | 权限/被引用 | 停用并记录 |
| 预置流能保存 | 是否误点 | 立即停，记录 |

## 八、清理与重复执行

1. **每次开始前**：检查 `TEST_CODE` 是否存在；存在则先停用/删除。
2. **每次结束后**：停用或删除测试流；确认参照流 `updateTime` 未变。
3. **失败时**：保留证据（接口 JSON、截图、错误码），**不要为了通过而改断言**；
   先判定是配置错、环境错、还是用例假设错，再决定改用例还是改配置。
4. **换环境/换单据**：只改参数表（`REF_FLOW_ID / TEST_TT / TEST_CODE`），用例步骤不变。
