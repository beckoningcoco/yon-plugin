# 销售出库单保存调用链 — NCC2505

> 采集口径见 [_call-chain-collection-standard.md](./_call-chain-collection-standard.md)。
> 证据等级：**反编译**（本机无 NCC2505 数据库连接，字段未做实测；SPR 单列一轮）。
> 环境：Home = `E:/NCProject/NCC2505/HOME_BYZY_BIP`。
>
> 本档案是**库存（`ic`）链的开篇**。库存链与前面 12 份都不同：它**自成一套体系**
> （自己的入参工具、自己的单据类型枚举 `ICBillType`、自己的过滤服务 `IICFilterData`、自己的续跑工具），
> 而入口是**模板方法模式**——子类只重写一个 `getBilltype()`，逻辑全在 `nccloud.web.ic.pub.action.SaveAction`。

## 1. 什么时候读我

- 客开要**在销售出库单保存前后插手**，或要理解库存单据为什么和采购/销售订单长得不一样。
- 要判断**出库单的状态语义**——它是**签字**流程（`ic.saleout.sign`），**没有审批流字段**。
- 要处理**货位/单品**相关逻辑（库存链有专门的 `*_l` 表和 `processLocationVOs` / `fillLocationVOs`）。

## 2. 怎么拿到这条链

**入口 XML**：`<HOME>/hotwebs/nccloud/WEB-INF/extend/yyconfig/modules/ic/outbound/config/action/saleout.xml`
```xml
<action>
    <name>ic.saleout.save</name>
    <label>销售出库单保存</label>
    <clazz>nccloud.web.ic.outbound.saleout.action.SaleOutSaveAction</clazz>
</action>
```
> **`SaleOutSaveAction` 只有 35 行**：
> ```java
> public class SaleOutSaveAction extends SaveAction {          // ← 包名没写，因为它与父类同属 ic 体系
>     protected ICBillType getBilltype() { return ICBillType.SaleOut; }   // "4C"
> }
> ```
> —— **真正的逻辑在父类 `nccloud.web.ic.pub.action.SaveAction`**（259 行，`external/lib/uiic_nccloud.jar`）。
> **父类不在 `saleout.action` 包里**，所以按包名搜 `ic.outbound.saleout.action.SaveAction` 会 0 命中——
> 用 **`ncc_class_search('nccloud.web.ic.pub.action.SaveAction')`** 定位。

**同族入口（30 个）**，与保存相关的是：`ic.saleout.sign`（签字）/ `ic.saleout.unsign`（取消签字）/
`ic.saleout.backBill`（退回）/ `ic.saleout.copy` / `ic.saleout.coopo45`（**协同生成采购入库单**）/
`ic.saleout.pickauto`（自动拣货）/ `ic.saleout.checkprem`（**`SaleOutDataPermissionAction`**，数据权限）。
> 注意：**出库单走"签字/取消签字"，不是"提交/审批"**；但也存在一个 `SaleOutDataPermissionAction` 权限动作。

## 3. 链路（10 跳）

| # | 层 | 位置 | 干什么 |
|---|---|---|---|
| 1 | HTTP | `POST /nccloud/ic/saleout/save` | 销售出库单卡片保存 |
| 2 | 入口（薄壳） | `SaleOutSaveAction#getBilltype:16`（**35 行**） | 只返回 `ICBillType.SaleOut`（`"4C"`） |
| 3 | **模板方法基类** | `nccloud.web.ic.pub.action.SaveAction#doAction:51`（259 行，`uiic_nccloud.jar`） | `implements ICommonAction`，**保存全流程在这里** |
| 4 | 续跑前置 | `ICPFResumeExceptionUtil.processBefore(request)` **直接返回 context** | 库存链的续跑工具（第 7 节） |
| 5 | 入参 | `json.fromJson(str, BillCard.class)` + `json.fromJson(str, SrcFlagDTO.class)` | **同一次 read 解析两个对象**：卡片 + 来源标记 |
| 6 | 转 VO | `ICBillCardOperator#toBill(request)` → `ICBillVO[]` → `fillBill(vos)` | |
| 7 | 通用出入库标志 | `GeneralOutVO`/`GeneralInVO` + `srcFlag`：`"assembly"`→`srcflag=1`、`"teardown"`→`srcflag=2` | 通用出/入库单的**组装/拆卸**标记 |
| 8 | 校验 | `checkReferencedBill(vos)`（被引用单据）+ `checkncorrespond(vos)`（不对应关系） | 库存专有校验 |
| 9 | 过滤 | `IICFilterData#filterFromFront(billtype, vos)` | **库存专有**：进引擎前按单据类型过滤 |
| 10 | **引擎** | `ICloudScriptPFlowService#exeScriptPFlow(context)`，`context.setActionName("WRITE")` | **与销售订单保存同一个 `actionName`（`"WRITE"`）** |
| 11 | 收尾 | `fillLocationVOs` → `processDelBody` → `ClientBillCombinServer.combine` → `processLocationVOs` → `handlerComputedPropertyField` → `afterProcess` → `GridCompareUtils` → `dealCarrier` | **七步收尾，含货位与承运商** |

**`doAction` 关键片段**（:68-95）：
```java
if (vos != null && vos.length > 0) {
    this.checkReferencedBill(vos);
    this.checkncorrespond(vos);
    vos = ((IICFilterData)ServiceLocator.find(IICFilterData.class)).filterFromFront(this.getBilltype().getCode(), vos);
    context.setBillType(this.getBilltype().getCode());        // ★ 由子类的 getBilltype() 决定："4C"
    context.setBillVos(vos);
    ICloudScriptPFlowService service = (ICloudScriptPFlowService)ServiceLocator.find(ICloudScriptPFlowService.class);
    context.setActionName("WRITE");                            // ★ 与销售订单保存相同
    ICBillVO[] obj = null;
    try {
        AppInfoContext.setBtnCode(this.getBtnCode());
        Object[] ret = service.exeScriptPFlow(context);
        obj = ret instanceof ICBillVO[] ? (ICBillVO[])ret : (ICBillVO[])ret[0];
    } catch (Exception e) {
        return ICPFResumeExceptionUtil.handleICResumeException(e);   // 库存续跑异常出口
    }
    obj = ((IICFilterData)ServiceLocator.find(IICFilterData.class)).fillLocationVOs(this.getBilltype().getCode(), obj);
    ClientBillCombinServer util = new ClientBillCombinServer();
    this.processDelBody(vos);
    util.combine(vos, obj);
    this.processLocationVOs(vos, obj);
    this.handlerComputedPropertyField(vos);
    BillCard retcard = this.afterProcess(operator, vos[0]);
    retcard = GridCompareUtils.compareBillCardGrid(operator.getOriginBillcard(), retcard);
    this.dealCarrier(retcard);
    return retcard;
}
return null;
```

> **链的形状**：入口（35 行薄壳）→ 基类模板（259 行）→ PFlow 引擎。
> 这与采购订单的"入口薄壳 + `AbstractOrderSaveAction` 父类"是**同一种设计**，
> 但**父类位于另一个模块（`ic`），且用的是库存自己的一套接口**。

## 4. 库存链接口的四件套（与采购/销售链的对照）

库存链不用 `SCM*` 那套，而是：

| 库存链（`ic`） | 采购/销售链（`scmpub`/`so`/`pu`） | 作用 |
| --- | --- | --- |
| `ICBillVO` | `AbstractBill` / `AggregatedValueObject` | 单据 VO 接口 |
| `ICBillCardOperator` | `ExtBillCardOperator` / `BillCardOperator` | 卡片↔VO 转换 |
| `ICPFResumeExceptionUtil.processBefore` / `handleICResumeException` | `PfResumeExceptionNccUtils` / `DealResumeException` | **续跑**（第 7 节） |
| **`IICFilterData`**（`filterFromFront` / `fillLocationVOs` / `getExtnum`） | 无对应 | **库存专有过滤 + 货位填充** |
| `ICBillType`（`getBilltype()`） | `SOBillType` / `POBillType` | 单据类型枚举 |

**`ICBillType` 是第三个单据类型枚举**（前两个是 `SOBillType` / `POBillType`），
且它比另两个多一个维度——**每个类型带一个 `ICBillTypeConst` 分类**：

| 分类 | 含义 | 例 |
| --- | --- | --- |
| `ICBillTypeConst.In` | **入库** | `PurchaseIn("45")` / `AssetIn("4401")` / `GeneralIn("4A")` / `ProductionIn("46")` |
| `ICBillTypeConst.Out` | **出库** | **`SaleOut("4C")`** / `GeneralOut("4I")` / `MaterialOut("4D")` / `AssetOut("4451")` |
| `ICBillTypeConst.Adjust` | **调整** | `AdjustBal("52")` / `Invcount("4R")` / `TransferWarehouse("4K")` / `Teardown("4M")` |
| `ICBillTypeConst.Other` | 其它 | `Reserve("4480")` / `FreezeThaw("4Z")` / `VmiSum("50")` |

**库存单据类型码全表（37 个，节选与本批相关的）**：

| 枚举 | code | 分类 | 含义 |
| --- | --- | --- | --- |
| **`SaleOut`** | **`"4C"`** | Out | **销售出库** ← 本档案 |
| **`PurchaseIn`** | **`"45"`** | In | **采购入库**（第 14 份） |
| `GeneralIn` / `GeneralOut` | `"4A"` / `"4I"` | In / Out | 通用入 / 通用出（第 3 节有特殊处理） |
| `AssetIn` / `AssetOut` | `"4401"` / `"4451"` | In / Out | 资产入 / 出 |
| `ProductionIn` / `SubContinIn` / `ReturnIn` | `"46"` / `"47"` / `"4B"` | In | 产成品入 / 委外入 / 退库 |
| `MaterialOut` / `PickBill` / `WasterProcess` | `"4D"` / `"4V"` / `"4P"` | Out | 材料出 / 拣货 / 废品处理 |
| `BorrowOut` / `BorrowIn` / `BorrowInBackOut` | `"4H"` / `"49"` / `"4J"` | Out / In / Out | 借出 / 借入 / 借入还出 |
| `Invcount` / `AdjustBal` / `AdjustErr` / `TransferWarehouse` / `Transform` / `Teardown` / `Assembly` / `StateAdjust` / `LocAdjust` | `4R`/`52`/`51`/`4K`/`4N`/`4M`/`4L`/`4460`/`4Q` | Adjust | 盘点 / 调平 / 调错 / 调拨 / 形态转换 / 拆卸 / 组装 / 状态调整 / 货位调整 |
| `InitializationIn` / `SapplyBill` / `WastageBill` / `VmiSum` / `Reserve` / `PRORESERVE` / `FreezeThaw` / `PackBill` / `DiscardIn` / `DiscardOut` / `TransIn` / `TransOut` / `OpenScrap` | 各自 | In/Out/Other | 初始化 / 领用 / 损耗 / VMI / 预留 … |

> **`ICBillTypeConst` 的 In/Out/Adjust 分类是库存链的"红绿灯"**——
> 判断"这张单是入库还是出库"用它，比枚举名可靠。

## 5. 表落点（出入库单的命名规律）

| 实体 | 表 | 字段数 | 说明 |

（元数据：`modules/ic/METADATA/business/ic_bill/ic_general_bill/ic_saleout.bmf`；VO：`nc.vo.ic.m4c.entity.*`。）

> **库存链的表名规律**：**表名 = 实体名去掉 `VO` + 后缀**，后缀即单据部位：
> `_h` 表头 / `_b` 表体 / `_l` 货位单品 / `_f` 费用项 / `_bf` 物料费用明细。

> 与前面基础档案（`bd_*`）、采购/销售订单（`po_*`/`so_*`，主子表直接加 `_b`）都不同——
> **库存是"一套后缀体系"，不是零散的子表名**。

## 6. 保存链上的库存专有处理

| 处理 | 方法 | 作用 |
| --- | --- | --- |
| 被引用校验 | `checkReferencedBill:127` | 检查单据是否被下游引用 |
| 不对应校验 | `checkncorrespond:99` | 检查**出入库不对应**关系（用 `IICFilterData.getExtnum` 取外部单据号） |
| 前置过滤 | `IICFilterData#filterFromFront` | 按单据类型过滤后可进引擎 |
| **货位填充** | `IICFilterData#fillLocationVOs`（**引擎前后各一次**） | 把 `*_l` 货位单品数据填充/回填 |
| 货位处理 | `processLocationVOs:179` | 货位 VO 的处理 |
| 删除行 | `processDelBody:193` | 剔除 `status==3` 的行 |
| 计算属性 | `handlerComputedPropertyField:172` | 计算属性字段回填 |
| 结果合并 | `ClientBillCombinServer#combine` | 服务端结果合并回界面 VO |
| 精度处理 | `getPrecisionHandler`（:253，**子类可覆写**） | 库存有 `ICBaseBillcardPrecisionHandler`（销售出库另有 `SaleOutBillGridPrecisionHandler`） |
| 承运商 | `dealCarrier:257` | 运输/承运商处理 |
| 单据类型 | `getBilltype:249`（**抽象，子类唯一要重写的**） | 返回 `ICBillType` |

> **模板方法的价值**：新增一种出入库单据，**只要写一个 35 行的子类返回自己的 `ICBillType`**，
> 就自动获得保存全流程（校验、过滤、货位、合并、精度、承运商）。

## 7. 续跑工具的第三个体系

| 体系 | 工具 | 用在 |
| --- | --- | --- |
| `scmpub` | `PfResumeExceptionNccUtils` | 销售订单保存/提交、到货单 |
| —— | `DealResumeException` | 请购单保存提交 |
| **`ic`** | **`ICPFResumeExceptionUtil`**（`processBefore` / `handleICResumeException`） | **销售出库（本份）、采购入库（第 14 份）** |

> `ICPFResumeExceptionUtil.processBefore(request)` **直接返回一个 `CloudPFlowContext`**——
> 即"续跑前置"同时负责**装配 context**（把上次失败现场恢复进 context）。
> 这是库存链特有的写法：**context 不是入口 new 的，是续跑工具给的**。
