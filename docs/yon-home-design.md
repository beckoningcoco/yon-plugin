# 安装目录（Home）管理：设计记录

> 记录**为什么这样设计**，不是接口手册。接口在各模块的 JSDoc 里，工具怎么用写在工具
> 描述里。数据源面板、知识库能力的设计分别见 `yon-panel-ui-design.md`、
> `yon-knowledge-design.md`。
>
> 批 1（**登记 + 探测 + 读**）见第一～十节。第十一节是**元数据索引**（批 A/B/C）的设计，
> 可执行方案在 `yon-meta-index-plan.md`。建类索引（批 2）、取类反编译（批 3）见文末。

## 一、要解决的问题

「NCC / BIP 的 Home 在哪」这件事，此前散在四个地方，**没有一处是界面，也没有一处被
插件真正用上**：

| 位置 | 谁写 | 谁读 |
|---|---|---|
| `~/.claude/skills/path_config.json` 的 `NCC_Home_2111/2312`、`BIP_Home_V5` | 人手改 | `db-query/scripts/check_config.py`、`uninstall.bat` |
| `…/yon-ncc-dev/ncc_home_path.json` | `build_index.py` 生成 | 技能里的源码分析工作流 |
| `…/yonyou-bip-dev/bip_home_path.json` | 同上 | 同上 |
| 插件自己的 `~/.dsh/yon-panel/knowledge/class_index_<版本>.json` | `knowledge_build_index` 工具 | `ncc_class_search` 工具 |

两个后果在代码里看得见：

1. **模型每次都得被喂一遍路径。** `knowledge_build_index` 的 `home` 是调用参数，
   `ncc_class_search` 只有 `version` 没有 home。于是「Home 在哪」这个事实模型只能
   从用户当轮那句话里现拿——换一次会话就没了。
2. **技能侧那套说明在插件里是空转的。** 插件把技能正文整段内联进了
   `skill-catalog.generated.ts`，其中写着 `with open('ncc_home_path.json')`——相对
   路径，在任何会话里都指不到技能目录。技能文字在教模型读一个它读不到的文件。

这一批要达成的：使用者在第六个面板里登记 Home，面板探测它并把「这确实是个 Home、
里面有什么」记下来；模型需要时通过工具拿到这份名单，并能在 Home 里**找文件**、**按
正确编码读文件**；技能侧的 `*_home_path.json` 同步写，让 Claude Code 那边的半数
工具链一起受益。

## 二、四份登记为什么只留一份真相

**面板自己的 `~/.dsh/yon-panel/home_config.json` 是主，保存时镜像回技能的两个文件。**

`home_config.json` 之所以不直接写进技能目录：技能目录可能没装（`~/.claude/skills`
不存在时面板仍然该能用），而**面板的存储必须是它自己拥有的**。反过来，只写面板自己
那份，Claude Code 那半工具链就继续看不见——那正是上面第 2 条病。所以保存是一次写两处：
面板那份是权威，技能那份是派生物。

镜像做成**合并**而不是覆盖（见第五节），所以它不是第五份真相，而是同一份真相在另一个
消费者眼里的样子。

另外两条存储上的决定：

- **读不出来时报错，不静默返回空。** 这一条**刻意不学** `wiki-store.ts` 那种"解析失败
  就返回空"：空列表会让"文件读坏了"和"还没登记过"长得一模一样，使用者会以为自己的
  登记丢了。报错至少指得出文件在哪。
- **首次运行不猜路径**（wiki 会 `guessVaults()`，这里不）：猜错一个安装目录的代价是
  模型去读一堆不相干的文件，而登记一次只要十秒。

## 三、探测：数名字，不开 jar

`probeHome()` 只走目录项、只数名字。**打开一个 jar 就是分钟级**（`buildClassIndex`
就是干这个的），所以探测是秒级的，代价是它只能给出名字层面的结论。于是：

- 走查有上限（目录项 6 万），到顶记 `capped: true`，界面上两个数字前面挂 `≥`。
  **宁可说「至少」，也不报一个看着精确、其实不精确的数字。**
- jar 计数跳过 `ufjdk/`（自带 JDK，几千个 jar 与业务无关）。跳过的判据复用
  `class-index.ts` 导出的 `isJdk()`，不另起一张会各自漂移的清单。
- jar 匹配**大小写敏感**（`endsWith('.jar')`），与 `buildClassIndex` 的 jar 分支一致——这样
  探测数出来的数，永远不会和照它建出来的索引对不上。**注意**：`buildClassIndex` 现在也读
  散装的 `.class`/`.java`（见 §十三），但 `totalJars` **只数 `.jar`**，所以这条对账关系不变。

分类规则（对着真机定的）：

| shape | 判据 |
|---|---|
| `ncc-home` | 有 `modules/` 且有（`ierp/` 或 `bin/startup.*`） |
| `bip-home` | 有 `modules/` 且不满足上一条 |
| `jar-collection` | 没有 `modules/` 但有 jar |
| `not-found` | 都不是 |

`jar-collection` 是**诚实的中间态而不是失败**：`E:/download2` 这种目录（实测 3 517 个 jar，
散在多层的 `iuap-*` 下）能按版本建类索引，但读不到 `.bmf` 和模块配置。面板把这句话说出来，
而不是画一个 home 形状的空结果。

**版本号由使用者填，探测器不猜。** 实测依据：根目录没有 `version.txt`；
`ierp/bin/prop.xml`、`resources/config.properties`、`bin/builtModules.txt`、根
`META-INF/MANIFEST.MF` 里都没有可信的版本串。既有约定也是这样——`build_index.py
<HOME> <version>` 本来就是人工给标签。

**一条跨文件的规则**：**一个版本对应一个 Home（同产品线内）**。技能侧那份名单是按版本
做键的，两个 Home 都自称 `2111` 就会轮流覆盖对方的 `path`。所以在保存的那一刻就拒绝，
并告诉使用者换版本号或先删掉那一条——这是移除一份数据 vs. 静默丢一份数据的区别。

## 四、模型拿到的是 id，不是路径

三个工具**都不写盘**，因此**不设 `tools/pre-execute` 闸门**（与 `class-tools.ts` 头部
同一条论证：闸门多了会训练使用者不看就批）。

| 工具 | 参数 | 作用 |
|---|---|---|
| `ncc_home_list` | 无 | 已登记的 Home：id、名称、产品线、版本、路径、是否默认、探测摘要、索引状态 |
| `ncc_home_find` | `home`, `name?`, `ext?`, `under?`, `limit?` | 按文件名/扩展名找，返回 Home 相对路径 |
| `ncc_home_read` | `home`, `path`, `lines?`, `encoding?` | 按正确编码读一个文本文件 |

**`home` 是 id，永远不是路径。** 与 `datasource_query` 的 `key` 同构。因为
`ncc_home_read` 是这个插件里唯一一处把「使用者指过的那个目录里的文件内容」交给模型的
地方，而它读的东西**来自使用者手输的路径**（不是插件自有的固定根）——如果参数可以是
路径，一段提示词注入就能把它指向任何地方。用 id 之后，「读哪」这件事在登记那一刻就
定死了。

读的三条边界：

- **包含性检查用 `path.relative`，不是前缀比较**，并且两边都先 `realpath`（符号链接 /
  junction 能绕出根），Windows 下按大小写不敏感比较。
- **上限**：单文件读入 1 MB、输出 6 万字符；`find` 有条目数、深度与走查上限。
- **只读**：这一批不对 Home 写任何东西。

### 编码：整文件试探，不看前缀

实测（真机 `…/jixieyuan/home`，取 `modules/` 下前 400 个 `.java`）：**286 / 400 必须
用 gb18030**；整文件 UTF-8 严格解码干净地失败；gb18030 解出来是正确的（`* 响应前台的
action 执行请求…`）；强行按 UTF-8 解则出现 34～1496 个替换符——那就是乱码本身。

所以：BOM → 按 BOM；文件头声明了 `encoding="…"` → 以声明为准；否则**整文件**跑一次
UTF-8 严格解码，失败退 gb18030；调用方给了 `encoding` → 用它。

**前缀试探是错的**：只看头 2000 字节时，「前段全 ASCII、中文在后头」的文件会通过
UTF-8 试探，然后整文件按 UTF-8 解就乱码了。这条写进了代码注释。

头 64 字节含 `NUL` 就当二进制拒读（实测 `starter.jar` 如此），并指向 `ncc_class_search`。
答案里带上**实际用的是哪种编码**——解错了得能自己看出来。

`.java` 与 `.class` 同目录（实测 `modules/aert/classes/nc/pub/iufo/cache/Cache.java`，
28 KB，中文注释），所以这一批**不需要碰 jar** 就能拿到源码；jar 里那部分留给批 3。

### 凭据：打码的**值**，不是键名

实测 Home 里确实有明文密钥：`resources/config.properties` 有 `client_secret` + RSA
`pubKey`，`ierp/bin/prop.xml` 有数据库密码。

规则：**键名照常返回，只把值换成 `***`**（并提示原长）。非敏感项（库地址、端口、路径、
用户名）原样返回——所以"配置排查"仍然做得了。返回文本顶部说明本次有几处被打码。

**键名命中判据是最后一个分隔词，不是子串。** `client_secret`、`db.password`、`user_password`
命中（最后一段分别是 `secret` / `password` / `password`），而 `keyType`、`pubKey` 不命中——
后者是证书的**公开**一半，打码它会把使用者配签名时正需要的值藏起来。活的反例是
`secret_level`：它含有 `secret` 子串，但最后一段是 `level`，**必须不打码**（真机文件里
就有这一条）。子串判据在这里会错两次——该挡的挡不住，不该挡的挡上。

**要认三种形状**（properties 行、`"key": "value"` 对、`name="…" value="…"` 属性对），
真机上有个值就藏在**被注释掉**的一行 JSON 里（见第九节）。

与既有约定一致：`datasource-catalog.ts` 的 `toViews()` 也是把密码挡在视图之外、只留
`hasPassword` 布尔。

## 五、镜像：合并而不覆盖

写 `…/yon-ncc-dev/ncc_home_path.json`（`product: ncc`）或
`…/yonyou-bip-dev/bip_home_path.json`（`product: bip`），字段与 `build_index.py` 写出来
的逐字段一致。三条硬约束：

1. **合并，不覆盖。** 面板不管理的版本（例如使用者自己跑 `build_index.py` 加进去的）
   原样保留；已有条目的 `index_file`/`jdk_version`/`indexed` 不动——那些描述的是**技能
   目录里**的索引，不是插件的索引，两回事。
2. **不撒谎。** 新建条目写 `indexed: false`。这一批不建索引。
3. **写不加 BOM，读容 BOM。** 实测两个文件现在都无 BOM，而 `build_index.py:75` 用的是
   `open(..., encoding='utf-8')` + `json.load`——**带 BOM 会直接抛**。读的一端先剥 `﻿`。

**撤回**：面板不再登记某个版本，且那条是 `indexed: false` 时删掉它。这个标记只有本模块
会写（`build_index.py:86` 无条件写 `True`），所以 `false` 的含义就是「面板登记的、从没
建过索引」。已经是 `indexed: true` 的条目即使登记没了也留着——索引文件还在，删掉条目只
会让它变得查不到。

目标目录不存在就**跳过并记一条警告**，不 mkdir 出一棵空技能树。

### `path_config.json` 为什么不镜像

**已知重复，显式不合并。** 三点理由：

1. 它是给 `check_config.py` 和 `uninstall.bat` 读的，键名是人工拟的中文
   （`NCC_Home_2111`），而且同一个文件里混着 Arthas 路径、知识库路径、Chrome 路径。
2. 它的键名把「版本」编进了名字里（`NCC_Home_2111`），于是加一个版本就要改键名——
   而面板的登记里版本是**值**。两边形状不同，镜像只能靠字符串拼接，那不是镜像。
3. 它是**人会被手改**的文件。写它等于制造一份会被手改坏的副本，而且坏掉的方式是
   静默的。

将来若要收编它，正确做法是让 `check_config.py` 改读 `ncc_home_path.json`，而不是让
面板去写两份。

## 六、界面：第六个面板

按前五条的写法加第六条（`id: 'home'`、`order: 60`）。左列是已登记的 Home，右列是这个
目录到底是什么：路径（等宽 + 复制）、探测结论（目录类型、模块数、jar 数、**关键路径命中
表**、警告）、索引状态（这一批只显示）。动作是新增 / 编辑 / 两步删除确认 / 设为默认 /
重新探测。

面板叫 **「Home 管理」**，不叫「安装目录」：这一屏管的是**登记**——一个登记要定的是产品线、
版本、路径三样，目录只是其中一样；叫「安装目录」等于用最不像"被管理的东西"的那个字段给它
命名，也漏掉了版本和产品线才是真正要人去定的部分。

两条量过的规矩照旧：零硬编码颜色（只用 `--dsw-*`）、容器 0.5px `border-l2`、控件
`border-l4`、8px 圆角。结构复用共享的对话框 chrome（`Modal` + `panel.module.css` 的
两栏、属性网格、表单行、动作行、空态、错误条），**不新造样式**——只有五条共享表覆盖不到
的规则进 `home/panel.module.css`（详情标题、路径与复制、失效行压暗、产品线下拉、关键
路径表）。

两处取舍：

- **路径失效的行压暗不隐藏**（与 wiki 面板同款）：它是一条真实存在的登记，使用者可能正
  打算修它，从列表里删掉只会让问题藏起来。它的 `ready` 是**当场**读目录判的，而
  `profile` 记的是**上次探测**的结论——两件事，所以是两个字段。
- 列表 8 条以上才出搜索框（与数据源面板同一条 `SEARCH_THRESHOLD` 约定）。

### 名称不是问出来的，是算出来的

表单里**没有名称那一格**。名字是 `homeLabelOf(产品线, 版本)`——命中预置表的用表里的标签
（`NCC2111`、`BIP V5`），表外的按同一个形状拼（`NCC2405`）。它是**算出来的**，不是存下来的：
`StoredHome` 和 `SaveHomeInput` 里都没有这个名字，`HomeView.label` 在 `viewOf()` 里现算
（`home-service.ts:108-124`），面板保存时也**不发**这一格。三处都是同一个理由：

1. **它不是一个独立的事实。** 同一个版本的 Home 在两个项目之间是互相通用的——技能侧的类
   索引按版本存，`ncc_home_find`/`ncc_home_read` 去的是登记指向的那个目录。名字里能写的
   任何区分（"机械院"、"终端公司"）都不会被任何一处读到，只多一个要填的格子。
2. **存一份就有一份会过期。** 手改文档把 `version` 从 `2111` 改成 `2312`，存着的名字还是
   「机械院 NCC2111」——列表上那一行会说自己是一个它已经不是的东西。现算就没有这个状态。
3. **它已经是这一行的身份了。** 服务本来就不允许同一产品线下两个登记占同一个版本
   （`home-service.ts:212-218`，技能侧那份名单是按版本互相覆盖的），所以 `(产品线, 版本)`
   早就是唯一键；名字只是把这个键写成人话。

id 跟着同一条身份走：`uniqueId` 生成 `<产品线>-<版本>` 并**转小写**（`ncc-2111`、`bip-v5`），
因为 id 是模型要回填给 `ncc_home_find` 的值，`bip-v5` 和 `bip-V5` 是同一个登记的两个拼法
这件事没有半点好处。版本本身原样不动（存的还是 `V5`）。

这一屏因此**只按版本区分登记**：同一个产品线下想同时留两个 2111 的两个目录做不到。这不是
这次改出来的——服务从一开始就拒绝它（技能侧那份名单是按版本互相覆盖的）；那时候要靠一条
报错才知道，现在名字直接写明了。`homeLabelOf` 与三条派生规则由
`tests/home-service.spec.ts` 钉住（连"手改 `version` 之后名字跟着变、id 不跟着变"一起）。

### 路径是选出来的，版本是从预置里选的

一屏三样里，只有路径是机器事实：它长、必须存在，打错一个字符要等探测走完整棵错误的树才
发现。所以表单里**路径只读，且只能由旁边那颗「选择目录…」填**。版本原来是自由文本框，
现在是预置下拉：NC65 / NCC1909 / NCC2105 / NCC2111 / NCC2207 / NCC2312
（`HOME_VERSIONS`），产品线切到旗舰版就是 `BIP V5` 那一条，出口是「其他（手输）」。

**下拉里存的是裸版本号**（`2111`、`V5`），带前缀的 `NCC2111` 只是标签。依据在磁盘上：
`path_config.json` 的键是 `NCC_Home_2111`、`BIP_Home_V5`，技能目录里是
`class_index_2111.json`，而镜像写进去的是 `index_file: class_index_<version>.json`——
存 `NCC2111` 会指向一个不存在的文件。两条产品线的表分开，因为它们的版本号本来就不是一套。

**服务端不拿这张表校验写入。** 面板没登记过的版本（使用者自己跑 `build_index.py` 加进去的
`2099`）照样要能镜像回技能目录，所以表只用来画下拉，不用来卡保存。

**选择器必须开在宿主上。** 浏览器给不出绝对路径：`showDirectoryPicker()` 给的是句柄，
`<input webkitdirectory>` 给的是相对所选根的路径，都不是 `E:/NCProject/NCC/...`。宿主的
`ctx.directoryPicker` 能，而使用者就坐在宿主前面——这是个桌面应用，"在服务端弹对话框"和
"在我眼前弹对话框"是同一句话。

于是多了一条 `POST /yon/api/pick-directory`。**它是顶层段，不是 `/homes/pick-directory`**：
后者会被 `handleHomes` 当成一个叫 pick-directory 的 Home id 读掉，在取数跑起来之前就 405 了。
它按形状读服务、不 import 宿主包——插件装在宿主仓库之外，而且没挂这个服务的宿主应当退化
成"按钮在那儿、点下去说明这台机器没有"，不是加载失败。三种答复：

| 答复 | 什么时候 | 面板怎么画 |
|---|---|---|
| `{kind:'native', path}` | 本地桌面，宿主弹自己的对话框 | 填进那个只读的路径框 |
| `{kind:'native', path:null}` | 使用者按了取消 | 原样不动（取消是答案，不是失败） |
| `{kind:'browse'}` / `{kind:'unavailable'}` | 从 SSH 或局域网地址打开的面板 | 按钮照旧，下面多一句「在这台机器上登记不了 Home」 |

**没有手输回退，这是刻意的。** 退一步给一个可打的框，等于把这一格重新变成"一个必须存在、
打错一个字要等探测走完整棵错误的树才发现"的字符串——正是这一屏要消掉的东西。代价说清楚：
从 SSH 或局域网地址打开面板时，**新建不了 Home，也改不了已有登记的路径**（那两件事都要一个
新的绝对路径）；已有登记照样能编辑、设默认、探测、删除，因为路径已经在里面了。真要在一台
拿不到对话框的机器上加一条，就手改 `~/.dsh/yon-panel/home_config.json` 或回本地桌面登记——
使用者就坐在宿主前面，所以这是给自己留的例外，不是日常要走的路。

两个细节值得写下来。**只有 `native` 会被驱动**：其它形状上即便有个 `pick`，它返回什么没人
承诺，而这一格必须是绝对路径——这是 harness 自己对"没实现的形状"给的规矩（藏起入口，不要
失败）。**`native` 这个词绝不在没有可用 `pick` 时回给面板**，否则那颗按钮会被画出来却永远
答不了话：不报错、没有路径、什么都不发生。`tests/http-picker.spec.ts` 里有一条专门钉它。
另外对话框活在一次请求之外，所以响应 `close` 时会 `abort()` 掉这次取数——面板关了不该留一个
没人接的 OS 窗口。

### 三处只有看图才能发现的

1. **两步删除的那句问话必须写在动作行里面。** 共享表的
   `.detailActions:last-child` 是 `position: sticky; bottom: 0`，写在它上面一行的内容会
   滚出视野——第一版就是这么写的，出图后确认页上只有「确认删除 / 取消」两颗按钮、一句
   问话都没有。而那句问话唯一必须被看见的时刻，正是它问的那两颗按钮在屏幕上的时刻。
2. **警告列表在静态预览页上永远看不见**，不是没人拍，是拍不出来：共享表
   `.body{height:min(62vh,520px)}` 把详情栏定死，警告排在 11 行关键路径表之后，而 62vh
   被 520px 截住——窗口开得再高也没用。所以 `.warnList` 的验收落在断言上（
   `render.spec.tsx` 的「jar 集合行」用例），看图的人要知道自己看的是滚动区的上半截。
   真机上面板是可滚动的，警告在下面。
3. **静态预览页会替 `select` 换一个值——图会撒谎。** 选中态是 DOM 属性，不进 `innerHTML`；

   截图里显示「NC65」。这不是样式问题：看图做判断正是这套预览的全部价值，一张显示成另一个
   值的图比没有图更坏。修在 `settle()` 里（`freezeSelects`：每次采样前把当前选中项写成
   `selected` 属性），一处理覆盖全部面板——顺带治好了所有面板里"当前值不是第一项"的下拉。
   这条断言只能在活 DOM 上钉：`render.spec.tsx` 的登记表单用例断言 `#yon-home-version` 的

## 十一、元数据索引：把 Home 里的元数据变成可查的

批 1 让模型能找到文件、能按正确编码读文件。这一节要解决的是它的下一步问题：**找得到，
但不知道去哪找、也不知道值不值得读。** 模型想知道「报销单据类型对应哪张表」，得先知道
`ermbilltype.bmf` 这个名字。所以真正要建的是**索引**，不是更好的搜索。

对真机 `…/jixieyuan/home` 的完整实测（数字见第十二节）定下了下面全部结论。

### 为什么不是「让模型现查」

三条路量下来的对比：

| 方案 | 第一次 | 之后（无变化） | 变了之后 | 磁盘 |
|---|---|---|---|---|
| 每次调用真扫 | 3.3 s | **3.3 s** | 3.3 s | 0 |
| 懒建内存缓存 | 3.3 s | **0** | 0.61 s 校验 + 只重解析变化的 | 0 |
| 落盘 + 指纹 | 3.3 s（仅首次） | 0.61 s 校验 + 载入 | 同上 | ~5.6 MB |

关键是**「工具」和「持久化」不在同一层**：工具是接口（模型怎么问），缓存是实现（数据从哪来）。
所以真正的选择不是「写工具 vs 落盘」，而是**这份数据活多久**。而 3.3 秒只在「第一次」和
「大版本升级后」付一次——一次对话里问三次反向问题，总共是 3.3 + 0.61 + 0.61 秒。

**换个说法**：全量重建只要 3.3 秒，所以**「索引会不会过期」根本不是一个需要精算的问题**。
增量重建在这里是「省 2.7 秒」的优化，不是可行性的前提——这与我最初的判断不同（见第十二节）。

**不需要数据库。** 数据库存在的三个理由在这里全不成立：数据（5.6 MB）比内存小得多；只有
一个进程读、只读不写，没有并发写；数据形状是一张扁平表，「查询」就是一次遍历。这个项目
已经在内存里加载过 57 MB 的类索引（`class_index_2111.json`），**先例就在手边**。

落盘的唯一真实理由是**跨会话、跨语言共享**（技能侧的 python 脚本要读）。这不是性能问题。

### 五层，按「维度预存、属性现取」切

一个文件：`meta_index_<版本>.json`。

| 层 | 内容 | 回答什么 | 体积（下界） |
|---|---|---|---|
| **L0 指纹** | 相关文件的**相对路径** → `mtime:size` | 要不要重建 | ~0.9 MB |
| **L1 身份** | 实体 5 573 / 枚举 2 947 / 操作 1 174 / 路由 162 / 接口绑定 2 304，各带中文名、表名、VO 全限定名、来源文件 | 「这个东西叫什么、在哪」 | ~1.4 MB |
| **L1.5 字段名** | 217 140 条 `字段名\|中文名` **按实体存** | 反查「哪些实体有这个字段」 | ~3.6 MB |
| **L1.6 枚举项** | 11 916 条，**全量存** | 枚举值含义 | ~0.16 MB |
| **L2 属性** | **不存**。命中后用 L1 里的文件路径现读那一个文件 | 「这个字段什么类型、多长、可空吗」 | 0 |

（上表按**权威树** `modules/*/METADATA` 计：3 600 个文件。整棵 Home 是 3 819 个文件、
5 831 实体，多出来的是 `update/*/patch_*` 补丁副本与 `microserver/`，**不进索引**。）

**凡是用来"定位"的维度（名字）预存，凡是"选中之后才看"的内容（属性）现取。** 全量字段属性
那层实测 19.8 MB，而它能回答的问题（按类型、按长度反查）远不如按名字反查常用——所以
不预存，需要时读一个 62 KB 的文件就够。

**合计约 5.6 MB（下界）。** 按 JS 字符串长度量的，中文在 UTF-8 里占 3 字节；真实落盘体积
以第一次真机建索引为准。

### 字段中文名：不能只存一张全局表

原计划是「字段名 → 中文名」存一张**全局去重表**，前提是它基本 1:1。**实测把这个前提否掉了**：

| 事实 | 值 |
|---|---|
| 不同字段名 | 36 350（不是 217 140 ——那是**出现次数**） |
| 有 >1 个中文名的字段名 | 7 645（**21.03%**） |
| 这些字段名覆盖的属性出现 | 163 665（**75.37%**） |
| 全局表体积 | 0.73 MB |
| 按实体存 `name\|label` 对 | 3.64 MB |

21% 的名字有多个中文名、且覆盖了四分之三的属性出现。样例里看得很清楚这不是脏数据而是
真语义差异：`creator` 有 `创建人 x2152 / 创建者 x32 / **授权人 x8**`，`defcode` 有
`语义模型编码 / 分析主题编码 / 语义关联编码`。**存全局表就等于：按「授权人」反查会查不到。**
而按实体存只多 2.9 MB，换算下来是值得的。

**决定：L1.5 按实体存 `字段名|中文名` 对，不建全局表。**

### 反查不建倒排表

L1.5 存的是**正排**（实体 → 它的字段），反查时在内存里扫一遍 21.7 万个条目——毫秒级。
这比维护一张倒排表简单，还省一半磁盘。**倒排是派生的，不落盘。**

### 保鲜：指纹按相对路径存，这就是「按版本复用」能成立的前提

走 `modules/*/METADATA`（**163 / 167 / 172 ms**）+ re-stat 已知文件（**466 / 483 ms**）
≈ **0.61 秒**，对比 L0 指纹；只重解析有差异的文件。**全量重建 ≈3.3 秒**（走查 163 ms + 解析
3 131 ms），只在首次发生。

**索引按版本做键**（不是按 Home）：不同的项目同为 2312 时，Home 里的文件基本相同，复用
省掉的是真金白银。但这条要成立，必须补一个机制——**指纹按相对路径
（`modules/erm/METADATA/ermbilltype.bmf`）存，不是绝对路径**。绝对路径的指纹换一个 Home
就全对不上，等于没有指纹。

两个会打破「同版本 = 同内容」的例外，正好被这一个机制吃掉：

1. **补丁级不同。** Home 里存在 `update/*/patch_*` 目录，说明 bmf 会被补丁整体替换。
2. **客开。** 客开的 bmf 只在自己项目里。

切到另一个同版本 Home 时，0.65 秒校一遍，差异文件增量重解析（差 5 个文件 ≈ 50 ms）；
差得多说明补丁级确实不同，**增量路径照样处理得对**，只是多花点时间。所以「按版本」不会错，
最坏情况是多花 0.65 秒；而「按 Home 存」会白扔掉跨项目复用。

### 重名：全返回，但顺序固定

**3 819 个 bmf 只有 3 514 个不同名——281 个名字重复**（`countryzone` ×4、`psndoc` ×4、
`settle` ×3）。所以 L1 的结构必须是 **`name → 数组`**，不是 `name → 单条`，每条带
`module` 和来源文件。

顺序规则固定为：**排除补丁副本 → 按 module 名排序**。固定顺序的意义不是好看，是同样的
提问每次得到同样的答案——否则「让模型自己选」就是每次掷骰子。工具描述里要写明「同名会
全部返回，按 module/文件判断；拿不准就问使用者」，不然模型会默默取第一个。

### 工具面：两个工具、封闭的四类

| 工具 | 参数 | 作用 |
|---|---|---|
| `ncc_meta_find` | `home`, `kind`, `q` | `kind` 只有 4 个值：`entity`（匹配名/中文名/表名/VO）、`field`（**反查**含该字段或该中文名的实体）、`route`（rest URL → Resource 类）、`op`（bpf 操作名 → 实现类） |
| `ncc_meta_detail` | `home`, `entity` | 现读原文件，返回该实体的全字段属性 |

**反查是受控的四种，不是通用查询语言。** 给模型一个能执行任意查询的接口，等于把「查询语言」
也变成要维护的东西，而且模型很容易问出全表扫描。四种够用且可预测，全部落在常驻层里，
一次都不用读那 253 MB。

`home` 传的是批 1 的 **id**，不是路径——索引由 id 找到版本、再找到对应的索引文件。

### 与类索引的缝

L1 里的 `fullClassName`（如 `nc.vo.er.djlx.DjLXVO`）是**把 bmf 世界和类世界缝起来的那根针**：

> 实体名 → VO 全限定名 → `ncc_class_search` → jar → 反编译（批 3）

这条链一旦接上，「这个实体对应哪个源码」就闭环了。所以 L1 **不能精简掉 `fullClassName`**。

### 批 A / B / C

| 批 | 内容 | 为什么这样切 |
|---|---|---|
| **A** | bmf 四层 + 版本键 + 相对路径指纹增量 + `ncc_meta_find`(`entity`/`field`) + `ncc_meta_detail` + 面板建索引入口 | 主菜，独立可用 |
| **B** | bpf / rest / upm 并入同一索引 + `kind=route\|op` | 只是多三张 L1 表 + 三个小解析器（11.5 / 0.1 / 3.9 MB），风险低 |
| **C** | 与类索引缝合（实体 → `fullClassName` → class_index → jar → 反编译） | 依赖类索引，也就是原来的批 2，放最后 |

**批 A 建议插在批 2（面板内建类索引）之前**：类索引是分钟级、要扫 7 941 个 jar；元数据索引
只要 33.5 秒、信息密度更高，先拿到收益更划算。

范围上**只做 NCC**，这条有证据而不是判断：

- **整个 BIP 技能树里 `.bmf` 零命中**（对 `~/.claude/skills/yonyou-bip-dev` 全库检索 `bmf`，
  0 个文件）。
- BIP 技能自己对「元数据获取」的定义是**一族 HTTP API**，不是文件：`…/报表SQL/01-需求分析与
  元数据获取.md` 的附录列了 4 个（`searchByName`、`getEntityListByBOId`、
  `getEntityInfoByBOIdAndEntityId`、`queryByUri`），按 URI 查，缓存层级是「进程内对象 →
  进程内 JSON → Redis → 磁盘 → API」。

所以这不是「我们省了 BIP」，是**两边的形态本来就不同**：NCC 的元数据在安装目录的文件里，
可以扫；BIP 的元数据在元数据服务后面，只能查。BIP 侧其实已经有对应物了——技能里那套
`fetch_metadata.py` + `metadata_lookup.json` + 四级缓存干的就是同一件事，只是形态是
「API + 缓存」而不是「扫文件 + 索引」。

真要在 BIP 侧也做，那是**另一个设计**，不是这一节的移植。而且**手上没有真的 BIP Home 可验**
（登记里那个 `V5` 指向 `E:/download2`，是 jar 集合不是 Home），所以连「BIP 安装目录里到底
有没有可索引的元数据」这个问题都还没条件回答。

## 十三、类索引接上散装文件（2026-10-03）

### 症状：没有 jar 的模块整个隐形

`buildClassIndex` 的走查里有一行 `if (!entry.name.endsWith('.jar')) continue`。后果不是
"路径不够好看"，而是**一个模块可以整块查不到**。实测（注销的 2312 home
`E:/NCProject/NCC2312/tianjiu/biphome_20260902`）：

| | |
|---|---|
| 模块数（`modules/` 下） | 263 |
| 零 jar 但有散装类的模块 | **1** |
| 那个模块 | `hadc`：284 个 `.java` + 323 个 `.class` = 607 个文件 |
| 全库 jar 里含 `hadc/` 条目的 | **0 / 2,779** |

`hadc` 是一份客开模块，横跨 `nc/itf/hadc/*`（接口）、`nc/impl/hadc/*`（实现）、
`nc/bs/hadc/*`（任务）、`nccloud/hadc/*`（NCCloud 侧工具类），散落在
`META-INF/classes/` 与 `classes/` 两处。**在别的 jar 里也没有副本** —— 扫遍该 home 的
2,779 个 jar 找 `hadc/` 条目，0 命中。

同时要记一笔反面数据，免得把这批说大：`modules/` 下 1,057 个散装 `.class` 里，
**841 个是模块自己有 jar 时的重复副本**（抽验 `modules/aeam/…/BapIOService.class` 同时在该模块
`aeam_amLevel-1.jar` 里）。所以真正新增的信息量不是"578 个源码可读"，而是"1 个模块 323 个类可见"。

### 两条规则

**类名从路径推**，砍到**最后一个 `classes` 段**：`modules/hadc/META-INF/classes/nc/impl/hadc/X.java`
→ `nc.impl.hadc.X`。实测 **1,635 / 1,635** 个散装文件都满足这条。没有 `classes` 段的路径
**不索引**（返回 `undefined` 而不是猜）——猜出来的名字会让检索"自信地"报一个不属于任何类的名字。

**合并优先级 jar > `.java` > `.class`**：

- jar 赢，因为 **jar 才是安装真正加载的东西**；`classes/` 下的文件是构建产物，来源不明，
  版本未必与编译产物一致。散装只在**没有 jar 认领**该名字时才用 —— 这正是 `hadc` 的情形。
- `.java` 赢过 `.class`，因为源码可以直接读。

### 实测收益（同一台机器，同一份 home）

| | 改前 | 改后 |
|---|---|---|
| 索引条目（去重类名） | 641,664 | **642,426** |
| 其中指向散装文件 | 0 | **762**（546 `.java` + 216 `.class`） |
| `hadc` 的类 | **0** | **323**（284 指向 `.java`、39 指向 `.class`） |

散装条目不只在 `modules/` 下：`hotwebs/nccloud` 27 条、`microserver/SessionServer` 18 条 ——
走查覆盖整个 home，而先前数散装文件时只看过 `modules/`。

**全量走查 8,486 个 jar + 1,635 个散装文件 = 26.2 s**（顺带修正一处措辞：工具描述里写
"minutes rather than hours"，实测 26 秒，这个说法保守了）。

### 工具面：`ClassHit.jar` 改名 `path`，并且下一句要分三种说

一个源码路径装不进名为 `jar` 的字段，所以改名。更要紧的是 render 末尾那句行动建议 ——
原来只有一句"拿到 jar 之后可以用 cfr 反编译"，对散装命中就是错的，而且**两种散装还不一样**：

| 结尾 | 该怎么办 |
|---|---|
| `.jar` | cfr 反编译（`cfr-0.152.jar` 随包） |
| `.java` | `ncc_home_read` 直接读 |
| `.class` | **二进制，读不了**，要反编译或找同名 `.java` |

第三种是必须分开的理由：216 条 `.class` 条目若被告知"用 `ncc_home_read` 读"，模型会撞上
`ncc_home_read` 自己的二进制拒读 —— 工具刚刚给的指引被它下一条回答推翻。`tests/class-tools.spec.ts`
有一条用例专门钉这个。

### 测试

`tests/class-index.spec.ts` 用**临时夹具**，不碰任何真实安装目录（`buildClassIndex` 会写盘这件事
只发生在 `knowledge_build_index` 的 `writeClassIndex` 那一跳）。夹具里的 jar 是**手工拼的字节**：
`classNamesOf` 只读中央目录与 EOCD，所以一个"有中央目录、没有本地数据"的文件就是忠实的替身 ——
这也意味着中央目录格式一变，这个测试先红。用例覆盖：零 jar 模块、jar 赢过散装、`.java` 赢过 `.class`、

## 十四、面板建索引，以及那个造出幽灵索引的入参（2026-10-03）

（批 3a。`docs/yon-home-design.md` 这一节起编号接 §十三。）

### 症状：两个描述"文档"目录的索引

操作者的 `~/.dsh/yon-panel/knowledge/` 里有两个索引文件：

| 文件 | 描述的目录 | 类数 |
|---|---|---|
| `class_index_EMPTY.json` | `C:\Users\99558\Documents` | 5,293 |
| `class_index_TEST.json` | `C:\Users\99558\Documents` | — |

两个都不是任何一次"给某台安装建索引"的产物，而且 `EMPTY` 这个名字还进过答案：`ncc_class_search`
不传 `version` 时取"最近建成的那个索引"，于是它答过一句 `索引 EMPTY` —— **答案里没有目录**，
所以它看不出来是错的。§十三给答案加的那一行「该索引描述的目录」就是冲着这个来的。

**根因是入参本身**：`knowledge_build_index` 当时收的是 `home` **路径**。路径没有"错"这个概念 ——
任何存在的目录都是一条合法路径，走查照样跑完、照样写盘。所以模型给了个路径形状的东西，
插件就老老实实索引了它。

### 改法：入参从路径改成已登记 Home 的 `id`

```
knowledge_build_index { home: "<id from ncc_home_list>" }
```

`id` 只能来自 `ncc_home_list`，找不到就**响亮地失败**（`HomeError('not-found')`），而版本号
从登记里读——索引本来就是按版本存的，**没有版本就没有文件名可写**。这条也单独挡住了：
登记里 `version` 为空时直接拒，不然会写出 `class_index_.json` 这种谁都再也找不到的文件。

判别用 `tests/class-tools.spec.ts` 钉了两条：`parameters.required` 恰为 `['home']`、
`properties` 恰为 `{home}`（一个路径形状的第二参数不许再溜进来），以及 `home` 的描述里
必须出现 `id` 与 `not a path`。

两个幽灵文件本身**没有动**。（文件名不是这一批能自作主张删的东西；面板的「删除索引」按钮
是长久之计。）

### 顺手抓到的一个性能缺陷：注释说读头部，代码在读全文

`listClassIndexes` 的文档注释写着"从每个文件的头部读，而不是整体解析"，`summaryOf` 也照这个
写 —— 但 `listClassIndexes` 当时调的是整文件 `JSON.parse`。批 3a 要把状态读放进每秒一次的
轮询里，这就必须先把这件事量清楚：

| 一份 43.2 MB、642,426 条的索引（按参考 Home 的量级合成） | 耗时 |
|---|---|
| 整文件读 + `JSON.parse` | **372 ms** |
| 读前 4 KB、切到 `"index":` 前、重新闭合后解析 | **1 ms** |

所以改成注释说的那样（`class-index.ts:summaryOf`），头部读不出来就退回整文件读
（那正是两个幽灵文件的路径）。**关键顺序是有约束的**：`writeClassIndex` 序列化
`{version, home, builtAt, totalJars, totalClasses, index}`，五条摘要必须在表前——
`tests/class-index.spec.ts` 里那条"写出来再读回去"的用例就是钉这个的，键序一改它就红。

### 服务层：一个版本一次走查（`class-service.ts`）

`class-index.ts` 只管写和读，不知道"现在正在建"。这三件事由新的一层管：

- **一个版本同时只走一趟**。面板的按钮离"被点两次"只有一次点击，而模型可以在面板正看着的
  时候让同一个版本再建一次 —— 两次走查会写同一个文件。第二次调用**加入**第一次，不并跑。
- **`startBuild` 只排队，不等**。参考 Home 一趟 26.2 s，HTTP 响应不能挂在那儿。它返回的
  `{started, status}` 里 `started` 回答的是"有没有真的开始新的一趟"——**不是**"现在有没有在跑"，
  已经在跑的那一趟恰恰是最该轮询的。
- **状态便宜到能轮询**，靠的就是上面那个头部读。`KEEP_DONE_MS = 30_000`：建完之后状态留 30 秒，
  否则轮询会在 `running: true` 与"什么都没有"之间丢掉"它停了"这一步，而轮询正是靠这一步停下来的。
- 走查**一个 jar 都没有、散装也一个都没有**时抛错而不是写空索引：空索引会让每次检索都答
  "没有匹配"，而实际意思是"你指错目录了"。

删除索引会连带把内存里的构建状态一起丢掉，另外 `dispose()` 只清状态、**不掐**正在跑的走查
（那是对别人磁盘的一次读，它跑完就完了；`inFlight` 也刻意不清，清了只会让第二趟并排开跑）。

### 面板：类索引从 `<dl>` 里的一行变成一个会动的块

改之前，详情栏里「类索引」是 `<dl>` 中一行只读文字，和路径、产品线并列。现在它有自己的小标题、
自己的两个按钮（建立/重建、删除索引）、自己的状态句和进度行 —— 判据就是这一条：**会被按下按钮的
东西要有自己的块**。路径和产品线留在 `<dl>` 里，因为它们只被读、不被操作。

三种结论各有一屏预览（已建 / 没有 / 建立失败），另有删除后两种答复各一句：
`索引已删除，随时可以重建。` 与 `本来就没有索引文件，没有删掉任何东西。`。后者不能省 ——
按下去时文件已经不在了，不吭声就等于骗人说删掉了。删除按钮只在**有文件**时画出来，
所以"没东西可删"这条答复只可能来自"状态刚说有时、按下去时没了"这个竞态。

「这是什么」那句解释（`home.classWhy`）在**没有索引且没在跑**时显示：它是给还没决定要不要花
半分钟的人看的；有索引了它没有读者，跑起来之后决定已经做过了。

### 三条路由

`GET` / `POST` / `DELETE /yon/api/homes/<id>/class-index`。三个形状各是一半对另一半的承诺：

| | 答复 | 为什么是这个形状 |
|---|---|---|
| `GET` | `200 {home, status}` | 状态包在 `home` 旁边，客户端只取 `.status` |
| `POST` | **202** `{home, started, status}` | 只排队，所以不是 200；`started` 与 `running` 是两个问题 |
| `DELETE` | `200 {home, removed}` | `removed` 是布尔："本来就没有"是面板有话要说的一种答复 |

没有 `fresh` 参数，和旁边的元数据路由不一样：那边 `fresh=0` 是为了跳过一次 0.61 s 的指纹走查，
这边状态读的是文件头，没有贵的一半可跳。

### 一处措辞修正：镜像里的 `indexed: false` 仍然对，但理由变了

`home-mirror.ts` 写着"这一批不从面板建索引"，现在面板会建了，所以那句话得改。但**结论不变**：
镜像写的是技能目录里那个 `class_index_<版本>.json`，由 `build_index.py` 生成；插件建的那份在
`~/.dsh/yon-panel/knowledge/`。**两个产物、两个写者**，所以面板写回时仍然只能写 `indexed: false`——
那个标志是 `build_index.py` 的，等它自己置真。
