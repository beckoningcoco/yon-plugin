# 运行时调试与现场重放（NCC）

> **什么时候读我**：要观察 NCC **运行中**某个方法的入参/返回值、要确认「这段逻辑到底走没走到」、
> 要验证「改了算法对不对」，而重启一次服务要几分钟的时候。
> 也用于排查「按钮点了没反应之后，后端到底执行了什么」——这一层比抓 HTTP 响应更深。
> **手上已经有具体症状、只想抄一条能跑的命令**：直接看 **`运行时调试配方.md`**（按症状查，
> 每个配方是「症状 → 命令 → 读什么 → 下一步」）。本文件是原理与实测依据。

> **边界**：本文件讲**运行中的 Java 进程**怎么观测。
> 性能报告（哪个接口慢、SQL 耗时）看 **`spr-log-analysis.md`**；
> 静态调用链走查（从按钮定位到 Action 再到落库）用 **`ncc-call-chain` 技能**；
> 报错堆栈优先看 `<HOME>/nclogs/`。

> **前置**：需要 Arthas（一个独立的 Java 诊断工具，不是用友产品）。本文件的所有结论来自
> **Arthas 4.3.5 + JDK 1.8.0_202 + NCC 1909 + Windows** 的实测。

## 一、先选对层：四种手段，成本差一个数量级

| 层 | 手段 | 反馈回路 | 什么时候用 |
|---|---|---|---|
| L1 | 抓 HTTP 响应 / 查库 / 读 `nclogs` | 秒~分 | 「按钮点了没反应」——先确认请求发出没有、发到哪 |
| **L2** | **Arthas `watch` / `trace` / `jad`** | 秒 | 「变量是什么」「走到哪了」「这个方法慢在哪」 |
| **L3** | **现场重放**：dump 对象 → 离线跑真实代码 | **秒，可无限重试** | 「改完逻辑怎么快速验」 |
| L4 | `redefine` 热替换 | 秒 | 不想重启（风险高，见第八节） |

**关键判断**：L2 解决「看见」，L3 解决「低成本地反复试」。
**只有 L2 的话，拿到了现场却仍然每改一次要重启，痛点还在。**

**L2 和 L3 的关系是供货与消费**——先用 L2 把运行中的对象 dump 下来，L3 才有东西可跑。

## 二、接入 Arthas

### 1. 找进程

```bash
<HOME>/ufjdk/bin/jps.exe -lv
```

`-Dnc.server.location=<HOME>` 那一个就是要找的 NCC 进程。一个开发机上可能有多个（端口不同），
**先确认要动的是哪一个**——本机的服务端口可以在 `netstat -ano | findstr <PID>` 里看到。

**只能按 `-Dnc.server.location=` 认，不能按主类认**：实测这台机器上它的主类是
`com.yonyou.studio.udt.launching.Launcher`（UAP Studio 的启动器），**不是** Tomcat、
也不是 NC 的某个 Bootstrap 类 —— 按主类匹配会一个都找不到。`jps -lv` 里带那个参数的行就是它。

### 2. 拿 boot jar

```bash
curl -o arthas-boot.jar https://arthas.aliyun.com/arthas-boot.jar
```

首次 attach 时会自动下载完整发行版到 `~/.arthas/lib/<版本>/`。

### 3. attach

```bash
<HOME>/ufjdk/bin/java -jar arthas-boot.jar <pid>
```

- **用目标 Home 自带的 JDK 启动它**（版本对齐最省事）。
  JDK 8 的 attach 依赖 `<HOME>/ufjdk/lib/tools.jar`，NCC 的 Home 里是有的。
- attach 成功后 agent 常驻，监听 **3658**（telnet）与 **8563**（http）。
- **重复 attach 是安全的**：会打印 `The target process already listen port 3658, skip attach.`

### 4. 两种驱动方式

**一次性执行（推荐，适合脚本和自动化）**：

```bash
# 执行多条命令，分号分隔
java -jar arthas-boot.jar -c "sc -d <类>; sm <类>" <pid>

# 或从批处理文件执行（避开命令行引号地狱）
java -jar arthas-boot.jar -f batch.as <pid>
```

`batch.as` 一行一条命令：

```
ognl -c <hash> '@aidebug.Dump@saveText("hi","smoke")'
sc -d aidebug.Dump
```

**执行完就退出**，不需要维持交互会话——这一点对自动化很重要。

## 三、HTTP API：唯一真正需要的通道

attach 之后 `8563` 上有一个 HTTP 接口。**实测下来这一条就够用**，另外三条路都不通或不必走：

| 通道 | 实测 |
|---|---|
| `POST /api` `{"action":"exec"}` **短命令** | ✅ 立即返回结构化 JSON |
| `POST /api` **长命令（watch/trace）** | ✅ **请求挂住 → 命中时返回结构化结果** |
| `GET /api` | ❌ `Unsupported http method: GET` |
| `{"action":"pull"}` | ❌ `unknown action: pull` |
| 裸 socket 连 3658 | ❌ 收到的是 telnet 协商字节，不是纯文本，不值得实现协议 |
| `{"action":"init_session"}` | 可用但**没用**，每次 exec 都会返回自己的 sessionId |

### 用法

```bash
curl -s -X POST http://127.0.0.1:8563/api \
     -H "Content-Type: application/json" \
     -d '{"action":"exec","command":"sc -d nc.impl.xxx.XxxServiceImpl"}'
```

**写文件的写法更省事**（省掉引号转义）：

```bash
# req.json:  {"action":"exec","command":"watch ... '{params}' -n 1"}
curl -s -X POST http://127.0.0.1:8563/api \
     -H "Content-Type: application/json" \
     --data-binary @req.json
```

### 「同步」恰好就是异步 —— 但它是**原子**的，没有增量

短命令立即返回；**watch / trace 这类会阻塞的命令，会让这个 HTTP 请求一直挂着，直到命令结束**
（实测：不设超时就能一直挂到 watch 命中）。

**所以挂一个不设超时的请求，就是天然的异步观测**——不需要 websocket、不需要后台 JVM 进程、
不需要 session 管理。这是本文件里最实用的一条。

**边界：一个 `watch -n 5` 不会一条一条吐结果。** 请求会一直挂到 5 次命中**全部**发生，
然后一次性返回。所以「轮询这个接口就能看到实时事件流」**不成立**——命令没结束就什么都读不到。
正确姿势是**挂一次、等它结束、一次拿走全部**。真要流式（挂着的同时看到每次命中）得走
websocket（`NettyWebsocketTtyBootstrap`），本文件未验证。

### 响应结构

```json
{"body":{
   "command":"watch ...",
   "jobId":17,"jobStatus":"TERMINATED","timeExpired":false,
   "results":[
     {"type":"enhancer","success":true,"effect":{"classCount":1,"methodCount":1,"listenerId":5}},
     {"type":"watch","className":"nc.impl.epmp.bgr.BgrReportSyncServiceImpl",
      "methodName":"buildReportJson","accessPoint":"AtExit","cost":0.5684,
      "ts":"2026-10-15 18:37:28.421","value":"@ArrayList[\n @String[...],\n]"},
     {"type":"status","statusCode":0}
   ]},
 "sessionId":"052f44d6-...","state":"SUCCEEDED"}
```

**结果天生结构化**，`type` 取 `enhancer` / `watch` / `status` / `reset`，不必解析文本。

### 必须知道的几点

**0）`state: "SUCCEEDED"` 不代表命令成功 —— 这是最容易搞错的一条。**

```json
// watch 一个不存在的方法 → 依然 SUCCEEDED
{"state":"SUCCEEDED","body":{"results":[
  {"type":"enhancer","success":false,"message":"No class or method is affected",
   "effect":{"classCount":1,"methodCount":0}},
  {"type":"status","statusCode":-1,"message":"…带 ANSI 转义的长提示…"}]}}
```

`state` 说的是**这个请求被处理了**。实测三种失败**全都**返回 `SUCCEEDED`：
watch 一个不存在的方法、`ognl` 加载不到类、`sc -d` 查一个不存在的类。

**命令成没成，看这两个：**
- `status.statusCode`：**0 = 成功，-1 = 失败**（原因在 `status.message`，**带 ANSI 颜色转义，要剥掉**）
- `enhancer.success`：`false` = 增强没注册上

只看 `state` 的后果很具体：**「观测挂上了、只是还没命中」和「观测压根没挂上」长得一模一样。**

1. **`results[].type=="enhancer"` 是「注册成功」的凭据**，但它和 watch 事件在**同一个响应**里返回。
   也就是说，**在挂起阶段无法确认注册成功**。
   → 正确姿势是 **「挂上 → 触发业务 → 读结果」**，不要试图「挂上 → 检查是否成功」。
   注意 `success: false` 时 `classCount` 仍可能是 1（那是"考察了几个类"，不是"增强成功几个"），
   **别单看 classCount 判断成功**。

2. **`action` 必填**，缺了报 `'action' is required`，写错报 `unknown action: <x>`（不会列出合法值）。
   非法命令行返回 `state: "FAILED"` 且**整个响应没有 `body`**，原因在顶层 `message` 里。

3. **`java.*` 默认不可增强**：watch `java.lang.String` 报 `No class or method is affected`，
   需要先执行 `options unsafe true`。

4. **`sc -d` 查不到类不报错**：返回 `SUCCEEDED`，`results` 里只有
   `{"type":"row_affect","rowCount":0}` + `{"type":"status","statusCode":0}`。
   「类不存在」要从**没有 `sc` 结果**判断，别等错误——它不会来。

5. **`reset` 的 HTTP 形状是 `{"type":"reset","affect":{"classCount":N,…}}`**，
   注意是 `reset.affect.classCount`，**不是** `enhancer.effect.classCount`。
   清理循环的终止条件就读这个数（见第八节）。

## 四、classloader hash：不指定就加载不到业务类

**这是 NCC 场景最硬的坑。**

```bash
sc -d nc.impl.epmp.bgr.BgrReportSyncServiceImpl
```

输出里的关键两行：

```
code-source       /E:/NCProject/.../ncc_scgf_v1909/bin/
classLoaderHash   7c29daf3
```

**`ognl` 默认用 SystemClassLoader，加载不到业务类**，报：

```
Failed to execute ognl, exception message: ognl.MethodFailedException:
Method "saveText" failed for object aidebug.DebugDump
[java.lang.ClassNotFoundException: Unable to resolve class: aidebug.DebugDump]
```

**必须显式指定 classloader**：

```bash
ognl -c 7c29daf3 '@aidebug.Dump@saveText("hi","smoke")'
```

| 命令 | 要不要 `-c` |
|---|---|
| `ognl` | **要**（否则加载不到业务类） |
| `watch` / `trace` | **通常不要**（用的是被增强类的加载器） |

**一个进程里可能有多个加载器**，所以 hash 要**按类名查**，不能一个进程记一个。

## 五、现场重放：把运行中的对象搬到离线来跑

目标：**用真实的业务代码，反复跑同一份现场数据**，把「改一行 → 重启几分钟」压成「4 秒」。

### 第 1 步：**不要**写落盘助手类 —— watch 表达式看不见它

原做法是「写一个 `aidebug.Dump`，丢进工程 `bin/`，让 watch 表达式调用它」。
**这条路在 NCC 上走不通**，原因是一个很容易漏掉的 classloader 事实：

> **`watch` 表达式的 OGNL 求值走的是系统类加载器**；承载工程 `bin/` 的那个业务加载器
> 是它的**子**加载器，而父看不到子的类。

三组实测把它钉死：

| 表达式 | 结果 |
|---|---|
| `{@java.lang.String@valueOf(returnObj)}` | ✅ 命中（JDK 类） |
| `{returnObj}` | ✅ 命中，能拿到返回值 |
| `{@aidebug.Dump@save(params[0], "t")}` | ❌ `watch failed … java.lang.NullPointerException` |

那个 NPE 就是「静态引用解析成 null，再在 null 上调方法」。**`-c <hash>` 救不了**：
`-c` 决定*增强哪个加载器里的类*，不决定*用哪个加载器求值表达式*（放表达式前、后都试过，一样 NPE）。

两个相关事实，都容易踩：

- **`java.class.path` 会骗你。** 这台 NCC 上它只有 `…/eclipse/uaplauncher.jar` 一项，
  看起来系统加载器什么都看不见 —— 但 `classloader -c <appHash> -u` 显示 NCC 启动后用**反射**
  往 AppClassLoader 里加了一大批 `modules/<mod>/META-INF/classes/` 目录。
  真要投放，那些目录是可行位置；但那要往使用者的**安装目录**里写文件，
  而且 JVM 从不重载已加载的类（投一次废一个类名），不值得。
- **覆盖 `.class` 文件 ≠ 替换类。** 某个类名**已被那个 JVM 加载过**的话，
  改源码、重编译、覆盖文件都毫无作用 —— JVM 留着内存里那份旧的，症状是 `NoSuchMethodException`。

### 第 2 步：落盘用一条纯 `java.io` 的 OGNL 表达式

序列化只需要 `java.io`，而 JDK 类在任何加载器下都看得见。把整个落盘写进 watch 表达式：

```bash
watch <全类名> <方法名> \
  '{(#d=new java.io.File("<目录>"),#d.mkdirs(),
     #f=new java.io.FileOutputStream("<目录>/<tag>.ser"),
     #o=new java.io.ObjectOutputStream(#f),
     #o.writeObject(returnObj),
     #o.flush(),#o.close(),
     "DUMP_OK <目录>/<tag>.ser")}' -n 1
```

要点：

- 外层 `{…}` 是 Arthas 的**表达式列表**，而括号 `( … )` 里的逗号序列被当成**一个**元素求值 ——
  所以多步操作能塞进一个表达式。`#` 变量在同一条序列里共享。
- 表达式里**不要用单引号**（Arthas 用它包裹表达式本身），字符串一律用双引号。
- **路径写正斜杠**（`C:/x/y.ser`）：反斜杠在 OGNL 字符串里是转义符。
- **必须先 `mkdirs()`**，否则 `FileOutputStream` 会因为目录不存在而失败。
- `writeObject` 之后要 `flush()` + `close()`：`ObjectOutputStream` 有内部缓冲，不关会丢数据。
- 文件名在**客户端**生成好、作为字面量写进去（如上例），别在 OGNL 里拼字符串。
- 对象**必须可序列化**。不可序列化的值会在 `writeObject` 里抛异常
  （Arthas 把异常名写在失败信息里），并留下一个半截文件。

实测这条表达式**真的落盘**：返回 `@ArrayList[ @String[DUMP_OK …] ]`，磁盘上出现一个 26 字节的 `.ser`。

实测：`com.ufsoft.table.CellsModel` 完全可序列化，一份 58×14 的报表落盘 **385,480 字节**
（这个数字来自更早一轮的手工实验，那一轮走的是 watch 还是带 `-c` 的 `ognl` 已不可考；
`CellsModel` 可序列化这一点与上面的改动无关，仍然成立）。

### 第 3 步：离线端准备 classpath（唯一麻烦的地方）

实测数字（两轮口径不同，都对）：

| 项 | 值 |
|---|---|
| 条目 | **5,481**（`classloader -c` 报的 URL 条数；更早一轮按 jar/目录数记是 3,436） |
| 拼成命令行 | **519,842 字节** → `The filename or extension is too long`（Windows 上限 ~32K） |
| JDK 8 的 `@argfile` | **不支持**（JDK 9+ 才有） |
| **解法** | **manifest-only jar**：`Class-Path` 分行写进 `MANIFEST.MF`，生成的 jar 只 **59,596 字节** |

**classpath 必须从运行中的 JVM 拿，不要猜目录**：

```bash
classloader -c <hash>      # 列出该 classloader 的全部 URL
```

> **`java.class.path` 这个属性会骗你。** 实测它只有 `…/eclipse/uaplauncher.jar` 一项，
> 看起来系统加载器什么都看不见 —— 但 NCC 启动后用**反射**往 AppClassLoader 里加了一大批
> `modules/<mod>/META-INF/classes/` 目录。**以 `classloader -c <hash>` 的输出为准。**

**生成 manifest jar 的三个要点。** 前两条是踩出来的，症状一模一样：一个指着明明在盘上的类说
`ClassNotFoundException`。

1. **每行 ≤72 字节，续行标记也算在内。** 这里的 URL 本身就有 150 字节，所以「一行一个条目」
   不成立，要按**字节预算**切。
2. **折行不要落在条目的分隔空格上。** manifest 的续行是「换行 + 一个空格」，解析器会删掉那个
   空格 —— 于是「`…/a.jar` + 换行 + 空格 + `…/b.jar`」拼回来是 `…/a.jar…/b.jar`，一个哪儿都
   不存在的路径。**把分隔空格收进前一行**，预算用 71（首行）/ 70（续行）。
3. 路径写成 `file:/` URL，**目录必须带尾部 `/`**，且**清单不支持 `*` 通配符**（要先展开成具体 jar）。

最后 `jar cfm cp.jar manifest.mf -C <空目录> .`，运行时
`java -cp "<Replay.class 所在目录>;cp.jar"`。

> **写完随手验一次**：把生成的行按「续行删掉一个前导空格」拼回去，与原值逐字节比一遍。
> 违反规则的 manifest 照样写得出来、照样产出 jar，只在很久以后、别的地方炸。

### 第 4 步：反射调用真实方法

```java
Class<?> cls = Class.forName("nc.impl.epmp.bgr.BgrReportSyncServiceImpl");
Object impl = cls.newInstance();
Method m = cls.getDeclaredMethod("buildReportJson", Class.forName("com.ufsoft.table.CellsModel"));
m.setAccessible(true);              // private 方法要开
Object result = m.invoke(impl, model);
```

**调的是真实代码，不是副本**，所以离线结果与线上一致，不存在「两份逻辑漂移」。

用**名字 + 参数个数**找方法通常够用 —— 现场里装的是**值**，不是签名，而签名正是这一步想避免
知道的东西。重载同名的会取第一个，所以最好把选中的签名打进输出头部：猜错要看得见。
另外 `newInstance()` 要求**公开无参构造**，构造需要参数的类回放不了。

> ⚠ **回放执行的是真实方法，没有任何副作用防护。** 它写库就写库、发消息就发消息。
> 选方法时挑**纯计算**的（`buildJson`、`pickParadim` 这类），不要把 `saveRow`、
> `syncReports` 这种名字里带动作的当回放目标。

### 实测效果

```
[1] deserialize: cellsmodel_...ser   → colNum=14 rowNum=58
[2] reflect-invoke buildReportJson   → cost = 30 ms
== 端到端 wall clock: 4447 ms ==
```

| | 容器内验证一次 | 离线回放 |
|---|---|---|
| 要重启 | 是 | **否** |
| 要重新取数 | 是（1~2 分钟） | **否** |
| 端到端 | 几分钟~十几分钟 | **1 秒上下**（含 JVM 启动；被调方法本身 4 ms） |

**改了算法后跑同一个 dump 做对比（diff），就是最便宜的回归测试。**

但**同一个 dump 跑两次，唯一的差异就是 `# cost=Nms` 那一行**（实测）。做对比时**必须忽略它**，
否则每一次对比都报「有差异」—— 而一个总报差异的工具就是没人读的工具，正好把这个办法的意义
反过来。忽略之后，「没有差异」才是一个**可信**的答案，而不是一个默认值。

## 六、异常自动捕获：把失败的现场留下

**要解决的问题**：一次调用失败之后，现场就没了 —— 请求结束、日志只剩堆栈，
"当时传进来的到底是什么"谁都答不上来。这一节让它留下来，**并且能离线重放**。

`arthas_catch` 干这件事：观察一个方法，**只抓抛异常的调用**（`watch -e`），
把异常**和入参**一起写进目标 JVM 的磁盘。

```
arthas_catch pid=45076 className=nc.impl.… methodName=save
  → 挂上之后，重放那次失败的业务动作
arthas_events session="3"
  → 事件流里直接显示 java.lang.IllegalStateException: …（不用打开文件就知道是什么错）
  → <catchDir>/catch_<时钟>.thrown.ser   异常对象（含堆栈）
  → <catchDir>/catch_<时钟>.args.ser     当时入参 —— 直接喂 replay_run 就能复现
```

`count=1`（默认）时文件名由插件定，挂上之前就报得出路径，并顺手写好侧车（面板可一键重放）；
要连抓多次（`count=5`）时插件只能定**前缀**、尾巴交给目标 JVM 的时钟，路径靠列 `前缀_*` 取。

### 异常变量是 `throwExp`，**不是** `throw`

自己写表达式时最容易踩的一个。`{throw}` 会死在

```
ognl.NoSuchPropertyException: com.taobao.arthas.core.advisor.Advice.throw
```

因为 `throw` 是 Java 关键字，Arthas 自己的 `Advice` 类上那个字段叫 **`throwExp`**。
`{params, throwExp}` 一次命中就把「入参」和「它导致的异常」放进同一个事件 ——
因果关系不需要再猜。

### 两个反直觉的坑

**`{(a, b)}` 不是「两项的数组」。** OGNL 把 `{(a, b)}` 求值为**含一个元素**的数组，
那个元素是序列 `(a, b)` 的**最后一项**。所以下面这种写法里那行 `DUMP_OK` 是白写的：

```
{(#f=new java.io.FileOutputStream(…), …写入…, "DUMP_OK "+#b)}
     ↑ 会被求值，然后丢掉 —— 文件写成功了，事件流里却看不到路径
```

`-x 2`、`-x 3` 都改不了（不是深度问题，也不是字符串太长）。
要以返回值传东西，就写成真正的数组字面量 `{a, b}`，并确认每个元素本身不带未加括号的逗号。

**写入顺序要挑。** OGNL **没有 try/catch**，一条语句抛异常，整个表达式就结束。
入参是最可能序列化失败的那个（业务 VO 不一定 `Serializable`），所以**先写异常、后写入参** ——
入参失败时至少异常还在盘上。

### 抓到的入参可以直接回放

`.args.ser` 里是 `params` 数组原样，而离线端 `Replay` 的规则是
**`Object[]` 当参数列表、其他当单个参数**，两者正好对上。实测：

```
Replay fixedname.args.ser p3.Probe boom out
→ REPLAY_FAIL java.lang.reflect.InvocationTargetException
    caused by java.lang.IllegalStateException: probe-boom-226      （exit 1）
```

线上那次失败 → 离线复现出**同一个异常**。改完代码再跑一次，就是"改对了没有"的答案。

### 限制

- 落盘的值**必须可序列化**，否则 `writeObject` 失败并留下一个半截文件。
- 目标 JVM **重启**后捕获就没了（agent 也随进程消失）。
- `-e` 挂在**不会抛异常**的方法上会一直等下去 —— 它只在异常时触发。
- **JDK 自己的类（`java.*`）默认挂不上。** 挂上去会报
  `No class or method is affected … Execute 'options unsafe true', if you want to enhance the
  classes under the java.* package`。所以别拿 `java.util.UUID.fromString("bad")` 这类当靶子；
  要抓「解析失败」，抓 NCC 自己的值类型 —— `nc.vo.pub.lang.UFDouble` / `UFDateTime` 就是现成的
  （实测 `new nc.vo.pub.lang.UFDouble("abc2")` → `NumberFormatException`）。开 `options unsafe`
  等于把整个 `java.*` 交给增强，不要开。
- **构造器写 `<init>`，而且 `-e` 会命中它的所有重载。** 实测
  `nc.vo.pub.lang.UFDouble <init>` 报的是 `methodCount=13` —— 增强的是 13 个构造器，不是 1 个，
  用完及时 `arthas_watch_stop`。

### 在真 NCC 上验过一遍（NCC 1909）

自建 JVM 只能证明机制，证明不了它在真实业务加载器里也成立。实测链路：

```
arthas_catch pid=45076 className=nc.vo.pub.lang.UFDouble methodName=<init>
arthas_exec "ognl -c 7c29daf3 'new nc.vo.pub.lang.UFDouble(\"abc2\")'"
  → 命中 · UFDouble#<init> · AtExceptionExit · @NumberFormatException[For input string: "abc2"]
  → thrown.ser 2758 字节 / args.ser 51 字节 / 侧车 191 字节
Replay 该 args.ser（classpath 用 manifest jar）
  → REPLAY_FAIL InvocationTargetException · caused by NumberFormatException: For input string: "abc2"
```

离线那一端加载的是 **NCC 的真类**（`nc.vo.pub.lang.UFDouble` 来自 `external/lib/basic.jar`）。

## 七、NCC 特有的几个事实

### 服务真正加载的是工程的 `bin/`，不是 `HOME/modules`

```bash
sc -d <类>
# code-source  /E:/.../ncc_scgf_v1909/bin/
```

**UAP Studio 把客开工程编译到 `bin/`，这个目录在服务 classpath 上，且优先于 `HOME/modules/<mod>/...`。**

| 改动类型 | 真正生效的落点 |
|---|---|
| Java 类（Service / Action） | **工程的 `bin/`** ← Eclipse 编译即可，不必手工拷进 HOME |
| `upm` / `action xml` / `authorize xml` | `HOME` 下对应目录（**容器启动时扫描，改完必须重启**） |

推论：往 `HOME/modules/.../classes/` 手工拷同名 class 是**无效的**（排在 `bin/` 之后）。

### 其余

| 事实 | 影响 |
|---|---|
| 客开源码多为 **GB18030** | 用 UTF-8 工具读会乱码，保存会损坏；用支持 GBK 的工具 |
| 服务跑在 **JDK 8** | Arthas 4 支持；`@argfile`、`address=*:port` 之类的 9+ 语法不可用 |
| `upm` 只在启动时扫描 | 新增/修改服务注册必须重启 |
| 类已加载后不会重新加载 | 改过的类要重启才生效（除非 `redefine`） |

## 八、危险动作与清理

| 动作 | 后果 | 建议 |
|---|---|---|
| `stop` | **卸载整个 agent**，3658/8563 一并消失，要重新 attach | 别用它来停 watch |
| `reset <类>` | 移除该类的所有增强 | **这才是停 watch 的正确做法** |
| `redefine` | 热替换运行中的类 | 高风险，改错了只能重启 |
| `ognl` | **等于任意代码执行** | 记录审计；能不用就不用 |
| `watch` 不带 `-n` | 永久挂着，持续有性能开销 | 观测时限次数或及时 reset |

**清理必须做，而且可能要反复做**：实测连续三次 `reset <类>` 得到 `classCount` = **1 → 1 → 0**，
说明**增强会残留**。

> **判据：循环 `reset <类>` 直到 `classCount == 0` 才算干净。**
> 这个数从 HTTP 响应里的 **`reset.affect.classCount`** 读
> （`{"type":"reset","affect":{"classCount":0,"methodCount":0,"listenerId":0}}`），
> **不是** `enhancer.effect.classCount` —— 读错字段会拿到"读不到"，而"读不到"很容易被当成"已经干净了"，
> 结果是增强留着、还报告清完了。

不带类名的 `reset` 是清全部，同样可以用 `classCount` 判断。
