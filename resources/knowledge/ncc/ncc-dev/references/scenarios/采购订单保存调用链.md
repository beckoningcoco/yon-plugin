>
> 本档案**顺手解开了另外两份档案的共同缺口**：第 7、8 份（销售订单保存/提交）都卡在
> "`IPFBusiAction` 的实现类找不到、业务动作处理器定位不到"。本份：
> ① 用 **UPM 反查**找到了实现类 `nc.bs.pub.pf.pfframe.PFBusiAction`；

## 1. 什么时候读我

- 客开要**在采购订单保存前后插手**，或要知道"采购订单保存到底调了哪些类/方法"。
- 要**给任何单据加一个保存前后的动作**（不写代码，配表就能加）——第 5 节是做法与表结构。
- 排查「保存时某个动作没执行」「动作执行顺序不对」「动作被条件挡住不执行」「换了用户表现不一样」。
- 要理解**为什么在代码里找不到业务逻辑**——采购/销售这类单据的业务动作是**配置驱动**的。

## 2. 怎么拿到这条链

**入口 XML**：`<HOME>/hotwebs/nccloud/WEB-INF/extend/yyconfig/modules/pu/poorder/config/action/poorderhandle.xml`
```xml
<action>
    <name>pu.poordercard.save</name>
    <label>采购订单卡片保存</label>
    <clazz>nccloud.web.pu.poorder.action.OrderSaveAction</clazz>
</action>
```
同 XML 的邻居：`saveandcommit`（保存提交）/ `OrderSaveCommit` / `arriveplansaveaction` / `delete` 等。

**三步定位**：
1. XML / `query-action.js` → `OrderSaveAction`（`external/lib/uipu_nccloud.jar`）；
2. 入口里就是 `IBatchRunScriptService#runBacth` —— **与销售订单提交那份同一个服务**，不用再猜服务接口；
3. `runBacth` → `ICloudScriptPFlowService`（PFlow）→ `CloudPfUtil` → `IplatFormEntry` → `IPFBusiAction`。

## 4. 入口（55 行全文要点）

```java
public class OrderSaveAction extends AbstractOrderSaveAction {
    protected SCMScriptResultDTO doScriptRemoteCall(OrderVO[] vos, PfUserObject pfUserObject, ExtBillCardOperator operator) {
        CloudPFlowContext cloudContext = this.getCloudPFlowContext(vos, pfUserObject);
        AppInfoContext.setBtnCode("Save");                                     // ★ 按钮码进上下文
        return ((IBatchRunScriptService)ServiceLocator.find(IBatchRunScriptService.class))
                   .runBacth(cloudContext, OrderVO.class);
    }
    private CloudPFlowContext getCloudPFlowContext(OrderVO[] vos, PfUserObject pfUserObject) {
        CloudPFlowContext context = new CloudPFlowContext();
        context.setActionName("SAVEBASE");                    // ★★ 第三个不同的动作名
        context.setBillType(POBillType.Order.getCode());       // "21"
        context.setBillVos(vos);
        context.setUserObj(new PfUserObject[]{pfUserObject});
        AppInfoContext.setBtnCode("Save");
        return context;
    }
    protected ExtBillCard doAfterCompare(ExtBillCard serverCard, ExtBillCard clientCard) { ... }  // 网格差异比对
}
```
**入口做的事**：装配 context（两次 `setBtnCode("Save")`）→ 交给批量脚本服务 → 回来后 `doAfterCompare` 把服务端卡片与客户端卡片做网格比对。

> ⚠️ **本入口没有权限检查、没有审计 `AuditUtils`**——那些在父类 `AbstractOrderSaveAction`（未展开）或下游。
> 对比：销售提交（第 8 份）在入口就做了 `checkPermission` + `AuditUtils`。**同为"保存/提交"类动作，入口层的职责并不一致**。

## 5. 【核心】业务动作处理器：UPM 反查 + 动作驱动表

### 5.1 UPM 反查结果（推荐给所有"找不到实现类"的场景）

文件：`modules/riawf/META-INF/P_platform50_rt.upm`

| 接口 | 实现类 |
| --- | --- |
| `nc.itf.uap.pf.IplatFormEntry` | `nc.bs.pub.pf.pfframe.PlatFormEntryImpl` |
| **`nc.itf.uap.pf.IPFBusiAction`** | **`nc.bs.pub.pf.pfframe.PFBusiAction`** |

> **为什么以前搜不到**：实现类叫 `PFBusiAction`，**没有 `Impl` 后缀**；
> `ncc_class_search` 对 `implements IPFBusiAction`、`PFBusiActionImpl`、`*SaveBP` 全部 0 命中。
> **UPM 反查是唯一可靠的办法**——按接口名在 `<HOME>/modules/<模块>/META-INF/*.upm` 里找 `<implementation>`。
> 这个文件里还注册了 `PFWorkflowQryImpl`（`IPFWorkflowQry`，第 8 份 `hasApproveflowExcute` 用的）、
> `WorkflowDefineImpl`（`IWorkflowDefine`，`hasApproveflowDef` 用的）、`WorkflowMachineImpl` 等一批流程服务。

### 5.2 `PFBusiAction` 是干什么的（2948 行）

它不是"某个单据的保存逻辑"，而是**流程驱动的调度器**：

| 方法 | 行 | 作用 |
| --- | --- | --- |
| `processAction` | 1373 | 单条动作入口 |
| `processBatch` | 2379 / 2519 | 批量动作 |
| `actiondrive` | 390 | **动作驱动**：拿 `queryActionDriveVOs` 的结果逐个执行 |
| `actioncrossdrive` | 542 | **跨单据驱动**（推出下游单据，如采购订单→到货单） |
| `queryDestParaVO` / `sameServiceVOChange` / `insertCrossServiceDriver` | 848 / 825 / 1126 | 跨服务（不同单据类型）驱动 |
| `startApproveFlowAfterAction` / `startWorkflowAfterAction` | 158 / 237 | **动作后启审批流/工作流** |
| `isHasFlowApproveWorkflowNote` / `isHasFlowApproveDriver` | 1280 / 1304 | 审批流判定（与第 8 份那两个判定并列的又一处） |
| `queryActionDriveVOs` | 1203 | **动作驱动查询入口** |

**关键点**：它引的是 `IPfExchangeService`（单据转换）与 `MDPersistenceService`，
**全文没有 `RuleCollection` / `IRule` / `pub_pluginitem`** ——
所以**"`IRule` 插件链"不是这类单据保存的主通道**（前 6 份档案里那条 `IRule` 的说法在这里再次被排除）。

### 5.3 动作驱动表（业务处理器的真正位置）

`PFBusiAction#queryActionDriveVOs:1203` → `PfUtilDMO#queryDriveAction:301` →
`queryDriveAction_db` → **SQL**（`PfUtilDMO:120`，`queryActionConstrict` / `queryActionDriverConstrict` 同构）：

```sql
select c.configflag, c.operator,
       a.classname as aclassname, a.returntype, a.functionnote, a.methodname as amethod, a.arguments as aparameter,
       c.ysf, c.value,
       b.classname as bclassname, b.functionnote, b.methodname as bmethod, b.arguments as bparameter,
       errhintmsg, c.isbefore, c.pk_businesstype, c.pk_group, c.PK_BILLTYPE, c.conditionXpression
  from pub_actionconstrict c
  inner join pub_messagedrive dr on c.pk_businesstype = dr.pk_driveconfig
  left  join pub_function a on c.functionid = a.pk_function
  left  join pub_function b on c.value      = b.pk_function
  left  join bd_busitype   d on c.pk_businesstype = d.pk_busitype
 where (c.pk_billtype = ? or c.pk_billtype = ?)          -- 参数：billType 与其"真实单据类型"
   and c.actiontype = ?                                   -- 参数：actionName
   and c.pk_businesstype = ?                              -- 业务类型（空时用 'KHHH0000000000000001'）
   and (c.pk_group = '~' or c.pk_group = ?)               -- 集团
   and (c.configflag = 1
        or (c.configflag = 2 and operator = ?)
        or (c.configflag = 3 and operator in (select pk_role from sm_user_role where cuserid = ?)))
 order by c.sysindex                                      -- ★ 执行顺序
```

**表与字段的含义**：

| 表 | 作用 |
| --- | --- |
| **`pub_actionconstrict`** | **动作约束/驱动配置**：一条 = "某单据类型 + 某动作类型下，要执行的一个动作" |
| **`pub_function`** | **函数注册表**：`classname`（类全名）+ `methodname`（方法名）+ `arguments`（参数）+ `returntype` |
| `pub_messagedrive` | 消息驱动配置（`pk_driveconfig` 关联） |
| `bd_busitype` | 业务类型档案 |
| `sm_user_role` | 用户角色（`configflag=3` 时用） |

**`pub_actionconstrict` 关键列及其语义**（从 SQL 的选择列表与参数推断）：

| 列 | 语义 |
| --- | --- |
| `pk_billtype` | 单据类型（**两个参数：本身 + `getRealBilltype()` 之后的**，所以交易类型也命中） |
| `actiontype` | **动作类型**（就是 `actionName`，如 `SAVEBASE` / `APPROVE` / `WRITE`） |
| `pk_businesstype` | 业务类型（空则用 `KHHH0000000000000001`） |
| `pk_group` | 集团（`'~'` 为通用） |
| `functionid` | → `pub_function.pk_function`：**要调的类与方法** |
| `isbefore` | **动作前 / 动作后**（决定在主体逻辑的哪一侧执行） |
| `sysindex` | **执行顺序**（`order by`） |
| `conditionXpression` | **执行条件表达式**（不满足就不执行） |
| `errhintmsg` | 失败提示语 |
| `ysf` / `value` | 运算/比较（另一种二元形态：`a` 与 `b` 两个 function 做比较，见 `bclassname`/`bmethod`） |
| `configflag` / `operator` | **可见性/生效范围**：`1`=通用；`2`=指定 operator；`3`=operator 所属角色命中 |
| `value` | → 第二个 `pub_function`（对比形态时用） |

**这解释了三件以前解释不了的事**：

1. **"业务处理器的类名在代码里搜不到"** —— 它写在 `pub_function.classname` 里，是**数据**。
2. **"同一个动作，不同的人/组织行为不一样"** —— `configflag` + `operator` + `pk_group` + `conditionXpression` 四重过滤。
3. **"动作执行顺序"** —— `sysindex` 排序；`isbefore` 分前后。

> **客开做法**：想给采购订单保存加一个"写日志/校验/回写"的动作，**不用改任何平台类**——
> 写一个类（含静态或指定签名的方法）→ 注册进 `pub_function` → 在 `pub_actionconstrict` 插一行
> （`pk_billtype='21'`、`actiontype='SAVEBASE'`、`isbefore` 选前后、`sysindex` 定顺序、`conditionXpression` 定条件、`configflag` 定生效范围）。
> 这正是**平台推荐的"动作驱动"客开方式**。

## 7. 三个动作名的对照（三份档案合起来看才有意义）

| 档案 | 业务动作 | 入口类 | actionName | billType | 引擎入口 |
| --- | --- | --- | --- | --- | --- |
| 第 7 份 | 销售订单**保存** | `SaleOrderSaveAction` | **`"WRITE"`** | `"30"`（硬编码） | `ISaleOrderMaintainWebService#save` → `exeScriptPFlow` |

> 排查"保存没执行应有的业务逻辑"时，**先确认真实 actionName**（在入口里看 `setActionName`）。

### 未覆盖项的详情

- **`po_order` 表名与字段未核实（⬜）**：计划里写的目标表是 `po_order`，但**本次没有像前几份那样从 VO 反编译拿
  `getDefaultTableName()`**。→ 续做应用 `ncc_meta_find(kind=entity, q='po_order')` 或找 `OrderVO` 的元数据路由
  （采购订单很可能与销售订单一样走 `BillMetaFactory`，即表名也在元数据里）。**别把计划里的 `po_order` 当已核事实用。**
- **业务处理器是运行时的（⬜，且是机制性的）**：`pub_actionconstrict` 里配了哪些类、按什么顺序，
  **只有连上库（或运行时打印）才知道**。本机无 NCC2505 连接，所以"采购订单保存到底执行了哪几个业务类"这一问
  **在离线条件下无法回答**——这不是挖得不够，是数据在库里。
  → 客开若在客户现场，一条 SQL 即可：
  `select sysindex, isbefore, classname, methodname, conditionXpression, configflag from pub_actionconstrict c join pub_function f on c.functionid=f.pk_function where c.pk_billtype='21' and c.actiontype='SAVEBASE' order by c.sysindex;`
- **`PFBusiAction` 的跨单据驱动（⬜）**：`actioncrossdrive:542`、`insertCrossServiceDriver:1126` 涉及"推出下游单据"
  （采购订单→到货单），2948 行的类只读了索引级；**未展开**。
- **审批流/工作流那一半（⬜）**：`startApproveFlowAfterAction:158`、`startWorkflowAfterAction:237`、
  `isHasFlowApproveWorkflowNote:1280`、`isHasFlowApproveDriver:1304` 只读到方法名。
