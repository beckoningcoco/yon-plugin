# Arthas 测试经验与 Q&A

> 本文档是 [[Arthas-API测试实战流程]] 的子文档，收录实战中积累的测试经验和常见问题解答。

---

## 常见问题 Q&A

### Q: tt 录到了 CGLIB 代理类，怎么看原始的？

`tt -l` 会同时显示原始类和 `$$EnhancerBySpringCGLIB$$xxx` 代理类，用原始类的 INDEX 查看即可。

### Q: 接口太慢（52秒），tt 需要等很久吗？

不需要。tt 是异步录制，方法一调用完就能 `tt -l` 看到结果，不需要保持连接等到方法结束。

### Q: 异常被 try-catch 吞了，怎么发现？

1. 用 `trace` 跟踪调用链，找到内部可能抛异常的方法
2. 在内部方法上挂 `watch ... -e` 只捕获异常
3. 看日志文件中是否有异常堆栈

### Q: 能否重放某次调用？

`tt -i <INDEX> -p` 会用相同的参数重新执行，但**可能产生副作用**（写库、调外部接口等），谨慎使用。

## 测试经验总结

> 来源：东软载波 ONES工时同步接口测试实战（2026-06-19），覆盖异步接口、镜像测试、分段测试全流程。

### 1. 异步接口 = 测试黑洞

Controller 用 `YmsExecutor` 把任务丢到另一个线程，HTTP 立即返回 200 `{"asynchronized":"true"}`。表面"调通了"，实际异步线程里可能正在扔异常、写脏数据（如 1970-01-01 的日期）。测试异步接口的第一步不是看返回值，是确认异步线程里到底发生了什么。

### 2. Arthas 也有盲区

Tunnel Server HTTP API 硬限制 30 秒超时。异步方法在 YMS 线程池里排队等几分钟才执行，所有监听命令（`tt`/`watch`/`trace`）全废。唯一能用的 `stack` 只告诉你方法"正在执行"，看不到入参和返回值。Telnet 直连无超时，但不适合脚本化自动化测试。

> **对策**：异步接口不要试图用 Arthas 直接监控——先改成同步再测。

### 3. `log.error` 是 BIP 的通用语言

YMS 框架的日志配置通常只输出 `ERROR` 级别。`log.info` 写得再好也看不到。测试代码里所有关键日志统一用 `log.error()` 输出，这是在 BIP 平台上做测试的生存法则。

### 4. 镜像 Controller 是最佳实践

同路径建测试 Controller，拷贝业务逻辑但改三样：
- **去异步**：去掉 `YmsExecutor`，同步执行
- **改日志**：`log.info` → `log.error`（绕过 YMS 过滤）
- **改返回**：从 `{"asynchronized":"true"}` 变成每步耗时 + 每条明细

原始代码零侵入，测完删掉不留痕迹。

### 5. 分段测试比单体强太多

长链路（200s+）拆成独立段落，每段通过 JSON 传参：

```
Seg1(拉数据) → {manhours} → Seg2(查员工) → {staffMap} → Seg3(查团队) → {teamResult} → Seg4(导入)
```

好处：

| 对比 | 单体 | 分段 |
|------|------|------|
| 单次耗时 | 200s | 每段 1~6s |
| 单独重跑 | ❌ 改一行等 3 分钟 | ✅ 只跑出错的那段 |
| 构造假数据 | ❌ | ✅ 跳过上游直接测某段 |
| 定位问题 | 黑盒 | 每段透明的白盒 |

### 6. 代码通了 ≠ 业务通了

代码层面 Bug 全修完，Seg4 导入还是可能失败——BIP 平台自身的业务规则（角色权限、项目有效期、工时重叠校验等）是最后一公里。测试工程师要区分"代码问题"和"平台/业务规则问题"，前者修代码，后者找产品/管理员。

### 7. 测试留痕是底线

没有完整记录的 Arthas 输出、时间线、异常堆栈，事后回溯根本不可能。省略一个字符省一秒，查问题多花十分钟。测试文档里所有入参、token、URL、日志、异常堆栈必须完整记录，一字不差。

### 8. API 返回 200 ≠ 业务成功

> 来源：东软载波项目状态同步接口测试（2026-06-22），BIP 批量变更API返回200+"成功"，前台数据纹丝不动。

BIP OpenAPI 的"成功"响应可能只是个回执——你发了请求，他收到了，返回 200。但实际业务是否执行成功，需要验证数据层面。**测试完成的标志不是 API 200，是数据库和前台的数据真的变了。**

**测试完成 checklist：**
- [ ] API 返回值正确（code=200 等）
- [ ] 用 Arthas `tt` 抓请求入参和返回值，确认实际传输内容
- [ ] 查数据库确认数据变更（如果可直连）
- [ ] **提示用户去前台验证**，并给出预期结果对照

**提示用户前台验证的模板：**
```
去前台验证以下数据：
  项目: RD-2026-A3-IPC-13
  预期状态: preset30（进行中）
  验证路径: 项目管理 → 项目列表 → 搜索项目编码 → 查看状态列
```
只说"接口通过了"是不够的，必须让用户知道"应该看到什么"。

### 9. 参数细节决定成败：空字符串 vs null

> 来源：东软载波项目状态同步（2026-06-22），`resubmitCheckKey` 传了空字符串 `""` 导致 BIP 幂等机制误判。

BIP 接口的参数中，空字符串 `""` 和 `null` 语义完全不同。幂等 key（`resubmitCheckKey`）传 `""` 时，BIP 可能视为"已提交过该请求"而跳过处理，返回"成功"但不执行。正确的做法是传 `null`（Java 中 `new String("")` 和 `null` 是两个概念）。

**对策**：DraftRequest/ChangeRequest 的 `resubmitCheckKey` 字段要明确设为 `null`，不要给默认值 `""`。
