# 交易类型占用：排查方法

> **症状**：启用业务流报 `000-533-020003 交易类型不滿足唯一性校验!`
> **适用**：旗舰版 BIP 业务流启用；**不依赖 SPR / BPR**，优先数据库直查。
> 来源：2026-10-18 实测（BPR 抓到的校验 SQL + `iuap_apcom_businesssflow.business_flow` 数据）。

---

## 一、先拿三个值

| 值 | 从哪拿 |
|---|---|
| 当前流 `id` / `BILL_CODE` / `ORG_ID` / `TRANSACTION_TYPE_ID` | `GET /iuap-apcom-supportcenter/businessFlow/getById?id=<id>` |
| 交易类型 id | 主体 `transactionTypeId`，或规则 `flowRule/list` 的 `srcBizTypeId` / `tarBizTypeId` |
| 租户 `tenantId` | `getById` 返回 |

> 注意：校验用的是**核心单据那一侧**的交易类型 id。销售订单类流看主体/来源侧，不是目标侧「普通发货」。

---

## 二、校验 SQL（从 BPR 抓到的真实条件）

```sql
SELECT count(id)
FROM iuap_apcom_businesssflow.business_flow
WHERE YTENANT_ID = '<tenantId>'
  AND BILL_CODE = '<核心单据编码>'
  AND STATUS = 1
  AND IS_CURRENT_VERSION = 1
  AND TRANSACTION_TYPE_ID LIKE '%<交易类型id>%'
  AND ID <> '<当前流id>'
  AND ORG_ID = '<orgId>'
```

**关键**：

- 只看 `STATUS = 1`，**没有 `DR` 条件**；
- 所以 `DR=1`（逻辑删除）但 `STATUS=1` 的流**仍算占用**；
- `STATUS=0`（停用）才算释放。

---

## 三、直查占用者（推荐）

把 `count` 换成明细：

```sql
SELECT ID, CODE, NAME, STATUS, DR, IS_CURRENT_VERSION,
       TRANSACTION_TYPE_ID, TRANSACTION_TYPE_NAME, BILL_CODE
FROM iuap_apcom_businesssflow.business_flow
WHERE YTENANT_ID = '<tenantId>'
  AND BILL_CODE = '<核心单据编码>'
  AND STATUS = 1
  AND IS_CURRENT_VERSION = 1
  AND TRANSACTION_TYPE_ID LIKE '%<交易类型id>%'
  AND ID <> '<当前流id>'
  AND ORG_ID = '<orgId>'
```

在 Yon 面板里用 `datasource_query`，连接 key 用该项目已登记的（如「金隅集团(BIP旗舰版)::dev」）。

---

## 四、判定

| 数据 | 含义 |
|---|---|
| `STATUS=1`、`ID<>自己` | **占用者**，启用会被拦 |
| `DR=1` 且 `STATUS=1` | 逻辑删除的脏数据，**仍占用** |
| `STATUS=0` | 已停用，释放 |
| `DR=1` 且 `STATUS=0` | 正常删除，释放 |

---

## 五、处理

1. **停用占用流**（首选）：列表选中 →「停用」→ 确认 `status=false`；
2. **改当前流交易类型**：换一个未被占用的类型；
3. **误删脏数据**（`DR=1 / STATUS=1`）：
   ```sql
   UPDATE iuap_apcom_businesssflow.business_flow
   SET STATUS = 0
   WHERE ID IN (...) AND YTENANT_ID = '<tenantId>' AND DR = 1;
   ```
   改库前先 SELECT 确认；
4. **不要直接删启用中的流**——会产生新的 `DR=1 / STATUS=1` 脏数据。

---

## 六、没有数据库连接时

按可信度排序：

1. **BPR / SPR 报告**：看「SQL耗时TOP10」里的 `count(id) ... TRANSACTION_TYPE_ID LIKE ...`，就是校验 SQL；
2. **F12 网络**：找 `businessFlow/changeStatus` 的请求/响应，响应里通常有错误码；
3. **接口遍历**：`businessFlow/list` 逐分类拉流，再逐条 `getById` + `flowRule/list` 比对交易类型。缺点：要先拿到每个分类的 `flowCategoryId`，较慢。

> BPR 的价值是「直接给 SQL + 调用链」；有数据库连接时，直查表更快、更准。

---

## 七、本次实例（2026-10-18）

- 「发出商品」`2527636005091018209`：
  - `TEST_BFL_20261018_01`（DR=1、STATUS=1）
  - `TEST_BFL_20261018_04`（DR=1、STATUS=1）
  - `11122`（DR=1、STATUS=1）
  - 三条都占用；把前两条 `STATUS` 置 0 后，仍剩 `11122`。
- 「借出转销售」`2527636005091018100`：
  - 生效流「借出转销售」（DR=0、STATUS=1）占用。
- `_06`（收款复制流，交易类型空）启用成功，说明复制/启用机制本身没问题。

**教训**：删除业务流必须先停用，否则 `DR=1 / STATUS=1` 会一直占着交易类型。

---

## 八、核心单据的交易类型下拉里"少了一项"

**症状**：新建业务流，拖入核心单据（如销售订单），规则里「来源交易类型」下拉**找不到**想要的交易类型（实测：找不到「直运销售」），下拉里只有寥寥几项。

**这不是档案问题、也不是权限问题**，是设计器的前端过滤：

- 拖入/加载节点时，`getBillInfo` 会对 `isCoreBill=true` 的节点**额外**调
  `GET /businessFlow/getUsedTransactionType?tenantId=&businessFlowId=&billCode=<单据>`；
- 返回 `data` 是**该单据在所有未删除业务流里用过的交易类型 id 数组**（其中有的元素是
  `"idA,idB"` 这样的逗号拼接串）；
- 前端把 `data.join(',').split(',')` 后，**凡出现在里面的 id 都被从下拉里剔除**：
  `!l.data.join(",").split(",").includes(e.id)`。

所以「下拉里没有」= **该交易类型已被别的业务流占用**，和"启用校验会不会拦"是同一个结论的两种表现：
下拉先过滤掉，即使硬配，启用时也会报 `000-533-020003`。

**注意两点**：

1. 只有**核心单据**节点会调这个接口；普通节点（目标侧）不调，所以同一交易类型在目标侧下拉里仍可能出现。
2. 占用判断必须用 `LIKE '%<id>%'`（见第二节）。本次需求单用等值 `=` 查，漏掉了
   `TRANSACTION_TYPE_ID="2527636005091018082,2558197721052217349"` 的启用流「直运销售-zjx」，
   于是误判"未被占用"，实际在下拉里根本选不到。

**验证脚本**：

```js
// 在已登录的设计器页签里跑
const r = await fetch('/iuap-apcom-supportcenter/businessFlow/getUsedTransactionType' +
  '?tenantId=jd4ofb7k&businessFlowId=<流id>&billCode=voucher_order', { credentials: 'include' })
const ids = (await r.json()).data.join(',').split(',')
ids.includes('2527636005091018082')   // true = 被占用，下拉不会列出
```
