# 供应商档案保存调用链

> 本文件是**实体档案**，按维度分节。要加新维度就**加一节**，不要重写整篇。
> 总索引：[_call-chain-archive-index.md](./_call-chain-archive-index.md)；采集口径见 [_call-chain-collection-standard.md](./_call-chain-collection-standard.md)。
> **行号与类名均来自 NCC2505 的 jar**，换版本可能漂移；类名与调用顺序比行号稳定。
> 同族对照：客户档案走的是同一套框架（`BDSingleBaseService` + `SingleBaseService`），
> 但客户侧没有"版本表 + 客户供应商关系表"这两层，差异见第 10 节。

**核心类**：`nc.impl.bd.supplier.baseinfo.SupplierBaseInfoImpl`
（`modules/uapbd/META-INF/lib/uapbd_supplier_rt.jar`），
声明在 :142 —— `extends BDSingleBaseService<SupplierVO> implements ISupplierBaseInfoService`。
**构造函数 :154-156 里 `super("720dcc7c-ff19-48f4-b9c5-b90906682f45", new String[]{"suplinkman", "supbankacc", "supcountrytaxes", "supvat"})`**
——第一个参数是 **`mdId`**（元数据主键，`BDCommonEventUtil(mdId)` 注册事件监听时要用），第二个是四个子表属性名。

> ⚠️ **同一个业务动作名会骗人**：`uapbd.supplier.saveSupplier` 的 XML 标签是「供应商保存」，
> 但它是一个**四分支复用入口**（新增/修改/建版本/客户供应商联动），分支由请求 JSON 里的
> `step` 和 `checkflag` 决定，**不是按钮决定**。见第 4 节。

## 1. 什么时候读我

- 要知道**供应商保存/修改/建版本，代码从哪进、在哪落库**，以便找地方挂插件或改逻辑
- 要判断**一次保存最终写哪几张表**（主表 + 4 子表 + 版本表 + 客户供应商关系表）
- 要理解 **NCC 基础档案（BD）的通用持久化模板**——`SupplierBaseInfoImpl.insertVO:399` 与
  `SingleBaseService.insertVO:123` 是父子两段，**换任何一张 BD 档案都长这样**（第 3、5 节）
- 要**加校验**：`getInsertValidator` / `validate()` 里有三处不同层级的校验器（第 9 节）
- 要**挂事件监听器**：mdId `720dcc7c-ff19-48f4-b9c5-b90906682f45`，事件码 1064/1065/1072/1073/1139/1140（第 8 节）
- 要**排查"客户和供应商数据不同步"**——供应商在这里是**双向**的：既写自己的主表，
  又写 `bd_cust_supplier` 关系表，还回头同步客户表（第 7、10 节）

## 2. 怎么拿到这条链

**第 1 条：查 action XML 定位入口——不用开环境。**
供应商卡片的按钮映射在：

```
<HOME>/hotwebs/nccloud/WEB-INF/extend/yyconfig/modules/uapbd/supplier/supplier/config/action/supplier.xml
```

其中保存那一项（:22-26）：

```xml
<action>
  <name>uapbd.supplier.saveSupplier</name>     <!-- 点换斜杠 → /nccloud/uapbd/supplier/saveSupplier -->
  <label>供应商保存</label>                     <!-- 中文按钮名 -->
  <clazz>nccloud.web.uapbd.supplier.supplier.action.SaveSupplierBaseInfoAction</clazz>
</action>
```

同一个 XML 里还注册了 `addSupplier`(新增) / `deleteSupplier`(删除) / `copySupplier`(复制) /
`approveSupplier`(审批) / `freezeSupplier` / `querySupplierBaseInfo` 等，**一次就能拿全这组动作的入口类**。

**第 2 条：类索引定位实现类。**
`ServiceLocator.find(ISupplierBaseInfoService.class)` 找到的**不是**实现类名，映射在 UPM 里：

```
<HOME>/modules/uapbd/META-INF/B_Supplier60_rt.upm
  <component singleton="true" remote="true" tx="CMT">
    <interface>nc.itf.bd.supplier.baseinfo.ISupplierBaseInfoService</interface>
    <implementation>nc.impl.bd.supplier.baseinfo.SupplierBaseInfoImpl</implementation>
```

> **`tx="CMT"` 是这里唯一写着事务模式的地方**（容器管理事务），
> `remote="true"` 说明这是可远程调用的 EJB 组件。别指望在代码里找到事务注解。

**第 3 条：cfr 逐层反编译**（`resources/knowledge/ncc/cfr-0.152.jar`）。
`ncc_class_search` 给出 jar 路径，`jar xf` 抽 class，`java -jar cfr` 反编译。

## 4. 入口 action 的四个分支

`SaveSupplierBaseInfoAction.execute` 按 `step` 与 `checkflag` 分派（:117、:170）：

| 条件 | 走的分支 | 说明 |
| --- | --- | --- |
| `step="0"` 或 `!checkFlag` | :117 起 | **正戏**——新增 / 建版本 / 修改三选一，见下 |
| `step="1"` 且 `checkFlag` | :170-175 | **客户供应商联动**：`ICustSupplierService.insertSupAndRelaToCust`（pk_supplier 空）或 `updateSupAndRelaToCust`（非空） |

`step="0"` 分支内部再按 `createVersion` 与 `pk_supplier` 否空三分（:118-168）：

| 条件 | 调用 | 语义 |
| --- | --- | --- |
| `createVersion == true` | `service.createSupplierVersion(vo)` :119 | **建新版本**（第 7 节） |
| `createVersion == false` 且 `pk_supplier` 为空 | `service.insertSupplierVO(vo, checkFlag)` :135 | **新增** |
| `createVersion == false` 且 `pk_supplier` 非空 | `service.updateSupplierVO(vo, checkFlag)` :168 | **修改** |

同分支还有两处前置（:120-136）：
- `copy_supplier != null` 时先 `insertSupplierVO` 再 `ISupplierAssignService.copySupplierAssignData`（复制分配数据）
- `copyAssign` 为真时把源供应商的 `SupCountryTaxesVO` 复制到新供应商（:125-132）

**修改路径在 action 层还有三道前置**（`pk_supplier` 非空后、调 `updateSupplierVO` 之前，:140-167）：

| # | 代码 | 行 | 作用 |
| --- | --- | --- | --- |
| 1 | `qrySer.querySupplierVOByPk(pk_supplier)` → `oldvo` | :141 | 取旧 VO 做对比 |
| 2 | `checkOldVONotNull(supplierVO, oldvo)`，非空则 `throw` | :142-145 | 旧 VO 取不到 → 用多语资源 `10140sub/010140sub0082` 拼 code+name 报文抛错 |
| 3 | 国家税制逐条比对 | :160-167 | `SupCountryTaxesVO` 里 `status==3`、`pk_country` 为空、或 `pk_country` 与主表一致 → **跳过**；否则抛 `10140supt/010140supt0000` |

> ⚠️ **`supprop` 由 0 变 1 时的重复账号检查是产品缺陷**（:146-159）：
> 条件满足后查 `bankAccBaseQryService.queryBankaccForCustSupUpdate(pk_org, pk_supplier)` 拿到
> `repeateaccnums`，只在 `:157` 用多语资源 `10140cub/110140cub0047` **拼了一个提示字符串**
> （参 `orgvo.getName()`、账号列表），**拼完既没 throw 也没放进返回值——这个变量被丢弃了**。
> 也就是说"同一个财务组织下账号重复"这条校验**在保存路径上不生效**。
> 客开若依赖它拦重，必须自己补；排查"账号重复也保存成功了"时，这里就是答案。

**保存前的字段兜底**（:99-116，都在 action 里，不在 service）：
- `blacklist=true` 且无 `blacklistdate`/`blacklistuser` → 取会话里的业务日期与当前用户补上；`blacklist=false` → 置空
- `calibrationstate="2"` 且 `latestcaltime` 为空 → 补当前时间
- `registerfund` 不合法 → 抛 `nccriauapbd0/0nccriauapbd00466`

**异常出口**（:177-204）：`UndeclaredThrowableException → InvocationTargetException` 拆包后
- `CustSupBusiException` → 把冲突的 `CustomerVO` 与提示语塞进返回 map（`customer` + `msg`），**不抛异常**，前端弹"同税号已有客户"
- `VersionConflictException` → 包业务异常（乐观锁版本冲突）
- `LockFailedException` → 取多语资源 `nccriauapbd0/0nccriauapbd00030`
- 其他 → `ExceptionUtils.wrapException`

**返回**（:205-218）：把子表 VO 重新挂回 `bill`（`SupLinkmanVO` / `CustbankVO` / `SupCountryTaxesVO` / `SupFinanceVO` / `SupStockVO`），
`ExtBillCardOperator(pageCode).toCard(bill, ...)` 转回卡片。

### 7.3 建版本 —— `createSupplierVersion:2377`
按 `iscustomer` 是否 false 分两条（:2382-2385）：
- `false` → `createSimpleSupplierVersion:2388`
- 否则 → `createCustSupVersion:2417`（多处理客户与关系表版本）

两条共有的骨架：`lockSourcePKs` → `BDVersionValidationUtil.validateSuperVO` →
`retrieveVO` 取旧值（取不到抛 `Custsupversion-00003`）→ `createVersionValidateVO` →
`getNewVersionData` → `insertSupplierVersionVO` 插 `bd_supplier_v` → 回写 `pk_supplier_v` →
`dbUpdateVO` 更新主表 → 同步结构 → `notifyVersionChangeWhenDataUpdated` →
`fireAfterUpdateEvent` → `synchronizeSupplierInfoVersionForInsert` → **`updateSupplierLatesetFlag` 换 latest 标志** →
写业务日志 `"createversion"`。

`updateSupplierLatesetFlag`（:2286 起）的三条 SQL 是理解版本机制的钥匙：
```sql
UPDATE bd_supplier_v        SET latest=?, enddate=? WHERE pk_supplier=? AND version=?
UPDATE bd_cust_supplier_v   SET latest=?, enddate=? WHERE pk_cust_sup=? AND supversion=?
UPDATE bd_cust_supplier     SET pk_cust_sup_v=?, supversion=?, begindate=? WHERE pk_cust_sup=?
```

## 9. 校验框架（三个层级，别混）

**第一层：卡片校验**——`SaveSupplierBaseInfoAction.validate:228-234`，硬编码三个校验器 + 一个服务：

```java
validators.add(new SupplierItemsValidator());        // 邮编必须 \d{6}
validators.add(new SupplierRepeatValidator());        // 联系人 pk_linkman 不能重复（status!=3 的）
validators.add(new SupplierSetfreecustValidator());   // ← 空实现，validate() 直接 return null
SupplierValidationService validateService = new SupplierValidationService();
validateService.setValidators(validators);
```

`SupplierValidationService`（17 行）构造函数里**又加两个**：

```java
this.addValidator(new SupplierNotNullValidator());    // code/name/pk_supplierclass/pk_country/pk_timezone/
                                                      // pk_format/supprop(+supprop=1 时必须 pk_financeorg)/
                                                      // pk_group/pk_org/联系人的 pk_linkman
this.addValidator(new SupplierUniqueValidator());     // ← 空实现，validate() 直接 return null
```

> **两个空校验器**（`SupplierUniqueValidator`、`SupplierSetfreecustValidator`）是历史残留，
> 唯一性实际上由下面第二层的 `BDUniqueRuleValidate` 与元数据配置管。**别以为这里在查重。**

**第二层：框架校验**——`SupplierBaseInfoImpl` 继承并覆写：

| 方法 | 位置 | 内容 |
| --- | --- | --- |
