# BIP 旗舰版 · 业务模型（业务对象）查询手册 —— 按实体核对字段

> 实测：2026-10-12，国投集团 `erpbip.sdic.com.cn`，旗舰版，租户 `bgq1ldsj`（`U8C3`），账号 `yhtmanager`。
> 关联：[[../元数据浏览器地址]]（元数据工具页地址）、[[../转换规则找不到字段的解决方案]]（字段放不出来时）、[[../旗舰版新建业务对象手动执行SQL建表]]、[[../报表SQL/07-经验-语义模型报表开发]]。

**一句话**

- **别问菜单叫什么，认服务码**：`BusinessObjectDesigner` 这个 `serviceCode` 从 V3R6 之前到现在**没变过**；菜单名一直在换（业务对象 ↔ 业务模型管理 ↔ 对象建模）。
- **核对字段两条路**：① 门户里进「对象建模」，搜到对象 → 切实体 → 看字段；② **直接调 `getEntityInfoByBOIdAndEntityId?uri=<实体URI>`**，一次拿到全量字段（含物理列名、类型、必填、引用、枚举）。**字段级核对用第 ② 条，UI 上给不了这么全。**
- **UI 点不动就调接口**；**接口名猜不到就读它自己的前端 chunk**（正则 `businessobject/[a-zA-Z0-9_]+` 一次捞 25 个）；**参数名猜不到就故意漏参数**，Spring 会把参数名报给你。

## 1. 名字为什么对不上（先统一口径）

同一套东西在不同版本、不同部署形态下叫法不同，**这是"搜不到"的最主要原因**：

| 叫法 | 出现场景 | 出处 |
|---|---|---|
| **业务对象** | V3R6 **之前** | 使用者确认（2026-10-12） |
| **业务模型管理** | V3R6 **之后** | 使用者确认（2026-10-12） |
| **业务对象** | **私有云**版本菜单名 | [[../转换规则找不到字段的解决方案]] |
| **对象建模** | 二级菜单名（国投环境实测） | 本会话实测：`数字化建模 > 系统管理 > 对象建模` |
| **BusinessObjectDesigner** | **服务码，恒定不变** | 本会话实测，`fullText/suggest` 返回 |

> ✅ **结论**：写脚本、查接口、找入口，认服务码 `BusinessObjectDesigner`；跟人沟通时，先问一句是哪个版本、公有云还是私有云，再决定说哪个名字。
>
> 另外有个"像但不同"的东西：**元数据设计器**（`iuap-metadata-designer`）是容器和宿主，业务模型只是跑在它里面的一个服务。同一个宿主里还有「关系模型」「表单管理」等（见国投环境三级菜单）。

## 2. 入口一：门户菜单（手工走）

```text
数字化建模 > 系统管理 > 对象建模        （国投环境，V3R6 之前 → 菜单名显示「业务对象」）
```

进页面后：

1. 左侧是按**领域**分的树（`div#obj-tree` / `myObjTree`），节点是 `数字化建模 / 财务会计 / 生产制造 / 采购服务公共 / 供应商管理 / …`。
2. 顶部搜索框写着 **「支持全局搜索：业务对象编码/名称，实体编码/名称/URI」**，右侧有搜索图标（`i[fieldid="metadata_object_index_btn_search"]`）。**输入后必须点这个图标**——实测输入和回车都不触发请求。
3. 列表表头：`编码 / 名称 / URI / 系统标识 / 状态 / 描述 / 标签`。
4. 要核字段，**切到「实体」页签**，找实体再点进去看属性。

> ⚠️ **实测踩到的坑（别浪费时间）**
>
> - **菜单项在收起的抽屉里**：DOM 里有 `业务对象` 这个 `span`，`getBoundingClientRect()` 出来是 **x = −575**（视口左边外面）。用坐标点它必然打空，`elementFromPoint` 也取不到。**别用"DOM 里存在"判断入口可用**。
> - **列表空不代表没数据**：切换页签后可能停留在「实体」标签，搜业务对象名自然「暂时没有数据哦~」。
> - **URL 不跟着变**：走门户打开是**内部页签**，`location.href` 始终是 `https://<host>/#/`。**不要用 URL 判断进没进去**。
> - **直接改 `location.hash` 打不开**：把 `fullText/suggest` 返回的 `url` 直接赋给 `location.hash`，hash 确实变了，但页面纹丝不动、也不发任何请求（实测）。门户的服务是由 tns SDK 打开的，**必须走门户点击**。

## 5. 核心：查询接口组

前缀 **`/iuap-metadata-base/metadata-designer/businessobject/`**（注意：**不是** `iuap-metadata-designer`，那是前端静态资源；`iuap-metadata-base` 才是服务）。

| 接口 | 方法 | 关键参数 | 给什么 |
|---|---|---|---|
| `search` | GET | `key=<中文名/编码>` | 业务对象清单 |
| `getEntityListByBOId` | GET | **`businessObjectCode=`** | 该对象下的**实体**（uri / 实体名 / **物理表名** / 术语） |
| `getEntityInfoByBOIdAndEntityId` | GET | **`uri=<实体URI>`** | **实体完整定义 + 字段清单**（52KB 级） |
| `getDomainTree` | POST | — | 领域 → 应用树 |
| `queryRuleList` | GET | `isSystem=false&scope=bo` | 该对象支持哪些规则场景（打印/编码规则/审批流…） |
| `getLitByAppCode` | GET | `appCode` | 按应用列业务对象 |
| `getAppsWithBusinessObjs` | GET | — | 带业务对象的应用 |
| `getServiceCodeTree` / `getServiceCodesByAppCode` | GET | — | 服务码树 / 按应用取服务码 |
| `getMetaTree` / `getDomainSyStemTree` | GET | — | 其他元数据树 |
| `getSensitive` / `getCharacterEntity` / `getcharactergroup` | GET | — | 敏感字段 / 特征相关 |
| `check` / `save` / `update` / `delete` / `addBo` / `sort` / `cleanCacheByBOId` | — | — | **写操作**，核对字段用不到，慎用 |

**`search?key=订单` 实测返回**（25717 字符）：

```jsonc
{"data":[
  {"code":"umall.cityexpressorder","domain":"umall","id":"2318384949640560832",
   "metaComponentUri":"um.orders","name":"同城配送订单","order":null,"description":null},
  {"code":"InBoundCostDetail","domain":"yonbip-fi-epcmweb","id":"2134778671254210835",
   "metaComponentUri":"EPCM.stdcost","name":"订单入库标准成本明细", …}
]}
```

**`getEntityListByBOId?businessObjectCode=umall.cityexpressorder` 实测返回**：

```jsonc
{"data":{
  "entities":[{
    "businessObjectId":"2318384949640563928","displayName":"同城配送订单",
    "name":"CityExpressOrder","uri":"um.orders.CityExpressOrder",
    "oriTableName":"city_express_order","tableName":"city_express_order",
    "tableType":"DB_TABLE","type":"trivial","isSystem":true,"status":"4","version":6,
    "terms":[{"code":"BusinessData","name":"交易数据"}]}],
  "serviceCodes":[…], "rules":[…], "services":[…]
}}
```

**`getEntityInfoByBOIdAndEntityId?uri=um.orders.CityExpressOrder` 实测返回**（52861 字符）：

顶层键：`id / name / uri / displayName / tableName / schema / domain / businessObjectId / metaComponentId / description / isExtend / ownedAttribute / terms / constraints / isSystem / businessProperties / businessSuperProperties / children / createTime / modifyTime / creator / modifyer / businessObjectCode / businessObjectName / mul_language / mul_language_resid`

实测值：`displayName=同城配送订单`、`tableName=city_express_order`、`schema=upmalls`、`domain=umall`、`isSystem=true`、**`businessProperties` 34 个字段**。

> ⚠️ **参数名和接口名对不上，别按字面猜**：
> - `getEntityListByBOId` 名字里是 BOId，实际参数是 **`businessObjectCode`**（传 `id` 会抛异常）。
> - `getEntityInfoByBOIdAndEntityId` 名字里是 BOId + EntityId，实际参数只有 **`uri`**（实测报 `Required request parameter 'uri' for method parameter type String is not present`）。
> - `getBOInfo` 存在，参数是 `businessObjectCode`，但实测用 `umall.cityexpressorder` 查会**返回 500**（后端 `BizObjServiceImpl.getBizObjByCode:178` 抛异常）。**要对象详情优先走 `search` + `getEntityListByBOId`**。

## 6. 复制即用：在浏览器 Console 里核对字段

在**任意已登录的 erpbip 页面**按 F12，粘这段（用的是页面自己的登录态，不需要 token）：

```js
const BASE = '/iuap-metadata-base/metadata-designer/businessobject/';
const q = async (u, opt) => (await fetch(u, { credentials: 'include', ...opt })).json();

// ① 按中文名/编码搜业务对象
const bos = (await q(BASE + 'search?key=' + encodeURIComponent('订单'))).data;
console.log(bos.map(b => `${b.code}  ${b.name}  [${b.domain}]`));

// ② 看这个对象下有哪些实体（拿到物理表名）
const ents = (await q(BASE + 'getEntityListByBOId?businessObjectCode=' + bos[0].code)).data.entities;
console.table(ents.map(e => ({ 实体: e.name, 中文: e.displayName, URI: e.uri, 物理表: e.tableName })));

// ③ 拿某个实体的全量字段 —— 核对字段就靠这一步
const ent = (await q(BASE + 'getEntityInfoByBOIdAndEntityId?uri=' + encodeURIComponent(ents[0].uri))).data;
console.log(ent.displayName, ent.schema + '.' + ent.tableName, ent.businessProperties.length + ' 个字段');
console.table(ent.businessProperties.map(p => ({
  属性: p.name, 中文名: p.displayName, 物理列: p.fieldName,
  业务类型: p.biztype, 基础类型: p.dataType && p.dataType.uri,
  必填: p.isRequired,
  引用到: (p.biztype === 'quote' && p.dataType) ? p.dataType.uri : '',
  场景: (p.rules || []).join('+'),
  系统属性: p.sysProp, 术语: (p.termCodes || []).join(',')
})));
```

## 7. 核对字段：到底要核对什么

第 ③ 步每个字段会给这些键（实测样本）：

```jsonc
{"name":"abnormalDesc","displayName":"运单异常原因描述","fieldName":"abnormalDesc",
 "uri":"um.orders.CityExpressOrder.abnormalDesc","biztype":"text_MDD",
 "dataType":{"uri":"String","metaType":"PrimitiveType"},
 "isRequired":false,"refType":null,"enumType":null,   // ⚠️ 引用/枚举别信这两个键，实测恒为 null，见下表
 "terms":[],"termCodes":[],"sysProp":true,
 "mul_language":{"zh_CN":{"displayName":"运单异常原因描述"}},
 "characterFields":[],"characterSuperProperties":[]}
```

**四组对照，逐项落实：**

| 要核对的 | 看哪个键 | 实测注意点 |
|---|---|---|
| **中文名对不对** | `displayName`；多语言再看 `mul_language.zh_CN.displayName` | 两者可能不同；`mul_language_resid` 指向多语资源 ID |
| **物理列名对不对** | `fieldName`（列）+ 实体的 `tableName` / `schema` | 实体的 `oriTableName` 与 `tableName` 可能不一致，**以 `tableName` 为准** |
| **类型对不对** | `biztype`（业务类型，如 `text_MDD`、`long`、`timestamp`）**和** `dataType.uri`（基础类型，如 `String`/`Long`/`Date`） | **两个都不是数据库列类型**，别拿去跟 `varchar(50)` 直接比；要真列类型就 `datasource_query` 查 `information_schema` |
| **必填** | `isRequired` | 业务约束，数据库里看不出来（实测销售订单主表 192 个字段里只有 1 个必填） |
| **引用到哪个对象** | ⚠️ **不是 `refType`**（实测恒为 `null`）—— 看 **`biztype === 'quote'`**，目标实体在 **`dataType.uri`** 上（`dataType.metaType === 'Class'`） | 实测 `"biztype":"quote"` + `"dataType":{"name":"User","uri":"base.user.User","metaType":"Class"}` |
| **枚举 / 选项** | `enumType`（可能为空）；选项类字段改看 `biztype` 是不是 `singleOption_int` / `OptionCT` / `FreeCT` | 实测销售订单主表的 `enumType` **全空**，选项信息不在这里 |
| **是不是系统字段** | ⚠️ `sysProp` **不是"系统字段"的意思，它是"标准产品预置"** | 实测销售订单主表 192 个字段里 **191 个 `sysProp=true`**，连 `vouchdate`（单据日期）、`code`（编码）都是 true。靠它分不出原厂/客开 |
| **字段放不放得出来** | **`rules` 数组**，如 `["workflow","report"]` | 实测主表：`workflow+report` 161 个、**空 30 个**、`FieldAuth+workflow+DataAuth+report` 1 个。`rules` 里没有 `workflow`，业务流/转换规则里就找不到它，见 [[../转换规则找不到字段的解决方案]] |

**和手上工具的配合：**

| 途径 | 覆盖 | 前提 | 什么时候用 |
|---|---|---|---|
| `bip_meta_find` / `bip_meta_detail` | 随包快照，**只有 8 个实体** | 离线 | 快速看平台预置实体；**查不到不代表没有** |
| `wiki_lookup` / `wiki_read` | 自己知识库记录过的 | 需要先有页面 | 复用已核过的结论 |
| **本文档的接口** | **实时、全量**（国投环境几千个业务对象） | 浏览器登着系统 | **核对具体环境的具体字段，只有这条给得出真答案** |
| `datasource_query` | 真实物理表结构 | 有登记的数据源 | 核**数据库列类型/长度**，与业务类型互补 |

> 🧭 **典型配合**：先用本文档接口拿到 `uri` + `tableName` + `fieldName` + 业务类型，再用 `datasource_query` 查真实列类型，两边一摆，字段口径就闭合了。
> 反过来也成立：**遇到一个不认识的物理表，先用 `search?key=<表名或中文名>` 反查它是哪个业务对象的哪个实体。**

## 8. 通用手法：接口名和参数名怎么挖出来

这招**不限业务对象，任何 BIP 模块都能用**。

### 8.1 接口名 —— 读它自己的前端 chunk

UI 上点不动、又猜不到接口时，直接读 JS：

```js
// ① 先问浏览器这个页面加载了哪些 JS
performance.getEntriesByType('resource').map(e => e.name)
  .filter(n => /metadata-designer/.test(n))
// → /iuap-metadata-designer/ucf-wh/20250529-164917/simple/js/chunk/873.1748508307095.js …

// ② 抓下来正则捞接口名
const t = await (await fetch('/iuap-metadata-designer/ucf-wh/20250529-164917/simple/js/chunk/873.1748508307095.js')).text();
[...new Set(t.match(/businessobject\/[a-zA-Z0-9_]+/g))]
// 一次命中 25 个：search / getDomainTree / getEntityListByBOId /
// getEntityInfoByBOIdAndEntityId / getBOInfo / getLitByAppCode / save / delete / addBo / …
```

> 💡 服务方法在压缩代码里长这样，能直接读出**方法名 + 路径 + 参数对象名**：
> ```js
> e.getBusinessobject = function(e){ return (0,t.get)(o + "/businessobject/getLitByAppCode", e) }
> e.saveBusinessobject = function(e){ return (0,t.post)(o + "/businessobject/save", e) }
> ```
> ⚠️ chunk 是**按需加载**的：显式找的接口可能在另一个 chunk 里。先 `performance` 列全，再逐个捞。

### 8.2 参数名 —— 故意漏掉，让后端告诉你

```http
GET …/getBOInfo
→ {"code":"500","errorMsg":"…Required request parameter 'businessObjectCode' for method parameter type String is not present"}

GET …/getEntityInfoByBOIdAndEntityId
→ {"code":"500","errorMsg":"…Required request parameter 'uri' for method parameter type String is not present"}
```

**比翻文档快得多。** 而且失败时返回的**异常栈会连后端类名行号一起带出来**：

```
com.yonyou.iuap.metadata.designer.domain.service.impl.BizObjServiceImpl.getBizObjByIdWithSys(BizObjServiceImpl.java:152)
com.yonyou.iuap.metadata.designer.domain.service.impl.BizObjServiceImpl.getBizObjByCode(BizObjServiceImpl.java:178)
```

—— 连"这个接口在服务端叫什么、走哪个 ServiceImpl"都知道了。

## 9. 已知坑（本会话实测，别重踩）

1. **别拿菜单名当唯一线索**。版本/部署不同名字就变（§1）。**认服务码 `BusinessObjectDesigner`。**
2. **`bip_meta_*` 查不到 ≠ 不存在**。那是随包快照（8 个实体），和具体环境无关。查具体环境的东西走本文档的接口。
3. **不要用 URL 判断页面进没进去**。门户内部页签 `location.href` 恒为 `https://<host>/#/`。
4. **不要直接改 hash 跳服务**。实测无效（hash 变了、页面不动、无请求），必须走门户点击（tns SDK）。
5. **DOM 里存在 ≠ 点得到**。菜单项可能在收起的抽屉里（实测 `x = −575`）。点之前先看 `getBoundingClientRect()`。
6. **搜索框输入/回车不触发**。必须点搜索图标（`i[fieldid="metadata_object_index_btn_search"]`）。
7. **别信接口名字里的参数名**。`getEntityListByBOId` 要的是 `businessObjectCode`，`getEntityInfoByBOIdAndEntityId` 要的是 `uri`。
8. **`biztype` / `dataType` 不是数据库类型**。要真实列类型去查库。
9. **实体诊断工具（`viewEntity.html`）本会话没驱动成功**（§4），要用先手工确认一次。
10. ⚠️ **引用关系不在 `refType` 上**。实测销售订单主表 32 个引用字段的 `refType` **全部为 null**，真正的目标是 `biztype === 'quote'` + `dataType.uri`（`metaType = "Class"`）。照 `refType` 找引用会一个都找不到。
11. ⚠️ **`sysProp: true` 不代表"系统字段"**，它是"标准产品预置"。实测销售订单主表 192 个字段里 191 个为 true，业务字段（`vouchdate`、`code`）也算。
12. ⚠️ **`getEntityListByBOId` 只返回主实体**。实测 `udinghuo.voucher_order` 只给出 `voucher.order.Order` 一个，而它实际有 **6 个实体、合计 602 个字段**（另有订单详情 312 / 自定义项特征 47 / 发票 20 / 收货地址 18 / Erp 13）。子实体要**从主表引用字段的 `dataType.uri` 反查**，或拿猜的 URI 直接调 `getEntityInfoByBOIdAndEntityId` 探。
13. ⚠️ **`fieldName` 可能是 `null`**。实测销售订单主表的 `status`（单据状态）、`auditor`、`tplid`、`priceDate`、`verifystate` 等都没有物理列 —— **派生/计算字段不落库**，别去数据库里找。
14. ⚠️ **`name` 和 `fieldName` 可能完全对不上**。实测：`code → cOrderNo`、`pubts → pubuts`（多一个 u）、**`creatorId → iSubmiterId`**（创建人映射到"提交人"列）、`shop → iShopID`。**永远以 `fieldName` 为准，别按 `name` 猜列名。**
