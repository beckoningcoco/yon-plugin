# 旗舰版业务规则测试经验

> 基于出库申请审核推送 MES 规则的完整测试过程总结，适用于所有 `IYpdCommonRul` 实现的业务规则场景。

## 一、测试流程总览

```
理解规则代码 → 分析字段文档 → 查数据库找测试数据
     ↓
构建镜像测试环境（Controller + test 方法）
     ↓
迭代修复（字段路径 → 值缺失 → 格式不对 → 翻译遗漏）
     ↓
Arthas 深入排查（params 结构、BizObject 数据）
     ↓
重构优化（数据源、批量查询）
     ↓
对照文档验收 → 输出测试报告
```

## 二、规则参数：怎么获取业务数据

### 2.1 两个参数

```java
public Object execute(RulCtxVO rulCtxVO, Map<String, Object> params)
```

| 参数 | 类型 | 来源 | 怎么用 |
|------|------|------|--------|
| `rulCtxVO` | `RulCtxVO` | 平台构建 | 4 个方法：`getBillnum()` / `getFullname()` / `getAction()` / `getDomain()` |
| `params` | `Map<String, Object>` | 平台传入 | 直接传给 `CommonRuleUtils.getBills()` |

### 2.2 标准取值范式

```java
// 1. 构建上下文（固定套路）
BillContext billContext = new BillContext(
    rulCtxVO.getBillnum(),    // "po_picking_requisition" — 表短名
    rulCtxVO.getFullname()    // "st.pickingrequisition.PickingRequisition" — 实体URI
);
billContext.setAction(rulCtxVO.getAction());  // "audit" / "unaudit"
billContext.setDomain(rulCtxVO.getDomain());  // "drzb" — 可为 null

// 2. 获取单据 BizObject（固定套路）
List<BizObject> bills = CommonRuleUtils.getBills(billContext, params);
BizObject bill = bills.get(0);
String billId = bill.getString("id");
```

> **关键认知**：`billnum` ≠ `fullname`。`billnum` 是表短名，`fullname` 是实体 URI 全名。ORM 查询用 `fullname`。

### 2.3 CommonRuleUtils 内部做了什么

```
params.get("param") → BillDataDto → dto.getData()
    ├─ List<Map>（首次）→ Objectlizer.convert → List<BizObject>
    ├─ List<BizObject>（缓存命中）→ 直接返回
    └─ String(JSON) → Objectlizer.decode
```

**核心优化**：首次解析后写回 `dto.setData(bills)`，同一请求链后续规则零开销复用。

## 四、镜像测试环境搭建

### 4.1 为什么需要镜像

业务规则通过规则链在前台触发，无法直接 HTTP 调用。镜像 Controller 模拟规则链传参，让你可以反复调试。

### 4.2 两类镜像方案

| 方案 | 适用场景 | 复杂度 |
|------|---------|:--:|
| **简化镜像**：传 billId，规则内自己 `queryBillById` | 快速验证，字段不复杂 | 低 |
| **完整镜像**：传真实 `execute()` 参数（RulCtxVO + params） | 需要精确复现规则链行为 | 中 |

### 4.3 完整镜像 Controller 模板

```java
@RestController
@RequestMapping("/xxx/test")
public class XxxRuleTestController extends BaseController {

    @Autowired
    private XxxRule rule;

    @PostMapping("/audit")
    public JSONObject test(@RequestBody List<Map<String, Object>> request) {
        // request[0] → RulCtxVO
        Map<String, Object> ctxJson = request.get(0);
        RulCtxVO rulCtxVO = new RulCtxVO();
        rulCtxVO.setBillnum((String) ctxJson.get("billnum"));
        rulCtxVO.setFullname((String) ctxJson.get("fullname"));
        rulCtxVO.setAction((String) ctxJson.get("action"));
        rulCtxVO.setDomain((String) ctxJson.get("domain"));

        // request[1] → params
        Map<String, Object> params = request.get(1);
        // params.param 必须是 BillDataDto 实例（非 Map），否则 ClassCastException
        Map<String, Object> paramMap = (Map) params.get("param");
        BillDataDto dto = new BillDataDto();
        dto.setData((List) paramMap.get("data"));
        dto.setBillnum((String) paramMap.get("billnum"));
        dto.setAction((String) paramMap.get("action"));
        params.put("param", dto);

        rule.execute(rulCtxVO, params);
        // ...
    }
}
```

> **踩坑**：`params.param` 直接传 Map 会报 `LinkedHashMap cannot be cast to BaseDto`。必须构造真实 `BillDataDto`。

## 五、字段映射常见问题与解决

### 5.1 字段路径不对 → 查询报错

```
Can't find attribute st.pickingrequisition.PickingRequisition/creator.code
```

**原因**：`creator` 是普通字符串字段，不是引用类型，不能穿透 `.code`。

**解决**：区分字段类型——引用字段（如 `orgId`、`creatorId`）可穿透 `.code`，普通字段（如 `creator`、`remark`）不能。

### 5.2 字段不存在 → 查询报错

```
Can't find attribute .../SYR
Can't find attribute .../batchno
```

**解决**：逐字段用 Arthas 日志验证，找到正确的 entity 字段名。特征字段路径如 `requisitionDefineCharacter.SYR.code`。

### 5.3 子表字段挂主表查 → 报错

主表和子表是不同的 entity，不能在一个 QuerySchema 里混合查询。需要分离查询子表，关联字段通常是 `requisitionId` 或 `demandapply` 等。

### 5.4 DB 查询拿到审核前值

`queryBillById` 查数据库，审核那一刻数据还没落库，`auditor`/`auditTime`/`status` 还是旧值。

**解决**：用 `CommonRuleUtils.getBills()` 返回的 `BizObject` 内存值，它是规则链传入的审核后内存数据。

### 5.5 身份字段传了名称不是编码

`BizObject` 里 `creator`="陈轩宏" 是中文名，MES 要员工号。

**解决**：用 `bill.get("creatorId")` 取 ID，再批量查 `base.user.User`（用户）或 `bd.staff.StaffNew`（员工）翻译成 code。

### 5.6 BizObject 取嵌套字段

`SYR` 嵌套在 `requisitionDefineCharacter` 里，`bill.getString("SYR")` 取不到。

**解决**：先 `bill.get("requisitionDefineCharacter")` 拿到嵌套对象（可能是 Map），再从里取 `SYR`。

### 5.7 性能优化：批量翻译

5 个人员字段如果逐个 `queryRefCode`，就是 5 次 DB 查询。

**优化**：收集所有 ID，一次 `IN (...)` 批量查询，返回 `Map<id, code>`，O(1) 查表。

## 六、设计原则

### 6.1 审核/弃审用同一个 Rule 还是分开

| 方案 | 优点 | 缺点 |
|------|------|------|
| 单 Rule + action 判断 | 代码复用 | 逻辑分支多 |
| 双 Rule 各管各 | 逻辑清晰 | 代码重复 |

本项目选择**双 Rule**，审核和弃审各自的类，但 `buildRequest` 等方法可共用。

### 6.2 数据来源：DB 查询 vs BizObject

| 来源 | 优点 | 缺点 |
|------|------|------|
| `queryBillById` (DB) | 可通过 `xxx.code` 取引用编码 | 审核后字段取到审核前值 |
| `BizObject` (内存) | 审核后实时数据 | 嵌套对象需特殊处理 |

**推荐**：主表字段用 BizObject，需要引用编码的用 `batchQueryRefCode` 批量翻译。

### 6.3 校验逻辑

- 组织校验：`isOrgEnabledForMes()` — 匹配 MES 自定义档案才推送
- 交易类型过滤：仅特定 `transTypeCode` 才推送
- 不匹配时 **静默跳过**（`return RuleExecuteResult()`），不抛异常

### 6.4 ⚠️ 卡片态 vs 列表态（重要！）

业务规则的入参在**卡片页**和**列表页**传入的 `params` 结构**不一样**，必须两个场景都测试：

| 对比维度 | 卡片页 | 列表页 |
|---------|--------|--------|
| `billnum` | `po_picking_requisition` | `po_picking_requisition_list`（含 `_list` 后缀） |
| `param.data[0]` | 完整的 BizObject，含所有字段+子表 | **扁平化精简**，大量字段缺失 |
| 缺失的字段 | — | `creatorId`、`operatorId`、`remark`、`outWarehouse`、`demandWarehouse` 等 |
| 子表数据 | 嵌套完整 | 顶层扁平化（如 `requisitionDetail_id`、`product_cCode`） |
| `billMapInDbBeforeAudit` | ✅ 包含完整快照 | ✅ 同样包含完整快照 |

**解决方案**：通过 `rulCtxVO.getBillnum()` 检测是否含 `"_list"` 判断列表态，列表态下优先从 `billMapInDbBeforeAudit` 快照取值：

```java
boolean isListPage = rulCtxVO.getBillnum() != null && rulCtxVO.getBillnum().contains("_list");
// 列表态从快照兜底
Object getField(BizObject bill, Map preBill, String fieldName, boolean isListPage) {
    if (isListPage && preBill != null && preBill.containsKey(fieldName)) return preBill.get(fieldName);
    return bill.get(fieldName);
}
```

> **教训**：不要只测卡片页就认为代码没问题。列表页入参精简了大量字段，如果不做快照兜底，生产环境列表页批量操作会静默丢数据。

## 七、操作顺序建议

```
1. 先看代码，理解 execute() 流程
1.5 杜绝自己蛮干，不要盲目的干，需要什么参数，比如说表名，URI，确认某个字段的取值逻辑之类的问题，都可以问用户。
2. 用 Arthas watch 抓一次 params，理解数据结构，这个可以给用户 arthas命令，让用户提供给你结果。
3. 看字段对照文档，标注差异，验证按照文档标注字段来测试代码，需要传code （包含数字，英文的编码）就不传name（中文名称）
4. 读 CommonRuleUtils 源码（Arthas jad），理解 BizObject 转换
5. 建镜像 Controller，迭代修字段
6. 从日志看实际推送报文，与文档对照 ，本地工程日志位置在 yms-home目录下的 logs目录下 的 微服务编码（例如 c-inv-fl-eastsoft） 下的 yms-application.log
7. 修复 → 重测 → 对照，直到全部字段对齐
8. 性能优化（批量查询、DB 查询转内存）
9. 输出测试报告
```
