# 物料档案保存调用链

> 本文件是**实体档案**，按维度分节。要加新维度就**加一节**，不要重写整篇。
> 总索引：[_call-chain-archive-index.md](./_call-chain-archive-index.md)；采集口径见 [_call-chain-collection-standard.md](./_call-chain-collection-standard.md)。
> **行号与类名均来自 NCC2505 的 jar**，换版本可能漂移；类名与调用顺序比行号稳定。
> ⚠️ **物料和供应商虽然同属 `BDSingleBaseService` 家族，但持久化姿势不一样**：
> 供应商让父类 `SingleBaseService` 走通用模板，物料**自己重写了 `insertVO` / `dbInsertVO` / `updateMaterial`**。
> 做物料客开时**别照搬供应商那一套**，差异见第 11 节。

**核心类**：`nc.impl.bd.material.baseinfo.MaterialBaseInfoServiceImpl`
（`modules/uapbd/META-INF/lib/uapbd_material.jar`），
声明在 :122 —— `extends BDSingleBaseService<MaterialVO> implements IMaterialBaseInfoService`。
**构造函数 :130-132 里 `super("c7dc0ccd-8872-4eee-8882-160e8f49dfad", new String[]{"materialconvert", "materialtaxtype"})`**
—— 第一个参数是 **`mdId`**，第二个是两个子表属性名。

## 1. 什么时候读我

- 要知道**物料新增/修改/版本，代码从哪进、在哪落库**（`bd_material` + `bd_material_v` + 2 子表 + PF 表群）
- 要**改物料保存的前后逻辑**——钩子在 `insertVO:379`、`updateMaterial:394`、`deleteVO:234`
- 要**加校验**：物料有三层校验器，`getInsertValidator`（11 个）与 `getUpdateValidator`（13 个）**不是同一组**（第 9 节）
- 要**处理编码规则**：物料走 `insertWithAutoCode:737`，有**预置码 + 冲突重试 + 临时码**三段逻辑（第 7 节）
- 要**排查"物料保存慢"**：一次保存可能碰 20+ 张按管理模式分表的 PF 表（第 6 节）
- 要**挂事件监听器**：mdId `c7dc0ccd-8872-4eee-8882-160e8f49dfad`，事件码 1064/1065 + `dataperm_change`

## 4. 入口 action 的分支与前置校验

`opr` 三选一（:100-106）：

| `opr` | 方法 | 语义 |
| --- | --- | --- |
| `"save"` | `saveMaterial:115` | 正戏（再按 `status` 分增/改，见下） |
| `"copy"` | `copyMaterial:145` | 复制物料（含 `copyAssign` 是否连带分配） |
| `"create"` | `createVersion` | 建新版本 |

`saveMaterial` 内按 `head.getStatus()` 二分：

| `status` | 调用 | 前置 |
| --- | --- | --- |
| `1` | `updateMaterial(head)` :120 | — |
| `2` | `insertMaterial(head)` :134 | 先 `getBillCodeContext("material", pk_group, pk_org)`；**无 pk_material 且非预置码时先把 code 设成临时码 `"material_temp_code"`** :130-132 |

**action 层三处校验（都在 service 之前）**：

1. `MaterialConvertValidator(head)` :75 —— 转换关系（计量单位换算）校验，多条错误拼成 `BusinessException` 一次抛出
2. `MaterialMeasRateValidator(head)` :86 —— 主计量单位换算率
3. `checkBeforeUpdateMabasclass(head)` :90 —— **只在 `opr=save` 且 `isSure!=1` 且 `status==1` 时**调，
   返回非空则直接返回 `{returnMsg: 010140mag0212}`，**让前端弹确认框**，用户确认后带 `isSure=1` 重发

`outcloselowerlimit` 为空时补 `UFDouble(0)`（:95-97）—— 这是 action 层的字段兜底。

```java

    vo.setPk_material(pk_material);
    vo.setPk_source(pk_material);                                     // :548 自指向

> **物料的新增是"先插主表 → 回写 pk_source 指向自己 → 再插版本表"**，与供应商同构；
> 供应商是在 `insertSupplierVersion` 里单独做，物料封装进 `dbInsertVO`。

## 10. 事务与锁

| 机制 | 调用点 | 实际行为 |
| --- | --- | --- |
| 容器事务 | UPM 里 `MaterialBaseInfoServiceImpl` 的 `tx` 属性（未逐字核） | 同供应商，代码里无注解 |
| 独立事务方法 | `deleteMaterial_RequiresNew:984` | 命名约定 |
| 主键锁 | `updatelockOperate:596`：`lockSourcePKs(vo)` + `super.updatelockOperate` | **比供应商多一步 `lockSourcePKs`**（锁整个版本链） |
| 删除锁 | `deletelockOperate:555`：同样先 `lockSourcePKs` | — |
| 业务锁 | 建版本走 `BizlockDataUtil.lockDataByBizlock`（:165、:187） | — |
| 批量锁 | `upgradeMaterials:468` 对每组的版本链行再 lock 一次 | — |
| 乐观锁 | `BDVersionValidationUtil.validateSuperVO`（:166、:188、:239、:399、:444） | 版本不符抛 `VersionConflictException` |

> **物料新增路径里没看到 `insertlockOperate`**（父类 `insertVO:128` 会调）——
> 物料的 `insertVO:379` 走的是 `insertWithAutoCode` → `super.insertVO`，所以**父类的锁仍然生效**。

## 11. 与供应商档案的差异（客开要记住）

| 维度 | 供应商 | 物料 |
| --- | --- | --- |
| 入口 action | `uapbd.supplier.saveSupplier`，四分支（step/checkflag） | `uapbd.material.saveMaterial`，`opr` 三分（save/copy/create） |
| `insertVO` | **不重写**，直接用父类 `SingleBaseService.insertVO:123` | **重写**（:379），自建编码逻辑后再调 `super.insertVO` |
| `dbInsertVO` | 子类 :1079 覆写：主表 + 写关系表 | 子类 :545 覆写：主表 + 回写 `pk_source` + 插版本表 |
| 编码规则 | `getBillCode_RequiresNew` 在别处；主保存路径里的取号时机**当时没闭合** | **闭合**：`insertWithAutoCode:737` 里取号/预置码/`32001` 重试全在一起 |
| 版本表 DAO | 无独立 DAO，直接在 Impl 里拼 SQL | 有 `MaterialVersionDAO` 独占 `bd_material_v` |
| 校验器数量 | 插入 2 个框架 + 5 个场景校验器 | 插入 11 个 / 修改 13 个（都很大） |
| 子表 | `suplinkman` / `supbankacc` / `supcountrytaxes` / `supvat`（4 个） | `materialconvert` / `materialtaxtype`（2 个） |
| 管理模式 PF 表 | 无 | **有**，20+ 张（第 6.2 节） |
| mdId | `720dcc7c-ff19-48f4-b9c5-b90906682f45` | `c7dc0ccd-8872-4eee-8882-160e8f49dfad` |

        }
        try { vo = super.insertVO(vo); sucessed = true; }
        catch (BusinessException e) {
            if (billCodeContext != null && "32001".equals(e.getErrorCodeString())) {
                AbandonBillCode_RequiresNew("material", pk_group, pk_org, vo.getCode())           // 归还
                vo.setCode(code); continue                                                         // 重试
            }
            throw e;
        }
    }
    vo = super.insertVO(vo); sucessed = true;
}
```

要点三条：
1. **`32001` 是编码冲突的错误码**，捕获后归还原号再重试（与客户档案里看到的是同一个码）
2. **预置码走 `getPreBillCode_RequiresNew`**，插入成功后 action 之外还要 `commitPreBillCode`
   （`insertVO:388-390`：`isPrecode()` 为真才提交）
3. **临时码 `"material_temp_code"` 是 action 层先填的**（`SaveMaterialAction:130-132`），
   靠"无 pk_material 且非预置码"判定——**新增页在保存前拿不到号时用它占位**
