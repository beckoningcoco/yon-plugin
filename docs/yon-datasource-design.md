# 数据源写入工具（`datasource_upsert`）：设计记录

> 记录**为什么这样设计**，不是接口手册。接口在 `datasource-tools.ts` 的 JSDoc 里，
> 工具怎么用写在工具描述里；面板那一侧见 `yon-panel-ui-design.md`。
>
> 状态：**已实现**（P0 + P1，2026-10-12）。`datasource_remove` 与提示词文案留待后续。

## 一、要解决的问题

数据源这一族此前**只能读**：`datasource_list` 看有什么、`datasource_query` 发语句。
登记一条新连接，模型没有任何入口——要么让使用者自己去面板点，要么手工编辑
`~/.dsh/yon-panel/db_config.json`（在他的用户目录里、工作区外，先被沙箱拒绝、提权才写得进去），
而那个文件写坏了是整个列表一起坏，工具侧还看不到这件事发生过。

真实的触发场景：使用者丢来一份环境信息文件（VPN、地址、账号、密码），说「维护项目信息和数据源」。
项目字段有 `project_*` 可写，数据源却只能靠改文件。

## 二、服务层、HTTP、面板早就有写入口

要补的不是一整套功能，是一条线：

| 层 | 早已存在 |
|---|---|
| 服务 | `save(input)` / `remove(key)` / `bind(key, projectId)`，含名称、`::`、端口 1–65535、host 非空的校验，全部串行在同一条读改写队列里（`datasource-service.ts`） |
| HTTP | `PUT /yon/api/datasources/<key>`、`/binding`，与面板**同一个** `save()` |
| 工具 | 只有 `list` / `query` |

所以新增的只有一个工具定义、一道审批门，和一次项目名解析。**面板怎么存，模型就怎么存**，
两条路不会各长一套校验。

## 三、为什么只做一个 upsert

- **不做 `datasource_bind`**：绑定是连接组的属性，而且 `save()` 本来就收 `projectId`。
  单独一个绑定工具会让"新建一个连接并绑到项目"变成两次要审批的调用。
- **不做 `datasource_remove`**：删一个分支的破坏性比写高一个量级（组随最后一个分支一起消失），
  而这个动作在面板里有人看着、频率也低。留待单独一轮，配上比 upsert 更强的确认。
- 于是参数里的 `project` 传空串表示解绑、省略表示不动绑定。

## 四、patch 语义：`save()` 是"整体替换"，工具必须自己补全

`save()` 把调用方给的东西整个写进那个分支，所以一个只想改地址的调用，必须先把其余字段的
当前值补上——否则它们会被自己没提过的值覆盖。工具层因此读一次 `list()`，用同一份读算
缺省值、算 diff、判断登录名会不会被缩小。

这次顺带修掉一个真的坑：**`service_name` 原本是 `input.serviceName?.trim() ?? ''`**，
即"省略＝清空库名"。面板的表单总是显式带上这个字段，所以从没暴露；而一个 patch 语义的工具
一上来就会踩——改个地址顺手把 `service_name` 抹掉，还没有任何提示。现在改成
`undefined`＝沿用、`''`＝清空，与 `users` 一致。

登录表同样是整体替换，所以：

- 省略 `user`/`password` → 已存登录名与密码原样保留；
- 给一个登录名 → 那一分支的登录表变成这一条，**其余登录名的密码一并丢弃**。
  因此分支上已存**多个**登录名、而本次只给一个不同的名字时，工具直接拒绝，
  要求显式 `replace_logins: true`——这是唯一一处"必须说第二遍才允许"的参数。

## 五、密码的走向：只进不出

密码有两个来源：使用者当面给的，和使用者给的文件里的。它进入工具参数是不可避免的，
能守的是**出口**：

- 工具的回答里不出现密码，只有「密码将写入」/「重设登录名「X」的密码」/「原密码一并替换」；
- 审批预览里同样不出现（预览会进会话记录，等同于回答）；
- 不提供 `users` 整表参数——那等于请模型把别人的密码抄一遍，而这个工具没有任何场合需要它。

## 六、门：写连接一律停下来问

`isDestructiveWrite()` 是**同步纯函数**，读不了盘，因此分不清这次调用是新建一个分支还是
覆盖一个已存的。覆盖的代价是别人存着的密码，一次点击的代价是一次点击——所以
`datasource_upsert` 一律按 destructive 处理：

- 只读会话 → `deny`，理由与项目族一致；
- 默认 / `ask` → `ask`，审批卡上那段文字由**同一份 plan** 生成，所以"批准的就是写下去的"；
- `approval=never` → 放行（那是使用者自己选的，项目族同一规则）。

参数不可用时门**不问人**，直接放行给工具自己报错——问一个跑不起来的调用是噪音，
还会让人以为自己批准了什么。

## 七、登录名的三种文案

diff 说"某东西移动到了它原本就在的地方"读起来像 bug，所以「只重设密码」与「换登录名」分开：

| 情形 | 文案 |
|---|---|
| 分支上还没有登录名 | `登录名：U（密码将写入）` |
| 同名、只重设密码 | `重设登录名「U」的密码` |
| 换成别的名字 | `登录名：A → U（原密码一并替换）` |

第三种的并列形态（多个登录名）会先说清已存的是哪几个，再要求 `replace_logins`。

## 八、`verify`：写入与连通性是两件事

`sources.probe()` 早就在，只是没暴露给模型。`verify: true` 时写入后再跑一次
`SELECT 1`。默认关，理由是：**写入的成败与网络的成败是两件事**，
探活失败时回答必须说「写入已完成，但探活失败」，不许被读成"没写进去"——
否则调用方会重试一次写入。测试里专门钉住了这一条。

## 九、与面板的关系

同一个 `save()`、同一个文件、同一条串行队列，因此：

- 模型写进去的连接，面板刷新即见；
- 面板仍是**删除**和**多登录名管理**的地方；
- 面板的"新增"表单不再是唯一入口，仅此而已。

## 十、顺带修掉的两处既有不一致

1. **`tests/host-plugin.spec.ts` 的工具清单缺了 browser 组**：21 个 browser 工具早已注册，
   清单里却没有，于是那三个计数/顺序用例**一直红着**。补上 `YON_BROWSER_TOOL_NAMES`。
2. **`YON_BROWSER_TOOL_NAMES` 的顺序与注册顺序不一致**：这个仓库的约定是"常量顺序＝注册顺序"
   （`host-plugin.spec.ts` 用 `toEqual` 钉住它），而 browser 那份是按"调用者该伸手的顺序"写的。
   改成注册顺序，并把约定写进它的 JSDoc。

**没修、留给人判断的一处**：`src/host/prompt.ts` 的 `YON_PROMPT_TEXT`（能力分十四组的概述）
里**没有 browser 组**，只在一处注释里提到 browser 这个词。之所以长期没暴露，是因为
`prompt.spec.ts` 自己那份 `ALL_TOOL_NAMES` 也没列 browser —— 守卫看不见没被登记的东西。
给 `prompt.spec.ts` 补上 browser 会立刻变红（正确的红），但改系统提示文案不在本轮范围内，
所以只记录，不动。

## 十一、没做的

- `datasource_remove`（见 §三）；
- 把"缺省补全"从工具层抽到服务层由面板共用——面板的表单总是给全，抽了是空转；
- 提示词里 `datasource_*` 那一组的措辞（现在只写"已登记的环境数据库连接，可执行 SQL 取真实数据"，
  没提"可以登记"）。工具描述足够让模型找到它，概述可以下一轮再补。
