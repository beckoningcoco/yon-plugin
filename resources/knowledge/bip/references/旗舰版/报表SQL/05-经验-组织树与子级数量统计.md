# BIP 报表平台：组织树 + 子级数量统计（可复用手册）

> 首次落地：金隅集团「集团外部结算账户汇总表-管理口径」（2026-09）
> 环境：BIP 旗舰版 / 达梦 / 租户 `jd4ofb7k` / schema `iuap_apdoc_basedoc`
> 后续凡是「组织树 + 统计子级组织的 XX 数量」这类报表，直接照本文抄。

---

## 0. 场景与结论速览

**需求形态**：表样上「组织」列设成树形，父组织行要显示**其所有子孙组织**的汇总数（账户数、法人单位数……）。
**为什么不能用表样公式**：树的层级和节点数是动态的，公式只能逐级手工加，深一层就废。
**结论**：把「上卷」做进 SQL——用**层级展开闭包（closure）**把每个子孙组织的数据挂到它的每个祖先节点上，表样只负责显示。

| 本案例 | 语义模型 | 编码 |
|---|---|---|
| 明细/树模型（一行一个组织） | 账户汇总表_总览 | `zhanghuzongshu` |
| 合计模型（整个体系一行） | 司库账户汇总合计 | `SK_HZ_HJ` |

两个模型**必须是两段独立 SQL**，不要试图让一个 SQL 同时干两件事。

## 1. 组织树的表结构：两个 ID 空间（第一号坑）

```
iuap_apdoc_basedoc.org_epm_orginization_ext    ← 组织体系成员（树形结构在这里）
  ├─ id              ← ①「成员 ID」  2570…开头   ← 树的节点标识，parent_org_id 指向它
  ├─ parent_org_id   ← 父节点（成员 ID）
  ├─ org_id          ← 指向 org_epm_organizations.id
  ├─ org_epm_systems_id ← 组织体系 ID（一个租户可有多套组织体系）
  └─ dr / ytenant_id

iuap_apdoc_basedoc.org_epm_organizations       ← 「组织体系」里的组织档案
  ├─ id              ← ② 体系内 ID 2531…/2532…
  ├─ org_source_id   ← ★ 桥：指向真实组织档案 org_orgs.id
  └─ name / code

iuap_apdoc_basedoc.org_fin_bankacct            ← 业务数据（本例：企业资金账户）
  └─ orgid           ← ★ 真实组织档案 ID，必须 = org_epm_organizations.org_source_id
```

**铁律：**
- 树遍历用 `org_epm_orginization_ext.id` / `parent_org_id`（①空间）
- 挂业务数据只能通过 `org_epm_organizations.org_source_id → 业务表.orgid`（②→③）
- 闭包输出给上层做 join 键时，**必须输出 `e.org_id`（成员 ID ①），不是 `e.id`**。写反了行数会少一大批且不报错（本次踩过）。

`org_epm_organizations.id`（②）和 `org_epm_orginization_ext.id`（①）看起来都是雪花 ID，肉眼分不出，务必按列名走。

## 2. `innercode` 不可用

该组织体系里 `org_epm_orginization_ext.innercode` 与 UI 树**对不上**（表现为第 2 层凭空多出 37 个节点，与本例实测的 L2=37 一致，但层级归属错误）。
→ **只信 `parent_org_id`**，不要用 `innercode LIKE 'xxx%'` 那套老写法做上卷。

## 3. 上卷闭包怎么写（核心模板）

### 3.1 结构

```sql
-- ① 闭包：每个"子孙节点"→ 它的每一个"祖先节点"
( select e0.org_id as desc_org_id, e0.id as anc_member_id
    from ...org_epm_orginization_ext e0 where <体系过滤>
  union all
  select e0.org_id, e1.id from ... e0 join ... e1 on e1.id = e0.parent_org_id and <体系过滤> where <体系过滤>
  union all
  select e0.org_id, e2.id from ... e0 join e1 ... join e2 on e2.id = e1.parent_org_id ... where <体系过滤>
  ...
) cl
```

- 第 0 段 = 节点自身（`anc = desc`）
- 第 n 段 = 往上跳 n 次
- **`on eX.id = e(X-1).parent_org_id`**，这才是"向上"；反过来 `e(X-1).id = eX.parent_org_id` 是向下，写反了结果是"每个节点统计自己的子孙"，方向是对的但语义变成自下而上，务必按需求确认方向
- 每一段都要重复 `<体系过滤>`（`dr=0 and ytenant_id=… and org_epm_systems_id=…`），否则会跨体系串
- **`<体系过滤>` 必须带表别名**（`e0.dr=0 and e0.ytenant_id=…`）。用模板生成 SQL 时最易漏：第 1 段只有 `e0` 不带别名也能跑，
  第 2 段起 join 了 `e1`/`e2`…，达梦立刻报 **`[CODE:-2112] 有歧义的列名[ytenant_id]`**，而且报错位置指向语句结尾，很难定位

### 3.2 要展开几层？用实测值，别拍脑袋

本案例（金隅 组织体系 `2570581176914280457`，2026-09 实测）：

| 项 | 值 |
|---|---|
| 成员总数 | **629** |
| 根节点 | `2570584346600144897`（金隅集团股份有限公司，code `18000000`），全体系唯一 |
| 最大深度（根=0） | **6** |
| 每层节点数 | L0=1，L1=12，L2=37，L3=226，L4=314，L5=36，L6=3 |

→ **闭包写 `e0..e6` 共 7 段就够**。本次交付版多写了一层（e0..e7），无害但没必要。
换组织体系时，先跑一次同样的深度统计再定层数（现成脚本：`05-附件-金隅账户汇总表/组织树深度统计.py`，改一下 `org_epm_systems_id` 即可）。

### 3.3 两层聚合，防 fan-out（第二号坑）

闭包展开后一个业务行会对应多个祖先，**必须先按节点聚合，再 join 回主表**，且每张派生表都要**聚到 `node_id` 唯一一行**：

```sql
left join (
    select node_id,
           count(acct_code) as accountCount,
           sum(case when purpose_code='D01' then 1 else 0 end) as cnt_d01,
           ... 
      from ( select cl.anc_member_id as node_id, acc.acct_code,
                    max(acc.purpose_code) as purpose_code
               from <闭包> cl
               join <组织体系组织> o2 on o2.id = cl.desc_org_id
               join <业务子查询> acc on acc.orgid = o2.org_source_id
              group by cl.anc_member_id, acc.acct_code ) t
     group by node_id ) x on x.node_id = e.id
```

**绝对不要**把两张各自一对多的派生表（如"账户表"和"法人标记表"）都直接 LEFT JOIN 到同一个基表上——会乘出笛卡尔积，数字虚高且不报错。
指标之间如果要互不影响，就各自独立成一段派生表（本例 `x` 账户数、`y` 法人数，互不干扰）。

## 4. 「合计模型」的坑：去重，不能求和

同一个账户可能挂在多个组织下（跨 org 重复）。全体系合计**必须去重**，不能把树模型的行相加：

| 算法 | 本案例结果 |
|---|---|
| 树模型各行 accountCount 朴素相加 | 1381 ❌ |
| `count(distinct 账户编码)` 去重 | **343** ✅ |

合计 SQL 的写法（完整实现见附件 `合计-全体系去重.sql`）：用 `union all` 拼两段互斥的口径（`'A'` 账户维度 / `'O'` 组织维度），外层再一次 `sum(case when kind=… and flag=… then 1 else 0 end)` 出各列：

```sql
select '全部单位合计' as "name",
       sum(case when u.kind='A' then 1 else 0 end) as "accountCount",
       sum(case when u.kind='A' and u.flag='D01' then 1 else 0 end) as "基本存款账户",
       sum(case when u.kind='O' and u.flag='1' then 1 else 0 end) as "法人公司数量",
       ...
from ( <账户维度：按账户编码 group by，取每条的最大用途> 
       union all
       <组织维度：按组织 group by，取是否法人> ) u
```

- 账户维度：`group by 账户编码` 后再 `max(用途编码)`，实现"一个账户只算一次"
- 组织维度：`group by 组织` 后再 `max(是否法人)`，实现"组织只算一次"
- 因此**合计模型的账户数 ≤ 树模型根节点的账户数**？不一定相等——根节点也可能因同一账户挂在根下多个组织而重复计数。要相等就得两边都用同一套去重口径，本例两者**故意不做相等**（合计=343 是全体系去重）。

## 5. 报表平台参数规范（写进语义模型 SQL）

```sql
-- 租户：系统变量，不带单引号、不用 param
and a.ytenant_id = ${var('tenantId')}

-- 自定义参数：正文里用 ${param('编码')}，不加单引号，不用 TO_DATE/STR_TO_DATE/CAST 包
<#if param('accountOpenStartDate')?? && param('accountOpenStartDate') != ''>
and a.accountOpenDate >= ${param('accountOpenStartDate')}
<#else>
and a.accountOpenDate >= '1997-01-01'
</#if>
```

**四条硬规则：**
1. `${param('xxx')}` **不加单引号**——平台渲染时替换值自带引号（平台校验的替换表就是 `'2024-12-31'` 这种形态），再套一层会变成 `''值''`。
2. **不用 TO_DATE/STR_TO_DATE/CAST 包参数**。
3. 自定义参数**必须**用 `<#if>` 包裹，判断必须是 `?? && != ''` **双重**，只写 `??` 的话用户传空串仍会过滤。
4. 租户是**系统变量** `${var('tenantId')}`，不是自定义参数。

**FreeMarker 位置规则（报错过一次）**：
- **标签内部**（`<#if …>`、`<#else>`、`<#assign>`）已在表达式模式 → 写 `param('xxx')`，**不能**写 `${param('xxx')}`
- **SQL 正文**（静态文本）→ 必须写 `${param('xxx')}`

写错会报：`You can't use ${...} (an interpolation) here as you are already in FreeMarker-expression-mode.`

**`<#else>` 兜底默认值的注意点**：平台校验脚本剥 `<#if>` 时**保留 if 分支、丢弃 else 分支**（平台校验脚本的既有行为），所以默认值那支平台校验覆盖不到，要自己在库上单独跑一次确认。

**纯 SQL 兜底（不引 Freemarker 时）**：`nvl(nullif(${param('xxx')}, ''), '1997-01-01')`。但这条依赖"平台未传参时渲染成带引号的空串"这一未证实前提，且违反规范的"自定义参数必须 `<#if>` 包裹"，优先用 `<#if>/<#else>`。

## 6. 一个筛选器给多个语义模型赋值（配置层）

报表设计器里，筛选器控件（本案例：`开始日期`/`结束日期`，筛选器类型=日期）右侧属性 → **「参数绑定」弹窗**，里面两个页签：

- **赋值参数** —— 把本控件的值赋给语义模型的参数。是一张**可增行**的表：`序号 | 参数 | 来源类型 | 值`
- **接收参数** —— 接收其它控件联动过来的值

**做法：一行绑一个语义模型的参数。** 两个模型有几个参数就加几行，`参数` 下拉里能同时看到两个模型的参数名——所以一个筛选器**可以**同时给多个语义模型赋值。

**关键：`参数` 必须逐字等于该语义模型里定义的参数编码。** 本例两个模型的参数编码本来就不同：

| | 树模型 `zhanghuzongshu` | 合计模型 `SK_HZ_HJ` |
|---|---|---|
| 租户 | `ytenant_id` | `ytenantid` |
| 开始日期 | `accountOpenStartDate_t` | `accountOpenStartDate` |
| 结束日期 | `accountOpenEndDate_t` | `accountOpenEndDate` |
| 组织体系 | `org_epm_systems_id_t` | `org_epm_systems_id` |

→ **不要为了"能绑一个"去把两个模型的参数编码改成一样**（客户试过，不行）；照着各自原有编码分别绑两行。
→ 同时提醒：**两个模型 SQL 里的 `${param(...)}` 也得各写各的名字**，一边写错就取不到值，表现为"参数是空"。

**未证实**：平台的匹配键到底是"参数编码全局唯一"还是"参数编码+所属模型"；（客户反馈改成同名也不行，暗示是后者，但无文档依据）；`_t` 后缀是平台生成还是手工加的。

## 7. 达梦（DM）上的实测结论

| 写法 | 结果 |
|---|---|
| `current_date` / `now()` / `curdate()` | ✅ |
| `to_char(current_date,'YYYY-MM-DD')` | ✅ |
| `cast(current_date as char)` | ❌ `[CODE:-6149] 数据类型转换失败` |
| DATETIME 列 与 字符串字面量比较（`a.dt <= '2026-09-22'`） | ✅（DM 会隐式转） |
| DATETIME 列 与 `to_char(current_date,…)` 比较 | ✅ |
| `nvl(nullif(<字符串>,''),'1997-01-01')` | ✅ |
| 参数以 datetime 绑定进 `nvl(nullif(?,''),…)` | ✅ |

`org_fin_bankacct.accountOpenDate` 实际类型是 **DATETIME**（不是 DATE），本案例 137 条有值的行**全部是 00:00:00 整点**，所以 `<= 'yyyy-mm-dd'` 不需要补 `23:59:59`，`<= current_date` 与 `<= to_char(current_date,…)` 结果一致。

**未证实**：客户报表上出现 `DateType mismatch`，DM 侧上述写法全部复现不出，怀疑是平台自己解析/改写 SQL 时的类型推导（混类型 `nvl(DATETIME列, VARCHAR)` 之类）拒绝，**无证据，待平台侧日志确认**。

## 8. 枚举取值以环境为准，别信文档

`org_fin_bankacct.acctopentype` / `acctstatus` 这类枚举，知识库里两份 API 文档说法互相矛盾且**都与实际数据对不上**。
→ 一律查环境自己的 `iuap_apdoc_basedoc.aa_enum`（`enumtype` / `enumcode` / `enumname` / `enumindex`）。

本案例实测：
- `enumtype='bd_accountOpenType'`：0=银行开户，1=结算中心开户，**2=财务公司**，3=其他金融机构，4=现金开户，5=数币钱包
- `enumtype='bd_accountStatus'`：0=正常，**1=已销户**，2=冻结
- 交叉验证：`acctstatus=1` ⟺ 有 `accountClosureDate`（9/9 命中）

排除条件写 `nvl(列,默认) <> 值` 而不是 `列 <> 值`：NULL 行会被保留而不是被静默丢掉（本例实测当前无 NULL，两者等价，但将来有 NULL 时行为不同）。

## 9. 交付前自检清单

- [ ] 闭包每段都带全体系过滤（`dr` / `ytenant_id` / `org_epm_systems_id`）
- [ ] 闭包输出的是 `e.org_id`（成员 ID），join 业务表走 `org_source_id`
- [ ] 每张派生表已聚到 `node_id` 唯一一行，没有两张一对多表并列 LEFT JOIN 到同一基表
- [ ] **单调性检查**：逐行比对父子，反常的定义是 **`child > parent`**（子比父大），不是 `child < parent`
- [ ] 用独立实现（Python 递归/DFS）逐节点复算一遍，与 SQL 输出对拍（现成脚本：`05-附件-金隅账户汇总表/校验-DFS逐节点对拍.py`；本例 0/629 不一致）
- [ ] 合计模型用去重口径，不拿树模型行相加
- [ ] 参数用 `<#if>…<#else>` + `${param('编码')}`，编码与语义模型里逐字一致
- [ ] 枚举值来自 `aa_enum`
- [ ] 交付后在**前台**打开报表核对数字，别只看 SQL 跑通
