# 知识库能力：设计记录

> 这份文档记录的是**为什么这样设计**，不是接口手册。接口在各模块的 JSDoc 里，
> 工具的用法在工具描述里。数据源面板的设计另见 `yon-datasource-panel-设计方案.md`。

## 一、这个能力要解决的问题

它不是一个"顺手加的查询功能"。它是**填补三块被排除的能力留下的洞**。

前一阶段的清点里，`yonyou-bip-dev` 和 `yon-ncc-dev` 技能带着这些资产：

| 资产 | 体积 | 处置 | 留下的洞 |
|---|---|---|---|
| `ncc数据字典/NCC2111/` | 24 MB / 7753 文件 | 排除（后续单独开发） | 写 SQL 前查不到表结构 |
| `class_index_*.json` | 187 MB | 排除（本机重建） | 查不到类在哪个 jar |
| `wiki/entities/` 引用、`bip_metadata_query.py` | — | 排除（数据字段相关） | 查不到实体对应的物理表 |
| `references/` 参考文档 | 2.9 MB | **迁移进包** | 内联的技能正文没有路径可解析 |

前三项指向同一件事：**写用友的 SQL 或代码时，落不到具体的表名、列名、类名上**。

而使用者的机器上，恰好有一个已经积累了很久的答案：`D:\yon-bip-obsidian\` 下那两套
Obsidian vault —— **5435 个实体页**，每页都有 `物理表`、`domain/服务域` 和字段映射表。
所以知识库能力不是新建一套，而是**把已有的知识接进来**。

## 二、vault 是什么，不是什么

**vault 是目录，Obsidian 只是可能的查看器。** 插件不依赖 Obsidian 安装或运行，读写的就是
markdown 文件。这一点决定了整个设计可以很轻：没有 API、没有服务、没有进程间协议。

**vault 的布局读自它自己的 `.wiki-schema.md`**，而不是硬编码。原因很实际：两套 vault 的
约定不一致 —— `yon-bip-obsidian` 用 `wiki/entities`，`yon-ncc-obsidian` 初始化时用了
`wiki/实体`。只认英文会让第二套静默查不到任何东西，而"查不到"和"没有"在界面上长得一样。

所以 `entityDirOf()` 依次尝试 `wiki/entities`、`wiki/实体`、`entities`、`实体`。

## 三、索引：为什么落在 vault 里

`wiki/.yon-index.json`，写在 vault 内部，不是插件的数据目录。

理由：**vault 是可移动的数据单元**。使用者把整个目录拷到另一台机器、或者并存到 git 上，
索引跟着走，省一次重建。它是派生文件，所以属于 vault 的 `.gitignore`。

实测：**5374 个实体页，约 3 秒**建完。够快，所以策略是"缺了才建、要新就显式重建"，
而不是每次调用都检查新鲜度 —— 5400 个文件的 mtime 检查比重建本身还贵，而且"内容改了但
mtime 没变"这种情况它照样漏。

索引里每条记录是解析出来的五个事实：URI、物理表、domain、平台版本、验证状态。
**验证状态一定要带出去**：vault 是手工维护、长期积累的，有的页面在真实环境验证过，
有的只是从文档提取的。返回时不说清哪个是哪个，就是在安静地误导。

## 四、四路匹配

`wiki_lookup` 接受模型手上**实际有的**那种名字，因为真实场景给的不是 URI：

| 模型手上有什么 | 来自哪里 |
|---|---|
| `voucher.order.Order` | 一行代码 |
| `ucg_baseapi_api_info` | 一条报错信息 |
| `PaybillLinkImpl` | 一段堆栈 |
| 「销售订单」 | 一句需求 |

排序是**先穷尽精确匹配，再考虑包含匹配** —— 否则查 `voucher.order.Order` 时，
`voucher.order.OrderDetail` 会和它并列。返回里带 `matchedBy`，让模型自己区分
"精确命中"和"只是恰好包含"。

## 五、重复页面的取舍（方案 B）

接手时 vault 里有 **17 组重复 URI**，每组两份页面，而且**内容全不相同**：
14 组是两套生成器（英文模板 `## All Fields (143)` vs 中文模板 `## 字段列表（按类型分组）`），
3 组是自动生成 vs 人工增强。

处理方式是**保留一份作为正式实体页，另一份移入 `wiki/sources/`**，并在移出页的
frontmatter 加 `snapshot_of` 指回正式页。

**代价要说清楚**：两份页面的章节几乎零重叠 —— 英文快照独有 `## Key/Code/Name`、
`## Suppliers`（接口清单）、`## Child Tables`；中文正式页独有 `## 继承接口`、
`## 关联引用`。移出后，`entities/` 里就没有 `## Suppliers` 这类信息了，只在 `sources/` 可查。

换到的是：**URI 恢复唯一**（5374 文件 = 5374 个唯一 URI，重复组 0），于是
`wiki_lookup` 不会再对一个查询返回两套互相矛盾的字段列表。

这是一个明确的权衡，不是无代价的整理。若日后发现某些独有章节重要，可以把它们逐组合并
回正式页 —— 那属于方案 (a)，随时可以做，不影响已完成的结构修复。

## 六、类索引：为什么一行字节码都不解压

`resources/knowledge/ncc/scripts/build_index.py` 原本能做这件事，但它有两个问题：
输出路径相对**自身位置**（也就是旧技能目录结构），而它的 BIP 分支指向一个已经不存在的
兄弟目录。改它意味着动一个"存在意义就是当可读原件"的文件。

所以改为纯 Node 实现，而且**不解压任何东西**：

> jar 是 zip。zip 的末尾有 End Of Central Directory 记录，指向中央目录，
> 而中央目录列出了每个条目的名字。类索引只需要名字。

于是每个 jar 只读**两小块**（尾部 + 中央目录），而不是把几十 GB 字节码解压出来再全丢掉。
实测 3 个真 jar / 3991 个类 / 0.3 MB 索引 / **不到 1 秒**。原脚本走 `zipfile` 全解压，
同样目录会慢一个量级。

**索引落在 `~/.dsh/yon-panel/knowledge/`，绝不写进安装目录** —— 它是几十 MB 的派生物，
而包目录在安装后可能是只读的。

## 七、两套知识，不要混

| | `resources/knowledge/` | Obsidian vault |
|---|---|---|
| 归属 | 随包，每台机器相同 | 使用者自己的，持续生长 |
| 工具 | `knowledge_search` / `knowledge_read` | `wiki_lookup` / `wiki_read` |
| 回答什么问题 | "平台是怎么表现的"、"这个错什么意思" | "这个实体的物理表是什么" |
| 可否写 | 只读 | 目前也只读（写入是后续、需单独门禁的事） |

分开的理由：把固定的库和生长的库混成一个，"这条知识是官方的还是我上次随手记的"
就分不清了。

## 八、技能正文里的路径

迁移进包的技能正文原样写着 `references/GBK文件编辑.md` 这类相对路径，而**内联的技能正文
没有路径可解析** —— 文件到了，路没到。

试过让工具侧兼容相对路径，**否决了**：`references/common/coding-standard.md` 在
`ncc-dev` 和 `ncc-plugin-dev` 下**各有一份**，同一路径对应两篇文档，只能报歧义 ——
等于把问题推给模型，比现状更糟。

最终做法是**迁移时改写成库内完整路径**（`ncc/ncc-dev/references/common/coding-standard.md`），
每个技能有一个由「vault + 迁移源目录」决定的固定基准。跨技能引用单独处理
（`` `<某技能>` skill 的 `references/x.md` `` 归属被提到的那个技能），否则
`ncc-background-task` 里指向 `ncc-dev` 的文档会被改错。

复验结果：**54 个路径真实存在、5 个已标注「待建」或「未随包提供」、0 个未解释的不存在**。

那 5 个里有 3 个是原作者标了「待建」的；另 2 个（`ncc-coding-patterns.md`、
`project-ztxx.md`）是**原技能的疏漏** —— 引用了 `scenarios/` 下并不存在的文件，也没标注。
迁移时给它们补上了「未随包提供」：让模型看到一个确定的"没有"，好过走一条必然失败的路。

## 九、门禁

| 工具 | 门禁 |
|---|---|
| `wiki_*`、`knowledge_*`、`ncc_class_search` | 无（只读） |
| `knowledge_build_index` | 无 —— 只写插件自己的数据目录 |
| `ncc_gbk_edit` 的 `edits` / `convert` | **审批** |
| `ncc_gbk_edit` 的 `read` / `grep` / `dryRun` | 无 |

`knowledge_build_index` 刻意不设门禁：它不动使用者的任何东西，而**给无害操作加门禁，
只会训练出"不看就批准"的习惯** —— 那正是门禁最负担不起的。它另有提示：`presentCall`
里写明"会扫描整个安装目录"。

## 十、打包

`files` 里的 `resources/**/*` 曾经把迁移脚本留下的 2322 个 `.bak-<时间戳>`（46 MB）
一并打进包。备份逻辑来自 `apply-datasource-panel.mjs` 的做法，但那个脚本要跑很多次
（每改一条迁移规则就得重跑），于是攒了起来。

处理：删掉备份、`apply.mjs` 不再产生（**回滚走 git**）、`.npmignore` 兜底拒绝该模式。

`npm pack` 现在：**525 文件 / 4.1 MB 压缩 / 10.4 MB 解压 / 无备份**。
