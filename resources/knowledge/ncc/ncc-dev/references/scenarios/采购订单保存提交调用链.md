## 4. 【核心】两阶段执行：`saveCommit` 的两趟引擎

`SCMPubSaveCommitServiceImpl#saveCommit:77-135`（最内层重载，其余 7 个重载都是逐级转调它）：

```java
public SCMScriptResultDTO saveCommit(AbstractBill[] bills, PfUserObject pfUserObject, Class clazz,
        String save, String commit, String billtype, UFBoolean isSCC,
        ISSClientageMatchService.BusiUnitTypeEnum busiUnitTypeEnum, String[] actionnames,
        Map eParam, IIgnoreNextActionCheck check) {
    ClientBillCombinServer utils = new ClientBillCombinServer();
    IBatchRunScriptService service = NCLocator.lookup(IBatchRunScriptService.class);
    SCMCloudPFlowContext context = new SCMCloudPFlowContext();      // ★ 子树类型，支持 actionNames 数组
    context.setBillType(billtype);
    PfUserObject userObject = new PfUserObject();
    userObject.setUserObject(pfUserObject);                          // ★ 又套一层 PfUserObject
    context.seteParam(eParam);
    context.setUserObj(new PfUserObject[]{userObject});
    context.setBillVos(bills);
    context.setActionName(save);                                     // ★★ 第一趟：save
    Object[] objects = service.run(context, clazz);                   // ── 引擎第 1 次
    this.filterDeleteBodyData(bills);
    utils.combine(bills, (AbstractBill[])objects);                    // 保存结果合并回界面 VO
    if (bills instanceof AbstractBill[] && check != null && check.isIgnore(bills[0])) {
        SCMScriptResultDTO dto = new SCMScriptResultDTO();            // ★ 提前返回：只保存，不提交
        dto.setSucessVOs(bills);
        return dto;
    }
    if (objects instanceof AbstractBill[]) {                          // 保存成功才继续
        context.setBillVos(bills);                                    // ★★ 显式重置 billVos
        if (SysInitGroupQuery.isCREDITEnabled() && SOBillType.Invoice.getCode().equals(billtype))
            BSContext.getInstance().setSession("InvoiceSaveAndCommitFlag", UFBoolean.TRUE);   // 信用+发票的标记
        if (isSCC.booleanValue()) {
            String[] actionNames = PfServiceScmForSSC.getFlowStartActionNames(bills, busiUnitTypeEnum);
            context.setActionNames(actionNames);                      // ★ 逐张动作名
            context.setActionName(actionNames[0]);
        } else {
            context.setActionName(commit);                            // ★★ 第二趟：commit
        }
        Object[] ret = actionnames == null ? service.run(context, clazz)
                                           : service.run(context, clazz, actionnames);
        if (SysInitGroupQuery.isCREDITEnabled() && SOBillType.Invoice.getCode().equals(billtype))
            BSContext.getInstance().removeSession("InvoiceSaveAndCommitFlag");
        if (ArrayUtil.isEmpty(ret)) return null;
        if (ret instanceof AbstractBill[]) {                          // 提交也成功
            // ... isfromCT / REVISE 两个特殊分支 → utils.combine(bills, ret) → 返回 dto
            return dto;
        }
        Object obj = ret[0];
        Object result = CommitAssignUtils.handleCommitAssignResult(obj, false);
        throw new SaveAndCommitException(result);                     // ★★ 第二趟失败 → 特殊异常带回现场
    }
    return null;
}
```

**六个要点**：

| # | 要点 | 为什么重要 |
| --- | --- | --- |
| 1 | **两趟 `service.run`，动作名不同** | "保存提交"不是原子操作，是**同一引擎跑两遍**：第一遍 `save`、第二遍 `commit` |
| 2 | **`SCMCloudPFlowContext`（不是 `CloudPFlowContext`）** | 它是子类型，多一个 `actionNames` 数组——**这正是第 8 份 `processSingleBill` 里那个"逐张取 actionName"分支的来源** |
| 3 | **`:97` 显式重置 `context.setBillVos(bills)`** | 第二趟提交用的 VO 是**界面 VO 被第一趟合并后**的状态，不是引擎返回的对象。少了这一行，提交会拿到脏数据 |
| 4 | **`IIgnoreNextActionCheck`**（`:91`） | 可在提交前**提前返回**（只保存不提交）。SCC/特殊场景用 |
| 5 | **`SaveAndCommitException`**（`:132`） | **提交失败时抛这个异常把现场对象带回**，而不是普通报错——入口 catch 里要专门认它 |
| 6 | **`isSCC` 分支**（`:101`） | SCC（供应链协同）场景动作名**逐张**由 `PfServiceScmForSSC.getFlowStartActionNames` 决定，不走固定的 `commit` |

## 5. `SaveAndCommitException`：为什么"报错了但单据存下来了"

入口层对它的处理（销售订单保存入口 `SaleOrderSaveAction:95-98`，采购侧同类）：

```java
catch (Exception e) {
    Throwable ee = ExceptionUtils.unmarsh(e);
    if (ee instanceof SaveAndCommitException) {
        Object object = ((SaveAndCommitException)ee).getObject();
        return object;                 // ★ 不报错，把对象原样返回
    }
    return PfResumeExceptionNccUtils.handleResumeException(e);
}
```

**含义**：**保存成功、提交失败**时，平台抛 `SaveAndCommitException` 并携带现场对象；
入口把它**当成一种"结果"返回**（而不是异常）——前端因此能拿到"已保存但未提交"的单据状态继续操作。

> 所以「保存提交报了个错，但去列表一看单据已经在」**是设计行为，不是 bug**。
> 反过来，若排查"为什么没提交成功"，要找的是 `SaveAndCommitException` 携带的那个对象与当时的错误，不是普通堆栈。

## 6. 销售 vs 采购：同一层的逐字对照（本档案的验证价值）

| | 销售订单保存提交 | 采购订单保存提交 |
| --- | --- | --- |
| 入口类 | `SaleOrderSaveCommitAction`（`uiso_nccloud.jar`） | `OrderSaveCommit`（`uipu_nccloud.jar`） |
| 服务接口 | `ISCMPubSaveCommitService` | **同一个** |
| 实现类 | `SCMPubSaveCommitServiceImpl` | **同一个** |
| 调用行 | `saveCommit(vo, userObj, SaleOrderVO.class, `**`"WRITE"`**`, `**`"SAVE"`**`, SOBillType.Order.getCode())` | `saveCommit(vos, pfUserObject, OrderVO.class, `**`"SAVEBASE"`**`, `**`"SAVE"`**`, POBillType.Order.getCode())` |
| `save` 动作名 | **`"WRITE"`** | **`"SAVEBASE"`** |
| `commit` 动作名 | `"SAVE"` | `"SAVE"` |
| billType | `"30"` | `"21"` |

**结论**：
1. `commit` 侧两单**都是 `"SAVE"`**——因为第二阶段语义统一是"送审/提交"，沿用第 8 份验过的 `SAVE`→`APPROVE` 改写。
2. `save` 侧两单**不同**（`WRITE` / `SAVEBASE`）——印证第 9 份的提醒：**动作名不能跨单据类推**。
3. **第 8 份的 `hasFlow` 改写机制在这里通用**：两趟都进 `IBatchRunScriptService`（`run` / `runBacth` 共用
   `processSingleBill`），所以第二趟的 `"SAVE"` 同样会被改写成 `"APPROVE"`（无审批流时）或保持 `"SAVE"`（有审批流时），
   再去 `pub_actionconstrict` 里按 `actiontype` 取业务类。

**`IBatchRunScriptService` 的两个入口（别混）**：

| 方法 | 用在哪 | 谁定动作名 |
| --- | --- | --- |
| `runBacth(context, clazz[, actionnames])` | 单独保存（第 9 份）、单独提交/收回（第 8 份） | 内部 `processSingleBill` 按 `hasFlow` 改写 |
| `run(context, clazz[, actionnames])` | **`saveCommit` 的两趟** | 调用方**显式**传 `save` / `commit` 两个动作名，再经同一改写 |

两者最终都到 `ICloudScriptPFlowService` → `CloudPfUtil` → `IplatFormEntry` → `PFBusiAction`（见第 9 份第 5 节的 UPM 反查与动作驱动表）。

## 7. 表落点

保存提交**不新增表**；落点与采购订单保存相同（`po_order` 主/子，**本档案未从 VO 核实**），
外加**两张动作配置表**（决定两趟各跑哪些业务类）：

| 表 | 作用 |
| --- | --- |
| `pub_actionconstrict` | 按 `(pk_billtype, actiontype)` 定位要跑的动作行；`actiontype` = **`"SAVEBASE"`（第一趟）** 与 **`"SAVE"`→可能被改写**（第二趟） |
| `pub_function` | `classname` + `methodname` = 真正的业务类 |

> **连库验证"采购订单保存提交到底跑了两批什么类"**：
> ```sql
> select c.actiontype, c.sysindex, c.isbefore, f.classname, f.methodname, c.conditionXpression
>   from pub_actionconstrict c join pub_function f on c.functionid = f.pk_function
>  where c.pk_billtype = '21' and c.actiontype in ('SAVEBASE','SAVE','APPROVE')
>  order by c.actiontype, c.sysindex;
> ```
> **预期能看到两批**（`SAVEBASE` 一批 = 保存阶段，`SAVE`/`APPROVE` 一批 = 提交阶段）——
> 这正是"两阶段"在数据上的投影。**本机无 NCC2505 连接，未实测。**

### 未覆盖项的详情

- **事务边界（⬜，本档案最重要的未决项）**：`saveCommit` 里两趟 `service.run` 是**两次独立调用**，
  第一趟的结果先 `utils.combine` 合并进界面 VO，第二趟再跑。**两者是否包在同一事务里，未验。**
  从"提交失败要专门抛 `SaveAndCommitException` 把现场带回"这个设计**反推**，更像是**保存阶段已落库、提交阶段独立**——
  但这是推断，**不能当结论**。要证需：读 `AbstractOrderSaveAction` / UPM 的 `tx` 属性，或实测（保存提交时故意让提交失败，看数据在不在）。
- **`po_order` 未核实（⬜）**：与第 9 份同一个缺口，两处都应一并补。
- **`AbstractOrderSaveAction`（⬜）**：三个入口的共同父类，模板方法、权限、可能的事务注解都在这里，**未展开**——
  这是把本份与第 9 份的"入口层职责"说清的最后一环。
- **`SCMCloudPFlowContext.actionNames` 的消费端（⬜ 半验）**：第 8 份已读 `processSingleBill` 里的
  `((SCMCloudPFlowContext)context).getActionNames()` 分支与本份 `setActionNames` 的生产端对上了，
  但**下标与单据的对应关系**（第 i 张用 actionNames[i]）只从长度判断过，未在数据上验。
- **`dealPseudoColumn` / `dealChildVOLengthChanged`（⬜）**：伪列与子表长度变化的对齐，只在 `isfromCT` / `REVISE` 分支触发。
- **权限与审计的完整链（⬜）**：入口有审计场景串、无权限检查；与第 8 份（入口就有 `checkPermission`）不一致，

- **业务处理器清单（⬜）**：需连库（第 7 节的 SQL 已给，含预期结果）。
