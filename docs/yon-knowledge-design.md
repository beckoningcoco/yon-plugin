# 知识库能力：设计记录

> 这份文档记录的是**为什么这样设计**，不是接口手册。接口在各模块的 JSDoc 里，
> 工具的用法在工具描述里。数据源面板的设计另见 `yon-datasource-panel-设计方案.md`。

## 一、这个能力要解决的问题

它不是一个"顺手加的查询功能"。它是**填补三块被排除的能力留下的洞**。

前一阶段的清点里，`yonyou-bip-dev` 和 `yon-ncc-dev` 技能带着这些资产：

| 资产 | 体积 | 处置 | 留下的洞 |
|---|---|---|---|
| `ncc数据字典/NCC2111/` | 24 MB / 7753 文件 | 排除（后续单独开发） | 写 SQL 前查不到表结构 |
| `class_index_*.json` | 187 MB | 排除（本机重建） | 查不到类在哪个 jar |
| `wiki/entities/` 引用、`bip_metadata_query.py` | — | 排除（数据字段相关） | 查不到实体对应的物理表 |
| `references/` 参考文档 | 2.9 MB | **迁移进包** | 内联的技能正文没有路径可解析 |

前三项指向同一件事：**写用友的 SQL 或代码时，落不到具体的表名、列名、类名上**。

而使用者的机器上，恰好有一个已经积累了很久的答案：`D:\yon-bip-obsidian\` 下那两套
Obsidian vault —— **5435 个实体页**，每页都有 `物理表`、`domain/服务域` 和字段映射表。
所以知识库能力不是新建一套，而是**把已有的知识接进来**。

## 二、vault 是什么，不是什么

**vault 是目录，Obsidian 只是可能的查看器。** 插件不依赖 Obsidian 安装或运行，读写的就是
markdown 文件。这一点决定了整个设计可以很轻：没有 API、没有服务、没有进程间协议。

**vault 的布局读自它自己的 `.wiki-schema.md`**，而不是硬编码。原因很实际：两套 vault 的
约定不一致 —— `yon-bip-obsidian` 用 `wiki/entities`，`yon-ncc-obsidian` 初始化时用了
`wiki/实体`。只认英文会让第二套静默查不到任何东西，而"查不到"和"没有"在界面上长得一样。

所以 `entityDirOf()` 依次尝试 `wiki/entities`、`wiki/实体`、`entities`、`实体`。

## 三、索引：为什么落在 vault 里

`wiki/.yon-index.json`，写在 vault 内部，不是插件的数据目录。

理由：**vault 是可移动的数据单元**。使用者把整个目录拷到另一台机器、或者并存到 git 上，
索引跟着走，省一次重建。它是派生文件，所以属于 vault 的 `.gitignore`。

实测：**5374 个实体页，约 3 秒**建完。够快，所以策略是"缺了才建、要新就显式重建"，
而不是每次调用都检查新鲜度 —— 5400 个文件的 mtime 检查比重建本身还贵，而且"内容改了但
mtime 没变"这种情况它照样漏。

索引里每条记录是解析出来的五个事实：URI、物理表、domain、平台版本、验证状态。
**验证状态一定要带出去**：vault 是手工维护、长期积累的，有的页面在真实环境验证过，
有的只是从文档提取的。返回时不说清哪个是哪个，就是在安静地误导。

## 四、四路匹配

`wiki_lookup` 接受模型手上**实际有的**那种名字，因为真实场景给的不是 URI：

| 模型手上有什么 | 来自哪里 |
|---|---|
| `voucher.order.Order` | 一行代码 |
| `ucg_baseapi_api_info` | 一条报错信息 |
| `PaybillLinkImpl` | 一段堆栈 |
| 「销售订单」 | 一句需求 |

排序是**先穷尽精确匹配，再考虑包含匹配** —— 否则查 `voucher.order.Order` 时，
`voucher.order.OrderDetail` 会和它并列。返回里带 `matchedBy`，让模型自己区分
"精确命中"和"只是恰好包含"。

## 五、重复页面的取舍（方案 B）

接手时 vault 里有 **17 组重复 URI**，每组两份页面，而且**内容全不相同**：
14 组是两套生成器（英文模板 `## All Fields (143)` vs 中文模板 `## 字段列表（按类型分组）`），
3 组是自动生成 vs 人工增强。

处理方式是**保留一份作为正式实体页，另一份移入 `wiki/sources/`**，并在移出页的
frontmatter 加 `snapshot_of` 指回正式页。

**代价要说清楚**：两份页面的章节几乎零重叠 —— 英文快照独有 `## Key/Code/Name`、
`## Suppliers`（接口清单）、`## Child Tables`；中文正式页独有 `## 继承接口`、
`## 关联引用`。移出后，`entities/` 里就没有 `## Suppliers` 这类信息了，只在 `sources/` 可查。

换到的是：**URI 恢复唯一**（5374 文件 = 5374 个唯一 URI，重复组 0），于是
`wiki_lookup` 不会再对一个查询返回两套互相矛盾的字段列表。

这是一个明确的权衡，不是无代价的整理。若日后发现某些独有章节重要，可以把它们逐组合并
回正式页 —— 那属于方案 (a)，随时可以做，不影响已完成的结构修复。

## 六、类索引：为什么一行字节码都不解压

`resources/knowledge/ncc/scripts/build_index.py` 原本能做这件事，但它有两个问题：
输出路径相对**自身位置**（也就是旧技能目录结构），而它的 BIP 分支指向一个已经不存在的
兄弟目录。改它意味着动一个"存在意义就是当可读原件"的文件。

所以改为纯 Node 实现，而且**不解压任何东西**：

> jar 是 zip。zip 的末尾有 End Of Central Directory 记录，指向中央目录，
> 而中央目录列出了每个条目的名字。类索引只需要名字。

于是每个 jar 只读**两小块**（尾部 + 中央目录），而不是把几十 GB 字节码解压出来再全丢掉。
实测 3 个真 jar / 3991 个类 / 0.3 MB 索引 / **不到 1 秒**。原脚本走 `zipfile` 全解压，
同样目录会慢一个量级。

**走查还会读散装的 `.class` 与 `.java`**（没有 jar 的模块靠这个才被索引到，见
`yon-home-design.md` §十三），但读的是**文件名字**，内容一个字节都不打开 —— 而且这些文件
本来就躺在目录列表里，比拆 jar 还便宜。所以"不解压任何东西"这条不变量没变。

**索引落在 `~/.dsh/yon-panel/knowledge/`，绝不写进安装目录** —— 它是几十 MB 的派生物，
而包目录在安装后可能是只读的。

## 七、两套知识，不要混

| | `resources/knowledge/` | Obsidian vault |
|---|---|---|
| 归属 | 随包，每台机器相同 | 使用者自己的，持续生长 |
| 工具 | `knowledge_search` / `knowledge_read` | `wiki_lookup` / `wiki_read` |
| 回答什么问题 | "平台是怎么表现的"、"这个错什么意思" | "这个实体的物理表是什么" |
| 可否写 | 只读 | 目前也只读（写入是后续、需单独门禁的事） |

分开的理由：把固定的库和生长的库混成一个，"这条知识是官方的还是我上次随手记的"
就分不清了。

## 八、技能正文里的路径

迁移进包的技能正文原样写着 `references/GBK文件编辑.md` 这类相对路径，而**内联的技能正文
没有路径可解析** —— 文件到了，路没到。

试过让工具侧兼容相对路径，**否决了**：`references/common/coding-standard.md` 在
`ncc-dev` 和 `ncc-plugin-dev` 下**各有一份**，同一路径对应两篇文档，只能报歧义 ——
等于把问题推给模型，比现状更糟。

最终做法是**迁移时改写成库内完整路径**（`ncc/ncc-dev/references/common/coding-standard.md`），
每个技能有一个由「vault + 迁移源目录」决定的固定基准。跨技能引用单独处理
（`` `<某技能>` skill 的 `references/x.md` `` 归属被提到的那个技能），否则
`ncc-background-task` 里指向 `ncc-dev` 的文档会被改错。

复验结果：**54 个路径真实存在、5 个已标注「待建」或「未随包提供」、0 个未解释的不存在**。

那 5 个里有 3 个是原作者标了「待建」的；另 2 个（`ncc-coding-patterns.md`、
`project-ztxx.md`）是**原技能的疏漏** —— 引用了 `scenarios/` 下并不存在的文件，也没标注。
迁移时给它们补上了「未随包提供」：让模型看到一个确定的"没有"，好过走一条必然失败的路。

## 九、门禁

| 工具 | 门禁 |
|---|---|
| `wiki_*`、`knowledge_*`、`ncc_class_search` | 无（只读） |
| `knowledge_build_index` | 无 —— 只写插件自己的数据目录 |
| `ncc_gbk_edit` 的 `edits` / `convert` | **审批** |
| `ncc_gbk_edit` 的 `read` / `grep` / `dryRun` | 无 |

`knowledge_build_index` 刻意不设门禁：它不动使用者的任何东西，而**给无害操作加门禁，
只会训练出"不看就批准"的习惯** —— 那正是门禁最负担不起的。它另有提示：`presentCall`
里写明"会扫描整个安装目录"。

## 十、关系与缺口：把已经存在的东西读出来

一个我自己的错误值得记下来，因为它改变了这一节的方向。

第一遍测量得出「99.6% 的页面是孤岛」——5374 页里只有 20 页有 `[[wikilink]]`。这个数字是错的，
而且错在方法：**这个知识库根本不用 wikilink 表达关系**，它用表格。`关联属性` 每行给一个
`目标实体`，`子表` 给子实体 URI，`继承接口` 给接口 URI，英文页面的 `Reference Fields` /
`Child Tables` 同理。把这些读出来，真实连通度是：

| | 页数 | 占比 |
|---|---|---|
| 有出链 | 5025 | 93.5% |
| 有入链 | 4246 | 79.0% |
| 真正孤立 | 193 | 3.6% |

出边 52580 条，其中 29528 条能落到具体页面。枢纽是 `yht.tenant.YhtTenant`（被 2380 页引用）、
`base.user.User`（557）、`org.func.BaseOrg`（383）。

**"没有链接"是测量的性质，不是 vault 的性质。** 所以这里不往页面里回写链接：派生出来的图可以
随时重算，5374 个被改写的页面不能撤销。

### 表头驱动，不猜列号

引用列的位置每种章节都不一样——`关联属性` 在第 4 列，`子表` 在第 2 列，`依赖接口` 在第 3 列，
`Child Tables` 又在第 4 列。但**它们都写出了列名**：`URI`、`typeUri`、`目标实体`、`引用类型`。
认表头而不是数列线，一次覆盖了全部 44 种「章节 × 表头」组合，包括只在一页上出现的那种。

### 两种互斥格式，重叠为零

4992 页用中文标题，382 页用英文标题，**没有一页同时用两种**。同一个信息在不同批次里叫不同名字：

| 信息 | 中文 | 英文 |
|---|---|---|
| 物理表 | `\| 物理表 \|` | `\| tableName \|` |
| 字段清单 | `## 直接属性（30个）` | `## All Fields (30)` |
| 加引言的字段清单 | `## 字段列表（按类型分组）` + `> 共 26 个直连字段` | —— |
| 父子关系 | `## 子表` | `## Child Tables` |
| 外键 | `## 关联属性` | `## Reference Fields` |

我在这一点上**连错三次**，每次都是"发现一种新格式 → 补一条规则"。第三次之后改成先把 945 个
原始标题归一化成 40 个族全部列出来，再设计读取规则。教训是：面对一份生成出来的语料，别猜它的
结构，先把它列完。`tests/wiki-graph.spec.ts` 里每个用例都同时覆盖两种格式，就是为了不再犯第四次。

### 分级，不评分

页面被判为三级，每级对应一个明确的能力：**可写查询**（有表名也有字段清单）、**可定位**（有表名
没字段清单）、**仅概念**（连表名都没有）。

不做 0–100 的总分，理由有三：分数是假精确；看到一个 73 分不知道下一步做什么；而且**权重依用途
而变**——写 SQL 的人不关心 `业务场景`，读需求的人不关心字段清单，一个总分必然对一半用户是错的。
分级还顺带给出"缺什么才能升到下一级"，那才是可行动的。

### 缺口有两个来源

- **静态**（从数据直接算）：页面引用了但知识库里没有页面的实体，23052 条边、2840 个实体。
  前几名是 `ucfbase.ucfbaseItf.IYTenant`(1566)、`base.itf.ITenant`(929)、
  `bip-usercenter.bip_user_ref`(818)——**都是平台基础接口**，不是业务实体。所以这份清单要读，
  不能当待办列表直接执行：它区分不了"该建页"和"本就不该建页"。
- **动态**（`~/.dsh/yon-panel/wiki-usage.jsonl`）：查了但没结果的词。这是唯一由真实需求产生的
  信号，因为它记录的是**有人真的要过**，而不是页面之间的互相引用。

日志是 JSON Lines，只追加不重写：追加不需要读-改-写，两次调用并发不会互相覆盖，写到一半崩了
只丢一行。记录是尽力而为的——**查询绝不能因为日志写不进去而失败**。

### 关系视图不丢解析不了的引用

`relationsOf` 最初把"指向不存在页面"的引用直接丢进 `unresolved`，结果 {hred_hrcandidate} 的 45 条
子表关系全部消失，页面被显示成几乎没有关系。这是错的：一个页面声称有 45 张子表，它就是有 45 张
子表，不管 vault 有没有给它们建页。改成出边保留全部、无法解析的另报计数与样本。

## 十一、消化验收：怎么知道一份消化做到了位

前面十节讲的是「怎么把知识取出来」。这一节讲的是**怎么知道取全了没有**。

起因是一次实测。vault 里躺着一份 1.1 KB 的摘要，frontmatter 写着
`confidence: EXTRACTED`（声称从原文抽取），正文列了「数据模型 / 业务逻辑 / API 服务 /
事件处理 / 安全权限 / 扩展机制」六大核心部分——**而文档真实的六章是「基本概念 /
技术架构 / UI 元数据驱动引擎 / 开发环境搭建 / 单据基本开发 / RESTful 接口」，没有一条
对得上**。那是照标题想象出来的，`DAO`、`VO/DO 转换` 这些词文档里一个字都没有。

**在文件列表里，它和一份合格产物长得一模一样。** 这就是「靠自觉消化」的失效模式：
不是做得少，而是**做没做都看不出来**。

### 七项指标

每一项都必须能被脚本算出来，不能是形容词：

| # | 指标 | 阈值 | 备注 |
|---|---|---|---|
| 1 | 结构完整 | frontmatter 必填字段齐全 | 实测 7 份旧 PDF 产物**全部不合格**（缺 `last_verified`/`status`） |
| 2 | 知识点覆盖 | 术语 / 标识符 / 章节 ≥ 85%，二级章节 ≥ 60% | 分四类算 |
| 3 | 保真率 | ≥ 98%，且逐条报出处 | 防幻觉；样本 < 20 时只报不比 |
| 4 | 溯源密度 | 带页码的小节 ≥ 50% | PDF 独有优势，丢了可惜 |
| 5 | 体积 | 1%–60% 之外只提示 | **不作判据** |
| 6 | 重叠门禁 | ≤ 85% | **消化前**就该跑 |
| 7 | 可寻址 | 抽样 20 个术语命中 ≥ 70% | 终端检验 |

**第 5 条为什么不作判据**：字节比衡量不了「全不全」。7 MB 的 PDF 抽出来只有
1.7 MB 文本（每页中位 627 字符），再扣掉 1846 次重复页眉、目录、版权页，真实信息量
还要小。用字节比当判据，会逼着人往产物里灌水。

### 阈值与模式抽到配置文件

`~/.dsh/yon-panel/digest_config.json`，逐层合并（只写想改的字段，不必抄一遍默认值）。
九个分组：阈值、体积区间、章节模式、术语参数、标识符参数、页码模式、约束句模式、
必填字段、vault 扫描范围。

**参数必须能改**，因为七项指标的**设计**与文档无关，而它们的**参数**高度依赖文档类型：

- 章节号写死成「1–2 位数字」，换成 `Part 3` 或纯 `###` 的文档就一条都认不出
- 页码引用写死成 `（pN）`，网页素材没有页码，这一项会永远 0%

### 检查器是被反例打出来的

第一版跑出来的三句话，每一句都错：

| 报告 | 真相 |
|---|---|
| 「产物只有 0 个标识符」 | 正则不认连字符，`UCF-MDD` 整个漏掉，`UCF` 又被 3 字母下限滤掉 |
| 第 1–2 章「什么都没覆盖」 | 那两章的知识主体是中文术语，而当时只按英文标识符算覆盖率 |
| 编造的摘要「保真 100%」 | 它只有 5 个标识符，分母太小，比例失效 |

修完这三处，又陆续修了四处：n-gram 把 `版权`/`文件` 当术语、拼接多个产物后才剥
frontmatter（只有第一份被剥掉）、批注里的更正建议被当成幻觉、wikilink 里的页面名被
当成标识符。

**所以标准不是写出来的，是被反例打出来的。** 拿它验新类型的素材时，大概率还要再修
几处——第一次验中文技术文档时的七处修正，全来自具体失败。

### 它验证不了什么

**只能验证「覆盖」与「保真」，验证不了「正确」。** 实测例：产物逐字照录了原文的
`pub_ref.bauth` 取值「1:不受，0:受」——保真率给它满分，可那个取值反直觉，原文自己
可能就写反了。正确性只有对照真实环境一条路。

**还有一处已知漏网**：纯英文单词形态的臆造（`DAO`、`Service`、`Controller`）不成
「标识符形态」，逃过保真检查。旧摘要编的那几个词就是这么漏掉的。

## 十二、打包

`files` 里的 `resources/**/*` 曾经把迁移脚本留下的 2322 个 `.bak-<时间戳>`（46 MB）
一并打进包。备份逻辑来自 `apply-datasource-panel.mjs` 的做法，但那个脚本要跑很多次
（每改一条迁移规则就得重跑），于是攒了起来。

处理：删掉备份、`apply.mjs` 不再产生（**回滚走 git**）、`.npmignore` 兜底拒绝该模式。

`npm pack` 现在：**525 文件 / 4.1 MB 压缩 / 10.4 MB 解压 / 无备份**。

## 十三、登记：面板唯一会写的那件事

在此之前，这个面是只读的，加一个知识库要手改 `~/.dsh/yon-panel/wiki_config.json`。批 3b
把「新增 / 编辑 / 移除登记」放进了面板，于是这个面上第一次出现了写动词 —— 所以「写什么、
不写什么」值得写下来，因为这正是最容易夸大的一句话。

**写的只是插件自己的那份名单。** 三个动词都只动 `wiki_config.json`：

- 不写 vault 里任何一个页面；
- **不在 vault 里删任何东西** —— 移除登记连它自己的派生索引都不动。留着的那个
  `wiki/.yon-index.json` 不是垃圾：它是**读**留下的（`ensureWikiIndex` 在首次读时建的），
  而且下次重新登记回来正好省一次重建。真正的代价是一次重建，不是一次丢失。
- 有一处要说准：**保存的回报本身会具现那个派生索引**。`saveVault` 回答的是 `list()`
  建的同一种视图，而在一个**已经是 vault** 的目录上建视图就是一次读 —— 所以「界面上的
  保存」在磁盘上顺带留下了 `wiki/.yon-index.json`，与读完全同一路径。写成"不写 vault"
  是不准确的，准确的说法是"不写页面，不删东西"。

**id 从目录名派生，编辑时不可改。** 与数据源面板「key/env 编辑时禁用」同一条约定：一次
编辑改的是它指哪儿，不是它的身份。id 是模型调 `wiki_write` / `wiki_lookup` 时传的
`vault` 参数，也是 URL 段；改了它，之前把查询限定到这个库的那次调用就指向别处了。所以
表单里**没有** id 那一格，只有一句说明为什么。

两个 id 派生规则各有理由：目录名 slug 出来是空的时候回落到 `vault`（`WikiVault.id` 的
契约是 `/^[a-zA-Z0-9_-]+$/`，而全中文目录名 slug 完什么都不剩），slug 撞了就在后面
数号（`reports`、`reports-2`）—— 两行共用一个 id 就是两行里只有第一行能被编辑和移除，
因为每个动词都按 id 寻址。

**路径只能选，不能打。** 与安装目录面板同一条：一个绝对路径打错一个字符，面板不会报错，
只会安静地列出一个空的知识库 —— 而"空的"和"这个目录里确实没有页面"在界面上长得一样。
所以那一格只读，值只从宿主的目录选择器来；没有选择器的宿主明说登记不了，不给手输回退。

**选出来一个不是 vault 的目录，接受。** 不拒绝：使用者指名的目录就是一条真实登记，拒绝
只会让他没有可修的东西。行压暗（`.rowNotReady`）、面板明说知识库只认哪四个布局 ——
这句话里的那份目录名清单**读自共享常量 `WIKI_ENTITY_DIRS`**，与 `entityDirOf()` 依次
尝试的是同一个来源，否则两处会各自漂移。

**读不出来就拒绝写。** 这是这一批补上的一个洞：`wiki-store.read()` 对解析失败的文档返回
空列表，这在只读时无害（"没登记过"和"文件读坏了"在界面上本来就分不开），但它一旦有了
写方就致命 —— 保存是"读回名单、改一行、写回去"，于是**一次保存会把一份还能手工修好的
名单替换成一行**。现在读的失败带着 `error` 出来，服务的 `readable()` 拒绝写入，文件
逐字节留在原地。`guessVaults()` 那边也顺手收紧了：它原先只按路径去重，现在 id 也去重，
两行共用一个 id 的名单不能再被它生出来。

**串行化不是可选项。** 两轮保存各自"读名单 → 改 → 写回"，不排队的话后写的那轮覆盖先写的，
而先写的那轮**已经报过成功**。服务里所有写走同一条 promise 链。
