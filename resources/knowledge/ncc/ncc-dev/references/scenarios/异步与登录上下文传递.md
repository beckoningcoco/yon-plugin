# NCC 异步执行与登录上下文传递

> 2026-10-26 实战总结：集团报表「完整上传」后台推送，每个任务都报 `token is null`。

## 一句话

NCC 里用 `new Thread` / `ExecutorService` 开新线程跑业务，**ThreadLocal 不会跟过去**。
凡是挂了 `SecurityAspect` 的服务（数据中心取数、凭证查询、任务查询等），都会报：

```
FrameworkSecurityException: User session expired,please re login!(0) --> token is null
```

必须**手动把 token 和 InvocationInfoProxy 搬过去**。换线程池、换 `ExecutorService`、换 `new Thread`
都一样，换写法解决不了这个问题。

---

## 一、根因：token 在 ThreadLocal 里

`SecurityAspect`（`lib/fwserver.jar`）对每个服务方法做前置校验：

```java
@Around(pointcut = "needProcess", patternType = PatternType.method)
public Object aroundMethod1(ProceedingJoinpoint pjp) throws Throwable {
    int status = this.tp.verifyToken(NetStreamContext.getToken());   // ← ThreadLocal
    if (status == 0) throw new FrameworkSecurityException(
        "User session expired,please re login!(0) --> token is null");
    ...
    return pjp.proceed();
}
```

`NetStreamContext.getToken()` 读的是**当前线程**的 ThreadLocal。主线程（Action）有值，
`new Thread` / 线程池线程里是空的。

调用栈长这样（一眼能认出来）：

```
FrameworkSecurityException: ... token is null
  at nc.bs.framework.server.SecurityAspect.aroundMethod1
  at ...DataCenterService.querySheetByTask
  at ...BgrReportSyncServiceImpl.loadSheetMap
  at ...BgrReportSyncServiceImpl$3.run        ← 线程池里的匿名 Runnable
```

## 二、两个关键的类

### `nc.bs.framework.comn.NetStreamContext`（token 就在这儿）

```java
public final class NetStreamContext {
  public static void setToken(byte[]);
  public static byte[] getToken();
  public static void reset();
  public static byte[] getToken(String);
  public static void setToken(String, byte[]);
  public static void resetAll();
}
```

**注意**：`InvocationInfoProxy` 和 `InvocationInfo` 里**都没有 token 字段**，
别在那儿找，直接看 `NetStreamContext`。

### `nc.bs.framework.common.InvocationInfoProxy`

```java
public static InvocationInfoProxy getInstance();
public String getUserId();        public void setUserId(String);
public String getUserCode();      public void setUserCode(String);
public String getGroupId();       public void setGroupId(String);
public String getLangCode();      public void setLangCode(String);
public String getUserDataSource(); public void setUserDataSource(String);
public String getProperty(String); public void setProperty(String, String);
public void reset();
```

`getInvocationInfo()` / `setInvocationInfo()` 是 `protected`，外部拿不到，所以走上面这些 setter。

## 三、标准做法：快照 → 恢复 → 清理

### 1) 在**有会话的线程**里抓一份快照

```java
static final class InvocationSnapshot {
    byte[] token;
    String userId, userCode, groupId, langCode, userDataSource, pkOrg;
}

static InvocationSnapshot captureInvocation() {
    InvocationSnapshot s = new InvocationSnapshot();
    s.token = NetStreamContext.getToken();                 // ★ 最关键
    InvocationInfoProxy p = InvocationInfoProxy.getInstance();
    s.userId = p.getUserId();
    s.userCode = p.getUserCode();
    s.groupId = p.getGroupId();
    s.langCode = p.getLangCode();
    s.userDataSource = p.getUserDataSource();
    s.pkOrg = p.getProperty("pk_org");                     // 组织要单独取
    return s;
}
```

### 2) 在每个工作线程**开跑前**恢复

```java
static void restoreInvocation(InvocationSnapshot s) {
    if (s == null) return;
    if (s.token != null) NetStreamContext.setToken(s.token);
    InvocationInfoProxy p = InvocationInfoProxy.getInstance();
    if (s.userId != null) p.setUserId(s.userId);
    if (s.userCode != null) p.setUserCode(s.userCode);
    if (s.groupId != null) p.setGroupId(s.groupId);
    if (s.langCode != null) p.setLangCode(s.langCode);
    if (s.userDataSource != null) p.setUserDataSource(s.userDataSource);
    if (s.pkOrg != null) p.setProperty("pk_org", s.pkOrg);
}
```

### 3) 线程里用

```java
final InvocationSnapshot snap = captureInvocation();   // Action 线程

Thread t = new Thread(() -> runAll(snap), "job-main");
t.setDaemon(true);
t.start();

// 线程池里每个任务
POOL.submit(new Runnable() {
    public void run() {
        try {
            restoreInvocation(snap);      // ← 必须是第一句
            doBusinessWork();
        } catch (Exception e) {
            Logger.error("job failed", e);
        } finally {
            latch.countDown();
        }
    }
});
```

**顺序很重要**：`restoreInvocation` 必须是 `run()` 的第一句，任何服务调用之前。

### ⚠ 绝对不要在服务端调 `NetStreamContext.reset()`

这一条是踩出来的坑，单独拎出来说。

`NetStreamContext.reset()` **只能在客户端调用**。在 NCC 服务端（`nc.impl.*` / `nc.bs.*` 这些跑在 JVM 里的类）里调它，平台会直接拒绝：

```
Running in server can't  call reset()
```

**为什么禁止**：token 存在 ThreadLocal 上，而服务端线程来自**线程池**——一个线程处理完请求就去处理下一个，是公共资源。`reset()` 会把这个身份清空，可能让**同一线程上后续的框架逻辑**（记日志、查权限、回写）变成"未登录"，甚至波及下一个请求。所以框架在 `reset()` 里做了角色检查，服务端一律拦下。

**为什么你多半也不需要它**：每个任务在 `run()` 第一句就 `restoreInvocation(snap)`，token 每次都被重新覆盖，上一条任务留下的值天然就没了，不需要先清空。

**这个坑的杀伤力**：如果写在 `finally` 里

```java
} finally {
    NetStreamContext.reset();   // ← 抛异常
    latch.countDown();          // ← 永远执行不到
}
```

`countDown()` 被跳过 → `latch.await()` 永久阻塞 → 整个批次卡死、一行数据都不落库，而日志里只有一句不起眼的 `Running in server can't call reset()`。排查时极易误判成"任务没跑起来"。

**正确的服务端上下文生命周期**：

| 操作 | 服务端可以吗 |
|---|---|
| `NetStreamContext.getToken()` | ✅ 读，随意 |
| `NetStreamContext.setToken(...)` | ✅ 设，用来恢复快照 |
| `NetStreamContext.reset()` | ❌ **禁止**，平台抛异常 |
| 什么都不做、靠下次 `setToken` 覆盖 | ✅ **推荐** |

## 四、什么时候需要搬、什么时候不用

| 场景 | 需要搬上下文？ |
|---|---|
| 纯写文件 / 纯计算 / 只发 HTTP 到外系统 | **不需要**（参考 `nc.bs.cmp.logger.AsyncLogger` 那种写法） |
| 调用 `NCLocator.lookup(...)` 拿到的**平台服务**（`IDataCenterService`、`IBGRVoucherService`、`ITaskQueryService`…） | **需要** |
| 直接 `BaseDAO` 跑 SQL | 一般不需要（不走 SecurityAspect），但同一次任务里通常还有服务调用，建议统一搬 |
| 调 `PubUtil` / `NtbSuperServiceGetter` 这类底层 | 多数不走切面，但为稳妥按"需要"处理 |

判断方法：**看异常从哪个类抛出来**。栈里出现 `SecurityAspect.aroundMethod1` 就是要搬。

## 五、更规范的选择：平台后台任务

如果这个异步任务**跑得久**（几十分钟到几小时）、需要看进度、需要失败重跑，
更合适的是平台的 `IBackgroundWorkPlugin`（见 `ncc-background-task` 技能）：

- 线程与上下文由平台管理，**不用自己搬 token**
- 在「后台任务管理」里能看到状态、可重跑
- 缺点：按计划/手动触发，不是点按钮就立刻跑

**点按钮触发的短任务**（几分钟）→ 快照搬运即可；
**长任务**（小时级）→ 建议改成后台任务类型。

## 六、排查方法

### 日志关键字

```bash
grep -n "User session expired" <Home>/nclogs/server/nc-log.log*
```

看到成批出现，且栈里是线程池线程（`xxx-pool-N`），基本就是这个问题。

### 快速验证上下文是否为空

在子线程开头打一行：

```java
Logger.error("token=" + (NetStreamContext.getToken() != null)
    + " userId=" + InvocationInfoProxy.getInstance().getUserId());
```

修复前会看到 `token=false userId=null`。

## 七、附：本次踩到的两个连带问题

1. **断点打不中不一定是没执行** —— 后台线程里第一句就抛异常了，
   断点如果打在 `try` 块内部靠后的位置，确实永远不会停。先看日志比看断点可靠。
2. **`like '%ACCM=1%'` 会匹配 10/11/12 月** —— 前端传 `month=1` 时若不补零，
   选 2024 年 1 月会捞出 10/11/12 月的任务（实测 521 变 1623）。
   拼接期间条件前一律 `String.format("%02d", month)`。
