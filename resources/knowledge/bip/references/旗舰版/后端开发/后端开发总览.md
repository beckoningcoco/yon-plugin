# 旗舰版BIP后端开发（iuap-c-server-codegen）

> **快速索引**：本文档 → [GUIDE.md](GUIDE.md) 深度指南

## ⚠️ 数据获取决策（必须遵循）

**在决定数据获取方式前，先分析用户需求中是否已提供相关信息。**

### 决策树（优先级从高到低）

```
用户描述需求
    │
    ├── 涉及BIP API调用？
    │   │
    │   ├── 是 → 必须先调用 iuap-c-openapi-integration 查询
    │   │        获取实际URL、请求方式、入参、出参
    │   │        ❌ 禁止臆想或推测API地址
    │   │
    │   └── 用户已提供完整API信息？ → 直接使用用户提供的信息
    │
    ├── 明确提到"IBillQueryRepository"或"数据库"或"Repository"
    │       ──► 使用 IBillQueryRepository
    │
    ├── 用户已提供完整的字段映射/接口规范/请求格式
    │       ──► 优先使用用户提供的信息
    │
    ├── 提到"翻译"、"翻译成"、"获取XX编码/名称"等
    │   且没有说"调用API"或"API接口"
    │   （指将某个ID/编码翻译为对应的名称/编码，属于本地档案查询）
    │       ──► 使用 IBillQueryRepository 查询本地业务对象进行翻译
    │
    ├── 提到"更新参照"、"参照回写"、"更新参照字段"
    │       ──► 使用 IYmsJdbcApi 更新本地业务对象
    │
    ├── 提到"查询XX"且XX是业务对象（如计量单位、供应商、物料等）
    │   （这里的"查询"指查询本地业务档案获取信息）
    │       ──► 使用 IBillQueryRepository 查询本地业务对象
    │
    ├── 涉及业务对象且没有上述任何条件
    │       ──► 查询元数据了解结构
    │
    └── 其他场景
            ──► 根据具体情况判断
```

### 决策原则

1. **"翻译"优先理解为本地档案查询**：当用户说"翻译计量单位ID为编码"时，应理解为查询本地的计量单位档案（IBillQueryRepository），而非调用 BIP API
2. **"查询XX"优先理解为查询本地业务对象**：当用户说"查询计量单位"时，应理解为查询本地的计量单位档案
3. **明确指示优于推测**：当用户说"调用API"或"使用XX系统接口"时，才使用 OpenAPI
4. **避免惯性思维**：不要因为之前用了 API 就习惯性地继续用 API
5. **字段翻译 → IBillQueryRepository**：计量单位、供应商、部门、物料分类等字段的翻译都应该用 IBillQueryRepository
6. **区分"翻译"和"调用API"**：
   - ✅ "翻译计量单位" → IBillQueryRepository（本地查询）
   - ✅ "调用计量单位API" → OpenAPI（外部调用）
   - ✅ "翻译成编码" → IBillQueryRepository（本地查询）
7. **参照更新 → IYmsJdbcApi**：当用户说"参照更新"、"参照回写"、"更新参照字段"时，使用 IYmsJdbcApi 更新本地档案
8. **❌ 禁止臆想API地址**：调用BIP API时，必须先通过 `iuap-c-openapi-integration` 技能查询实际的URL和参数。禁止根据路径模式推测（如保存是 `/xxx/save`，不能推测详情是 `/xxx/getDetail`）

### 典型场景判断

| 用户话术 | 决策 | 原因 |
|---------|------|------|

| "将供应商ID翻译成供应商编码" | ✅ 使用 IBillQueryRepository | 翻译=本地档案查询 |

## ⚠️ 特征字段处理决策（必须遵循）

当需求涉及**特征字段**时，必须按以下决策树处理：

### 决策规则

```
识别到特征字段
      │
      ▼
需求是否提到 API/接口？
      │
   ┌──┴──┐
   │     │
   │ YES │───────────────────→ 查询 API 是否支持 characteristic
   │     │                           │
   │     │                      ┌────┴────┐
   │     │                      │         │
   │     │                 支持 │         │ 不支持
   │     │                      │         │
   │     │                      ▼         ▼
   │     │              特征组Map赋值    先API保存
   │     │                            再ElasticTool更新
   │     │
   │ NO │
   │     │
   ▼     ▼
使用 ElasticTool 更新特征
```

### 决策表

| # | 需求描述关键词 | 处理方式 |
|---|--------------|---------|
| 1 | 提到 **API** 或 **接口** | ① 查API是否支持characteristic<br>② 支持 → 特征组Map赋值<br>③ 不支持 → 先API保存，再ElasticTool更新 |
| 2 | 提到 **数据库**、**JDBC**、**更新**<br>但**没有**提到API | 直接使用 **ElasticTool** |
| 3 | **只描述**特征更新<br>没有提任何实现方式 | 使用 **ElasticTool** |

### 识别 characteristic 字段

调用 `iuap-c-openapi-integration` 技能查询接口，检查入参中是否有 `characteristic` 类型字段：

```bash
bash run_query.sh --all-interface-desc "XX接口名称" 2>&1 | grep -E "characteristic|特征"
```

| API 查询结果 | 结论 |
|-------------|------|
| 入参中有 `characteristic` 类型字段 | ✅ API **支持**特征赋值 |
| 入参中**没有** `characteristic` 类型字段 | ❌ API **不支持** |

### API 支持特征赋值的代码示例

当 API 支持 characteristic 类型字段时，使用嵌套 Map 赋值：

```java
// 构建特征字段（characteristic 类型字段的规范赋值方式）
Map<String, Object> arrivalOrdersDefineCharacter = new HashMap<>();
arrivalOrdersDefineCharacter.put("vehicleNumber", request.getVehicleNumber());  // 用字段编码作key
bodyItem.put("arrivalOrdersDefineCharacter", arrivalOrdersDefineCharacter);
```

## ⚠️ 事件开发强制要求

**当涉及事件监听或事件订阅开发时，必须先调用 `事件查询（见 events/ 目录下事件订阅配置指南）` 技能获取事件信息：**

| 开发场景 | 必须查询的内容 |
|----------|---------------|
| **事件监听开发** | 事件编码 (eventCode)、事件报文 (example) |
| **事件订阅开发** | 事件编码 (eventCode)、事件报文 (example) |

**查询命令：**
```bash
# 查询事件类型
python scripts/event_query.py --query "待办"

# 查询事件详情（获取报文结构）
python scripts/event_query.py --detail {eventId} --json
```

**⚠️ 禁止臆想事件编码和报文结构**

## ⚠️ OpenAPI调用规范（强制规则）

### 调用BIP API前必须查询

**在生成任何 BIP API 调用代码之前，必须先使用 `iuap-c-openapi-integration` 技能查询：**
- API接口地址（URL）
- 请求方式（GET/POST）
- 入参结构
- 出参结构

**禁止行为**：
- ❌ 根据接口路径模式推测API地址（如保存接口是 `/xxx/save`，就推测详情是 `/xxx/getDetail`）
- ❌ 臆想API路径
- ❌ 根据其他接口路径类推

**正确流程**：
```
1. 识别需求中涉及的BIP API（如"发货单保存"、"到货单查询"）
         ↓
2. 调用 iuap-c-openapi-integration 技能查询
         ↓
3. 获取API地址、请求方式、入参、出参
         ↓
4. 根据实际查询结果生成代码
```

### 查询示例

```bash
# 查询发货单保存API
调用 iuap-c-openapi-integration 技能
参数: --all-interface-desc "发货单保存"

# 查询发货单详情查询API
调用 iuap-c-openapi-integration 技能
参数: --all-interface-desc "发货单详情查询"
```

### 为什么不能推测

**案例**：本次开发中，用户说调用"发货单保存"接口。我看到接口是 `/cpu/deliveryOrderApi/saveDeliveryOrder`，就推测详情接口是 `/cpu/deliveryOrderApi/getDeliveryOrderDetail`。但实际上正确的是 `/cpu/deliveryorder/detail`。

**结论**：即使是同一个业务对象，不同操作的API路径也可能完全不同。必须通过技能查询获取，不能推测。

### 多API依赖场景

如果需求涉及多个BIP API（如保存+查询），必须**分别查询**每个API：

```
用户需求：调用发货单保存接口，保存后查询详情
         ↓
必须分别查询：
1. 发货单保存 API → 获取保存地址和入参
2. 发货单详情查询 API → 获取查询地址和出参
         ↓
不能用一个查询结果推测另一个
```
