# 操作录制与性能报告

> 本文事实来自 2026-10-14 在**金隅共享 `dev-fssc.bbmg.com.cn`**（旗舰版，登录人 yhtmanager）
> 的一次完整实测：录了 45 秒，两份报告都打开验证过。
> 旗舰版各版本的菜单路径与报告分区可能变，**用前先按本文给的 DOM 特征确认一遍**，别照抄当常量。

## 一句话

旗舰版**没有 SPR**（SPR 是 NCC 的 `nc.bs.framework.mx.monitor` + `/spr/` servlet，两者毫无关系）。
旗舰版对应的是工作台右上角头像菜单里的**「开始录制」**，结束时会弹一个对话框，由它给出两份报告。

## 一、入口与操作

都在**工作台首页右上角的头像**上：

1. 点头像 —— 元素是 `div.workbenchSelfAvator`（类名里的 `avator` 就是这么拼的）。
   **hover 不出菜单，必须点击。**
2. 弹出用户中心面板（`div[class*="info--"][class*="settingshow"]`），里面有分组 **「开发调试」**，两项：
   - **开始录制**：`div.record-btn`，外层 `li[title="开始录制"]`，带 `data-uba-title="开始录制"`
   - **开启录屏**：同一分组里的一个勾选项
3. 点「开始录制」后：
   - 菜单项文字变成 **「结束录制」**
   - 右下角出现录制指示器（`div[class*="ymc-record-"]`，`title="双击结束录制"`，图标类 `uf-video`）
4. 做你要录的业务操作。
5. 再点头像 → 点「结束录制」。

## 二、★ 结束后的对话框 —— 必须读一次页面

**结束录制不会自己开报告页签**，它弹一个对话框：

```text
提示：
录制已结束。报告ID：sw7ts5zov3
[关闭] [哈勃报告] [BPR报告]
```

所以点完「结束录制」**一定要 `browser_read` 或 `browser_eval` 读一次页面**，
否则会误判成"没有报告"——本文作者第一次只查了录制指示器和网络请求，就得出过错误结论。

DOM 特征（可以直接用这段抓）：

```js
[...document.querySelectorAll('.ok,.cont')].map(e => e.textContent.trim())
// ["录制已结束。报告ID：sw7ts5zov3", "哈勃报告", "BPR报告"]
```

`.ok` = 哈勃报告按钮，`.ok.expand` = BPR报告按钮，`.cont` = 提示文字。

## 三、两份报告分别是什么

### 3.1 哈勃报告 —— YMC 分布式链路追踪

点击后**新开页签**：

```text
https://{host}/ymc/#/link/tracing-report/detail/{报告ID}
标题：YMC - 链路报告详情 - 链路分析 - YonBIP 监控中心
```

分区：报告概览 / 业务操作列表 / 链路数据 / 链路分析 / 链路详情 / 链路拓扑；
顶部另有 **链路报告数据(JSON)**、**录屏回放**、**链接分享**，以及 **Jaeger UI** 入口。

它按 **TraceId** 把一次业务操作跨多个微服务的调用串起来，每个 span 给所属应用、耗时、
SpanId、状态码；链路详情里能展开出**完整 SQL 原文**。

### 3.2 BPR 报告 —— 服务端剖析

点击后新开页签：

```text
https://{host}/iuap-ymc-server/proxy/server/bpr/open?pk={pk}
标题：BPR - YonBIP Monitoring Center
```

**注意 `pk` 与"报告ID"不是同一个值**（实测 pk 是 32 位随机字母串，报告ID 是 10 位左右），
所以 BPR 报告**不能靠报告ID 拼 URL**，只能从对话框点进去。

分区（15 个）：

```text
报告信息 / 前端概要 / 服务端概要 / 统计概览 / 建议关注 / 业务操作 /
微服务链路 / 服务调用明细 / SQL耗时TOP10 / SQL结果集TOP10 / SQL详情 /
事务详情 / 后端错误详情 / 线程剖析 / 服务端环境
```

页面顶部有 **回放**、下载、分享。其中：
- **微服务链路**：树形展示各微服务耗时占比，每个节点带 `sql: xms/n`、`rs: xms/n`、`err: n`、`cache: xms/n`
- **SQL耗时TOP10 / SQL结果集TOP10**：**完整 SQL 原文 + 库连接串 + 耗时 + 结果集行数**
- **后端错误详情**、**线程剖析**：BPR 独有，哈勃报告里没有

### 3.3 两份不是重复的：该看哪一份

**职责不同、互补，不是二选一。**

| 你想知道 | 看哪份 | 具体分区 |
|---|---|---|
| 慢在哪一跳 / 哪个微服务 | 哈勃 | 链路数据、链路拓扑、链路详情 |
| 把调用关系画出来 | 哈勃 | 链路拓扑、**Jaeger UI** |
| 单次操作的时间轴（每个 span 多久） | 哈勃 | 链路数据 |
| 哪条 SQL 最贵 / 返回多少行 | BPR | SQL耗时TOP10、SQL结果集TOP10 |
| **报错了没有 / 错在哪** | **BPR** | 后端错误详情（哈勃没有这个分区） |
| **线程在忙什么 / 卡在哪** | **BPR** | 线程剖析（哈勃没有这个分区） |
| 有没有优化建议 | BPR | 建议关注 |
| 整体统计 | BPR | 统计概览、服务端概要 |

一句话分工：

> **哈勃回答"慢在哪一跳"，BPR 回答"为什么那一跳慢"。**

这正好是排查的两步。所以**两份都点开**——点开本身不额外采集，报告在结束录制时就已生成好；
但**别都通读**，按上表定位到 2–3 个分区即可。

排查顺序：**先在哈勃定位到那一条 span，再用 BPR 看它的 SQL / 报错 / 线程**。

### 3.4 「错误日志数」不是错误数

BPR「服务端概要」最后一列是**错误日志数**，微服务链路树里对应根节点上的 `err: n`
（实测挂在 `Front end page` 上）。**这个数字看着吓人，其实它只是"时间窗内采集到的日志条数"，
没有按级别过滤。**

实测那份（`sw7ts5zov3`）标 **38** 条，点开「后端错误详情」逐条看：

| 这一类 | 条数 |
|---|---|
| MDD 插件 trace（`QueryExtensionHandler:将要执行 / 执行前置QuerySchema插件 X`） | 24 |
| `QuerySqlBuilder:[INFO] orm_query_entity` / `orm_query_schema_before` | 8 |
| 明写 `[INFO]` 的其他日志 | 8 |
| **`[ERROR]`** | **0** |
| **`[WARN]`** | **0** |

最后两条长这样——都是开发者自己打的 INFO 流水：

```text
com.yonyou.yht.utils.ExternalDomainUtils:external host is https://dev-fssc.bbmg.com.cn
com.yonyou.iuap.intellis.core.cache.SystemConfigCache:【配置项监控】,--加载系统配置项: 【gray_switch】,值为空
```

**怎么用**：别把 38 当成 38 个故障。要判断真出没出错，去「后端错误详情」表里**认字样**——
`Exception`、堆栈、`[ERROR]`、SQL 报错，才值得追；插件 trace 与配置加载可以整片跳过
（这次 `Exception` 只出现 1 次，还只是嵌在别的参数文本里，不是抛出来的）。

> 这些日志**归不到具体某个 span**，所以全挂在链路树**根节点**上，而不是散布在各微服务下。

**同理**：NCC 的 SPR 报告首页那行 **「是否存在错误 = YES」** 是同一套采集机制的产物 ——
有日志就可能是 YES，不能只看这一个字段下结论。

## 四、底层接口

| 环节 | 请求 |
|---|---|
| 开始 / 结束 | `GET /iuap-ymc-agent/monitor/record?uid={uid}&isDiwork=true&host={host}&env={env}&userId={userId}&userName={userName}`（script，各出现一次） |
| 上传日志 | `POST /iuap-ymc-agent/upload/log/{uid}.json`（fetch） |
| 收尾 | `GET /iuap-ymc-agent/bprcall?userId=…&bprId={uid}&userName=…&startTime=…&endTime=…&ubainfo=…&tgap=…`（fetch） |

- `uid` = 录制会话 id = 界面上的**报告ID**
- 组件侧：`iuap-gp-recordui-fe`（录制 UI）+ `iuap-ymc-agent`（代理上传）+ `uba-init.js`（UBA 用户行为分析 SDK）
- `localStorage.YMC_TGAP` 存的就是请求里 `tgap` 的值
- **`bprcall` 是一次性的**：事后重放返回 `500 服务端异常（code 999-999-999999）`，不要拿它当读接口

## 五、实测样本（2026-10-14 金隅）

全程只做了一次"在搜索框输入**供应商**"：

```text
报告编号    sw7ts5zov3
录制人      yhtmanager
时间        2026-10-14 21:33:05 → 21:33:50（45s）
业务操作 1  微服务 7  HTTP 30  RPC 18  SQL 35  Redis 47  MDD Rule 0

业务操作：GET /fullText/suggest  222.4ms  TraceId bc4b40b27ffe9c63
服务端耗时 222ms / 计算 96ms / Cache 23ms(156次) / SQL 36ms(46次)
读结果集 67ms(48) / 异步任务 19 / RPC 19 / 错误日志数 38
```

哈勃报告给出的调用链：

```text
iuap-apcom-workbench       222ms  GET /fullText/suggest
 └ iuap-apcom-messagecenter 158ms  POST /out-api/user/search
    └ iuap-apcom-staffdoc     87ms  IStaffQueryService.getUserBaseInfo
 └ iuap-aip-search           64ms  ISearchClientRpcEndpoint/getQueryDTO
 └ iuap-apcom-org            13ms  FuncOrgDataQryXTService.paginationSubOrgForXT
```

BPR 的 SQL耗时TOP10 里能看到两条关键 SQL（连库连接串一起给出）：

```sql
-- 10ms / 11行   库：iuap_apcom_benchservice@jdbc:dm://192.168.22.103:5236
SELECT ... FROM wb_service
WHERE ytenant_id='jd4ofb7k' AND service_name LIKE '%供应商%'

-- 7ms / 0行     库：iuap_apdoc_basedoc@jdbc:dm://192.168.22.103:5236
SELECT ... FROM org_orgs
WHERE ... (name LIKE CONCAT('%','供应商','%') OR shortname LIKE ...)
```

> 那个环境用的是**达梦**（`jdbc:dm://`），不是 Oracle/MySQL。
> 链路里暴露的微服务名与库 schema 名另见同目录《BIP微服务与库schema地图》——那是排查
> "慢在哪个服务上"的索引。

## 六、和 NCC 的 SPR 对照

| | NCC | 旗舰版 |
|---|---|---|
| 入口 | 头像菜单「录制SPR」/ 热键 `ctrl+~` / 顶栏 `.spr-record` | 头像 → 开发调试 → 开始录制 |
| 结束 | 自动弹 `/spr/temp/*.html` 报告页签 | 弹对话框，两个按钮各开一个报告 |
| 形态 | 单机 HTML 文件 | Web 平台（YMC），带 Jaeger UI、链路拓扑、回放 |
| 粒度 | 单 JVM + 前后端耗时 | **跨微服务的分布式链路** + Redis + 事务 |
| 取回 | 页面「保存到本地」/ `/spr/download?param=` | 「链路报告数据(JSON)」/ 分享链接 / BPR 回放 |
