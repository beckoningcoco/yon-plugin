# 请购单保存（含四个同名入口）调用链 — NCC2505

> 采集口径见 [_call-chain-collection-standard.md](./_call-chain-collection-standard.md)。
> 证据等级：**反编译**（本机无 NCC2505 数据库连接，字段未做实测；SPR 单列一轮）。
> 环境：Home = `E:/NCProject/NCC2505/HOME_BYZY_BIP`。
>
> 本档案的价值集中在**一个业务动作有四个入口**这件事上（第 2、4 节）：
> 四个入口的 label **全都叫「请购单保存」**，但其中两个**逐行同构**（重复入口）、一个其实是查询、
> 只有一个是真正的保存提交。另附**第二种"两阶段"写法**（第 6 节）。

## 1. 什么时候读我

- 客开要**给请购单保存挂逻辑**——**先看清挂在哪一个入口上**，四个入口同名，挂错等于没挂。
- 排查「请购单保存后列表出现重复单据」「同一个保存操作有两条日志」「我改的入口没有生效」。
- 想对比"两阶段提交"的两种写法（本份手写两趟 vs 第 10 份调 `saveCommit`）。

## 2. 【核心】四个 save 入口的真相

入口 XML：`<HOME>/hotwebs/nccloud/WEB-INF/extend/yyconfig/modules/pu/buyingreq/config/action/*.xml`

| 动作名 | **label（都叫"请购单保存"）** | 类 | 实际是什么 |
| --- | --- | --- | --- |
| `pu.buyingreq.save` | 请购单保存 | `BuyingreqInfoSaveAction`（84 行） | **真·保存**：`SAVEBASE` + `runBacth` |
| `pu.buyingreq.newSave` | 请购单保存 | `BuyingreqInfoNewSaveAction`（68 行） | **与上面逐行同构**——同一个动作的**重复入口** |
| `pu.buyingreq.copy` | 请购单保存 | `BuyingreqCopyAction`（141 行） | **不是保存**：调 `IBuyingReqQueryCardInfoService`（**查卡片信息**），是"复制/带入" |
| `pu.buyingreq.saveCommit` | 请购单保存提交 | `BuyingreqInfoSaveCommitAction`（107 行） | **真·保存提交**：手写两趟（第 6 节） |

> **这是本批 16 份里"label 重名"最严重的一例**——三个入口在界面上可能都表现为"保存"，但代码路径完全不同。
> `copy` 那条最容易误判：它的 label 是"请购单保存"，而它做的事是查询。
> **客开的落点判断必须用「动作名 + 类名」，不能只看 label**（这也是本批计划注 3 与采集标准反复强调的一条）。
> 另有 `pu.buyingreq.saveandcommit`（`SaveAndCommitAction`，label「请购单保存提交」）——**第五个入口**，
> 与 `saveCommit` 并存，本档案未展开它的差别（见第 9 节）。

**四个入口的类都在同一个 jar**：`external/lib/uipu_nccloud.jar`。

## 3. 链路（真·保存：`BuyingreqInfoSaveAction`）

| # | 层 | 位置 | 干什么 |
|---|---|---|---|
| 1 | HTTP | `POST /nccloud/pu/buyingreq/save` | 请购单卡片保存 |
| 2 | 入口 | `BuyingreqInfoSaveAction#doAction`（84 行，`uipu_nccloud.jar`） | **`implements ICommonAction`**（第一种基类形态） |
| 3 | 转 VO | 卡片 → `PraybillVO` | 主子（`PraybillHeaderVO` / `PraybillItemVO`） |
| 4 | 子表挂主键 | `setDefaultValue(PraybillVO)`：`item.setPk_praybill(pk)`，新增行 `pk_praybill_b=null` | **请购单特有**：给 `status==2`（新增）的行补主键关联 |
| 5 | 装配 | `context.setBillType(POBillType.PrayBill.getCode())` = **`"20"`**；`context.setActionName("SAVEBASE")` | |
| 6 | 批量脚本 | `IBatchRunScriptService#runBacth(context, PraybillVO.class)` | 与采购订单保存同一入口方法 |
| 7 | 引擎 | `ICloudScriptPFlowService` → `CloudPfUtil` → `IplatFormEntry` → `PFBusiAction` | 见第 9 份第 5 节 |
| 8 | 业务类 | `pub_actionconstrict`（`pk_billtype='20'`, `actiontype='SAVEBASE'`）⋈ `pub_function` | 运行时的 |

> **`newSave`（`BuyingreqInfoNewSaveAction`，68 行）与第 3~6 跳完全一致**：同样
> `POBillType.PrayBill.getCode()` + `setActionName("SAVEBASE")` + `runBacth(context, PraybillVO.class)`。
> 两者差别只在入口层的报文解析细节与长度——**对下游（引擎、动作驱动表、业务类）完全无差别**。
> 客开若只挂一个入口，**两个都要挂**（否则从另一个按钮进来就不生效）。

## 4. `copy` 为什么不是保存

`BuyingreqCopyAction`（141 行）：
```java
IBuyingReqQueryCardInfoService service =
    (IBuyingReqQueryCardInfoService)ServiceLocator.find(IBuyingReqQueryCardInfoService.class);
```
它调的是**查询服务**（`IBuyingReqQueryCardInfoService`），拿卡片信息。
——「复制」在请购单里的语义是"**从来源单据带入数据**"（请购来源见第 8 节的 `fpraysource` 枚举），
带入的过程中界面上提示"保存"，但**后端没走保存链**。
**这条路径上挂保存钩子不会生效**，排查时极易误判。

## 6. 第二种"两阶段"写法：手写两趟（`BuyingreqInfoSaveCommitAction`）

它与第 10 份的 `ISSaleOrderSaveCommitService` 路子**完全不同**——不是调 `saveCommit`，而是**在入口方法里手写两趟**：

```java
// BuyingreqInfoSaveCommitAction#action（107 行，节选）
CloudPFlowContext context = new CloudPFlowContext();              // ★ 普通 CloudPFlowContext（不是 SCMCloudPFlowContext）
context.setBillType(POBillType.PrayBill.getCode());               // "20"
context.setBillVos(vos);
context.setActionName("SAVEBASE");                                // 第一趟
SCMScriptResultDTO objSave = ((IBatchRunScriptService)ServiceLocator.find(IBatchRunScriptService.class))
                                 .runBacth(context, PraybillVO.class);
AbstractBill[] sucessVOs = objSave.getSucessVOs();
this.checkPermission((IBill[])sucessVOs);                         // ★★ 权限检查在两趟之间，用"保存成功后的 VO"

CloudPFlowContext contextCommit = new CloudPFlowContext();        // ★ 另起一个 context
contextCommit.setBillType(POBillType.PrayBill.getCode());
contextCommit.setActionName("SAVE");                              // 第二趟
contextCommit.setBillVos(vos);                                    // ★ 塞回原 vos
SCMScriptResultDTO obj = ((IBatchRunScriptService)ServiceLocator.find(IBatchRunScriptService.class))
                             .runBacth(contextCommit, PraybillVO.class);
card = operator.toCard(obj.getSucessVOs()[0]);
this.afterProcess(card);                                          // BuyingReqScaleUtil（标量回填）
```

**与第 10 份写法的对照**：

| | 第 10 份（采购/销售/到货） | **本份（请购单）** |
| --- | --- | --- |
| 载体 | `ISCMPubSaveCommitService#saveCommit`（公共服务） | **入口自己写** |
| context | **`SCMCloudPFlowContext`** | 普通 `CloudPFlowContext`（两个） |
| 引擎入口 | `service.run(...)` | **`runBacth(...)`** |
| 动作名 | `save` / `commit` 由调用方传入 | 硬编码 `"SAVEBASE"` / `"SAVE"` |
| 权限检查 | 无（入口基类不含） | **有**，且**在两趟之间**（`checkPermission(sucessVOs)`） |
| 基类 | `AbstractOrderSaveAction` | **`DataPermissionAction`**（同到货单） |
| 摘要 | `AuditUtils.setSceneAndBillType` | 未见 |

> **两条结论**：
> ① "保存提交"在平台里**至少有两种实现**（公共服务 vs 入口手写），**不能假设都调 `saveCommit`**。
> ② `checkPermission` 的位置又多了一种：**保存之后、提交之前**，且**权限判的是"保存成功的那批 VO"**——
> 这是本批见到的第 4 种权限检查位置（第 11 份归纳了三种基类形态，这里是基类自带方法被**在手写流程中间调用**）。

**权限元数据**（本类实现，与到货单同款）：`getPermissioncode()` = `POBillType.PrayBill.getCode()`（`"20"`）、
`getActioncode()` = `PowerActionEnum.COMMIT.getActioncode()`、`getBillCodeField()` = `"vbillcode"`。

### 未覆盖项的详情

- **两个"保存提交"入口（⬜）**：`pu.buyingreq.saveCommit`（`BuyingreqInfoSaveCommitAction`，本档案已展开）
  与 `pu.buyingreq.saveandcommit`（`SaveAndCommitAction`）**并存**——
  后者类名与到货单的 `SaveAndCommitAction` 同名（**不同包**），很可能走 `saveCommit` 公共服务那条路。
  **续做应对比这两个类**，这能确认"一个单据两种保存提交实现"是否真的并存。
- **修订链（⬜）**：`pu.buyingreq_r.*` 一整套（`_r.save` / `_r.saveAndCommit` / `_r.reviseDelete` / 修订历史查询）
  与 `pu.buyingreqarrange.*`（安排/取消安排）。请购单的修订是**独立入口组**，不是同一入口的分支。
- **业务处理器清单（⬜，需连库）**：
  ```sql
  select c.actiontype, c.sysindex, c.isbefore, f.classname, f.methodname, c.conditionXpression
    from pub_actionconstrict c join pub_function f on c.functionid = f.pk_function
   where c.pk_billtype = '20' and c.actiontype in ('SAVEBASE','SAVE','APPROVE')
   order by c.actiontype, c.sysindex;
  ```
- **事务边界（⬜）**：本份手写两趟的写法下，**两趟之间没有任何事务标记**（连 `SCMCloudPFlowContext` 都不是），
  比第 10 份更让人怀疑是两段独立事务——但仍是**推断**。
- **锁（⬜）**：与第 7~11 份一致，已读层无锁调用。
- **字段实测（⬜）**：需要能连 NCC2505 的库。
