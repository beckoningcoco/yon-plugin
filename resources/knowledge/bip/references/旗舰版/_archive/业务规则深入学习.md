## 一、业务规则基础

### 1.1 核心接口

> **导包参考（以下为正确的包路径）：**
> ```java
> import com.yonyou.ypd.bill.basic.service.api.IYpdCommonRul;       // 规则接口
> import com.yonyou.ucf.mdd.common.model.rule.RuleExecuteResult;     // 规则返回值
> import com.yonyou.ypd.bill.basic.vo.RulCtxVO;                     // 上下文
> import com.yonyou.ypd.bill.context.BillContext;                    // 单据上下文
> import com.yonyou.ypd.bill.basic.util.CommonRuleUtils;             // 工具类
> import com.yonyou.iuap.bizobject.bizobject.BizObject;              // 单据对象
> ```

```java
public interface IYpdCommonRul {
    Object execute(RulCtxVO rulCtxVO, Map<String, Object> params);
}
```

### 1.2 关键对象

| 对象 | 来源 | 用途 |
|------|------|------|
| `RulCtxVO` | 平台传入 | `getBillnum()` 单据类型、`getFullname()` 实体URI、`getAction()` 动作、`getDomain()` 域 |
| `Map<String, Object> params` | 平台传入 | 扩展参数 |
| `BillContext` | 手动构建 | 封装单据上下文，供 CommonRuleUtils 使用 |
| `BizObject` | `CommonRuleUtils.getBills()` | 触发规则的单据数据 |
| `CommonRuleUtils` | 平台工具 | 获取单据列表 |
| `RuleExecuteResult` | 返回值 | 规则执行成功返回此对象 |

### 1.3 标准模板

```java
@Slf4j
@Component("xxxRule")  // 有注解：规则名=xxxRule；无注解：规则名=类名首字母小写
public class XxxRule implements IYpdCommonRul {

    @Override
    public Object execute(RulCtxVO rulCtxVO, Map<String, Object> params) {
        try {
            BillContext billContext = new BillContext(
                    rulCtxVO.getBillnum(), rulCtxVO.getFullname());
            billContext.setAction(rulCtxVO.getAction());
            billContext.setDomain(rulCtxVO.getDomain());

            List<BizObject> bills = CommonRuleUtils.getBills(billContext, params);
            if (CollectionUtils.isEmpty(bills)) {
                throw new BusinessException("ERR-001", "未获取到单据数据");
            }

            BizObject bill = bills.get(0);
            String billId = bill.getString("id");
            // ... 业务逻辑 ...

            return new RuleExecuteResult();
        } catch (BusinessException e) {
            throw e;
        } catch (Exception e) {
            log.error("规则异常", e);
            throw new BusinessException("ERR-002", e.getMessage());
        }
    }
}
```

## 三、审核/弃审规则实战

### 3.1 审核与弃审的区分

通过 `rulCtxVO.getAction()` 判断：

```java
private String resolveOperationType(String action) {
    if (action != null && action.contains("unaudit")) {
        return "弃审";
    }
    return "审核";
}
```

也可以用两个独立的 Rule 类分别处理审核和弃审。

### 3.2 完整流程

```
审核/弃审触发
  → CommonRuleUtils.getBills() 获取单据
  → queryBillById() 查询完整数据
  → 组织校验（MES档案匹配）
  → 交易类型过滤
  → buildRequest() 组装报文
  → queryDetailByRequisitionId() 查询子表
  → mesHttpClient.post() 推送MES
```

### 3.3 常见问题与解决

| 问题 | 原因 | 解决 |
|------|------|------|
| 字段取值为 null | entity 字段路径不对 | 确认正确路径（如 `creatorId.code` vs `creator.code`） |
| QuerySchema 穿透失败 | 非引用字段用了 `.code` | 检查字段是引用还是普通字符串 |
| 子表查询失败 | 子表 entity 名不对 | 确认子表 URI 和关联字段名 |
| MES 请求格式错误 | 报文结构不匹配 | 对齐文档：`ObjectName` + `RequestString` 数组 |
| 日志看不到输出 | YMS 过滤了 info 级别 | 关键步骤改用 `log.error()` |

## 四、事件订阅 vs 业务规则

| 对比维度 | 业务规则 | 事件订阅 |
|---------|---------|---------|
| 触发方式 | 同步，规则引擎直接调用 | 异步，事件中心回调 |
| 事务支持 | 支持（在同一事务中） | 不支持 |
| 配置方式 | 规则链中配置 | 事件中心配置 |
| 回调地址 | 不需要 | `域名/微服务编码/controller路径` |
| 返回值 | `RuleExecuteResult` | 字符串 `"success"` |

### 8.2 params Map 结构（审核后规则，Arthas 实测）

> 完整 JSON 结构见：[[params结构-审核后规则]]

> ⚠️ **重要**：本文档目前研究的是**审核后规则**的传参逻辑。保存后规则、修改保存规则等其他触发时机，`params` 的内容和结构可能不同。

```bash
watch com.yonyou.ucf.mdf.cggy.biptomes.rule.OutstockApplyAuditMesRule execute 'params[1]' -x 6
```

params 是一个 `Map<String, Object>`，共 21 个 key，分为三层：

**业务开发者需要关心的（3 个）**：

| key | 类型 | 作用 |
|-----|------|------|
| `"return"` | `HashMap` | ⭐ **审核后的完整单据数据**（含子表 + 特征字段，可以直接取） |
| `"convBills"` | `ArrayList<HashMap>` | 转换后的单据列表，结构同 return |
| `"param"` | `BillDataDto` | 请求上下文：`action`、`billnum`、`parameters`（含事件名等） |

**排查问题时可能用到（3 个）**：

| key | 类型 | 作用 |
|-----|------|------|
| `"billMapInDbBeforeAudit"` | `HashMap<id, 单据>` | 审核前数据库快照 → 对比 status 从 0→1 |
| `"billMapInDbAfterSave"` | `HashMap<id, 单据>` | 保存后数据库快照 → 查出谁改了哪些字段 |
| `"requestData"` | `ArrayList<HashMap>` | 触发时的请求数据 |

**平台内部状态（不用管）**：

`stockCheckTiming`、`isEffectStock`、`billDirection`、`config`、`skipErrorMessage` 等。

**关键发现：`return` 里可直接拿到完整子表**：

```java
Map returnData = (Map) params.get("return");
List detailList = (List) returnData.get("requisitionDetail");
Map detail = (Map) detailList.get(0);
// detail.get("materialCode")  → "30101040046"
// detail.get("quantity")      → 1.00000000
```

**特征字段 key 格式**：

| 查询方式 | 分隔符 | 示例 |
|---------|:--:|------|
| QuerySchema 扁平化 | `_` | `requisitionDetailDefineCharacter_WLWYBM` |
| BizObject 内存中 | `__` | `requisitionDetailDefineCharacter__WLWYBM` |

实际取值：
```
requisitionDetailDefineCharacter__WLWYBM       → "2559438365306912769" (ID)
requisitionDetailDefineCharacter__WLWYBM_name  → "30101040046" (名称)
```

## 九、CommonRuleUtils.getBills() 深度剖析

### 9.1 作用

从 `params` 中把触发规则的单据数据取出来，封装成 `List<BizObject>`。

```java
List<BizObject> bills = CommonRuleUtils.getBills(billContext, params);
BizObject bill = bills.get(0);
String billId = bill.getString("id");
```

### 9.2 为什么需要它

`params` 里有至少 4 处包含单据数据（`return`、`convBills`、`requestData`、`billMapInDbBeforeAudit`），自己挖太脆弱。`CommonRuleUtils` 封装了内部结构。

### 9.3 好处

| 好处 | 说明 |
|------|------|
| **封装** | 不需要知道数据在 params 的哪个 key |
| **缓存复用** | 首次解析后写回 dto，后续规则零开销 |
| **规则类型无关** | 审核/弃审/保存用同一个 API |
| **强类型** | `getString()`/`getDate()` 直接取值 |

### 9.4 源码逐行解读（反编译）

**入口方法 `getBills(BillContext, Map)`**：

```java
BaseDto obj = getNewBillDataDto(paramMap.get("param"));  // ① 从 params 取 "param" key
if (null == obj) return null;                            // ② 无 param → 非规则触发
List<T> bills = decodeBills(billContext, obj);            // ③ 核心解码
obj.setData(bills);                                      // ④ 写回缓存（关键优化）
return bills;                                             // ⑤ 返回
```

④ **是关键**：首次调用 `dto.data` 是 `List<Map>`，解析成 `List<BizObject>` 后写回。同一请求链中后续规则再调 `getBills` 时，直接命中 `list.get(0) instanceof BizObject` 分支，**零开销**。

**核心方法 `decodeBills` — 5 种分支**：

| data 类型 | 含义 | 处理 |
|-----------|------|------|
| `String` | JSON 字符串 | `Objectlizer.decode(json, fullname)` |
| `List<BizObject>` | 已解析（缓存命中） | 直接返回 |
| `List<Map>` | 未解析（首次调用） | 逐行 `Objectlizer.convert(Map, fullname)` |
| `BizObject` | 单个对象 | 包装成 List |
| `Map` | 单个未解析 | `Objectlizer.convert` → 包装 |

**辅助方法**：

| 方法 | 作用 |
|------|------|
| `clearParent(list)` | 递归清理 `"_parent"` 键，防止循环引用 |
| `clearStatus(list)` | 清理 `"_status"` 键 |
| `removeParallelData(list)` | 删除 key 中含 `!` 的平行表字段 |
| `clearChildren(bills, fullname)` | 按元数据删除所有子表属性 |
| `map2BizObject(obj)` | 简化版：`BizObject.init(map)` |

**完整数据流**：

```
params.get("param") → BillDataDto
  └─ dto.getData()
       ├─ String(JSON)     → Objectlizer.decode
       ├─ List<Map>        → 逐行 Objectlizer.convert(Map, fullname)
       ├─ List<BizObject>  → 直接返回（缓存命中）
       ├─ BizObject        → 包一层
       └─ Map              → convert → 包一层
            └─ dto.setData(bills)  ← 写回缓存
```

实际输出：
```
result=[
    "po_picking_requisition",                    ← billnum    单据表名（短名）
    "st.pickingrequisition.PickingRequisition",  ← fullname  实体URI（全名）
    "audit",                                     ← action    审核动作
    null,                                        ← domain    可为空
]
```

**关键结论**：

| 发现 | 说明 |
|------|------|
| `billnum` ≠ `fullname` | `billnum` 是短名/表名（`po_picking_requisition`），`fullname` 是实体URI全名（`st.pickingrequisition.PickingRequisition`）。ORM 查询用 `fullname` |
| `domain` 可为 null | 内部部署/某些场景下 domain 为空，校验逻辑要处理空值 |
| `action` 是纯字符串 | `"audit"` / `"unaudit"` 等，用 `contains("unaudit")` 判断即可 |

| 字段 | getter | 常用度 | 含义 |
|------|--------|:--:|------|
| `billnum` | ✅ | ⭐⭐⭐ | 单据类型，传给 BillContext |
| `fullname` | ✅ | ⭐⭐⭐ | 实体URI，传给 BillContext |
| `action` | ✅ | ⭐⭐⭐ | 区分审核/弃审 |
| `domain` | ✅ | ⭐⭐⭐ | 数据域 |
| `ruleId` | ✅ | ⭐ | 规则ID，较少用到 |
| `isMakeup` | ❌ | — | 无 getter，不可访问 |

## 九、CommonRuleUtils.getBills() 深度剖析

### 9.1 作用

从 `params` 中把触发规则的单据数据取出来，封装成 `List<BizObject>`。

```java
List<BizObject> bills = CommonRuleUtils.getBills(billContext, params);
BizObject bill = bills.get(0);
String billId = bill.getString("id");
```

### 9.2 为什么需要它 —— params 里有多处重复的单据数据

Arthas 实测 `params` 里至少 4 个地方有单据：

| 位置 | 说明 |
|------|------|
| `params.return` | 审核后的完整单据 |
| `params.convBills` | 转换后的单据列表 |
| `params.requestData` | 原始请求数据 |
| `params.billMapInDbBeforeAudit` | 审核前数据库快照 |

如果不用 `CommonRuleUtils`，需自己知道去哪个 key 取——换个规则类型 key 可能就变了。

### 9.3 好处

| 好处 | 说明 |
|------|------|
| **封装** | 不需要知道数据在 params 的哪个 key 下 |
| **版本免疫** | 平台升级改内部结构，代码不受影响 |
| **规则类型无关** | 审核/弃审/保存/删除都用同一行代码，方法内部根据 BillContext 路由 |
| **强类型 BizObject** | `getString("id")`、`getDate("vouchdate")` 直接取值，无需手动类型转换 |
| **统一模式** | 所有 BIP 规则开发者都用这个套路 |

### 9.4 工作原理推测

```
CommonRuleUtils.getBills(billContext, params)
    ├─ billContext.getFullname() → 确定 entity 类型
    ├─ billContext.getAction()   → 确定去哪个 key 取（audit→"return"）
    ├─ 从 params 中找到对应单据数据
    ├─ 包装成 List<BizObject>
    └─ 返回
```
