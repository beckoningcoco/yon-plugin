## 二、四个实测坑

### 坑 1：直接用 `businessDesigner?...&id=<流id>` 的 URL 打开，右侧属性面板永远不出来

**症状**：画布能画、节点能拖、边能连，但点节点/边**没有**「单据信息」「规则信息」面板；
`document.querySelector('.relation-item')` 为 null。

**原因（实测现象）**：这种打开方式下，设计器根组件的 `activeFlow` 只有 `{billCode}`，
缺 `id`/`code`/`status`/`isPreset` 等字段，选中逻辑拿不到流上下文，面板的 `v-if` 永远为假。

**判据**（排查时直接看一眼）：

```js
// 找到持有 activeFlow 的组件实例
const root = document.getElementById('app').__vue__
let c = null
;(function walk(x, d) { if (!x || c || d > 9) return
  if (x.$data && 'activeFlow' in x.$data) c = x
  ;(x.$children || []).forEach(y => walk(y, d + 1)) })(root, 0)
Object.keys(c.activeFlow)   // 只有 ['billCode'] = 没加载成功；应含 id/code/status/…
```

**做法**：回列表页，悬停该行点「设计」重新打开。已经拖好的节点**不会**自动带过去，
要重拖（画布内容只在内存里，没保存就关页签就没了）。

> 反过来也能用：`activeFlow` 字段齐不齐，可以作为"这个设计器页签是否可正常操作"的前置检查。

**顺带一个更隐蔽的 id 坑**：列表行的 `data-row-key` **不是**流 id。
实测某行 `data-row-key="26552829399468605490"`（20 位），而真实 id 是 `2655282939946860549`（19 位）；
拿 20 位去调 `getById`，**接口不报错**（`flag:0, msgSuccess:true`），返回 `data: {}` ——
设计器于是拿到空对象，画布空白、`activeFlow` 只剩 `billCode`，现象与"直开 URL"一模一样。
所以：**id 一律从 `activeFlow.id`（或列表接口返回）取，不要用 `data-row-key` 拼**。

### 坑 2：规则名称填了又被改成转换规则名

**症状**：新建规则时先填「订单开票」，选完转换规则后保存，规则名和连线名都变成了
「销售订单生成销售发票」。

**原因**：**新建规则**时选转换规则会用规则名回填 `nameStr`，覆盖此前手填的值；
而「修改规则」（编辑）不会。

**做法**：
1. **先选转换规则，再填规则名称**；
2. 已经覆盖了的：点规则卡片的「编辑」进去改名再确定。
3. 名称是**多语言字段**（`businessFlowFe_multiLangInput_input`），用 CDP 的
   `set_value` / `type` 只改 DOM 值，**不会**更新组件的 `langName`（保存时用的是后者）。
   实测有效的写法是直接改组件数据后 `$forceUpdate()`：
   ```js
   const c = /* designBaseInfo 组件实例 */
   c.langName = { ...c.langName, zh_CN: '订单开票' }
   c.$forceUpdate()
   ```
   然后点「确定」。改完用规则卡片上的「规则名称 : …」核对。

### 坑 3：`flowRule/list` 返回空数组，以为规则没保存

**症状**：`getById` 能看到边，但 `flowRule/list?nodeId=<边id>` 返回 `data: []`。

**原因**：`getById` 的 `content.edges[]` 结构是 **`{ data: { id, name, … }, source, target }`**，
边 id 在 **`edge.data.id`**，`edge.id` 是 `undefined`。
传 `nodeId=undefined` 不会报错，只是返回空数组——很容易误判成"规则没落库"。

**做法**：

```js
const c = JSON.parse(flow.content)
const edgeId = c.edges[0].data.id          // ✅ 不是 c.edges[0].id
const rules = (await (await fetch(
  `/iuap-apcom-supportcenter/flowRule/list?businessFlowId=${flow.id}&nodeId=${edgeId}`,
  { credentials: 'include' })).json()).data
```

> 同理：`content.edges[].data` 里还存着 `transactionTypeId` / `tarBizTypeId` / `name`，
> **只看边就能判断这条边用了什么交易类型**，不必先查规则。

### 坑 4：保存后"已启用"，再点启用反而会停用

**症状**：按"保存并启用"的清单走到"启用"一步，发现列表里已经是「已启用」，按钮文字是「停用」。

**原因**：新建业务流默认就是 `status=true`；未开启版本控制的流，保存后仍保持启用态
（`03` 第五节、`08` 第四节已记录）。此时再点那个按钮执行的是**停用**。

**做法**：保存后先 `getById` 看 `status`；已是 `true` 就不必再点，把它当作"已启用"验收。
只有保存后变 `false`（开了版本控制的流）才需要点「启用」。

## 三、回读脚本模板（复制即用）

```js
// 在已登录的业务流列表页/设计器页签里跑
const id = '<业务流id>'
const flow = (await (await fetch(
  `/iuap-apcom-supportcenter/businessFlow/getById?id=${id}`, { credentials: 'include' })).json()).data
const content = JSON.parse(flow.content || '{}')

const nodes = (content.nodes || []).map(n => ({ name: n.name, code: n.code, isCore: n.isCoreBill }))
const edges = (content.edges || []).map(e => ({ name: e.data.name, id: e.data.id }))

const rules = []
for (const e of content.edges || []) {
  const r = await (await fetch(
    `/iuap-apcom-supportcenter/flowRule/list?businessFlowId=${id}&nodeId=${e.data.id}`,
    { credentials: 'include' })).json()
  for (const x of r.data || []) rules.push({
    name: x.name, refRuleCode: x.refRuleCode,
    src: x.srcBizTypeName, tar: x.tarBizTypeName,
    pushOpportunity: x.pushOpportunity, pushMode: x.pushMode, createUserType: x.createUserType,
    showConvertedBill: x.showConvertedBill,
    custom: !!(x.dataItems || x.groupItems || x.filterItems)   // false = 全沿用
  })
}
console.log({ status: flow.status, version: flow.version, nodes, edges, rules })
```

验收口径：`nodes.length === 2`、`edges.length === 1`、`rules.length === 1`、
`isCoreBill` 恰好一个 true、`rules[0].refRuleCode` 等于预期规则编码、`custom === false`
（表示全部沿用系统规则）。

## 四、交易类型的两条硬规则

1. **核心单据的交易类型必须设，且只能在规则里设**（见 `03`）。
2. **核心单据的交易类型下拉只列"未被占用"的类型**（见 `10` 第八节）。
   下拉里找不到某类型，先当"被占用"排查，别怀疑档案或权限。

**校验 SQL 必须用 `LIKE`**，`TRANSACTION_TYPE_ID` 是逗号拼接字段：

```sql
SELECT ID, CODE, NAME, STATUS, DR, TRANSACTION_TYPE_ID
FROM iuap_apcom_businesssflow.business_flow
WHERE YTENANT_ID = '<tenantId>'
  AND BILL_CODE = '<核心单据>'
  AND TRANSACTION_TYPE_ID LIKE '%<交易类型id>%'
  AND DR = 0;
```

等值 `=` 会漏掉 `"idA,idB"` 这种一条流挂多个交易类型的记录——本次就是因此把"已被占用"
误判成"可安全使用"，配到一半才卡住。

## 五、给需求单/确认单写的核对项

配置前用下面三项代替"感觉没问题"：

| 核对项 | 取法 |
|---|---|
| 交易类型是否被占用 | 上节 `LIKE` SQL，看 `STATUS=1 AND IS_CURRENT_VERSION=1` 的条数 |
| 转换规则是否存在 | `Cache.sysRuleList` 里按中文名找，拿 `code` 与 `originDes/targetDes` |
| 编码是否重复 | `business_flow` 里 `CODE='<编码>'` 的条数 |
