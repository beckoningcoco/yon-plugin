# 大批量数据处理优化方案

## 一、需求背景

### 业务场景

智慧芽(PatSnap)专利数据同步功能，涉及以下流程：

1. **SFTP 下载**：从智慧芽 SFTP 服务器下载 ZIP 文件（含 JSON 数据包 + PDF 文件包）
2. **JSON 解析入库**：解压 `_json.zip`，流式解析 JSON，路由到 10+ 个子表（专利著录、法律状态、专利家族、权利要求、说明书等）
3. **PDF 上传**：解压 `_file.zip`，逐 PDF 上传到文件服务，获取下载链接回写数据库

### 数据规模

| 指标 | 规模 |
|------|------|
| 单次 JSON 文件大小 | 100MB ~ 2GB |
| 单 JSON 文件专利条数 | 1万 ~ 20万+ |
| 拆分子表数量 | 19 张 |
| PDF 文件数量 | 2千 ~ 2万+ |
| 数据库类型 | 达梦（DM），IN 列表上限约 5000 |

### 核心矛盾

- **单线程处理**：几小时甚至十几小时才能完成，不可接受
- **盲目并行**：数据库连接池被打爆、内存 OOM、达梦 IN 超限
- **内存爆炸**：一次性加载大 JSON 到内存 → GC 频繁 → 服务不可用

## 二、优化方案（分片段）

### 2.1 线程池配置 —— 有界队列 + 背压策略

```java
private static final ThreadPoolExecutor PDF_UPLOAD_EXECUTOR = new ThreadPoolExecutor(
        3,                          // 核心线程数
        5,                          // 最大线程数
        60L, TimeUnit.SECONDS,      // 空闲线程存活时间
        new LinkedBlockingQueue<>(50), // ★ 有界队列，防止无限堆积导致 OOM
        new ThreadFactoryBuilder().setNameFormat("pdf-upload-%d").build(),
        new ThreadPoolExecutor.CallerRunsPolicy() // ★ 队列满时主线程兜底，自然背压
);
```

**要点：**
- **禁止无界队列**（如 `new LinkedBlockingQueue<>()` 不传参）→ 任务堆积 → OOM
- **推荐 CallerRunsPolicy**：队列满时调用者线程（主线程）自行执行，形成自然背压，不会被拒绝异常打断
- **线程命名**：方便 jstack / 日志定位

### 2.2 动态线程池 —— 根据数据量自适应调整

```java
private ThreadPoolExecutor createPdfPool(int pdfCount) {
    int threads = Math.max(3, Math.min(pdfCount, 16));  // 3~16 之间
    return new ThreadPoolExecutor(
            threads, threads,
            60L, TimeUnit.SECONDS,
            new LinkedBlockingQueue<>(Math.max(50, threads * 20)),
            new ThreadFactoryBuilder().setNameFormat("pdf-upload-%d").build(),
            new ThreadPoolExecutor.CallerRunsPolicy());
}
```

**要点：**
- 数据量少时不浪费线程（下限 3）
- 数据量多时不无限扩张（上限 16，根据 CPU 核数和下游承受力设定）
- 队列长度与线程数成正比

### 2.3 Semaphore 信号量限流 —— 防止打爆数据库连接池

```java
Semaphore sem = new Semaphore(3);  // 最多同时 3 个写库任务
List<CompletableFuture<Void>> futures = new ArrayList<>();
for (Map.Entry<String, List<Map<String, Object>>> e : allData.entrySet()) {
    sem.acquire();  // ★ 主线程阻塞获取许可，防止无限提交
    futures.add(CompletableFuture.runAsync(() -> {
        try {
            save(e.getKey(), e.getValue());
        } finally {
            sem.release();  // ★ 必须在 finally 中释放
        }
    }, pool));
}
CompletableFuture.allOf(futures.toArray(new CompletableFuture[0])).join();
```

**与 Executor 队列限流的区别：**
- 线程池队列限流控制的是"排队中的任务数"
- Semaphore 控制的是"正在执行的任务数"（即并发度）
- 两者配合使用：队列防止堆积，Semaphore 防止并发过高打爆数据库

**经验值参考：**
| 下游资源 | 建议 Semaphore 值 |
|----------|------------------|
| 达梦数据库写库 | 3 ~ 5 |
| HTTP API 调用 | 10 ~ 20 |
| 文件上传 | 5 ~ 10 |

### 2.4 Jackson 流式解析 —— 避免大 JSON 一次加载到内存

```java
// ❌ 错误：一次性加载整个 JSON 到 List
List<Map<String, Object>> list = mapper.readValue(inputStream,
    new TypeReference<List<Map<String, Object>>>() {});

// ✅ 正确：流式逐个解析 JSON Object
private List<Map<String, Object>> dealJsonCollect(String entryName, InputStream inputStream) throws IOException {
    List<Map<String, Object>> dataList = new ArrayList<>();
    JsonFactory factory = new JsonFactory();
    factory.disable(JsonParser.Feature.AUTO_CLOSE_SOURCE);  // ★ 不让 parser 关闭底层流
    try (JsonParser parser = factory.createParser(inputStream)) {
        while (parser.nextToken() != null) {
            if (parser.currentToken() == JsonToken.START_OBJECT) {
                dataList.add(mapper.readValue(parser, Map.class));
            }
        }
    }
    return dataList;
}
```

**要点：**
- 逐对象解析，内存只保留当前 Object
- `AUTO_CLOSE_SOURCE` 设为 false，因为 ZipInputStream 的 entry 边界由调用方管理
- `try-with-resources` 确保 parser 关闭

### 2.5 两阶段处理 —— 解析与写库分离

```java
// 第一遍：收集所有 JSON 文件数据（纯 IO/CPU，无 DB 操作）
Map<String, List<Map<String, Object>>> allData = new LinkedHashMap<>();
while ((entry = zis.getNextEntry()) != null) {
    if (entryName.endsWith(".json")) {
        allData.put(type, dealJsonCollect(entryName, zis));  // 只解析，不写库
    } else {
        skipStream(zis);  // ★ 主动跳过不需要的 entry
    }
}
zis.close();     // ★ 解析完立刻关闭 ZIP 流

// 第二遍：并行写库（纯 DB 操作，无 IO 阻塞）
// 使用 YMS 线程池 + Semaphore 限流，并行写入各表
for (Map.Entry<...> e : allData.entrySet()) {
    sem.acquire();
    CompletableFuture.runAsync(() -> save(e.getKey(), e.getValue()), pool);
}
```

**为什么这么做：**
- ZIP 解压和 JSON 解析是 CPU/IO 密集型，和 DB 写入混在一起会互相阻塞
- 分离后第二阶段可以并行写各表，最大化吞吐
- 第一步完成后立即关闭 ZIP 流，释放文件句柄

### 2.6 分批提交 —— 避免无限堆积 Future

```java
private static final int BATCH_SIZE = 200;

List<CompletableFuture<UploadResult>> batch = new ArrayList<>(BATCH_SIZE);
while ((entry = zis.getNextEntry()) != null) {
    // ... 构建 CompletableFuture ...
    batch.add(future);

    if (batch.size() >= BATCH_SIZE) {       // ★ 满一批就等待
        waitForBatch(batch, BATCH_TIMEOUT_MINUTES);
        processResults(batch);              // 主线程处理 DB 操作
        batch.clear();
    }
}
if (!batch.isEmpty()) {
    waitForBatch(batch, BATCH_TIMEOUT_MINUTES);
    processResults(batch);
}
```

**要点：**
- 不一次性提交所有 Future（可能数万个），防止 Future 对象内存堆积
- 逐批等待 + 处理，保证内存可控
- 超时兜底：`CompletableFuture.get(timeout, TimeUnit)`，防止死等

```java
private void waitForBatch(List<CompletableFuture<UploadResult>> batch, long timeoutMinutes) {
    try {
        CompletableFuture.allOf(batch.toArray(new CompletableFuture[0]))
                .get(timeoutMinutes, TimeUnit.MINUTES);
    } catch (Exception e) {
        long done = batch.stream().filter(CompletableFuture::isDone).count();
        log.warn("批次等待超时，已完成 {} / {}", done, batch.size());
    }
}
```

### 2.7 数据分片并行 —— 大 List 拆成多片处理

```java
// P012 数据量可能非常大（10万+），拆成 5 片并行
int chunkSize = Math.max(2000, dataList.size() / 5 + 1);
Semaphore sem = new Semaphore(5);
for (int i = 0; i < dataList.size(); i += chunkSize) {
    int end = Math.min(i + chunkSize, dataList.size());
    List<Map<String, Object>> chunk = dataList.subList(i, end);
    sem.acquire();
    CompletableFuture.runAsync(() -> {
        try {
            // 每片内部做：批量删除 → 逐条解析写库
            bulkDeleteByPatentIds(...);
            for (Map<String, Object> data : chunk) { ... }
        } finally { sem.release(); }
    }, pool);
}
CompletableFuture.allOf(futures).join();
```

**分片原则：**
- 每片至少 2000 条，确保分摊线程调度开销
- 片内操作尽量独立，片间无共享状态
- 片数控制在 3~8（匹配 CPU 核数或数据库连接数）

### 2.8 分批 DELETE —— 兼容达梦 IN 列表限制

```java
private void bulkDeleteByPatentIds(List<String> patentIds, String... tables) {
    if (patentIds == null || patentIds.isEmpty()) return;
    List<String> ids = patentIds.stream().filter(id -> id != null && !id.isEmpty())
            .distinct().collect(Collectors.toList());
    if (ids.isEmpty()) return;

    int chunkSize = 2000;  // ★ 达梦 IN 列表上限约 5000，选择保守值 2000
    String sqlBase = "DELETE FROM YYBIP.";
    for (int i = 0; i < ids.size(); i += chunkSize) {
        int end = Math.min(i + chunkSize, ids.size());
        String inClause = ids.subList(i, end).stream()
                .map(s -> "'" + s + "'")
                .collect(Collectors.joining(","));
        for (String table : tables) {
            ymsJdbcApi.update(sqlBase + table + " WHERE patent_id IN (" + inClause + ")",
                    new SQLParameter());
        }
    }
}
```

**要点：**
- 先 distinct 去重，减少 IN 列表长度
- 分片大小 2000 是保守值（达梦实际情况可能支持更大，但留足余量）
- 支持多表批量删除

### 2.9 batchUpdate 批量写入

```java
// ✅ 用 batchUpdate 代替逐条 insert
private <T> void batchInsert(String sql, List<T> items, ParamBuilder<T> builder) {
    List<SQLParameter> batch = new ArrayList<>();
    for (T item : items) {
        batch.add(builder.build(item));
    }
    ymsJdbcApi.batchUpdate(sql, batch);
}

// 泛型构建器接口
@FunctionalInterface
private interface ParamBuilder<T> {
    SQLParameter build(T item);
}
```

**对比：**
```java
// ❌ 逐条 insert：N 次网络往返 + N 次事务
for (Map<String, Object> item : list) {
    ymsJdbcApi.update(sql, createParam(...));
}

// ✅ batchUpdate：1 次网络往返
batchInsert(sql, list, item -> createParam(patentId, pn, item.get("name")));
```

### 2.10 skipStream —— 必须主动消费被跳过的 ZIP Entry

```java
private void skipStream(InputStream inputStream) throws IOException {
    byte[] buffer = new byte[8192];
    while (inputStream.read(buffer) != -1) {}
}
```

**要点：**
- ZIP 中不处理的 entry（如非 PDF 文件），必须把 InputStream 读完
- skip() 不可靠（某些流实现不支持），用 read 到 -1 最安全
- 8KB 缓冲区，复用缓冲区减少 GC

### 2.11 内存去重 —— 处理同一 JSON 中重复的专利

```java
private void save(String entryName, List<Map<String, Object>> dataList) {
    Set<String> seen = new HashSet<>();
    List<Map<String, Object>> deduped = new ArrayList<>();
    for (Map<String, Object> d : dataList) {
        String pid = (String) d.get("patent_id");
        if (pid == null || seen.add(pid))
            deduped.add(d);
    }
    if (deduped.size() < dataList.size()) {
        System.out.println("[去重] " + dataList.size() + " → " + deduped.size());
    }
    dataList = deduped;  // 替换为去重后的列表
    // ... 后续路由 ...
}
```

**要点：**
- 数据源可能包含重复的 patent（如同一专利在多个 JSON 中出现）
- 内存去重成本极低（O(n)），远低于"写到一半被主键冲突回滚"
- 打印去重日志，方便了解数据质量

### 2.13 断点续传 —— 复用已有查询跳过已处理项

**适用场景：** 长耗时批量任务（文件上传、API 调用等）中断后，需跳过已完成项接着跑。

**核心思路：** 不在内存预加载"完成列表"，而是**复用已有的单条业务查询**，多加一个状态字段判断。

```java
// ❌ 方案一：预加载 HashSet（数据量大时内存不可控）
Set<String> done = queryAllDoneIds();  // 10万条 → 10MB+
for (T item : items) {
    if (done.contains(item.getId())) continue;  // 快速，但 Set 在内存
    process(item);
}

// ❌ 方案二：每次额外查一次（增加 DB 调用）
for (T item : items) {
    if (isAlreadyDone(item.getId())) continue;  // 每条多 1 次 DB 查询
    process(item);
}

// ✅ 方案三：复用已有的查询（零额外成本）
for (T item : items) {
    Map<String, Object> record = queryByBizId(item.getId());  // ← 本来就要查的
    if (record == null) { skip(); continue; }
    if (isNotEmpty(record.get("status_field"))) { skip(); continue; }  // ← 多取一个字段，无额外开销
    process(item);
}
```

**方案对比：**

| 方案 | 内存 | DB 查询次数 | 适用数据量 | 长期退化 |
|------|------|-----------|-----------|---------|
| HashSet 预加载 | HashSet 存 N 条 | 1 + 0 | < 5 万 | 逐年膨胀 |
| 额外逐条判断 | 0 | 1 + N（加倍） | 不限 | 无 |
| **复用已有查询** | 0 | N（不变） | **不限** | **无** |

**选型决策：**

| 场景 | 推荐方案 |
|------|---------|
| 数据量 < 1 万 + 已有查询为空 | HashSet 预加载 |
| 数据量 > 1 万，或数据会持续增长 | **复用已有查询** |
| 循环里原本没有 DB 查询 | 额外逐条判断（1 次额外 DB 可接受） |
| 状态字段在同一表且已有索引 | 复用已有查询（最优） |

**本例落地（智慧芽 PDF 上传）：**

```java
// 只需改两处：

// 1. SQL 多查一个字段
// 改前：SELECT patent_id, pn FROM YYBIP.ods_zscq_p012_patent WHERE pn = ?
// 改后：
String sql = "SELECT patent_id, pn, zlbg FROM YYBIP.ods_zscq_p012_patent WHERE pn = ?";

// 2. 循环里加一行判断

    skipStream(zis); zis.closeEntry(); uploadedSkipCount++; continue;
}
// ... 原来上传逻辑不变 ...
```

### 2.14 HTTP 调用重试与超时 —— 应对下游服务不稳定

**适用场景：** 批量 HTTP 调用（上传/API）时，总有一部分因下游服务波动而超时失败。

**问题模式：**

```
单次上传 65 秒，HTTP 读超时 30 秒
→ 服务端响应慢于 30 秒 → 超时断开 → 该条永久丢失
→ 但实际有 80%+ 的请求能成功（耗时 65 秒）
→ 说明不是超时设得太短，是服务器偶尔慢过阈值
```

**解决方案：指数退避重试**

```java
CompletableFuture<Result> future = CompletableFuture.supplyAsync(() -> {
    int maxRetry = 3;
    long baseDelay = 2000;  // 2秒起步
    for (int retry = 0; retry < maxRetry; retry++) {
        try {
            return Result.success(remoteCall(params));
        } catch (TimeoutException e) {
            if (retry == maxRetry - 1) {
                log.error("调用失败(重试{}次): {}", maxRetry, params, e);
                return Result.fail(e.getMessage());
            }
            // 指数退避：2s → 4s → 8s（也可用随机抖动避免惊群）
            Thread.sleep(baseDelay * (1L << retry));
        }
    }
    return Result.fail("max retry exceeded");
}, pool);
```

**重试策略参数选择：**

| 参数 | 建议值 | 原因 |
|------|--------|------|
| 最大重试次数 | 2~3 | 重试过多延误整体进度 |
| 初始退避时间 | 2~5 秒 | 给服务端喘息时间 |
| 指数因子 | 2 | 2s→4s→8s 总耗时 14s，可接受 |
| 仅重试超时？ | 是 | 业务错误（404/参数错误）重试无意义 |
| 超时时间设置 | 不改或微调 | 重试在应用层解决，底层超时可保守 |

**与超时配置的配合：**

| 策略 | 优点 | 缺点 |
|------|------|------|
| 加大超时（如 30s→120s） | 简单，一次改动 | 影响全局，hang 更长 |
| 加重试（不改超时） | 精准兜底，不影响其他调用 | 需要改代码 |
| **两者都做** | 最稳健 | 改动较多 |

> **推荐**：先加重试（改动小、风险低），观察失败率；如果 3 次重试后仍有失败，再考虑加大超时。

## 三、经验总结

### 核心原则：六字口诀

> **分** — 分批处理、 **流** — 流式解析、 **控** — 控制并发、 **断** — 断点续传、 **重** — 重试兜底、 **观** — 可观测性

### 决策清单

| 问题 | 判断 | 方案 |
|------|------|------|
| 数据量有多少？ | < 1000 条 | 单线程处理即可 |
| | 1000 ~ 10万 | 线程池 + batchUpdate |
| | > 10万 | 分片并行 + Semaphore 限流 |
| 文件是否是大 JSON？ | > 100MB | Jackson 流式解析 |
| 数据库是否为达梦？ | 是 | IN 列表分片 2000、Semaphore ≤ 5 |
| 是否需要上传文件？ | 是 | 动态线程池 + 分批等待 |
| 是否需断点续传？ | 是 | 复用已有查询，不预加载全集 |
| 下游服务是否不稳定？ | 是 | 指数退避重试（2~3次） |
| 耗时是否超过 5 分钟？ | 是 | 必须打印各阶段耗时日志 |

### 代码模板速查

```java
private static final ThreadPoolExecutor EXECUTOR = new ThreadPoolExecutor(

    new ThreadFactoryBuilder().setNameFormat("task-%d").build(),

        try { process(item); } finally { sem.release(); }
    }, EXECUTOR));
}
CompletableFuture.allOf(futures.toArray(new CompletableFuture[0])).join();

// 3. 分批 DELETE（兼容达梦）
int BATCH = 2000;
for (int i = 0; i < ids.size(); i += BATCH) {
    String in = ids.subList(i, Math.min(i + BATCH, ids.size()))
        .stream().map(s -> "'" + s + "'").collect(Collectors.joining(","));
    ymsJdbcApi.update("DELETE FROM T WHERE id IN (" + in + ")", new SQLParameter());
}

// 4. batchUpdate
List<SQLParameter> batch = new ArrayList<>();
for (T item : list) { batch.add(buildParam(item)); }
ymsJdbcApi.batchUpdate(sql, batch);

// 5. 流式解析 JSON
JsonFactory factory = new JsonFactory();
factory.disable(JsonParser.Feature.AUTO_CLOSE_SOURCE);
try (JsonParser parser = factory.createParser(inputStream)) {
    while (parser.nextToken() != null) {
        if (parser.currentToken() == JsonToken.START_OBJECT) {
            Map<String, Object> obj = mapper.readValue(parser, Map.class);
            // 处理 obj
        }
    }
}

// 6. 断点续传：复用已有查询跳过已完成项
for (T item : items) {
    Map<String, Object> rec = queryByBizId(item.getId());  // 本来就要查的
    if (rec == null || isNotEmpty(rec.get("status"))) continue;  // 已处理则跳过
    process(item);
}

// 7. 指数退避重试
for (int retry = 0; retry < 3; retry++) {
    try { return doRemoteCall(params); }
    catch (TimeoutException e) {
        if (retry == 2) throw e;
        Thread.sleep(2000L * (1L << retry));  // 2s → 4s → 8s
    }
}
```

### 反模式（禁止项）

| 反模式 | 问题 | 正确做法 |
|--------|------|----------|
| `new LinkedBlockingQueue<>()` 无参构造 | 无界队列 → 任务堆积 → OOM | 指定容量，如 `new LinkedBlockingQueue<>(50)` |
| `Executors.newFixedThreadPool()` | 无界队列，同上 | 用 ThreadPoolExecutor 显式指定队列 |
| `DiscardPolicy` / `AbortPolicy` | 丢任务 / 抛异常中断流程 | 用 `CallerRunsPolicy` 主线程兜底 |
| 一次性 `readValue(stream, List.class)` | 大 JSON → 内存爆炸 | Jackson 流式解析 |
| 逐条 `update()` 插入 | N 次网络往返 | `batchUpdate()` |
| `IN (...)` 列表不拆分 | 达梦超过上限报错 | 每批 2000 |
| ZIP entry 不读就 close | 流污染、后续 entry 读取异常 | `skipStream()` 读完 |
| 不设 Semaphore 直接并行 | 连接池被打爆，全链路雪崩 | Semaphore(3~5) |
| 无超时的 `CompletableFuture.get()` | 一个线程 hung 住，整体卡死 | `get(timeout, TimeUnit)` |
| 不打印分阶段耗时 | 出问题无法定位瓶颈 | 每个阶段 `System.currentTimeMillis()` |

### 调优优先级

1. **先打日志** → 定位真正的瓶颈（IO？CPU？DB？）
2. **流式解析** → 解决大文件内存问题（见效最快）
3. **batchUpdate** → 解决 DB 写入慢（10x+ 提升）
4. **分批 DELETE** → 解决达梦 IN 超限报错
5. **Semaphore 限流** → 解决连接池打爆
6. **分片并行** → 解决单线程 CPU 瓶颈
7. **有界队列** → 解决内存无限增长
