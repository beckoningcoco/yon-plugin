# 会计科目保存调用链

> 本文件是**实体档案**，按维度分节。要加新维度就**加一节**，不要重写整篇。
> 总索引：[_call-chain-archive-index.md](./_call-chain-archive-index.md)；采集口径见 [_call-chain-collection-standard.md](./_call-chain-collection-standard.md)。
> **行号与类名均来自 NCC2505 的 jar**，换版本可能漂移；类名与调用顺序比行号稳定。

## 1. 什么时候读我

- 要知道**会计科目保存/修改/删除，代码从哪进、在哪落库**（`bd_account` + `bd_accasoa` + `bd_accass`）
- 要**理解"科目表按期间分期"这件事在代码里怎么落地**——同一科目在不同科目体系版本里落在
  `bd_accasoa` 还是 `bd_accasoahistory`，由 `pk_accchart` 的 `endperiod` 是否为 `9999-99-99` 决定（第 6 节）
- 要**挂事件监听器**：mdId `23a89307-5992-460e-95dd-c628c85f7f95`
- 要**加校验**：新增与修改各挂 6 个校验器，**新增用 `AccountUniqueValidator`、修改用 `AccountWithHistoryUniqueValidator`**（第 9 节）
- 要**排查"同一科目表下保存被别的用户挡住"**——锁粒度是**科目体系（`pk_accsystem`）**，不是单个科目（第 10 节）
- 要**改编码段规则**：`getCodeRule()` 从 `bd_accsystem.acccoderule` 解析，不是科目自己的字段（第 12 节）

## 4. 入口 action 的分支

只有两个主分支，由 `pk_account` 是否为空判定（:57-65）：

| 条件 | 调用 | 返回 |
| --- | --- | --- |
| `pk_account` 为空 | `serv.insert(headvo)[0]` | `saveMode="add"` |
| `pk_account` 非空 | `serv.update(headvo)[0]` | `saveMode="update"` |

返回体只有四个字段（:66-71）：`saveMode` / `code` / `pk_chart`（取 `pk_currentchart`）/ `pk_account`。

**action 层做掉的字段兜底**（`modifyAccountVO:74-109`）：
17 个 UFBoolean 字段（`incurflag`、`balanflag`、`bothorient`、`inneracc`、`outflag`、`balancetype`、
`bankacc`、`billdate`、`billnumber`、`billtype`、`innerinfo`、`quantity`、`price`、`combineform`、
`endflag`、`allowclose`）为空时置 FALSE；`dataoriginflag` 空则 0；
清 `modifier` / `modifiedtime`；**新增时**（`pk_account` 空）清掉
`dispname`~`dispname6`、`ts`、`innercode`、`pk_currentchart`、`pk_originalaccount`、`creationtime`、`creator`。

> 保存前的字段兜底写在 **action** 层而不是 service，说明这些字段由前端"看起来有值"其实要后端定。
> 改科目保存逻辑时**先看这里**，别只改 service。

## 7. 编码规则

`AccountOptBase.getCodeRule:154-159`：
```java
AccountCodeUtil.parseCodeRule(AccountBGUtil.getCodeRuleByChart(pk_accchart))
```
`getCodeRuleByChart:202-209` 的 SQL 是裸的：
```sql
select acccoderule from bd_accsystem
where pk_accsystem = (select pk_accsystem from bd_accchart where pk_accchart = ?)
```
取不到或不止一条 → 抛 `010140accb0185`。

编码段规则的用法：
- `AccountCodeUtil.getAccLev(code, codeRule)` → 科目级次（:549）
- `AccountCodeUtil.getParentCode(code, codeRule)` → 父科目编码（:554、`AccountBGUtil:450`）
- `AccountCodeUtil.getTopCode(code, codeRule)` → 顶级科目编码（`AccountBGUtil:461`）
- 校验器 `AccountCodeValidator(getCodeRule())`（:119）

> **科目的编码规则不在科目上，在科目体系制度（`bd_accsystem.acccoderule`）上**。
> 要改"科目编码几位一级"，改的是科目体系制度，不是科目，也不是系统参数。

## 9. 校验框架（三层）

**第一层：`AccountServiceImpl` 前置**——`AccDistEditableChecker.check(...)`（分布式部署下"这个节点能不能改"）
+ `checkNameAndCode(vo)`。每个动作都做，位置在命令类之前。

**第二层：命令类的框架校验**——`AccountOptBase.validate:106-108` =
`ValidationFrameworkUtil.createValidationService(validators).validate(vo)`。

**新增（`insertAccountHistory:119`）6 个**：
`AccountCodeValidator(getCodeRule())`、**`AccountWithHistoryUniqueValidator(getCodeRule())`**、
`AccObligateValidator`、`AccAssMaxNumValidator(…010140accb0306,{9})`、`AccountCtrlLevelWithHistoryValidator`、
`RefPkExistsValidator({pk_acctype})`

**新增（`insertAccount:73`，不带历史那条路）6 个**：同上，但
`AccountUniqueValidator` 代替 `AccountWithHistoryUniqueValidator`、`AccountCtrlLevelValidator` 代替
`AccountCtrlLevelWithHistoryValidator`。

**第三层：继承场景校验**（只在 `accLev > 1` 时）：
- `beforeInheritValidate(vo, parentVO)`（:318-323）：父科目 `enablestate == 3`（已停用）→ 抛 `010140accb0215`；
  再 `validate(vo, new AccParentVOValidator(parentVO))`
- `afterInheritValidate(vo)`（:307-310）：`AccountFieldCtrlValidator(getSystemId(), getCodeRule())` +
  `AccAssMaxNumValidator(010140accb0310, {9})`

**删除（`AccountOptDelete.validate:293-300`）2 条硬校验**（见 5.4）。

## 10. 事务与锁

| 机制 | 调用点 | 实际行为 |
| --- | --- | --- |
| 锁粒度 | `AccountBGUtil.lockAccChartVO:477-484` → `lockAccSystem:491-493` → **`BDPKLockUtil.lockString(new String[]{pk_accsystem})`** | **锁的是科目体系制度（`pk_accsystem`），不是科目、也不是科目体系（`bd_accchart`）** |
| 版本校验 | `checkVersionAndLock:465-475`：`retrieveByPK(AccChartVO)` 后 lock，再查 `endperiod != "9999-99-99"` → 抛 `VersionChangedException(010140accb0188)` | 不许往历史科目体系里写 |
| 新增用哪个 | `insertAccountHistory` 用 `lockAccChartVO`（:116，**只锁不校验期间**） | 与 `checkChartVersionAndLock` 的差别就是少了 endperiod 那条校验 |
| 修改用哪个 | `checkChartVersionAndLock`（:70、`updateAccountHistory`） | 校验 + 锁 |
| 删除用哪个 | `lockAccChartVO`（:86）+ `checkVersionWithHistory(vo)` | — |
| 独立事务 | 未见 `_RequiresNew` 命名方法 | 命令类**没有**名字带 `_RequiresNew` 的方法（与供应商/物料不同） |
| 容器事务 | 未读 UPM | **没查** `AccountServiceImpl` 的 `tx` 属性 |

> **一次科目保存会锁住整本科目体系制度**。两个用户在同一科目体系下同时保存不同科目，
> **后到的会等**（`BDPKLockUtil.lockString`）。这与客户/供应商/物料锁单条或版本链**完全不同粒度**，
> 排查"保存转圈/锁超时"时要想到这一条。

## 11. 与 BD 通用模板的差异（本档案最该记住的）

| 维度 | 供应商 / 物料（BD 通用模板） | 会计科目 |
| --- | --- | --- |
| 服务实现基类 | `extends BDSingleBaseService<T>` | **不继承**，`implements IAccountService` |
| 业务逻辑在哪 | `XxxServiceImpl` 自己（+父类十步模板） | **在命令类里**（`AccountOptInsert` 等），Impl 只有四行委托 |
| 持久化 | `dbInsertVO` → `getPersistenceUtil().insertVO` → `VOPersister` | `getMdService().saveBill(vo)` 或 **直接 `getBaseDAO().insertVOWithPK`** |
| 事件 | `fireBeforeInsertEvent`（父类统一） | `AccountOptBase` 自己封的 `fireBeforeInsert`（内部还是 `BDCommonEventUtil`） |
| 校验器组装 | `getInsertValidator()` / `getUpdateValidator()` 覆写返回数组 | 在命令类方法体里 `new Validator[]{...}` 硬编码 |
| 版本机制 | 版本表 `_v` + `latest` 标志 | **期间分割**：当期表 `bd_accasoa` vs 历史表 `bd_accasoahistory`，靠 `AccChartVO.endperiod` 判定 |
| 锁 | `BDPKLockUtil.lockSuperVO` + `BizlockDataUtil.lockDataByBizlock`（单条/版本链） | **`BDPKLockUtil.lockString(pk_accsystem)`（一整本体系）** |

> 看到"科目保存"不要再去找 `insertVO` 十步模板——**找不到的**。
