> 来源：2026-10，与使用者讨论「接到一张报表需求后能否有固定结构化产出」时确立。
> 关联：[[07-经验-语义模型报表开发]]（口径与静默错误）、[[05-经验-组织树与子级数量统计]]、
> [[../报表设计器/08-操作手法与判据纪律]]（判据纪律）。
> 模板：`bip/assets/report/报表开发确认单-模板.md`（可直接复制）。

## 一、这张单是什么

**一句话**：接到报表需求、把**需求与字段确认完**之后，模型产出的**唯一施工依据**。

对标供应商的采购单，它有四个特征，缺一不可：

| 采购单 | 本单 |
|---|---|
| 双方确认才生效 | 业务方确认口径，模型确认物理落点；**待确认项清零**才算确认 |
| 逐条列项（品名/规格/数量/单价） | 逐字段列项（表样位置/表头/口径/物理落点/取数逻辑/验证方法） |
| 履约依据 | 后续 SQL、语义模型、设计器配置**全部引用它的字段序号**，不再各自解释口径 |
| 变更要改单 | 口径变更出 **v2**，写明"第 N 版替代第 N-1 版"，旧版留痕 |

**没有这张单会怎样**：口径散在聊天记录、表样截图和 SQL 注释里，等到验收时发现某个字段理解错了，
没人能说清是哪一步偏的——返工成本是整张表重做。

---

## 二、它在流程里的位置

```text
01 接单（口头：项目 / 产品线 / 大概做什么）
  → 材料归档 user/（表样 + 字段取值逻辑文档）
  → 对齐两份材料，产出本单 + 待确认项
  → 业务方答复待确认项 ← ← ← 这一关不过，不写 SQL
  → 冻结（= 订单确认）
02 物理落点 → 03 SQL（库上验证）→ 04 语义模型 → 05 展现层 → 06 验收 → 07 交付
```

## 三、与需求条目的分工（别混）

| | 放什么 | 能否改写 |
|---|---|---|
| **需求条目**（`requirement_create`） | 使用者**要什么**——他的原话、目标、范围、明确不做的 | **不可改写**；新事实用 `requirement_annotate` 追加 |
| **本单**（条目 `generated/`） | 双方**确认下来怎么算**——口径、物理落点、参数、验收判据 | **可版本化**；同名覆盖时旧版自动进 `.history` |

两样分开，日后才分得清"是他要的和做出来的不一致"还是"做的过程理解偏了"。

|---|---|---|

## 五、两条填写纪律 【硬规则】

1. **物理落点一律先查后填**：先 `bip_meta_find` / `ncc_meta_find` / `bip_meta_detail`，
   查不到再 `datasource_query` 实测（先 `COUNT` 看哪列真有数，再 `GROUP BY` 看值域）。
   特征字段（`vcolN` / `bcolN` 类）的列位**不可外推**——同一套业务模型换个对象列位就变，
   按 [[07-经验-语义模型报表开发]] §2.6 的做法先问使用者，再用实测排掉。
2. **业务口径只录原话，不做转写**：他写"未销户账户数"，就记"未销户账户数"。
   模型的解读写进「取数逻辑」列，两列分开放，是他给的和我想的分得清。

## 六、确认单冻结后的施工路线（六个阶段）

确认单一冻结，施工令生效。顺序不能反：**数据层在库上先跑到对，展现层再进平台配，最后用权威源对账**。
反过来做（先进设计器边配边试）会把大量时间烧在平台的调试成本上。

| 编号 | 阶段 | 做什么 | 权威判据 | 主要翻车点 |
|---|---|---|---|---|
| **02** | 物理落点核实 | 把 `_01` 里标 `<待查>` 的格子填满：元数据查 → 库上实测 | 每个字段都能指到 `表.列`，且该列**确实有数据** | 特征字段列位外推；元数据登记的列位与实落列位不一致 |
| **03** | SQL 构建（**全在库上**） | 分段落单跑 → 拼装 → 恒等式对拍 → 三类静默错误专项 → 方言错误码 | `datasource_query` 直查出数；**非零数能由明细推导**、恒 0 数能解释原因 | 一对多派生表扇出（数字虚高不报错）；关联键跨 ID 空间（恒 0 不报错）；口径只改了一处 |
| **04** | 语义模型 | SQL 进模型 → 声明参数 → 脚本编辑器执行验证 → 保存 | 模型「执行」出数正确 | 参数不包单引号；`<#else>` 分支平台校验覆盖不到，默认值那支要**自己单独跑一遍**；保存弹「已被对象引用」**必须点「修改」** |
| **05** | 展现层配置 | 挂数据集 → 绑字段 → 表样增删列/写字 → 筛选器 → 参数绑定（三个下拉）→ 合计行（**独立数据集+独立参数，各绑一遍**）→ 超链接 | 服务端定义 `GET /iuap-data-analytic/report/design/<报表ID>` 里有这个东西 | 名称框不认合成事件；值字段只认 CDP 真实拖拽；`setDataAtCell` 只在内存、保存不进去 |
| **06** | 端到端验收 | 拿 `_01` 第 6 章逐条打勾；与 `_03` 取数验证记录对账 | 报表预览 = 语义模型预览；筛选器**实测**生效；明细与合计共享列一致 | 拿界面提示 / DOM 变化 / hook 记录当证据——**一律不算** |
| **07** | 交付与沉淀 | 发布 / 授权 / 挂菜单 → 交付说明 → 条目 `requirement_annotate` → 知识库回写 | 使用者在真实菜单里、用自己的账号能看到正确数 | ⚠️ **发布授权段尚未实测**，第一次做时当场补进 [[../报表设计器/00-设计器总览与操作纪律]] |

**一个中途检查点**：**04 结束就停下来给使用者核一次数**，再做 05。展现层配完才发现口径错，等于白配一遍；
这时候改口径的成本只是一段 SQL。

**打回纪律**：施工中发现口径写错、或某字段库上根本找不到 → **回 `_01` 出第 2 版**，
写明"第 2 版替代第 1 版"，**不要就地把 SQL 改了**。就地改会让确认单与实现脱钩，下次谁也说不清哪版是真的。

## 七、产出物清单与命名规范

编号即阶段号，**按文件名排序就等于按流程顺序**。

| 编号 | 产出物 | 文件名 | 必备 | 谁消费 / 不出的后果 |
|---|---|---|---|---|
| **01** | 报表开发确认单 | `报表开发确认单_01.md` | ✅ | 我施工 + 使用者核对；不出＝口径无锚点 |
| **02** | 字段核查（特征字段列位、关联键这类曲折排查） | `字段核查_02-<对象>.md` | 按需 | 下次做同类报表的自己；排查很费劲时才值得留 |
| **03** | 取数 SQL | `取数SQL_03-<报表名>.sql` | ✅ | 语义模型直接引用、返工、使用者复核 |
| **03** | 取数验证记录（库上每个关键数字 + 推导链） | `取数验证记录_03.md` | ✅ | 06 验收的对账基准；不出＝半年后没人能证明数算对了 |
| **05** | 平台定义快照（接口原样存档） | `平台定义快照_05-<报表ID>-<日期>.json` | 建议 | 改前改后对比、误改恢复、被人复制这张报表 |
| **06** | 验收记录（`_01` 第 6 章逐条打勾 + 证据） | `验收记录_06.md` | ✅ | 交付凭证、日后复查 |
| **07** | 交付说明（怎么用、口径要点、遗留项） | `交付说明_07.md` | ✅ | 使用者 + 接手的下一个人 |

**阶段性结论不单独产出文档**的三处：

- **04 语义模型**：参数编码 / 类型 / 默认值**回填 `_01` 第 3 章**，不另开文件
- **05 展现层**：配置说明**不手写** —— 权威源是平台定义，手写的必然与之脱钩，一律用 `_05` 快照代替
  （除非要给别人照着配一遍，那才值得写操作说明）
- **02 物理落点**：结论回填 `_01` 第 2 章，只有排查很费劲时才留 `_02`

### 命名规则

```text
<产出物名>_<两位阶段号>[-<细节>].<扩展名>
```

- 阶段号**固定两位**（`_01`…`_07`），保证字典序 = 流程顺序
- 细节段可选：报表名、对象名、报表ID、日期
- **版本号默认不写进文件名**，写在正文头部与变更记录里；同名覆盖时旧版自动进 `.history`（可回查）
- 只有需要**并存多版**（如两套并行口径）时才用 `-v2` 后缀，并在需求条目标注里写明"第 N 版替代第 N-1 版"
- 全部落在需求条目的 `generated/` 下

### 三条收敛原则

1. **有下游消费者才产出** —— 没有下一个动作会读它，就不写
2. **能存权威快照的，绝不手写描述** —— 这正是 05 不写配置说明的原因
3. **与客户口径绑定的留条目，可复用的进知识库**：
   - 某客户的账户口径、某张表的字段映射 → `generated/`（换客户就没用）
   - "达梦递归 CTE 要写列别名"这类跨项目成立的方法 → 知识库（`wiki_write`）
   - 与某个具体项目绑定的踩坑现场 → 项目记忆（`memory_write`）

## 附录 A：表样确认 6 问（表样是截图时**必须**逐条问）

截图必然丢失这些信息，而它们直接决定 SQL 怎么写：

1. **合计行 / 列在哪**，是"合计"还是"小计"（两者去重口径常不同）
2. **哪些区域是扩展区**（随数据伸缩），哪些是固定表头
3. **表头是否多级**（合并表头，如"期初 / 借方 / 贷方"之上还有一层）
4. **单位与精度**：元还是万元、几位小数、四舍五入还是截断
5. **行骨架**：某组织/科目本期没数据，是**出一行 0**（左连接）还是**整行不出现**（内连接）
   —— 业务文档几乎从不写，做错了整张表少行
6. **冻结列、打印导出、超链接跳转**要求

> 表样是 Excel 时，还要把**样例数据**与**表头/标签**分开：他贴的几行真数据只是示意，
> 不是要写进表样的固定行。

## 附录 B：字段口径确认 8 问（逐字段说明也会漏的地方）

这 8 处都属"不报错但数不对"，所以**主动逐条问**，不要等他自己写：

| # | 歧义点 | 典型问法 |
|---|---|---|
| 1 | 时间口径 | "本年累计"从 1 月 1 日还是账套启用日起？截止日含当天吗？多段 SQL 折算规则是否统一 |
| 2 | 去重键 | "账户数"按账号唯一还是账号+币种？跨机构同名账号算一个吗 |
| 3 | 过滤条件 | 作废 / 未审核单据算不算？`dr=0` 之外还有没有状态列要卡 |
| 4 | 空值归哪边 | 布尔型字段全空的那批算"否"还是"未知"，要不要单独出一列 |
| 5 | 关联键 | 跨表按**编码**还是按 **ID**？两边 ID 空间不同时匹配恒不成立、**且不报错** |
| 6 | 层级 / 上卷 | 含不含下级？含下级时汇总**不能**拿明细各行相加（会被每个上级重复计） |
| 7 | 汇总 vs 明细 | 合计与明细是否同源同口径（平台上是**两个数据集、两个参数**，要各绑一遍） |
| 8 | 行骨架 | 同附录 A 第 5 条 |

第 5、6、7 条对应 [[07-经验-语义模型报表开发]] 里真实踩过的坑（三类静默错误、组织树三个 ID 空间、
上卷不能相加），不是理论担心。

## 附录 C：两份材料的对齐校验

表样说"有 18 列"、文档说"每个字段怎么取值"——这两份材料天生对不上。对齐时必然浮出三类问题，
**单独列成待确认项，不埋在正文**：

| 现象 | 处理 |
|---|---|
| 表样有这列，文档没写取值逻辑 | **缺口径，必须问** |
| 文档写了，表样上没这列 | 是漏画还是不要了？**问** |
| 两边都有但对不齐（文档说按账号去重，表样上却有"币种"列） | **口径冲突，问** |

## 附录 D：什么时候算过关

**待确认项清零**（或明确书面挂账）后，单据状态改「已确认」，版本冻结 v1。
此后：

- SQL、语义模型、设计器配置**引用字段序号**（如"2 字段 #3"），不再另行解释口径；
- 验收直接拿第 6 章逐条打勾；
- 口径要改 → 出 v2，在需求条目标注里写明"第 2 版替代第 1 版"。
