# 销售订单保存调用链 — NCC2505

> 采集口径见 [_call-chain-collection-standard.md](./_call-chain-collection-standard.md)。
> 证据等级：**反编译**（本机无 NCC2505 数据库连接，字段未做实测；SPR 单列一轮）。
> 环境：Home = `E:/NCProject/NCC2505/HOME_BYZY_BIP`。
>
> ⚠️ **本档案是前 6 份的反例**：销售订单**不走**任何一套 BD 基础档案模板
> （既不是 `SingleBaseService`、也不是 `MultiManageTypeBaseService`、也不是 `TreeBaseService`），
> 而是一条 **`PFlow`（单据流程引擎）** 通道。前 6 份学到的"十步模板"在这里**一步都对不上**。

## 1. 什么时候读我

- 客开要**在销售订单保存前后插手**，或者想知道"销售订单保存到底调了哪些规则"。
- 要判断**销售订单走的是事件订阅还是规则链**——本档案给出取证结果：**两者都不是纯的，是 PFlow + 规则**。
- 排查「保存报错但没有堆栈指向业务类」「保存时单据状态被重置」「收款金额被改写」这类现象。
- 需要知道**服务层为什么只有 171 行**——业务逻辑不在这里。

## 5. 服务层的三步（`SaleOrderMaintainWebServiceImpl`）

```java
public SaleOrderVO save(SaleOrderVO vo, SaleOrderUserObject invoiceuserobj) throws BusinessException {
    this.beforeCheck(vo);                                  // ① 业务前置校验
    vo = this.process(vo, invoiceuserobj);                 // ② PFlow 流程
    this.doAfterAction(vo);                                // ③ 保存后金额回写
    return vo;
}
```

**① `beforeCheck:114-121`** 三项：
| 项 | 方法 | 内容 |
| --- | --- | --- |
| 收款超限 | `checkGathering:129` | `bpreceiveflag` 为真且 `npreceivequota < npreceivemny` → 拼 `4006011_0/04006011-0283` + 单据号 + `-0468` 抛错 |
| 状态重置 | `reSetBillStatusForNoPass:123` | `fstatusflag == BillStatus.NOPASS` → **重置为 FREE**（"未通过"的单据再存一次就回到自由态） |
| 赠品类型 | `checkCarsubtypeid:146` | 交易类型 `blrgcashflag` 为真时 `carsubtypeid` 必填，否则抛 `-0506` |

**② `process:53-82`**（PFlow 装配）：
```java
CloudPFlowContext context = new CloudPFlowContext();
context.setActionName("WRITE");                     // ★ 动作名
context.setBillType("30");                          // ★ 单据类型（销售订单 = 30）
context.setBillVos(new SaleOrderVO[]{vo});
PfUserObject userObj = new PfUserObject();          // 包装两层：userObj → userObj1 → invoiceuserobj
userObj.setUserObject(invoiceuserobj);
userObj1.setUserObject(userObj);
context.setUserObj(new PfUserObject[]{userObj1});
SaleOrderVO bill = (SaleOrderVO)service.exeScriptPFlow(context)[0];
// 回填：真实子表覆盖回 vo（跳过 status==3 的行），再按 rowid 合并
new ClientBillCombinServer().combine(new SaleOrderVO[]{vo}, new SaleOrderVO[]{bill});
```
> **`PfUserObject` 套两层**是平台约定：外层放框架参数、内层放业务 userObject（本处就是 `SaleOrderUserObject`）。
> 客开在动作处理器里取业务参数时要按这个层数取。

**③ `doAfterAction:158-170`**（金额回写，**不要跳过这段**）：
```java
VOKeyValue keyValue = new VOKeyValue(vo);
UFDouble thisreceivemny = keyValue.getHeadUFDoubleValue("nthisreceivemny");
UFDouble receivedmny   = keyValue.getHeadUFDoubleValue("nreceivedmny");
```

—— **"保存后 `nreceivedmny` 变了、`nthisreceivemny` 变 null"就出在这**，而 `ntotalorigmny` 是它的上限。

## 6. PFlow 引擎怎么判动作（`NCCloudScriptPFlowServiceImpl`）

`procFlow:39-145` 的判据**全靠 `actionName` + `billType` 两个字符串**，用 `PfUtilBaseTools` 判类型：

| 判定 | 方法 | 效果 |
| --- | --- | --- |
| 撤回/反保存 | `isRecallAction(...)` \|\| `isUnSaveAction(...)` | 走 `runScriptPFlow_UnSaveNoFlowBatch` |
| 新保存/新启动 | `isNewSaveAction(...)` \|\| `isNewStartAction(...)` | 走 `runScriptPFlow_CommitNoFlowBatch(New)` |
| 保存/启动（线程内） | `isSaveAction(...)` \|\| `isStartAction(...)`（`exeScriptPFlowOnThread:253`） | 若单据 `isapprovebill` 为真 → `commitAction`，否则 `procFlow` |

**关键：`hasFlow` 判定（:92-99）**——逐张单据查它有没有配流程：
```java
boolean isApprove = PfUtilBaseTools.isNewSaveAction(actionName, billType);
boolean hasFlow = isApprove
    ? PfUtilTools.isHasStartFlow(trantype/billType, aggvo, pk_group, WorkflowTypeEnum.Approveflow)
    : PfUtilTools.isHasStartFlow(trantype/billType, aggvo, pk_group, WorkflowTypeEnum.Workflow);
if (!hasFlow) nofloiwAggvos.add(aggvo);   // 没配流程 → 走"无流程"批量通道
else          floiwAggvos.add(aggvo);     // 配了流程 → 走流程引擎
```
然后把两类分别处理、结果合并（:136-143）。
—— **"同一批单据里有的走审批流、有的不走"是平台支持的**，不是异常。

`eParam` 的两个默认开关（`procFlow:43-52`）：`NCCLOUD_ENTRY=true`、`IS_RELOADBILL=true`。

## 8. 机制判据：销售订单到底走哪条？（对照 `ncc-event-and-rule-mechanism.md`）

按该文档第 6 节的取证顺序，本次结果：

| 判据 | 结果 |
| --- | --- |
| ① Service 实现里有 `fireBeforeInsertEvent` / `fireAfterInsertEvent`？ | **没有**（`SaleOrderMaintainWebServiceImpl` 全文无 fire 调用）→ 不走第 4 节那条"事件订阅" |
| ② 有 `XxxListener extends AbsBdDocListener`？ | 未见（本档案范围内 0 命中） |
| ③ 有规则链？ | **有，但是"编辑态规则"，不是保存链规则** —— `nccloud.pubimpl.so.saleorder.operator.beforerule.*`（2 个）与 `operator.bodyafterrule.*`（25 个），每个都 `implements IBeforeRule` / 对应 after 接口 |
| ④ 录 SPR 验证？ | 未做 |

**第 ③ 项的形态**（以 `GlobalExchgrateBeforeRule` 为例）：
```java
package nccloud.pubimpl.so.saleorder.operator.beforerule;
import nccloud.dto.scmpub.pub.event.rule.IBeforeRule;      // ★ 接口来自 scmpub 模块

public class GlobalExchgrateBeforeRule implements IBeforeRule {
    public Map<String, Object> beforeEdit(Map<String, Object> userobject) throws BusinessException {
        // 判全局本位币开关，返回 {"isedit": true/false}
    }
}
```

**三点必须记住**：

1. **接口名不是 `IRule`**：这里是 `IBeforeRule`（在 `nccloud.dto.scmpub.pub.event.rule`），
   方法签名是 `Map beforeEdit(Map userobject)` —— **入参出参都是 Map**，与 `IRule.process(E[])`（对象数组）完全不同。
   `ncc_class_search('IBeforeRule')` 命中 4 个**同名接口**，分属 `mmpub` / `scctpub` / `scmpub` / `uapbd` 四个模块——
   **又一次"同名接口按 jar 分辨"**（与 `IRule` 三个同名接口同一个坑）。
2. **这批 operator 的名字是 `*EditRule`（`MaterialEditRule` / `NumEditRule` / `PriceItemEditRule` …），
   语义是"编辑某个字段时联动算另一个字段"**（物料改了算价、数量改了算金额），
   **不是"保存前校验"**。把它们当成保存链规则会答错。
3. 所以销售订单的保存链上，**规则链这一层本次没有定位到装配点**。
   真正的业务动作处理（`IPFBusiAction` 实现）未展开，规则是否在其中装配、是否读 `pub_pluginitem`，**未验**。

## 10. 与前 6 份档案的横向对照（本档案最有价值的一节）

| 维度 | 前 6 份（基础档案） | **销售订单** |
| --- | --- | --- |
| VO 基类 | `SuperVO` / `BDSingleBaseService<T>` 家族 | **`AbstractBill`** + `@AggVoInfo` |
| 表名来源 | `getDefaultTableName()` **硬编码** | **`BillMetaFactory.getBillMeta("so.so_saleorder")` 元数据反查** |
| 单据类型标识 | 无（就一张主表） | **`billType = "30"`**（字符串常量走完全程） |
| 保存入口 | `XxxServiceImpl#insertVO` 十步 | **`ICloudScriptPFlowService.exeScriptPFlow(context)`** |

## 10.5 【本档案缺口已补】第 10 跳以下：动作驱动表

> 本节是 2026-10-15 采集采购订单时补齐的（见 [采购订单保存调用链.md](./采购订单保存调用链.md) 第 5 节）。
> 补进来是因为它回答的正是本档案当时留下的最大 ⬜：**"第 10 跳以下是什么、为什么找不到业务类"**。

**① `IPFBusiAction` 的实现类找到了**：`nc.bs.pub.pf.pfframe.PFBusiAction`（2948 行）。
来源是 **UPM 反查**——`modules/riawf/META-INF/P_platform50_rt.upm` 里

`IWorkflowDefine` → `WorkflowDefineImpl`。）
**类名没有 `Impl` 后缀**，所以按 `PFBusiActionImpl` / `*SaveBP` / `implements IPFBusiAction` 搜永远 0 命中——
**"找不到实现类"时先做 UPM 反查**。

**② 业务动作处理器不在代码里，在数据库表里**——这是本档案当时最想不通的地方，答案：

```
PFBusiAction#queryActionDriveVOs:1203
  → PfUtilDMO#queryDriveAction:301 → queryDriveAction_db
    → SQL 查 pub_actionconstrict ⋈ pub_function
      → pub_function.classname + pub_function.methodname   ← ★ 真正的业务类与方法（数据，不是代码）
```

| 表 | 作用 |
| --- | --- |
| **`pub_actionconstrict`** | 一条 = "某单据类型 + 某动作类型下要执行的一个动作"；`sysindex` 定顺序、`isbefore` 定前后、`conditionXpression` 定条件、`configflag`/`operator` 定生效范围 |
| **`pub_function`** | 函数注册表：`classname` / `methodname` / `arguments` / `returntype` |
| `pub_messagedrive` / `bd_busitype` / `sm_user_role` | 关联的业务类型、消息驱动、角色 |

过滤参数是 `(pk_billtype=? or pk_billtype=?)` + `actiontype=?` + 业务类型 + 集团 ——
**其中 `actiontype` 就是本档案第 5 节的 `context.setActionName("WRITE")`**。
即：**`"WRITE"` 这个名字错了，动作驱动一条都查不到，业务逻辑一个都不会执行**。

> 对第 7 份的直接含义：`actionName="WRITE"` 不是随便起的标识，它是 `pub_actionconstrict.actiontype` 的过滤键。
> 想知道"销售订单保存到底跑了哪些业务类"，只能连库查：
> `select sysindex, isbefore, classname, methodname, conditionXpression from pub_actionconstrict c join pub_function f on c.functionid=f.pk_function where c.pk_billtype='30' and c.actiontype='WRITE' order by c.sysindex;`

**③ `IRule` 插件链被再次排除**：`PFBusiAction`（2948 行）全文**无** `RuleCollection` / `IRule` / `pub_pluginitem`，
用的是 `IPfExchangeService`（单据转换）与 `MDPersistenceService`。本档案第 8 节"没定位到规则链装配点"，
现在可以收敛为：**这类单据走的是动作驱动表，不是 `IRule` 插件链**。
