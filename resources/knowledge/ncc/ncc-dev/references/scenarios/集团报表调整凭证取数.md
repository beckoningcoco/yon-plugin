# NCC 集团报表「调整 / 分摊凭证」取数（epmp → bgr vouch）

> 适用：集团报表（BGR）里按「任务定义 + 单位 + 期间」取调整凭证（个别调整、抵销、对账调整）及分录明细。
> 实测版本：**NCC 1909**，结论来自反编译（cfr）+ 真机调试 + SQL 对照。

## 一、用哪个服务，别用错的那一个

接口 `nccloud.pubitf.bgr.vouch.IBGRVoucherService`
（`modules/epmp/lib/pubepmp_nccloud.jar`，实现 `nccloud.pubimpl.bgr.vouch.BGRVoucherService`，
注册在 `modules/epmp/META-INF/ncc_vouch.upm`）。

它有两个"查凭证头"的方法，背后是两套 SQL：

| 方法 | 背后实现 | 说明 |
|---|---|---|
| `queryTaskVouchHead(cond, pageNum, pageSize, otherMap)` | `nc.bs.bcs.vouch.QueryTaskVouchHeadAction` → `QueryVouchHeadAction`（BCS 版 SQL） | **产品「调整分摊凭证单」页面用的就是它**（SPR 实录见第三节） |
| `query(cond, pageNum, pageSize, otherMap)` | `nc.bs.bgr.vouch.QueryBGRVouchHeadAction` | BGR 专用版，SQL 结构几乎一致，但**必须**给 `otherMap.showMode` |

`queryTaskVouchHead` 的两个硬约束——不是"不能用"，是"必须照产品的传法传"：

1. **必须带 `otherMap.put("funcode", "1886002005")`**：`QueryVouchHeadAction.getVouchByOrcale`
   第一句就是 `String funcode = otherMap.get("funcode").toString();`，不给直接 **NPE**；
   而 `BGRVoucherService` 只 `catch (BusinessException)`，NPE 会漏到调用方，页面上表现为静默失败。
   `1886002005` 是「调整分摊凭证单」节点的应用注册码（SPR 里那条
   `select ... from sm_appregister where code = '1886002005'` 就是它）。
2. **它按 `vbody.pk_selforg` 过滤单位**（走 `pk_org_array`，或在没给时走 funcode 的组织权限），
   且 `vouch_type` 不传时默认 `in (2,6)`。

> 而且 `funcode` 在 BCS 版里还兼职决定 `vouch_type`：`1882002000`→`in(2,6)`、
> `1880004000`→`=7`、`1880010000`→`in(4,3)`…… 用它做"取全部调整凭证"根本办不到。

## 二、`query()` 的参数怎么填（实测有效）

```java
DTOBMVouchHead cond = new DTOBMVouchHead();
cond.setPk_taskdef(pkTaskdef);              // → and vHead.key2 = ?

ArrayList orgs = new ArrayList();
orgs.add(pkEntity);
cond.setPk_org_array(orgs);                 // → and vbody.pk_selforg = ?

Map<String, String> period = new HashMap<String, String>();
period.put("ACCP", "2024");                 // 年：bcs_dynamicdim.pk_levelval 的明文
period.put("ACCM", "05");                   // 月：两位补零
cond.setPeriodDimMap(period);               // → inner join bcs_dynamicdim

cond.setVouch_type(Integer.valueOf(26));    // → vouch_type in ('2','6')，与产品口径一致

Map<String, Object> otherMap = new HashMap<String, Object>();
otherMap.put(IVoucherConstant.SHOWMODE, IVoucherConstant.SHOW_COMMEN);   // 必填

DTOBCSPageDecorator page = service.query(cond, 1, 500, otherMap);        // pageNum 从 1 开始
```

| 想过滤 | 填哪 | 平台拼出来 |
|---|---|---|
| 任务定义 | `setPk_taskdef` | `and vHead.key2 = ?` |
| 单位 | `setPk_org_array` | `and vbody.pk_selforg = ?`（**给了它就不再取登录用户的组织权限，也就不会去读 `funcode`**） |
| 期间 | `setPeriodDimMap` | `inner join bcs_dynamicdim`（只按 `pk_levelval` 匹配，key 只当别名） |
| 凭证类型 | `setVouch_type` | 位数 1 → `= ?`；位数 > 1 → `in (...)` 逐字符拆 |
| 模式 | `otherMap["showMode"]` | `SHOW_COMMEN=0` 按凭证头；`SHOW_JOURNAL=1` 按分录行 |

### 五个坑（都踩过）

1. **`pk_taskyear` / `pk_taskmonth` 传了没用**：`QueryBGRVouchHeadAction.queryPeriod` 根本不读它们，
   期间只走 `periodDimMap`。`bcs_vouch_head.pk_taskyear/pk_taskmonth` 在库里本身就是 `~`。
2. **`pk_paramentity` 是死代码**：`queryHead` 里 `String query_pk_paramentity = ...` 取到后再没出现过，
   单位过滤只能靠 `pk_org_array`（它拼的是 `vbody.pk_selforg`，不是头表的 paramentity）。
3. **`vouch_type` 不传时默认 `in(2,6)`** —— 正好是「个别调整数」（2 自动 + 6 手工）。
   要取抵销/对账调整得自己传，例如 `6347` → `in ('6','3','4','7')`。
4. **`pageNum` 从 1 开始**：内部 `between (pageNum-1)*pageSize and pageNum*pageSize`，
   传 0 会算出 `between -n and 0`，一条都取不到。
5. **`DTOBCSPageDecorator.getData()` 返回的是 `DTOBMVouchHead[]` 数组，不是 `List`**。
   `if (!(data instanceof List)) break;` 这种防御会直接把已经拿到的数据丢掉。

## 三、分录明细怎么拿

`SHOW_COMMEN` 只给凭证头：`setBodyMsg` 仅仅把摘要、编制单位名挂到头上（`setFirstNote` / `setOrgs`），
**不挂分录列表**。要明细再按头查一次：

```java
DTOBMVouchBody[] bodies = service.queryBody(head.getPk_vouchhead());
```

`DTOBMVouchBody` 注意：`debitamount` / `creditamount` 是 **String**（不是 UFDouble），
`dynamicdims` 是 `List<DTODynamicDim>`，期间就在里面（`pk_dimlevel` = `TB_DIMLEV_ACCP_00001` / `TB_DIMLEV_ACCM_00001`）。

`SHOW_JOURNAL` 能一次拿头+体，但 body 被展平进头的 `*2` 字段
（`debitamount2` / `creditamount2` / `measureName` / `dynamicdims` 维度名串），
**丢掉了 `pk_measure`**，要指标编码的场景不能用它。

## 四、SPR 实录：产品「调整分摊凭证单」到底怎么查

用 SPR 录一次这个页面的查询（远程调用名 `bcs/bgrVoucher/queryTaskVouchHead`），SQL 原文把口径说全了：

```sql
select count(distinct vHead.pk_vouchhead) from (
  ( select iorder, pk_vouchhead, ... from bcs_vouch_head head
    inner join ( select pk_detail from (
        ( select pk_detail from bcs_dynamicdim where pk_levelval = '2024' ) firsttable
        inner join ( select pk_detail from bcs_dynamicdim where pk_levelval = '01' ) tempACCM
        on firsttable.pk_detail = tempACCM.pk_detail ) ) period
    on head.pk_vouchhead = period.pk_detail ) vHead
  inner join ( select pk_vouchhead, pk_measure, pk_selforg, pk_countorg from bcs_vouch_body vbody ) vbody
  on vHead.pk_vouchhead = vbody.pk_vouchhead )
where 1 = 1
  and vHead.key2 = '1001F410000000364KR4'        -- 任务定义
  and vouch_type in ( 2, 6 )                     -- 个别调整数
  and vbody.pk_selforg = '0001H310000000003XCG'  -- 单位
```

- 分页 10 条/页（`rn between 0 and 10`），本次返回 8 条
- 随后逐张 `SELECT * FROM bcs_vouch_body WHERE pk_vouchhead = ? order by iorder` 取分录
- `funcode` 来自 `select ... from sm_appregister where code = '1886002005'`，是节点的应用注册码

**结论**：产品自己也是「按头取全部 body」，跨单位的对方侧分录照样带出来。
所以「一张凭证只留本单位那侧」并不是产品行为 —— 要么跟着产品（完整凭证），要么自己在应用层再过滤。

## 五、同一口径的 SQL 复核（NCC 1909 / 2024-01）

```sql
select h.vouch_type, count(distinct h.pk_vouchhead) heads, count(*) bodies
  from bcs_vouch_head h join bcs_vouch_body b on b.pk_vouchhead = h.pk_vouchhead
 where h.key2 = '1001F410000000364KR4'
   and h.vouch_type in (2, 6)
   and b.pk_selforg = '0001H310000000001G5E'
   and exists (select 1 from bcs_dynamicdim d where d.pk_detail = h.pk_vouchhead
                and d.pk_dimlevel = 'TB_DIMLEV_ACCP_00001' and d.pk_levelval = '2024')
   and exists (select 1 from bcs_dynamicdim d where d.pk_detail = h.pk_vouchhead
                and d.pk_dimlevel = 'TB_DIMLEV_ACCM_00001' and d.pk_levelval = '01')
 group by h.vouch_type;
```

- 淮南首创水务（供水）`0001H310000000003XCG`、2024-01：**8 张**，与页面一致
- 安徽淮创 `0001H310000000001G5E` 同期：**0 张**（该单位只有自动抵销 type 4，没有个别调整）
  —— "凭证取不到"往往不是取数错，而是这家单位这个月本来就没有个别调整
